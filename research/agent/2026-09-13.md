# Agent Ecosystem Radar — 2026-09-13

> 研究窗口：截至 2026-09-13 08:26（Asia/Taipei）。本報告只追蹤 Agent Ecosystem；AI / Agent Security 由獨立 Security Radar 處理。今日優先採原始 GitHub commits、官方 implementation evidence 與可重現 runtime 行為，不以 star 數或宣傳熱度排序。

## 執行摘要

- **Codex 正把 context accounting 從「transport payload 大小」修正成「模型真正看到多少內容」。** 最新 commit 不再把 message ID、metadata、外層 JSON escaping 等 transport envelope 一起算進 history token estimate，而是依 text、tool payload、image、audio、encrypted content 等 model-visible content 分類估算，並排除不會 replay 給模型的 bookkeeping / plaintext reasoning。這件事看似只是 token estimator 修正，但它直接影響 compaction 觸發時機、long-running context 壽命、成本估計與 benchmark 公平性。
- **Codex 的多 server / background-agent runtime 開始明確採用 single-writer、multi-reader 語義。** 一個 task 若正被另一個 app server 管理，本地 Command Center 現在不再只顯示「無法 attach」，而是載入 frozen read-only history snapshot；不 replay buffered requests、不恢復 paused goal，也不能從該 view 啟動新 turn，直到原 owner 釋放後才可明確 retry attach。這是「execution authority」與「observation/history access」分離的具體 implementation。
- **Google ADK 把 cancellation 補成真正的一級 lifecycle path。** `asyncio.CancelledError`（例如 client disconnect、RPC timeout）以前會跳過 `after_agent_callback`，使 plugin metrics / timers 洩漏；新版在 cancellation 時補跑 after callback，但仍保留原 cancellation，不讓 cleanup error 蓋掉真正的終止原因。這說明 long-running Agent 的 correctness 不能只測 success/error，還要測 cancel / disconnect / generator close 等 termination semantics。
- **Google ADK 的 parallel tool calls 暴露出 state merge contract 問題。** 以前兩個平行 tool response 同時寫 `state_delta` list 時，後者會 silent overwrite 前者；現在 list 改為 concatenation，但 commit 也明確警告：若每個 tool 寫的是「完整 list」而不是 append delta，會產生 duplicate。這表示 parallelism 的真正難題不只是「同時呼叫幾個工具」，而是 mutable state 的 merge semantics 是否可組合、可重放、可推理。
- **Deep Agents 開始把「trajectory efficiency」做成可斷言、可記錄的 eval primitive。** `TrajectoryScorer` 現在會逐項 log `AgentSteps`、`ToolCallRequests`、`MaxToolCallRequests`、特定 `ToolCall` 等 efficiency assertion，即使沒有整體 step/tool count expectation，也保留 tool-only efficiency result。這對研究「multi-agent / delegation 是否值得」很重要：未來不該只比 final quality，而要把不必要 tool calls、額外 agent steps、coordination overhead 一起當 correctness-adjacent metric。
- **OpenViking 的 Understanding layer 開始明確走 parser-backend adapter 化。** 新增 LlamaParse v2 bridge，把 OpenViking 的 Files / Responses / polling contract 映射到外部 parser job，支援 PDF/DOCX/PPTX/XLSX 與 public image/audio URL，並保留 job ID 使 bridge restart 後仍可重新 poll / rebuild artifact。這代表 Agent knowledge ingestion 正從「內建 parser」走向「穩定 Understanding contract + 可替換後端」，但 parser parity、成本與失敗語義仍需要 benchmark。

今天仍然**沒有新的可信 evidence 可以支持「多 Agent 普遍優於 single-agent」**。相反地，今天最強的 implementation signal 是：production Agent 的瓶頸正在轉向 **context accounting、task ownership、termination semantics、parallel state merge、trajectory efficiency 與 knowledge-ingestion contract**。這些基礎 contract 若不正確，增加更多 subagent 只會把錯誤放大。

## 重要發展

### 1. OpenAI Codex：History Token Estimate 改成 Model-visible Content Accounting

**類型：** Context engineering / context compaction / cost accounting / multimodal history  
**來源：**
- https://github.com/openai/codex/commit/b04a2c264516ec2e6b3c91dd73ad18a21fd5a88f
- https://github.com/openai/codex

#### 1) 發生了什麼變化

Codex 修正 history token estimation：過去一般 `ResponseItem` 會先序列化成 JSON，再依 serialized byte size 粗估 token。

問題是 serialized envelope 裡包含很多**模型不會真的看到**的 transport overhead，例如：

- message / call IDs
- metadata
- outer JSON field names
- JSON escaping
- bookkeeping events

新版改成依 `ResponseItem` 類型直接估「模型可見內容」：

```text
Text message
→ text bytes

Tool call
→ tool name + namespace + arguments

Tool result
→ visible output body

Image / audio
→ modality-specific estimate

Encrypted content
→ encrypted payload estimate

Plaintext reasoning / bookkeeping-only event
→ replay accounting = 0
```

對 structured tool payload 仍保留 JSON syntax，因為那些 JSON 本身就是模型實際接收的內容。

#### 2) 它解決什麼問題

如果 transport metadata 被算進 context budget，runtime 會高估 history 大小，導致：

- 過早 compaction
- 過早 offload / truncate
- 錯誤的「剩餘 context」顯示
- benchmark 中 context pressure 被人為放大
- 相同文字內容只因 message IDs / metadata 不同就得到不同估算

commit 專門加了一個 remote compaction regression test：**相同長度文字即使 message ID、metadata、JSON escaping 不同，也應得到相同 token estimate，而實際提交的 messages 不需要改動。**

#### 3) 為什麼重要

昨天我們研究的是「Agent-managed context vs runtime-managed compaction」。今天這個 commit 提醒：在比較兩者之前，還有一個更底層問題：

> **Runtime 知不知道自己到底還剩多少真正 model-visible context？**

如果 estimator 本身有偏差，任何 threshold policy 都可能看起來不公平。

因此 context management 應該拆成至少三層：

```text
Model-visible token accounting
        ↓
Context pressure estimator
        ↓
Compaction / offload / new-window policy
```

不能把三者混成一個 black box。

#### 4) 核心架構與資料流

舊路徑：

```text
ResponseItem
→ serialize whole transport envelope
→ byte count
→ token approximation
→ compaction threshold
```

新路徑：

```text
ResponseItem
→ classify content type
→ keep only model-visible payload
→ modality-aware estimate
→ token approximation
→ compaction threshold
```

#### 5) Technical mechanism / implementation evidence

commit 明確覆蓋：

- text / agent message
- function / custom tool call
- function / custom tool output
- image input，包括非 base64 URL
- audio input
- encrypted content
- additional tools / tool search / shell / web-search structured payload
- image-generation result
- compaction / configuration / trigger bookkeeping

特別值得注意的是，**plaintext reasoning 被排除於 replay accounting**；這反映 runtime 開始區分「歷史中存在」與「下一次 request 真的重播」兩件事。

#### 6) 與既有方法差異

常見做法是：

```text
serialized request size ≈ context size
```

Codex 現在更接近：

```text
context size ≈ semantic payload actually replayed to model
```

這對 multimodal Agent 特別重要，因為 base64 byte size、image token cost、audio token cost 根本不是同一比例。

#### 7) 成熟度、近期活躍度與限制

**成熟度：production runtime fix。** 有 unit + remote compaction regression coverage。

限制：

- 仍然是 coarse estimate，不是真正 provider tokenizer exact count；
- modality cost 仍需要 approximation；
- 不同 model/provider tokenizer 可能不同；
- encrypted content 的模型端解碼/計價 contract 仍依平台實作。

#### 8) 對 Agent Engineering 的實際影響

任何 long-running Agent benchmark 若比較：

- compaction 次數
- peak context
- tokens before reset
- context utilization

都應該先確認 estimator 是算 **model-visible content**，而不是 wire payload。

#### 9) 是否改變既有假設

是。它挑戰「token accounting 只是 telemetry」的想法。對 long-running Agent 而言，token estimator 實際上參與 runtime control decision，因此是 control-plane input。

#### 10) 可做 experiment / benchmark

**Research Candidate：Yes — P0**

- **研究問題：** Token-estimation bias 對 compaction policy、task quality、總成本會造成多大影響？
- **為什麼現在值得測：** Codex 已有明確 pre/post implementation 可對照。
- **Baseline：** whole-envelope serialized-size estimator。
- **Variant：** model-visible content estimator；provider exact usage 作近似 ground truth。
- **Task set：** text-heavy、tool-heavy、multimodal、長期 coding agent 四類 trajectory。
- **Metrics：** estimation error、compaction trigger error、task success、total tokens、compaction count、wall-clock latency、critical-fact retention。

### 2. OpenAI Codex：Task Ownership 採 Single-writer / Read-only History Fallback

**類型：** Long-running agents / background agents / multi-server runtime / task ownership  
**來源：**
- https://github.com/openai/codex/commit/7efb0262d6cb62abd059835453d118255da25620
- https://github.com/openai/codex

#### 1) 發生了什麼變化

Command Center 過去如果嘗試 attach 一個正由另一個 app server 管理的 task，只能報錯：task open elsewhere。

現在若 attach 因 active-writer conflict 失敗，會 fallback 成：

```text
frozen read-only history snapshot
```

使用者仍可以看 saved history；但 runtime 明確禁止把這個 view 當成 live ownership。

#### 2) 它解決什麼問題

多 server / daemon / desktop / remote executor 的 Agent 系統會遇到一個很典型的分散式 ownership 問題：

> 同一個 long-running task 到底可以有幾個 active writer？

最危險的做法是兩邊都覺得自己能 resume / steer / replay queue，造成：

- duplicate turns
- duplicate tool execution
- goal state 分叉
- buffered request 重放兩次
- history / workspace 寫入衝突

Codex 的方向很明確：**live execution 只有一個 owner，但 history 可以被其他 client 觀察。**

#### 3) 為什麼重要

這其實是 Agent runtime 版的 database single-writer semantics。

它把兩種權限拆開：

```text
Can observe task history
        ≠
Can mutate / resume / steer task
```

這比「attach 失敗就完全看不到」更適合 background agents，也比「任何 client 都能 resume」安全且一致。

#### 4) 核心架構與資料流

```text
Client B wants task
       ↓
Try live resume/attach
       ↓
Active writer exists?
   ├─ No → Live attachment
   └─ Yes
       ↓
Read frozen history snapshot
       ↓
mark ExternalWriter view
       ↓
No request replay
No paused-goal resume prompt
No new turn
       ↓
Owner releases
       ↓
Explicit retry
       ↓
Live attachment
```

#### 5) Technical mechanism / implementation evidence

commit 測試鎖定幾個重要 invariant：

- read-only view 不會 start turn；
- buffered request 不 replay；
- paused goal 不自動 resume；
- draft / selection 可以保留；
- reopen 同一 task 仍維持 frozen snapshot；
- owner 釋放前 retry 仍是 read-only；
- owner 釋放後 explicit retry 才轉成 `Live` attachment。

這些細節比 UI 行為更重要，因為它們定義了真正 ownership contract。

#### 6) 與既有方法差異

弱實作常見兩種：

```text
A. attach conflict → 完全拒絕
B. attach conflict → force takeover
```

Codex 現在是第三種：

```text
observe without authority
→ explicit ownership transition later
```

#### 7) 成熟度與限制

**成熟度：production-facing implementation。** 但這不是完整 distributed consensus。

仍需追：

- owner crash 後 lease / timeout 如何處理；
- stale owner detection；
- cross-region latency；
- network partition 下是否可能 split-brain；
- ownership transfer 是否有 durable epoch / fencing token。

#### 8) 對 Agent Engineering 的實際影響

長時程 Agent 如果要支援：

- desktop + cloud 同時查看
- supervisor dashboard
- mobile observe
- background daemon
- operator takeover

最好明確定義：**observer、writer、owner transfer** 三個概念，而不是只用「session connected / disconnected」。

#### 9) 是否改變既有假設

是。Thread / task 不能只被視為聊天紀錄；它同時是帶 execution ownership 的 runtime object。

#### 10) 可做 experiment / benchmark

**Research Candidate：Yes — P0**

- **研究問題：** long-running task 在多 client / server 下，哪種 ownership protocol 最能避免 duplicate execution 又保持可恢復性？
- **Baseline：** unrestricted multi-writer；attach-conflict hard fail。
- **Variant：** single-writer + read-only observer + explicit transfer。
- **Task set：** 30–120 分鐘 coding/background tasks，加入 reconnect、owner crash、viewer attach、late buffered input。
- **Metrics：** duplicate execution count、lost input、time-to-recover、state divergence、resume success、operator effort、wall-clock latency。

### 3. Google ADK：Cancellation 現在會完整走 Lifecycle Cleanup

**類型：** Agent runtime / cancellation / observability / plugin lifecycle  
**來源：**
- https://github.com/google/adk-python/commit/37aa7308bbcfd41a2eebee73f51e6f40a5448e78
- https://github.com/google/adk-python

#### 1) 發生了什麼變化

ADK 修正 `run_async` 與 `run_live`：當 execution 因 `asyncio.CancelledError` 中止，例如：

- client disconnect
- RPC timeout
- runtime cancellation

以前 `_handle_after_agent_callback` 會被 bypass，造成掛在 plugin callback 裡的 metrics / timers / cleanup state 無法結束。

現在 cancellation path 會在特定 invariant 下補跑 after callback，再重新拋出原本 cancellation。

#### 2) 它解決什麼問題

Agent runtime 很容易把 termination 只分成：

```text
success / error
```

但 production 裡至少還有：

```text
cancelled
client disconnected
timeout
generator closed
superseded
end_invocation short-circuit
```

如果 lifecycle hooks 沒有明確定義，觀測數據會出現「永遠沒結束的 invocation」，resource cleanup 也可能洩漏。

#### 3) 為什麼重要

對 long-running Agent，取消不是 exception corner case，而是正常 control signal。

例如：

- 使用者停止任務；
- supervisor 決定 kill worker；
- 新 turn supersede 舊 turn；
- mobile/web client 斷線；
- RPC deadline 到期。

因此 cancellation semantics 應該像 transaction rollback 一樣被明確測試。

#### 4) 核心機制

ADK 新增兩個 lifecycle marker：

```text
before_callback_completed
after_callback_called
```

只有在：

- before callback 已完成；
- after callback 尚未跑；
- invocation 沒有被 `end_invocation` short-circuit；

才在 `CancelledError` path 補跑 `after_agent_callback`。

若 after callback 自己出錯，會 log 但不蓋掉原 cancellation；若 cleanup 又被再次 cancel，也仍保留 cancellability。

#### 5) Implementation evidence

新增大量 regression tests，覆蓋：

- `run_async` / `run_live`
- cancellation
- generator close
- cancellation 發生在 before callback 中
- cancellation 發生在 before callback 已 yield event 後
- after callback 自己 error
- after callback hang 時再次 cancel
- `end_invocation=True` short-circuit
- 避免 after callback 被跑兩次

這是相對完整的 lifecycle state-machine coverage。

#### 6) 與既有方法差異

很多 framework 的 callback API 其實沒有回答：

> after hook 到底是「成功後 hook」還是「execution finally hook」？

ADK 現在正在把這兩者界線變清楚：cancelled execution 需要 cleanup side-effects，但 `end_invocation` 與 unhandled error 又有自己的 contract。

#### 7) 成熟度與限制

**成熟度：production runtime fix。**

限制：

- after callback 仍可能包含任意 user code；
- cleanup 是否 idempotent 仍由 plugin author 負責；
- distributed worker death（process kill）不一定能執行 callback；
- cancel 後 durable state 是否一致是另一個問題。

#### 8) 對 Agent Engineering 的實際影響

建議所有 Agent runtime 都把 termination matrix 納入測試：

```text
Success
Error
Cancel
Timeout
Disconnect
Supersede
Worker crash
```

每一種都要定義 metrics、checkpoint、lock、tool lease、callback 到底如何收尾。

#### 9) 是否改變既有假設

是。`CancelledError` 不應被視為「不用管的 exception」，而是 runtime protocol 的一部分。

#### 10) 可做 experiment / benchmark

**Research Candidate：Yes — P1**

- **研究問題：** 主流 Agent runtimes 在不同 termination path 下，能否保持 lifecycle / metrics / durable state 一致？
- **Baseline：** success/error-only integration tests。
- **Variant：** explicit cancellation state machine + idempotent cleanup。
- **Task set：** tool-heavy long-running tasks，在固定 phase 注入 cancel/disconnect/timeout/supersede。
- **Metrics：** leaked invocation count、unfinished timer/span、orphaned tool lease、resume success、state consistency、cleanup latency。

### 4. Google ADK：Parallel Tool Calls 的 State Delta 從 Overwrite 改為 List Concatenation

**類型：** Tool use / parallel execution / shared state / orchestration semantics  
**來源：**
- https://github.com/google/adk-python/commit/7b246e0166b77dbeda83e94d622de4ca92c3539e
- https://github.com/google/adk-python

#### 1) 發生了什麼變化

ADK 的 `deep_merge_dicts` 原先對非-dict value 使用 last-write-wins overwrite。

當兩個 parallel tool calls 各自回傳：

```python
state_delta = {"items": ["a"]}
state_delta = {"items": ["b"]}
```

merge 後可能只剩後者，前一個 tool 的 state update 被 silent drop。

新版對「兩邊都是 list」時改用 concatenation：

```python
["a"] + ["b"] → ["a", "b"]
```

#### 2) 它解決什麼問題

Parallel tool execution 常被當成降低 latency 的簡單 optimization：

```text
serial tools → parallel tools
```

但只要 tool 有 side effects / state deltas，就立刻變成 concurrency problem。

如果 merge contract 不明確，parallelism 可能帶來 silent data loss。

#### 3) 為什麼重要

這和 multi-agent shared state 本質上是同一類問題：

> 多個 actor 同時產生 state update 時，應該用 overwrite、append、set union、keyed merge，還是 conflict？

不同 data type 需要不同 algebra。

#### 4) 核心架構與資料流

```text
Tool A ──→ state_delta A ┐
                         ├→ merge_parallel_function_response_events
Tool B ──→ state_delta B ┘
                         ↓
                  shared agent state
```

新版規則：

```text
dict + dict → recursive merge
list + list → concatenate
other       → overwrite
```

#### 5) Implementation evidence

commit 新增 tests 驗證：

- list concatenation；
- nested dict recursive merge；
- scalar overwrite；
- mixed types overwrite；
- parallel function response event 的 list state delta 不再遺失；
- duplicate item **刻意保留**。

最後一點非常重要：這不是 universal correct merge，只是避免 silent overwrite。

#### 6) 與既有方法差異

Last-write-wins 對 scalar 很直覺，但對 append-only event list 不合理。

另一方面，無條件 concat 也可能錯：若每個 tool 寫的是 full snapshot，會變：

```text
existing=[a]
Tool1 writes [a,b]
Tool2 writes [a,c]
→ [a,b,a,c]
```

因此真正的設計問題不是「concat 比 overwrite 好」，而是：**state field 是否應該攜帶 merge type / operation semantics。**

#### 7) 成熟度與限制

**成熟度：bug fix。**

限制已被 commit 自己明確承認：

- 不 deduplicate；
- full-list delta 會 duplicate；
- set / keyed semantics 應改用 dict；
- 沒有 general CRDT / conflict detection。

#### 8) 對 Agent Engineering 的實際影響

只要系統開始 parallel tool calls、subagents 或 fan-out，就應避免讓 arbitrary mutable state 使用一個 generic `deep_merge` 解決所有問題。

更健全的 schema 可能需要：

```text
append-only list
set union
keyed map merge
counter add
compare-and-swap
exclusive owner
conflict / manual resolution
```

#### 9) 是否改變既有假設

是。Parallel tool calls 不只是 execution scheduling feature；它會迫使 framework 定義 state algebra。

#### 10) 可做 experiment / benchmark

**Research Candidate：Yes — P0**

- **研究問題：** 不同 shared-state merge strategy 在 parallel tool / multi-agent workload 中會產生多少 silent corruption？
- **Baseline：** last-write-wins generic deep merge。
- **Variant：** concatenate；typed merge operations；versioned optimistic conflict detection。
- **Task set：** parallel research aggregation、batch file analysis、parallel test runners、multi-agent evidence collection。
- **Metrics：** state-loss rate、duplicate rate、conflict rate、task success、retry count、coordination latency、developer effort。

### 5. Deep Agents：Trajectory Efficiency 變成一級 Eval Assertion

**類型：** Agent evaluation / tool-use efficiency / orchestration benchmarking  
**來源：**
- https://github.com/langchain-ai/deepagents/commit/9e7d62ff6e7131505995a706d717e01837aa8617
- https://github.com/langchain-ai/deepagents

#### 1) 發生了什麼變化

Deep Agents 的 `TrajectoryScorer` 現在會把每一個 efficiency expectation 單獨 log 成 feedback，例如：

- `AgentSteps`
- `ToolCallRequests`
- `MaxToolCallRequests`
- 特定 `ToolCall`

而且即使 eval 沒設定 aggregate `expected_steps` / `expected_tool_calls`，只有「某個 tool 應該 / 不應該被呼叫」的 expectation，也會保留 `EfficiencyResult`。

#### 2) 它解決什麼問題

Agent benchmark 很容易只剩：

```text
Final answer correct?
Patch passes tests?
```

但兩個 Agent 都成功時，一個可能：

```text
5 steps / 4 tool calls
```

另一個：

```text
28 steps / 37 tool calls / 3 subagents
```

如果只看 success rate，後者的 orchestration waste 完全看不出來。

#### 3) 為什麼重要

這正好對應我們一直追的問題：

> **多 Agent / delegation 到底是真的提升品質，還是只是增加 token、tool call 與 coordination？**

要回答這個問題，efficiency 不能只在事後看 telemetry，而應該是 eval contract。

#### 4) 核心機制

每個 assertion 會得到獨立 feedback key：

```text
efficiency_agent_steps_*
efficiency_tool_call_requests_*
efficiency_max_tool_call_requests_*
efficiency_tool_call_*
```

fail 時會附上 `describe_failure(trajectory)`，因此可以知道是「哪個 efficiency contract 被破壞」。

#### 5) Implementation evidence

新增 deterministic tests 驗證：

- 某 tool call expectation match → pass；
- missing tool call → fail + failure description；
- `max_tool_call_requests(0)` 等 assertion 會被獨立記錄；
- tool-only expectation 不再因沒有 aggregate expected count 而丟失結果。

#### 6) 與既有方法差異

常見 eval：

```text
quality metric + global token/cost
```

Trajectory assertion 更接近：

```text
quality
+ allowed trajectory shape
+ expected tool behavior
+ efficiency constraints
```

也就是把「怎麼做到」部分也納入評測。

#### 7) 成熟度與限制

**成熟度：evaluation infrastructure improvement。**

限制：

- 少 tool calls 不等於更好；
- 某些任務多探索是合理的；
- static expectation 可能懲罰有效的新 strategy；
- 尚需與 token/cost/latency 一起看。

#### 8) 對 Agent Engineering 的實際影響

未來做 single-agent vs multi-agent、Skill vs subagent、fixed model vs router 時，建議至少同時報：

```text
Task success
Total tokens
Agent steps
Tool calls
Delegation count
Retries
Wall-clock latency
```

並對某些 task 定義「不應出現的 redundant tools / loops」。

#### 9) 是否改變既有假設

它強化一個重要方向：**Agent correctness 不只是 endpoint correctness，也包含 trajectory quality。**

#### 10) 可做 experiment / benchmark

**Research Candidate：Yes — P0**

- **研究問題：** 加入 trajectory efficiency constraint 後，哪些 orchestration 策略會從「看似更強」變成 Pareto-dominated？
- **Baseline：** final-task-success-only ranking。
- **Variant：** success + token + steps + tool calls + delegation overhead Pareto ranking。
- **Task set：** repo QA、coding、browser research、multi-source synthesis。
- **Metrics：** quality/task success、model cost、token use、agent steps、tool calls、delegation frequency、coordination failure、wall-clock latency。

### 6. OpenViking：Understanding API 新增 LlamaParse v2 Bridge，Parser 後端開始 Adapter 化

**類型：** Knowledge systems / multimodal ingestion / parser abstraction / long-running job integration  
**來源：**
- https://github.com/volcengine/OpenViking/commit/84bbf79711f3d18000beb1d16708e69627743b0e
- https://github.com/volcengine/OpenViking

#### 1) 發生了什麼變化

OpenViking 新增一個 reference bridge，把自身 Understanding API 映射到 LlamaParse v2，而不需要修改 OpenViking core。

主要 mapping：

```text
OpenViking POST /files
→ LlamaParse upload

OpenViking POST /responses
→ LlamaParse parse job

OpenViking GET /responses/{id}
→ poll LlamaParse job state

LlamaParse Markdown + images
→ rebuild 成 OpenViking 期待的 artifact ZIP
```

#### 2) 它解決什麼問題

Agent memory / knowledge pipeline 常把 parser 綁死：

```text
document → built-in parser → chunks → index
```

但 PDF、PPTX、XLSX、image-heavy docs 的 parser 能力與成本差異很大。

OpenViking 現在示範另一個架構：

```text
Stable Understanding contract
        ↓
Adapter / bridge
        ↓
Parser backend A / B / C
```

文件明確說相同 pattern 可用來接 Azure AI Document Intelligence、Amazon Textract 等服務。

#### 3) 為什麼重要

如果 knowledge ingestion 能替換 parser backend，就可以真正 benchmark：

- parsing quality
- table / layout preservation
- image extraction
- latency
- cost
- failure recovery

而不需要連 Agent memory API 一起重寫。

#### 4) 核心架構與資料流

```text
Agent / Resource import
        ↓
OpenViking Understanding API
        ↓
Bridge
        ↓
External parser async job
        ↓
polling
        ↓
Markdown + images/audio references
        ↓
OpenViking artifact package
        ↓
resource / retrieval pipeline
```

#### 5) Technical mechanism / implementation evidence

這個 bridge 不只是 happy-path demo：

- job ID / file ID 可重用；
- bridge restart 後仍可重新 poll remote job；
- completed ZIP 有短期 cache；
- cache 消失後可重新 rebuild；
- ZIP 在報 `completed` 前先建立，避開 OpenViking 固定 artifact-download window；
- 支援 local file、public document/image/audio URL；
- partial page failure 時若仍有 usable Markdown，可保留結果並註記 failed page；
- 沒有 usable Markdown 才整體 fail；
- mocked contract tests 不消耗 LlamaCloud credits。

#### 6) 與既有方法差異

這不是「OpenViking 改用 LlamaParse」，而是更重要的：**把 parser 變成 contract 後面的可替換 implementation。**

#### 7) 成熟度與限制

**成熟度：reference example / bridge。**

限制：

- hosted parser 成本與 vendor dependency；
- private credential-gated URL 不支援；
- video 不支援；
- multimodal extraction 的 downstream retrieval quality 尚未看到完整 benchmark；
- bridge cache 是 in-memory，不是 durable artifact store。

#### 8) 對 Agent Engineering 的實際影響

Knowledge system 的 benchmark 不應只比較 vector DB / embedding。前面的 parser / understanding layer 很可能對 Agent 最終品質有更大影響。

#### 9) 是否改變既有假設

是。Memory/RAG infrastructure 應該把 ingestion backend 也視為 pluggable runtime component，而不是 preprocessing 細節。

#### 10) 可做 experiment / benchmark

**Research Candidate：Yes — P2**

- **研究問題：** 不同 parser backend 對 Agent downstream task quality 的影響是否大於 retrieval backend 差異？
- **Baseline：** OpenViking built-in parser。
- **Variant：** LlamaParse bridge；其他 compatible parser adapter。
- **Task set：** PDF/PPTX/XLSX technical docs、table-heavy reports、image-rich manuals。
- **Metrics：** extraction completeness、layout/table fidelity、retrieval recall、Agent QA/task success、ingestion latency、cost、retry/recovery rate。

## 今日綜合判斷

今天最值得保留的不是某個新 framework，而是六個 runtime contract 開始變得更明確：

```text
1. Context contract
   到底算模型真正看到的內容，還是 transport envelope？

2. Ownership contract
   誰能看 task，誰能改 task，誰是唯一 active writer？

3. Termination contract
   cancel / timeout / disconnect 後 callback、metrics、state 怎麼收尾？

4. Merge contract
   parallel tools / subagents 同時寫 state 時怎麼合併？

5. Evaluation contract
   成功之外，trajectory 是否浪費 steps / tools / delegation？

6. Knowledge contract
   ingestion parser 是否能在穩定 interface 後面被替換與重試？
```

這些問題共同指向一個越來越清楚的結論：

> **Agent system 的差異化正在從「誰有更多 orchestration 元件」轉向「runtime contract 是否可重放、可恢復、可量測、可組合」。**

這也會影響我們之後研究「強模型是否降低 orchestration complexity」的方式。真正公平的比較不應是：

```text
Single Agent vs Multi-Agent
```

而應該至少控制：

```text
相同 model-visible context accounting
相同 task ownership semantics
相同 state merge contract
相同 cancellation/recovery rules
相同 trajectory-efficiency metrics
```

否則 framework-level bug 或 runtime overhead 很容易被誤判成模型 / multi-agent architecture 的能力差異。
