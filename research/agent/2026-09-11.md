# Agent Ecosystem Radar — 2026-09-11

> 研究窗口：截至 2026-09-11 08:27（Asia/Taipei）。本報告只追蹤 Agent Ecosystem；AI / Agent Security 由獨立 Security Radar 處理。今日優先採原始 GitHub commits、implementation evidence 與近期 systems research，不以 star 數或宣傳熱度排序。

## 執行摘要

- **Open SWE 把 context compaction 從「模型偷偷做摘要」進一步做成可顯式觸發、可觀測、但不污染使用者串流的 conversation offloading。** 新 middleware 可自動或用 `/offload` 手動觸發摘要，summary model 被標記為 `nostream` / `langsmith:hidden`，摘要內容不直接出現在一般 token stream；runtime 另外輸出 `started / completed / failed / skipped` 狀態，並把 offload state 存進 Agent state。這是「context management 應該是 runtime primitive，而不是聊天 UI 裡的一段摘要文字」的明顯訊號。
- **Codex 開始把 `AGENTS.md` 類 global instructions 當成 live control plane，而不是 thread 啟動時的一次性 prompt。** active root thread 現在會在每個 model-request boundary 重新載入 global instructions；同一個 turn 裡 tool call 之後的下一次 model request 也會看到更新。讀取失敗時保留最後成功版本，新 subagent 則取得 parent 當下已套用的 instruction snapshot。這對長時程 Agent 很重要：**instruction freshness、snapshot consistency、subagent inheritance 必須同時處理。**
- **Multi-agent observability 開始補「工作是從哪裡被觸發、實際由哪個模型花掉多少 token」這兩條 provenance。** Codex 新增 `turn_trigger` 跨 spawn、nested subagent、peer follow-up 傳遞；同時 turn telemetry 改成依「實際產生 response 的 model」分攤 token，而不是用 session-level selected model 粗略標記。這使 scheduled automation、composer、delegated work、model switching 的成本與成效終於比較有機會被正確量測。
- **OpenViking 把 background task observability 從 UI 合成 log 改成 bounded durable execution history。** Task snapshot 現在可以持久化最多 64 個、32 KiB 的 execution events，包含 created、status/stage change、first sanitized error、waiting-for-descendants 等，並以 `seq` 排序；Studio 改讀真正 persisted events。這個方向比「多印一些 logs」更接近可 crash-resume、可 audit 的 long-running workflow runtime。
- **Open SWE 主動 revert 一套「自動修復 stuck pooled stream」機制，因為 frozen-transcript 症狀仍然回來。** 這是很有價值的反面 evidence：在 Agent UI / runtime 中，server truth、SSE stream truth、pooled client instance、跨 tab / Slack / scheduler 啟動狀態並不容易 reconcile；加 polling、remount generation、reconnect attempts 不代表真的修好。Recovery 機制如果沒有可證明的 state model，很容易只增加複雜度。

今天沒有找到新的、足夠可信且 compute-matched 的證據，可以支持「多 Agent 普遍優於 single-agent」或「更強模型已經讓 orchestration 不再必要」。反而今天的 implementation evidence 更支持另一個方向：**現在的核心瓶頸正在從 prompt 本身移向 context lifecycle、trigger/provenance、durable execution state、stream reconciliation 與 observability。**

## 重要發展

### 1. Open SWE：Conversation Offloading 把 context compaction 變成 runtime primitive

**類型：** Context engineering / context compaction / long-running agents  
**來源：**
- https://github.com/langchain-ai/open-swe/commit/a1e1345a937ef17d0c205f8849d9af9b9677dd33
- https://github.com/langchain-ai/open-swe

#### 發生了什麼變化

Open SWE 新增 `ConversationOffloadingMiddleware`，建立在 Deep Agents 的 `SummarizationMiddleware` 上，但改變了 compaction 的產品與 runtime 語意。

它現在支援兩種觸發：

```text
automatic
→ token / message threshold 到達時自動 offload

manual
→ 使用者執行 /offload
```

手動 offload 不能對新 conversation 執行，必須作用在既有 thread；觸發時會把本次 run 標記 `offload_conversation=true`，且不需要再塞一段 user input 給主模型。

更關鍵的是 summary model 被加上：

```text
nostream
langsmith:hidden
```

所以 internal summary token 不會被當成一般 Agent 回覆流到 UI。Runtime 另外輸出結構化狀態：

```text
conversation_offloading
├─ started
├─ completed
├─ failed
└─ skipped
```

completed state 還會保存 `cutoff_index` 與 `file_path`。

#### 它解決什麼問題

傳統 conversation compaction 很常有三個問題：

1. **使用者看到 internal summary token**，UI 像是 Agent 突然自言自語；
2. **compaction 與正常 reasoning 混在同一 stream**，難以觀測與 debug；
3. **沒有明確操作語意**，使用者不能在適當時機主動 offload。

Open SWE 現在的方向是：

```text
Conversation history
      ↓
Compaction / Offloading runtime
      ├─ durable summary / file artifact
      ├─ structured lifecycle state
      └─ hidden internal model output
      ↓
Normal agent turn continues
```

#### 為什麼重要

Long-running Agent 不可能永遠把完整 transcript 塞回 context。真正的問題不是「要不要 summarize」，而是：

- 什麼時候 compact？
- 誰觸發？
- compact 的 state 要不要持久化？
- summary 是否應出現在 user-visible stream？
- compaction failure 對正常 turn 的影響是什麼？
- subagent 是否採同一套 policy？

這些問題已經是 runtime design，不是單純 prompt engineering。

#### 核心架構與資料流

```text
Conversation
     ↓
ConversationOffloadingMiddleware
     ↓
_should_summarize()
     ├─ automatic threshold
     └─ manual /offload
     ↓
summary model (nostream / hidden)
     ↓
summary artifact / summarization event
     ↓
conversation_offloading state
     ↓
next normal model request
```

Open SWE 也把相同 offloading middleware 掛到 general-purpose subagent，表示 context lifecycle 不再只屬於 root Agent。

#### Implementation evidence

commit 的 tests 明確覆蓋：

- 手動 offload 不把 private summary stream 給使用者；
- history 與 summary event 仍保存在 checkpoint state；
- `started → completed` lifecycle；
- 沒有可 compact 內容時回 `skipped`；
- automatic offload 在主 handler 執行前完成；
- custom middleware 可以取代預設 summarization middleware。

#### 與既有方法 / 舊版本差異

舊方式比較像：

```text
Context 太長
→ framework 自動 summary
→ summary message 插回 conversation
```

現在更像：

```text
Context lifecycle subsystem
→ independently observable
→ user-triggerable
→ internal summary hidden from normal output
→ state persisted
```

#### 成熟度與已知限制

**成熟度：中。** 已進 production-oriented Open SWE code path，但目前 evidence 主要證明 integration correctness，不代表 summary quality 已被 benchmark。

仍不知道：

- offload 前後 task success 是否下降；
- summary artifact 是否遺漏 decision-critical evidence；
- root / subagent 使用不同 model 時，summary fidelity 是否不同；
- 多次連續 offload 是否產生 information decay。

#### 對 Agent Engineering 的實際影響

值得把 Agent context 分成：

```text
Live working context
Durable conversation history
Offloaded summaries / artifacts
Retrieved context
```

而不是只有「messages[]」。

#### 是否改變既有假設

是。它支持：

> **Context compaction 應該是一個有 lifecycle、state、telemetry 的 runtime capability，而不是黑盒 summary。**

#### 可做實驗

**Research Candidate：Yes — 最高優先級**

- **研究問題：** conversation offloading 是否能在不顯著犧牲 task quality 的情況下降低 live-context token 與 latency？
- **為什麼現在值得測：** Open SWE 已有可操作的 manual / automatic implementation。
- **Baseline：** full history / window truncation / generic summarization。
- **Variant：** structured offloading + hidden summary + persisted artifact。
- **Task set：** 20–50 個 30–120 分鐘 coding / repo investigation tasks，刻意讓 context 觸發 1–5 次 compaction。
- **Metrics：** task success、final patch quality、input tokens、cached tokens、latency、compaction count、critical-fact retention、recovery after resume、developer intervention。

### 2. OpenAI Codex：Global Instructions 改成每個 Model Request 都可刷新

**類型：** Context engineering / instruction lifecycle / subagent inheritance  
**來源：**
- https://github.com/openai/codex/commit/935ac7710da6d33cf700b3fd953a878f9e1c4535
- https://github.com/openai/codex

#### 發生了什麼變化

先前 running root thread 會保留啟動時讀到的 global `AGENTS.md` instructions；如果使用者在 Agent 執行途中更新 global instructions，active session 不會自動套用。

現在 Codex 在 capture model-request context 時重新 refresh global instructions，包含同一個 turn 中 tool 執行完、下一次要再次 call model 的邊界。

它另外處理幾個很容易被忽略的 corner cases：

- instruction 沒改 → 不重複插入；
- repository environment / trust level 沒變 → 不重新做不必要的 repository instruction discovery；
- refresh 讀檔失敗 → 保留最後成功的 global instructions；
- 同一個持續錯誤 → warning 不重複洗版，恢復後若再次失敗才重新警告；
- source 被刪除或內容變空 → 正確清掉舊 instructions；
- refresh 被 cancellation 中止 → 不阻塞後續 request；
- new subagent → 繼承 parent 已經 apply 的 snapshot，而不是自己重新抓一份可能不同步的 global state。

#### 它解決什麼問題

長時程 Agent 的 instructions 很可能在任務執行期間改變，例如：

- owner 修改 global coding rules；
- 新增一條「不要碰某個 migration」；
- 改 deployment policy；
- 新 subagent 在 parent 已執行數十分鐘後才 spawn。

若 instruction 只在 thread startup 讀一次，就會出現：

```text
Filesystem authority truth 已更新
≠
Agent 正在使用的 instruction truth
```

#### 為什麼重要

這把 `AGENTS.md` 從 static prompt file 往 **live configuration plane** 推了一步。

但 live refresh 也不能只是「每次重新讀檔」：root、subagent、resume、fork、compaction 都需要 snapshot consistency，否則同一個 task tree 裡不同 Agent 可能在不同規則下工作。

#### 核心架構與資料流

```text
Global instructions provider
        ↓
serialized refresh
        ↓
last-successful cache / warning state
        ↓
request-boundary validated snapshot
        ↓
root model request
        ↓
spawn subagent
        ↓
inherit parent's applied snapshot
```

#### Implementation evidence

Codex 加入大量 regression coverage：

- live edit / removal；
- read failure → recovery；
- warning suppression；
- cancellation；
- resume / fork / compaction；
- subagent inheritance；
- Guardian reviewer reuse 在 instructions 改變後不錯誤 reuse 舊 reviewer state。

這比「重新讀一下 AGENTS.md」完整得多。

#### 與既有方法差異

常見 Agent harness：

```text
session start
→ read system/project instructions
→ freeze for whole thread
```

Codex 現在更像：

```text
request boundary
→ refresh mutable global layer
→ combine with stable repository/environment context
→ validate snapshot
→ execute
```

#### 成熟度與已知限制

**成熟度：中高，屬 Codex core runtime。**

限制：

- global instruction freshness 提升，但不是 distributed config system；
- subagent 採 snapshot inheritance，代表 spawn 後 parent 再變更 global instruction，既有 child 是否要同步更新仍是另一個 policy question；
- instruction 變更是否應中斷正在進行的高風險 action，不是這個 commit 解決的問題。

#### 對 Agent Engineering 的實際影響

值得把 instructions 區分：

```text
Static model/system policy
Mutable global owner instructions
Repository-local instructions
Turn-specific user intent
Inherited subagent snapshot
```

不同層應該有不同 refresh / snapshot semantics。

#### 是否改變既有假設

是。它支持：

> **長時程 Agent 的 instruction state 不能預設永遠 frozen；但 live refresh 必須與 snapshot consistency 一起設計。**

#### 可做實驗

**Research Candidate：Yes**

- **研究問題：** request-boundary refresh 相比 session-start-only instructions，能否降低 stale-policy execution，同時避免 context churn？
- **Baseline：** startup-only instruction load。
- **Variant：** request-boundary global refresh + parent snapshot inheritance。
- **Task set：** 長時 coding tasks，中途修改 1–3 次 owner instructions，包含 spawn subagent、resume、compaction。
- **Metrics：** stale-instruction violation、task success、instruction tokens、cache invalidation、latency、subagent consistency、developer intervention。

### 3. Codex：Delegation 開始保留 Trigger Provenance，Telemetry 也改成按實際模型歸因

**類型：** Multi-agent / delegation / observability / model routing  
**來源：**
- https://github.com/openai/codex/commit/e004dc6a4b36f58086083cfa1cce47bf3c518bed
- https://github.com/openai/codex/commit/c8a8295e798af970ef5a2bcd9ce2229db87edb6b
- https://github.com/openai/codex

#### 發生了什麼變化

Codex 同一天補上兩個很適合一起看的 observability primitives。

第一個是 `turn_trigger`：

```text
composer
scheduled automation
heartbeat
...
```

現在 trigger 會從 initiating turn 往下傳到：

- spawned child agent；
- nested agent；
- reused agent 的 follow-up；
- Multi-Agent V2 peer follow-up；
- pending mailbox work 啟動的新 turn。

但如果同一個 active turn 被 steer，新的 submission trigger 不會覆蓋原本 active turn 的 trigger；這維持了「這一條工作最初是怎麼開始的」的 provenance。

第二個是 model attribution：過去 turn completion metrics 使用 session-level telemetry；如果 turn 中換過 model、step override model、compaction 用一個 model、正常 response 又用另一個 model，token 可能被錯誤標在 session selected model。

現在 Codex 會依每個 response 的 resolved step settings，把 token usage 累積到實際 model，最後每個 model / token type 各送一個 histogram sample。

#### 它解決什麼問題

只知道「這個 thread 花了 100k tokens」不夠回答：

- 是 user 手動觸發還是 scheduler 觸發？
- 是 root Agent 花的還是 delegated chain 花的？
- balanced model 花多少？performance model 花多少？
- compaction model 的成本有沒有被算進主模型？
- 一個 subagent follow-up 是新的 workload 還是某個 parent task 的延續？

如果 attribution 不正確，所有 model-routing / multi-agent ROI 分析都會失真。

#### 為什麼重要

我們一直關心：

> 多 Agent 是否真的值得？Adaptive routing 是否真的省錢？Automation 是否在背景默默燒 token？

這些都先需要 **可正確歸因的 telemetry**，否則 benchmark 只能靠外部估算。

#### 核心架構與資料流

```text
Initiating turn
  ├─ turn_trigger
  └─ root_turn_id
       ↓
spawn / peer follow-up / mailbox
       ↓
delegated turns preserve trigger

每個 model response
       ↓
resolved step settings
       ↓
model-specific token accumulator
       ↓
turn completion
       ↓
per-model token histograms
```

#### Implementation evidence

Trigger tests涵蓋：

- spawned / nested child；
- reused agent；
- peer follow-up；
- steering 不覆蓋 active turn trigger。

Telemetry tests涵蓋：

- model switch；
- step-level model change；
- compaction + response；
- compaction-only / aborted turn；
- no-response turn；
- repeated requests 聚合同一 model sample。

#### 與既有方法差異

簡化 observability 常只有：

```text
thread_id + selected_model + total_tokens
```

現在開始接近：

```text
root work provenance
+ trigger provenance
+ actual execution model
+ step-level usage
+ delegated topology
```

這才足以做 orchestration economics。

#### 成熟度與已知限制

**成熟度：中高。** 已落在 core telemetry / multi-agent execution path。

但仍有缺口：

- token attribution ≠ cost attribution，還要套正確 price table / cache pricing；
- 目前看到的是 trigger 與 model attribution，還沒有完整 critical path latency breakdown；
- delegated task quality contribution 仍需要 outcome attribution 才能判斷 marginal value。

#### 對 Agent Engineering 的實際影響

如果要做 Agent benchmark，最低限度應保存：

```text
root task id
turn id
parent turn id
trigger
agent identity / role
actual model
input / cached / output / reasoning tokens
tool calls
wall time
outcome
```

否則「multi-agent 比較」很容易只剩總 token 與最終分數。

#### 是否改變既有假設

不直接證明 multi-agent 更好，但它讓真正驗證「什麼時候不該 delegate」變得更可行。

#### 可做實驗

**Research Candidate：Yes — 高優先級**

- **研究問題：** 有完整 trigger / model / topology attribution 後，哪些 delegation 真的有正 marginal value？
- **Baseline：** single-agent fixed model。
- **Variants：** single-agent adaptive routing、multi-agent fixed model、multi-agent adaptive routing。
- **Task set：** SWE-bench 類 coding tasks + repository investigation + scheduled maintenance tasks。
- **Metrics：** task success、cost、tokens by model、delegation frequency、marginal quality gain per delegated call、critical-path latency、coordination failure、retry count。

### 4. OpenViking：Background Task 改用 Persisted Execution Events，而不是 Synthetic Logs

**類型：** Long-running agents / task runtime / observability / checkpoint-recovery  
**來源：**
- https://github.com/volcengine/OpenViking/commit/a57d7f941a9d85591f189df3eb44cb2c6c079066
- https://github.com/volcengine/OpenViking

#### 發生了什麼變化

OpenViking 的 task snapshot 新增 bounded `execution_events` history，HTTP detail API 可用：

```text
GET /api/v1/tasks/{task_id}?include_events=true
```

取得真正持久化的執行歷史。

目前事件種類包含：

```text
created
status_changed
stage_changed
error_recorded
waiting_for_descendants
```

事件與 task state 會一起成功寫入後才對外發布；同 timestamp 時以 `seq` 決定 task-local ordering。

每個 task 最多：

```text
64 events
32 KiB serialized history
```

超出後刪最舊 event，`dropped_count` 記錄被移除數量；legacy task 若中途才開始產生 event，標記 `started_mid_task=true`，不假裝重建不存在的過去。

Studio 也從 synthetic logs 改為顯示 persisted task events。

#### 它解決什麼問題

Long-running background task 如果只靠 process log 或 UI 根據目前 status 猜歷史，restart 後很難回答：

- task 到底走過哪些 stage？
- error 是在哪個 lifecycle point 被接受？
- 是否正在等待 descendants？
- restart 前已經完成過哪些 state transition？

如果沒有 durable event history，checkpoint 有 state，但沒有可解釋的 state transition provenance。

#### 為什麼重要

一個可恢復的 Agent workflow，不只需要：

```text
Current State
```

還需要至少有限度的：

```text
How did we get here?
```

這對 debug stuck tasks、reconciliation、retry policy、operator UX 都很重要。

#### 核心架構與資料流

```text
Task transition / process fact
        ↓
TaskTracker
        ↓
append bounded event
        ↓
state + event snapshot persisted together
        ↓
optional detail API
        ↓
Studio renders persisted truth
```

#### Implementation evidence

commit 包含：

- task event data structure；
- sequence ordering；
- size / count bounds；
- opt-in API response；
- task ownership / authorization；
- durability tests；
- event ordering tests；
- Studio translations 與 rendering；
- downgrade / legacy behavior 文件。

#### 與既有方法差異

常見 UI：

```text
poll status
→ 根據 status 合成「正在處理...」log
```

現在是：

```text
runtime accepted fact
→ durable event
→ UI only renders persisted fact
```

#### 成熟度與已知限制

**成熟度：中。** 已是完整 end-to-end implementation，但 intentionally bounded，不是 full trace system。

限制：

- 64 events / 32 KiB 對非常長 workflow 會截斷早期細節；
- `recorded_at` 是 TaskTracker 記錄時間，不一定是底層真實發生時間；
- error 是 sanitized summary，不是 stack trace；
- 仍需要 OpenTelemetry / component logs 才能做完整 performance debugging。

#### 對 Agent Engineering 的實際影響

比較合理的 observability layering 是：

```text
Durable lifecycle events
→ 用於 recovery / operator / audit

Telemetry / traces
→ 用於 latency / cost / performance

Raw logs
→ 用於深度 debug
```

三者不能互相取代。

#### 是否改變既有假設

是。它支持：

> **Background Agent 的 task history 應該是 runtime-owned state，而不是 UI-owned interpretation。**

#### 可做實驗

**Research Candidate：Yes**

- **研究問題：** durable bounded event history 是否能顯著降低 background-agent failure 的診斷與 recovery 成本？
- **Baseline：** current status + ephemeral logs。
- **Variant：** state snapshot + bounded persisted lifecycle events。
- **Task set：** 50 個長時 resource import / coding / queue workflows，注入 crash、cancel、descendant delay、retry、server restart。
- **Metrics：** root-cause identification accuracy、time-to-diagnosis、recovery success、operator steps、storage overhead、missing-event rate。

### 5. Open SWE：Stuck Stream Recovery 被 Revert，顯示「Reconciliation」比看起來難

**類型：** Agent runtime / streaming / client-server reconciliation / recovery  
**來源：**
- https://github.com/langchain-ai/open-swe/commit/6f2b36e49fe2b02166cc1a58347079b53ba57c4a
- https://github.com/langchain-ai/open-swe

#### 發生了什麼變化

Open SWE 主動 revert 先前為 pooled Agent stream 加上的 recovery machinery。

原方案試圖處理兩種 mismatch：

```text
A. server 認為 thread running
   但 local stream 沒有 loading / 沒訂閱到 run

B. server 已 idle
   但 local stream 永久卡在 loading
```

修復機制包含：

- running thread 每 3 秒 poll server truth；
- idle thread 每 10 秒 poll，偵測從 Slack / GitHub / scheduler / 另一 tab 開始的 run；
- stream state 與 server state 不一致超過 grace period 時 `kick()`；
- bump `generation` 強制 React remount `useStream` instance；
- 增加 reconnect attempts 與 Datadog actions。

但 commit 直接寫明：

> frozen-transcript symptom appears to be back, so the recovery machinery is not carrying its weight.

因此整套 reconciliation / remount logic 被撤回，等待重新診斷。

#### 它解決什麼問題

Agent runtime 的 streaming state 不等於普通 chat streaming，因為一個 thread 可能由多個 source 啟動：

```text
Web UI
Slack
GitHub event
Scheduler
Another browser tab
```

同時 UI client 可能 retain pooled stream instance、SSE transport 可能失聯、server task 還在繼續。

#### 為什麼重要

這個 revert 很值得研究，因為它說明：

> **Recovery feature 的存在不等於 recovery correctness。**

如果沒有明確定義每個 state 的 authority：

```text
server task status
SSE connection
local loading state
pooled client instance
last received event
```

reconciliation heuristic 可能只是反覆重啟 client，而根因仍在。

#### 與既有方法差異

很多 frontend recovery 會採：

```text
poll + retry + remount
```

但 Agent thread 需要更像 distributed system 的 reconciliation contract：

```text
server authoritative execution epoch
client last-seen sequence / cursor
resumable event log
idempotent reconnect
explicit gap detection
```

而不是只比較 `running !== isLoading`。

#### 成熟度與已知限制

這是**負向 implementation evidence**，不是新的成功架構。

目前只能確定：先前的 heuristic recovery 未能穩定解決 frozen transcript；不能從 revert 推論根因一定在 SDK、SSE、pooling 或 server 任一單點。

#### 對 Agent Engineering 的實際影響

值得把「Agent 還在跑」與「我還看得到 Agent 在跑」拆開：

```text
Execution durability
Event delivery durability
Client state reconciliation
UI representation
```

四個是不同問題。

#### 可做實驗

**Research Candidate：Yes — 高優先級**

- **研究問題：** 哪種 event-stream reconciliation contract 才能在多入口啟動與 network interruption 下可靠恢復 Agent transcript？
- **Baseline：** SSE + client local state；poll + heuristic remount。
- **Variants：** resumable sequence cursor、server event journal、execution epoch + gap detection。
- **Task set：** long agent runs，隨機注入 tab sleep、network drop、backend deploy、cross-tab run、Slack-triggered run。
- **Metrics：** transcript completeness、time-to-reconcile、duplicate event、missed event、false remount、UI stuck rate、server task success。

## 近期研究補追：AgentSysBench 指出 Agent Serving 的瓶頸大量不在 LLM 本身

**論文：** `From LLM Inference to Agentic Workloads: Characterization and Implications for Serving Systems`  
**來源：** https://arxiv.org/abs/2608.15127

這篇 2026-08-15 的研究不是今天發布，但目前 repo 尚未收錄，而且和最近幾天看到的 runtime changes 高度吻合，因此值得補進 Radar。

作者建立 `AgentSysBench`，分析十種 agentic applications 與 production traces。論文報告的幾個 systems-level 結果很重要：

- 10 個 applications 中有 5 個的 latency 主要由 non-LLM components 主導；
- sandbox working-set memory 單 session 可達 28 GB；
- 不同 component latency 可差到 32×；
- production Agent session 會把 state idle 保留數分鐘到數小時；
- auxiliary LLM calls、tool schemas、observations 造成明顯 control-plane tax；
- production traces 存在大量 search / web fetch redundancy。

作者的 design explorations 報告：

- task-aware serving latency -29% 到 -40%；
- communication-aware placement 最多 4.5×；
- state offloading memory usage降低 4.6×；
- tool-result caching 去掉 35.2% redundant search calls，aggregate search latency -19.3%。

這些數字來自論文作者自己的 benchmark，仍需獨立重現；但研究方向與今日 Open SWE offloading、OpenViking persisted tasks、Codex per-model telemetry 非常一致：

> **Agent serving 應被當成 heterogeneous, stateful workflow workload，而不是「LLM API 多 call 幾次」。**

**Research Candidate：Yes — 中高優先級。** 建議未來把我們自己的 Agent benchmark 從只量 model tokens / task score，擴成：LLM latency、tool latency、sandbox CPU/RAM、idle retained state、context overhead、cacheable external calls、control-plane calls。

## Research Candidates

### Candidate A：Conversation Offloading Quality–Cost Curve

- **研究問題：** offloading 能省多少 context / latency，代價是多少 task quality 與 information retention？
- **Baseline：** full context、sliding window、generic summary。
- **Variant：** Open SWE-style structured offloading。
- **Task set：** 長時 coding / repo research tasks，強制多次 context pressure。
- **Metrics：** task success、patch quality、critical fact retention、input/cached tokens、latency、compaction count、resume quality。

### Candidate B：Live Instruction Refresh vs Frozen Thread Instructions

- **研究問題：** 長時 Agent 中途更新 rules 時，request-boundary refresh 是否更可靠？
- **Baseline：** session-start-only instructions。
- **Variant：** live global refresh + snapshot inheritance。
- **Task set：** 中途修改 policy / coding convention、spawn subagent、resume / compact。
- **Metrics：** stale-rule violations、task success、context churn、cache invalidation、subagent consistency。

### Candidate C：Delegation ROI with Correct Attribution

- **研究問題：** 當 trigger、model、parent/child attribution 都正確時，哪些 delegation 才真正值得？
- **Baseline：** single-agent fixed frontier model。
- **Variants：** adaptive single-agent、fixed-model multi-agent、adaptive multi-agent。
- **Task set：** coding / investigation / automation maintenance。
- **Metrics：** quality、cost、per-model tokens、delegation rate、marginal delegated gain、critical-path latency、coordination failure。

### Candidate D：Durable Task Event History

- **研究問題：** persisted lifecycle events 是否比 ephemeral logs 更能支援 crash diagnosis / recovery？
- **Baseline：** status snapshot + logs。
- **Variant：** bounded task-owned event journal。
- **Task set：** crash / cancel / descendant wait / restart scenarios。
- **Metrics：** diagnosis accuracy、time-to-recovery、operator effort、event completeness、storage cost。

### Candidate E：Agent Stream Reconciliation

- **研究問題：** Agent execution truth 與 client stream truth 要靠什麼 contract 才能可靠 reconcile？
- **Baseline：** polling + local loading state + remount heuristic。
- **Variants：** resumable cursor、event journal、execution epoch / sequence gap detection。
- **Task set：** tab sleep、network drop、cross-channel trigger、server restart。
- **Metrics：** missed / duplicate events、stuck UI rate、recovery latency、false remount、transcript completeness。

## 今日綜合判斷

今天的 material changes 可以抽象成四層：

```text
1. Context lifecycle
   → Open SWE conversation offloading

2. Instruction lifecycle
   → Codex live global-instruction refresh

3. Work provenance / economics
   → Codex turn-trigger + actual-model attribution

4. Runtime truth / recovery
   → OpenViking persisted events
   → Open SWE stream reconciliation revert
```

這幾層共同指向一個趨勢：

> **Agent architecture 正從「LLM + tools + prompt loop」轉成 stateful workflow runtime。**

下一階段真正值得 benchmark 的問題，不只是「哪個模型答得比較好」，而是：

```text
Context 是否可控地縮減？
Instructions 是否保持最新且一致？
Delegated cost 是否可正確歸因？
Background task 是否能解釋自己怎麼走到現在？
Client 掉線後能否重建完整 execution view？
```

這些都是 production Agent 在跑數小時、跨多個 Agent、跨多個工具之後才會真正暴露的問題。
