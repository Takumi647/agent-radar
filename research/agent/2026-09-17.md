# Agent Ecosystem Radar — 2026-09-17

> 研究窗口：截至 2026-09-17 上午（Asia/Taipei）。本報告只追蹤 Agent Ecosystem；不以 Security 題材補篇幅。今日優先檢查 9/16 上午之後的原始 GitHub commits、runtime implementation evidence 與近期 coding-agent benchmark。

## 執行摘要

- **Open SWE 已把 adaptive model routing（自適應模型路由）從「有這個功能」推進成真正的 production A/B test（正式流量分流對照實驗）。** 啟用 routing 的 thread 以 `thread_id` 雜湊做穩定 50/50 cohort：一半走 `auto`，由 classifier 選 fast / balanced / performance；一半固定走 `performance`，而且 control 組直接跳過 classifier。這是目前最接近我們一直想驗證的問題：**固定強模型 vs 路由到較便宜模型，能不能在 quality 不降的前提下降低實際 model monetary cost。**
- **Open SWE 同時把 fallback retry（模型失敗後切換備援模型的重試）做成可觀測的 trace。** 每次 retry 現在會記錄 failed model、next model、backoff、error type、status code 與 outcome。這很重要，因為「routing 選到便宜模型」和「模型失敗被迫 fallback」如果混在一起，成本與延遲分析會失真。
- **Microsoft Agent Framework 修到一個 long-running context 很關鍵的 compaction consistency bug。** 舊版會在 model-input view 裡插入工具結果摘要，但 durable transcript 只留下「原訊息已排除」旗標，沒有把摘要本身存回去；重新載入並 `skip_excluded` 後，舊工具結果就真的消失。修正後 summary 會 reconcile 回正式 transcript。這再次證明：**模型眼前的 context 與可恢復的 durable history 必須有一致的語意。**
- **Google ADK 開始讓 Skill 具有可釋放的生命週期。** 新的 experimental `unload_skill` 能在任務完成後把 Skill 貢獻的 dynamic tools 從後續 request 移除，不再讓已載入 Skill 的工具永久佔據整個 session；但 Skill instructions 仍留在 conversation history。這表示 progressive disclosure（漸進揭露）下一步不是只「需要時才載入」，而是還要回答「什麼時候釋放」。
- **Open SWE 修到一個很典型的 multi-worker sandbox identity 問題。** thread 在另一個 worker reset / recreate sandbox 後，本 worker 的 per-thread cache 仍可能保有舊 sandbox，甚至把舊 ID 寫回 durable metadata，讓 thread「跳回」已離開的隔離環境。修正後 durable thread metadata 是 binding authority，process-local connection cache 改以 immutable `sandbox_id` 為 key。這是一個非常乾淨的 runtime lesson：**logical thread identity 不等於 resource identity。**
- **PydanticAI 把完成的 Agent run 變成穩定可序列化 artifact。** `AgentRunResult` 現在有 public serialized shape，保存 output、messages、usage、run/conversation IDs、metadata 與 trace context；完成的 `StreamedRunResult` 也能 settle 成同一種結果。這把「streaming execution object」與「可跨 process / queue / storage 傳遞的 durable run artifact」正式分開。
- **Real-SWE 提供一組值得警惕、但必須標明限制的 private-code benchmark evidence。** Specific Labs 在私有真實 production codebase 上以 native harness 評估 model+harness pair；最佳 Fable 5.1 + Claude Code 也只有 38.8% resolution rate，且多數模型的常見失敗來自 missed requirement、unverified assumption 與 integration error。這些數字是 benchmark-owner reported，private task 也無法由外界完整獨立重現；但它強烈提醒：**公開 benchmark 的 coding success 不等於陌生企業 codebase 的 end-to-end engineering success。**

今天依然沒有新的可信、compute-matched 證據能證明「multi-agent 普遍優於 single strong agent」。反而今天出現了一個更可驗證的方向：**先用 production A/B 直接測『固定 performance model vs adaptive routing』；只有當 routing / single-agent 已經被正確歸因後，再研究 delegation / fan-out 的額外收益。**

## 重要發展

## 1. Open SWE：Adaptive Model Routing 正式進入 50/50 Production A/B Test

**類型：** model routing / agent coding / evaluation / observability / cost optimization  
**來源：**
- https://github.com/langchain-ai/open-swe/commit/ca0ff5e83e70052fb349e43b1d8fafd94d56cb7c
- https://github.com/langchain-ai/open-swe/commit/03ead1f9ffa6003eb17f8313bc917f3fc9c368cf
- https://github.com/langchain-ai/open-swe

### 1) 發生了什麼變化

Open SWE 前幾天已經加入 adaptive model routing：先用 routing classifier 判斷工作強度，再在 fast / balanced / performance model 間切換。

今天更重要的改變是，它開始內建真正的 A/B 實驗：

```text
thread_id
   ↓ SHA-256 deterministic bucket
50%                       50%
 ↓                         ↓
auto routing           performance control
 ↓                         ↓
classifier             不跑 classifier
 ↓                         ↓
fast / balanced /      固定 performance
performance
```

`_MODEL_ROUTING_SPLIT = 0.5`，而 cohort 由 `thread_id` 決定，所以同一 thread 不會每次 request 隨機換組。

另外，Open SWE 同步把 model fallback retries 做成 `model_retry` trace span。每個 retry 可以看到：

- `attempt` / `max_attempts`
- `failed_model`
- `next_model`
- `error_type`
- `status_code`
- `backoff_seconds`
- `retry_with = primary | fallback`
- retry outcome

### 2) 它解決什麼問題

單純實作 router 不能證明 router 有價值。

如果看到平均成本變低，可能是：

- router 真的把簡單工作交給便宜模型；
- 實驗組剛好收到比較簡單的工作；
- 便宜模型常失敗，但 fallback 成功，成本其實被藏掉；
- classifier 本身的 token / latency 沒算；
- 只有短期 task success 一樣，但 retry / developer intervention 增加。

Thread-stable 50/50 cohort + retry tracing，至少開始提供可做 causal comparison 的基礎。

### 3) 為什麼重要

這正面回答我們長期追蹤的：

> 強模型變強之後，還需要多少 orchestration complexity？

在進入 multi-agent 之前，最小的 orchestration 就是：

```text
先判斷 task difficulty
→ 再選 model
```

如果連這一層都無法在 quality 相同時穩定節省 USD，那更複雜的 fan-out / delegation 就更難合理化。

反之，如果 production A/B 顯示 auto routing 能在同品質下降低大量實際模型成本，那「先 routing，後 delegation」可能比「先 multi-agent」更有效率。

### 4) 核心架構與資料流

```text
Incoming thread
   ↓
Experiment cohort assignment
   ├─ auto
   │   ↓
   │ routing classifier
   │   ↓
   │ model_route persisted in state
   │   ↓
   │ chosen model
   │
   └─ performance
       ↓
       skip classifier
       ↓
       performance model

Model call failure
   ↓
ModelFallbackMiddleware
   ↓
model_retry span
   ↓
backoff + alternate model
```

Routing decision 存入 Agent state，因此同一 run 後續 request 不會反覆重跑 classifier。

### 5) 技術機制與 implementation evidence

原始 commit 顯示：

- 新增 `RoutingMode = Literal["auto", "performance"]`；
- `thread_id` 以 SHA-256 分桶；
- control 組完全跳過 routing classifier；
- experiment mode 寫入 metadata；
- routing decision 只執行一次，後續 reuse state；
- test 明確驗證 auto 路徑包含 `Gemini 3.8 Flash`、`GPT-5.6 Sol`、`Claude Opus 5` 的 route candidates；
- retry trace 包含模型切換與 backoff，而不把 exception body 寫入 trace。

這比單純 leaderboard 或「我們用了 router」有更強的 implementation evidence。

### 6) 與最接近方案 / 舊版本差異

舊狀態：

```text
routing enabled
→ 看起來成本可能比較低
```

新狀態：

```text
same production traffic population
→ deterministic randomized cohort
→ auto vs fixed performance
→ retry/fallback 可追蹤
```

這才開始接近真正可比較的 deployment experiment。

### 7) 成熟度、近期活躍度與已知限制

**成熟度：高活躍、production-oriented experiment implementation。**

限制：

- 現在看到的是 experiment infrastructure，不是最終 A/B 結果；
- thread-level hash split 不等於 task-level exact matching；
- 不同 thread 可能工作量高度不均；
- classifier 自己的 cost / latency 必須納入；
- fallback 會污染「route 本身是否成功」的觀察，因此分析時要分層。

### 8) 對 Agent Engineering 的實際影響

應該把 model routing 視為一個可被實驗驗證的 runtime policy，而不是 prompt trick。

更重要的是，成本分析至少要分開：

```text
intended route cost
+ classifier cost
+ fallback/retry cost
+ recovery cost
```

不能只看 final model 或 output tokens。

### 9) 是否改變 single-agent vs multi-agent / delegation 既有假設

它強化一個目前越來越合理的順序：

```text
1. 單一強模型 baseline
2. adaptive model routing
3. selective escalation
4. contract-aware delegation
5. fan-out only when justified
```

也就是在加第二個 Agent 之前，先測「同一個 Agent 換模型」能不能取得大部分 cost-quality tradeoff。

### 10) 可做的 experiment / replication / benchmark

**Research Candidate：Yes — P0**

**Adaptive Routing ROI Benchmark**

- **研究問題：** adaptive routing 能否在 task success 不降的情況下降低實際 model monetary cost？
- **為什麼現在值得測：** Open SWE 已有 production A/B implementation，可直接借鑑 cohort 與 tracing 設計。
- **Baseline：** fixed performance model。
- **Variant A：** adaptive routing。
- **Variant B：** adaptive routing + fallback。
- **Variant C：** fixed performance + fallback，用來隔離 fallback 本身的效果。
- **Task set：** code review、bug fix、feature implementation、repo exploration、docs/config change、跨檔案 refactor。
- **Metrics：** quality / task success、actual model cost、token use、wall-clock latency、tool calls、retry count、fallback frequency、reliability、developer intervention、route confusion matrix。

### 11) 是否值得列為 Research Candidate

**是，P0，今天最高優先級。**

## 2. Microsoft Agent Framework：Compaction 不能只改 Model Input，Durable Transcript 也必須同步

**類型：** context engineering / context compaction / long-running agent / checkpoint-resume  
**來源：**
- https://github.com/microsoft/agent-framework/commit/e24a1f2c408a836c98bad76493592692aca3944b
- https://github.com/microsoft/agent-framework

### 1) 發生了什麼變化

Agent Framework 的 in-run compaction（單次執行內的上下文壓縮）會把舊 tool-call groups 標成 excluded，並插入一個 summary 讓模型保留必要資訊。

問題是：

```text
working model input
  ├─ excluded original tool group
  └─ inserted summary   ← 有

returned ChatResponse / persisted history
  ├─ excluded original tool group
  └─ summary            ← 沒有
```

當下一回合 history provider 用 `skip_excluded=True` 載入 history 時，原始 tool group 被正確丟掉，但替代它的 summary 不在 durable transcript，於是那段資訊永久消失。

修正後 `_reconcile_compaction_summaries()` 會把有合法 back-link 的 summary merge 回正式 transcript，再 return / persist。

### 2) 它解決什麼問題

它解決的是典型的「兩個 context source of truth」：

- model request 當下看到一個壓縮後世界；
- durable history 儲存另一個世界。

Agent 在當下 turn 可能表現正常，因此 bug 不容易立即出現；真正失敗會在下一次 resume / next turn 才發生。

### 3) 為什麼重要

所有 long-running Agent 都可能經歷：

```text
large tool output
→ compaction
→ persisted history
→ process restart / next turn
→ reload
```

如果 summary 只是 ephemeral model-input artifact，就不能稱為真正可恢復的 memory state。

這表示 context compaction 的 correctness 不該只測：

> 壓完模型還答不答得出來？

還要測：

> 壓完、persist、reload 後是否仍然答得出來？

### 4) 核心架構與資料流

修正後：

```text
Source transcript
   ↓
Compaction strategy
   ├─ mark old group excluded
   └─ create summary with summary-id backlink
          ↓
Prepared model input
          ↓
Model call
          ↓
Reconcile summary → source-owned transcript
          ↓
Final ChatResponse
          ↓
HistoryProvider persistence
          ↓
reload(skip_excluded=True)
          ↓
summary survives
```

### 5) 技術機制與 implementation evidence

commit 不只修 code，也把 invariant 寫進 function-calling-loop spec，並新增：

- Phase-2 terminal path test；
- max-iterations terminal path；
- nested compaction；
- early terminal exit；
- agent-level `InMemoryHistoryProvider` persistence test。

這表示它被當成 runtime contract，而不是一個偶發 formatting bug。

### 6) 與舊版本差異

舊版：

```text
summary 是 model-request optimization
```

新版：

```text
summary 是 durable conversation state 的替代 artifact
```

這個 conceptual shift 很重要。

### 7) 成熟度、近期活躍度與已知限制

**成熟度：production framework bug fix，evidence 強。**

限制：

- 目前主要處理 tool-result compaction；
- summary 自身的 factual fidelity 仍沒有因此被保證；
- 多次 summary-of-summary 是否會累積 distortion，仍需另外 benchmark；
- provider / storage backend 的 serialization 差異仍可能產生其他 resume 問題。

### 8) 對 Agent Engineering 的實際影響

Compaction 應至少區分三個 artifact：

```text
raw transcript
compacted model view
durable compacted transcript
```

並明確定義哪個是 canonical state，以及 resume 如何重建。

### 9) 是否改變 context / memory 既有假設

是。它削弱「只要 prompt context 當下正確就好」的假設。

對 long-running Agent，memory optimization 必須同時通過 persistence / replay / resume correctness。

### 10) 可做的 experiment / replication / benchmark

**Research Candidate：Yes — P0**

**Compaction Persistence Consistency Benchmark**

- **研究問題：** 壓縮後 immediate quality 正常，是否代表 persist/reload 後也正常？
- **為什麼現在值得測：** 已有具體 production bug 與修補方式。
- **Baseline：** summary 只存在 model-input view。
- **Variant A：** summary reconcile 到 durable transcript。
- **Variant B：** external structured summary store + transcript reference。
- **Task set：** 10–50 次 tool calls、長 tool outputs、跨 process resume、iteration limit exit、nested compaction。
- **Metrics：** post-resume task success、lost-fact rate、summary fidelity、token use、compaction count、retry/recovery、reliability、wall-clock latency。

### 11) 是否值得列為 Research Candidate

**是，P0。**

## 3. Google ADK：Skill 從「只會 Load」進化成可 Unload 的 Session Capability

**類型：** skills / tool routing / context engineering / capability lifecycle  
**來源：**
- https://github.com/google/adk-python/commit/ce53a36c0a221542afbd22dc4f3d6f5e3c8fecd7
- https://github.com/google/adk-python

### 1) 發生了什麼變化

Google ADK 的 `SkillToolset` 過去可以 `load_skill`，但 load 之後 activation state 沒有 release path。

Skill 的 `metadata.adk_additional_tools` 因此會在後續每次 model request 持續被宣告，直到 session 結束。

新的 experimental `SKILL_LIFECYCLE` feature 加入：

```text
unload_skill(skill_name)
```

它會從 `_adk_activated_skill_<agent>` session state 移除 Skill，讓它的 dynamic tools 從之後的 tool declaration 消失。

### 2) 它解決什麼問題

Load-only Skill 系統會有累積效應：

```text
Task A → load Skill A
Task B → load Skill B
Task C → load Skill C

後面 request 的 tool surface：
A + B + C + ... 永久累積
```

即使 Skill A 只對第一個 subtask 有用，它還會繼續佔：

- tool schema tokens；
- tool-selection attention；
- 命名 collision / confusion surface；
- 模型決策空間。

### 3) 為什麼重要

這使 progressive disclosure 不再只是：

```text
Don't show everything upfront.
```

而進一步變成：

```text
Acquire capability when needed.
Release capability when no longer needed.
```

這更接近 resource / capability lifecycle，而不是靜態 prompt engineering。

### 4) 核心架構與資料流

```text
Skill Registry
   ↓ list/search
load_skill
   ↓
session activated-skill state
   ↓
additional tools declared to model
   ↓
subtask completed
   ↓
unload_skill
   ↓
remove from activated state
   ↓
future request no longer declares those tools
```

### 5) 技術機制與 implementation evidence

- feature flag 預設 off；
- enabled 時才 expose `unload_skill`；
- system instruction 也會教模型何時 release；
- unload 只操作 session state，因此 Skill 即使已從 registry 移除仍可 release；
- tests 驗證 feature off 不改舊行為、feature on 才新增工具。

### 6) 與舊版本 / 近似方案差異

舊版 Skill activation 是 session-monotonic：只增不減。

新版開始成為 reversible lifecycle。

但目前只釋放 **tools**；Skill instructions 已寫進 conversation history，**不會被 erase**。

因此：

```text
tool-surface cleanup ≠ context-semantic cleanup
```

### 7) 成熟度、近期活躍度與已知限制

**成熟度：experimental、default off。**

commit docstring 已明確揭露 concurrency limitation：activated-skill list 是整體 rewrite；平行 `load_skill` / `unload_skill` 的 state delta 可能 last-writer-wins，兩個 unload 同時成功回覆後仍可能留一個 Skill active。

這也呼應前幾天看到的 parallel state merge 問題：Skill lifecycle 最後仍需要明確 state algebra，而不是普通 list replacement。

### 8) 對 Agent Engineering 的實際影響

Skill 是否應該常駐，現在可以變成可測政策：

- session-long；
- task-scoped；
- turn-scoped；
- lease / TTL；
- explicit unload；
- isolated subagent-only。

### 9) 是否改變 delegation / context / tooling 既有假設

是。

有些原本為了避免主 Agent 工具太多而使用 subagent 的情況，可能可以先試：

```text
single agent
+ narrow task-scoped skill activation
+ release afterwards
```

如果這就能控制 context/tool surface，就不一定需要多 Agent。

### 10) 可做的 experiment / replication / benchmark

**Research Candidate：Yes — P0/P1**

**Skill Activation Lifetime Benchmark**

- **研究問題：** Skill 應該 permanent-load、task-scoped unload，還是隔離在 subagent？
- **為什麼現在值得測：** ADK 已提供 explicit lifecycle primitive。
- **Baseline A：** 所有工具常駐。
- **Baseline B：** lazy load，但不 unload。
- **Variant A：** lazy load + explicit unload。
- **Variant B：** TTL / task-boundary auto release。
- **Variant C：** Skill 只存在 subagent。
- **Task set：** 連續多領域任務，每個 task 只需要 1–2 個 Skill，但整個 session 可見 10–30 個 Skill。
- **Metrics：** task success、model cost、token use、tool schema size、wrong-tool rate、tool calls、wall-clock latency、delegation frequency、coordination failure、developer effort。

### 11) 是否值得列為 Research Candidate

**是。** 如果目標是降低 orchestration complexity，這是一條非常直接的替代路徑。

## 4. Open SWE：Sandbox Binding 的 Source of Truth 不能是 Per-Thread Process Cache

**類型：** sandbox/runtime architecture / long-running agent / multi-worker correctness / recovery  
**來源：**
- https://github.com/langchain-ai/open-swe/commit/4729d3abc165e20364f3bef43a467552832ca595
- https://github.com/langchain-ai/open-swe

### 1) 發生了什麼變化

Open SWE 的 sandbox connection cache 原本主要按 `thread_id` 存 process-local backend handle。

當 worker A 對 thread 做 sandbox recreate / reset 時：

```text
Durable metadata:
thread X → sandbox NEW

Worker B process cache:
thread X → sandbox OLD
```

Worker B 下一次 run 可能先相信自己的 stale cache，甚至 mismatch handling 會把 OLD sandbox ID 寫回 metadata，於是 thread 又被綁回舊 sandbox。

修正後：

- 先讀 durable thread metadata 的 `sandbox_id`；
- process-level connection cache 改成 `sandbox_id → connection`；
- thread proxy 仍可保持 stable，但真正 backend 由 durable binding 決定；
- 只有「這次真的 create sandbox」時才更新 thread metadata；
- metadata lookup failure 不再被吞成 `{}`，避免把暫時讀取失敗誤判成「thread 尚未綁 sandbox」。

### 2) 它解決什麼問題

這是 distributed runtime 常見的 stale cache / authority inversion：

```text
cache 應該只是加速讀取
卻反過來覆蓋 durable source of truth
```

對 coding Agent 特別危險，因為 sandbox 裡可能包含：

- working tree；
- installed dependencies；
- generated files；
- uncommitted work；
- environment setup。

錯綁 sandbox 就可能讓 Agent 看見錯的 execution state。

### 3) 為什麼重要

這跟 long-running Agent 的 checkpoint / resume 同一類問題：

> 哪個 state 才是 authority？

Thread 是 logical execution identity；sandbox 是 physical runtime resource。兩者可以 rebind，不能用同一個 key 假設永久 1:1。

### 4) 核心架構與資料流

修正後：

```text
thread_id
   ↓
read durable thread metadata
   ↓
sandbox_id
   ↓
SANDBOX_CONNECTIONS[sandbox_id]
   ├─ hit → reuse
   └─ miss → reconnect
        ↓
stable thread proxy points to resolved backend
```

只有沒有 `sandbox_id` 且 metadata 讀取成功時，才進 create path。

### 5) 技術機制與 implementation evidence

commit 裡明確新增：

```text
SANDBOX_CONNECTIONS: dict[sandbox_id, backend]
```

而不再把 cached backend by thread 當 resource authority。

另外測試直接覆蓋：

- thread 已在其他 worker rebind；
- local worker 還握著 stale backend；
- runtime 不可重新採用舊 sandbox；
- metadata fetch failure 必須 propagate。

### 6) 與舊版本差異

舊版：

```text
thread_id → cached sandbox handle
```

隱含假設 resource binding 很少改變。

新版：

```text
durable metadata owns thread→sandbox binding
sandbox_id owns connection identity
thread proxy only provides stable call surface
```

### 7) 成熟度、近期活躍度與已知限制

**成熟度：production bug fix，實際 multi-worker failure model 清楚。**

限制：

- durable metadata 本身仍依賴外部 store consistency；
- concurrent recreate 的 serialization contract 仍需考慮；
- sandbox resource 的 in-flight tool calls 如何 drain / cancel 仍是另一層問題。

### 8) 對 Agent Engineering 的實際影響

Agent runtime 應把這三種 identity 分開：

```text
logical actor/session identity
execution attempt identity
physical runtime/resource identity
```

尤其不能讓 process-local cache 重新定義 durable authority。

### 9) 是否改變 runtime authority 既有假設

是，而且很直接：

**runtime authority 應該外置、持久化、可 reconcile；Agent intelligence 與本地 process cache 都不應決定自己目前擁有哪些 physical resource。**

### 10) 可做的 experiment / replication / benchmark

**Research Candidate：Yes — P0**

**Multi-worker Resource Rebinding Torture Test**

- **研究問題：** Agent thread 在 sandbox reset/recreate/failover 後，其他 workers 是否仍會使用 stale resource？
- **為什麼現在值得測：** 已有 production implementation defect 作為具體 failure model。
- **Baseline：** cache by logical thread identity。
- **Variant：** durable binding + cache by immutable resource ID。
- **Task set：** multi-worker concurrent runs、sandbox recreate、metadata timeout、worker restart、old connection still alive、new sandbox provisioned。
- **Metrics：** wrong-sandbox rate、lost-work rate、task success、retry/recovery、rebind latency、reliability、operator intervention。

### 11) 是否值得列為 Research Candidate

**是，P0。**

## 5. PydanticAI：把 Streaming Run 與 Durable Run Artifact 正式分離

**類型：** agent runtime / streaming / persistence / workflow handoff / observability  
**來源：**
- https://github.com/pydantic/pydantic-ai/commit/5f43723ee1b96a3b5f12cd65762d8a02a86b91a0
- https://github.com/pydantic/pydantic-ai

### 1) 發生了什麼變化

PydanticAI 現在讓 `AgentRunResult` 擁有穩定 public serialized shape，可直接 round-trip through Pydantic JSON。

保存內容包含：

- output；
- complete messages；
- new-message boundary；
- output tool name；
- usage；
- run ID / conversation ID；
- metadata；
- trace context。

而 execution-only scratch state 不會被保存。

對 streaming 路徑，完成後可：

```text
StreamedRunResult.result
→ AgentRunResult
```

變成同一種 settled durable form。

### 2) 它解決什麼問題

Streaming object 通常綁定：

- active connection；
- event iterator；
- ambient tracing context；
- process-local state。

這些東西不適合直接丟進 queue / DB / workflow step。

因此需要明確的「執行中 object」和「執行完成 artifact」邊界。

### 3) 為什麼重要

Long-running Agent / workflow orchestration 很常需要：

```text
Agent step finishes
→ save result
→ another worker / process picks it up
→ resume workflow
```

如果 run result 沒穩定 serialization contract，就只能自己拼 transcript + IDs + usage，容易遺漏 provenance 或 boundary。

### 4) 核心架構與資料流

```text
active stream
   ↓ events
StreamedRunResult
   ↓ completion
capture final output + trace context
   ↓ settle
AgentRunResult
   ↓ stable serialization
DB / queue / workflow / audit
```

取消中的 stream 不會假裝有 settled output；只保留 interruption 前 messages。

### 5) 技術機制與 implementation evidence

commit 加入：

- `AgentRunResult` custom serializer / validator；
- legacy private serialized shape migration；
- `StreamedRunResult.result`；
- stream completion 時 capture `traceparent`，因為 stream 結束後 ambient span 已關閉；
- cancelled-before-output 會明確拒絕產生 settled result。

### 6) 與舊版本差異

舊狀態偏向 runtime object。

新狀態則明確把 completed Agent run 當成一種 domain artifact。

### 7) 成熟度、近期活躍度與已知限制

**成熟度：framework API contract 正在成形。**

限制：

- serialized run 不代表所有 external side effects 都可 replay；
- run-local scratch 故意不存，因此不能把它當 execution checkpoint；
- schema evolution 仍需要長期 compatibility policy。

### 8) 對 Agent Engineering 的實際影響

應區分：

```text
checkpoint
run result
transcript
artifact
```

它們不是同一件事。

`AgentRunResult` 解決的是「完成結果可持久化」，不是「任意中斷點可恢復」。

### 9) 是否改變 long-running / orchestration 假設

它強化一個 pattern：

> workflow boundary 應交接穩定 typed artifact，而不是把 live Agent object 傳下去。

這對 multi-agent handoff 也同樣成立。

### 10) 可做的 experiment / replication / benchmark

**Research Candidate：Yes — P1**

**Run Artifact Handoff Benchmark**

- **研究問題：** typed settled run artifact 能否降低跨 worker / subagent handoff 的 state-loss 與 developer effort？
- **Baseline：** 自行拼 transcript + metadata dict。
- **Variant：** stable serialized run result。
- **Task set：** streaming coding run → queue → evaluator、background agent → reviewer、human pause → later process consumption。
- **Metrics：** handoff success、missing-field defects、reliability、developer effort、serialization overhead、recovery/debug time。

### 11) 是否值得列為 Research Candidate

**是，P1。**

## Benchmark Evidence：Real-SWE 顯示 Private Production Code 仍遠比公開 Benchmark 困難

**來源：**
- https://realswe.withspecific.com/

Specific Labs 於 2026 年 9 月推出 `Real-SWE`，使用授權的 private production codebases，並以 model + native harness 組合進行評估。

官方目前公布的整體 resolution rate：

| Model | Harness | Resolution rate |
|---|---|---:|
| Fable 5.1 | Claude Code | 38.8% |
| GPT-6 Astra | Codex CLI | 33.8% |
| Gemini 3.8 Flash | Gemini CLI | 31.2% |
| GLM 5.3 | Claude Code | 28.8% |
| Grok 4.6 | Grok Build | 23.8% |
| Muse Spark 1.3 | Muse Code | 23.8% |
| Kimi K3 | Kimi Code | 18.8% |
| GPT-5.6 Sol | Codex CLI | 16.2% |

官方定義 resolution rate 等價於 pass@1，對每個 task 跑 8 次獨立 trial，再平均。

### 值得注意的訊號

1. **最佳組合也低於 40%。** 代表 frontier coding agent 在陌生 production system、business rules、cross-service integration 下仍有很大 gap。
2. **它測的是 model+harness pair，不是純模型。** 因此不能直接把排名解讀成 foundation model ranking；tooling、prompt、context handling、sandbox 都混在結果裡。
3. **平均成本與成功率不是單調關係。** 官方估計平均 rollout cost 從約 $2.50 到 $6.96，但更貴不保證更高 resolution rate。
4. **failure taxonomy 很實用。** 常見類型包括 unverified assumption、missed requirement、integration error、regression、wrong file；這比只看 final pass/fail 更適合用來設計 Agent workflow。
5. **跑久不代表就會成功。** 官方報告小於 10 分鐘 rollout failure 71.4%，10 分鐘以上 73.4%，說明簡單加長 runtime 並不是需求理解問題的答案。

### 但必須保留的限制

這不是可完全獨立重現的公開 benchmark：

- codebases / full tasks 是 private；
- benchmark owner 同時負責 setup 與 analysis；
- native harness 不同，因此 model 與 harness effect 無法完全拆開；
- 成本為 benchmark owner 的估計值。

因此應標示為 **benchmark-owner reported evidence**，不能拿來當「模型 X 絕對比模型 Y 強」的定論。

### 對我們研究方向的價值

它最有價值的不是 leaderboard，而是提醒 evaluation 必須往：

```text
public benchmark pass rate
        ↓
private / unfamiliar repo
        ↓
requirements discovery
        ↓
integration correctness
        ↓
cost + latency + tool trajectory
```

擴展。

## 對核心研究問題的更新

### 強模型是否降低 orchestration complexity？

**今天仍不能下結論，但 Open SWE 的 production A/B 是目前最值得等待的直接證據之一。**

如果 fixed performance model 的品質與成本 Pareto 不輸 auto routing，router 都可能沒有必要；反之，如果 auto 明顯省成本且 quality 不掉，則 orchestration 的最小有價值形式可能是 model routing，而不是 multi-agent。

### 什麼時候不該 delegate？

今天新增一個更具體的判斷：

如果目標只是避免主 Agent 被太多工具污染，先測 **task-scoped Skill activation + unload**，未必需要開 subagent。

### Multi-Agent 是否真的帶來品質提升？

今天沒有新的 compute-matched general evidence。

因此不更新「multi-agent 普遍更好」的假設。

### Context / Memory infrastructure 是否真的降成本而不犧牲品質？

今天的 Agent Framework bug 提醒：

**不能只量 immediate turn quality。** Context compression 必須把 persist / reload / resume 放進 benchmark，否則可能當下省 token、下一回合卻遺失 state。

### Long-running Agent 如何 checkpoint / resume / reconcile？

今天增加兩個 runtime contract：

1. durable transcript 必須包含壓縮後替代 artifact；
2. logical thread 與 physical sandbox binding 必須由 durable metadata reconcile，而不是 process cache。

### Runtime authority 與 Agent intelligence 如何分離？

Open SWE sandbox fix 再次提供具體答案：

```text
Agent / local process
可以使用 runtime resource

但「這個 thread 現在綁哪個 resource」
應由 durable runtime metadata 決定
```

## 今日結論

今天的訊號很集中，而且比「又多一個 Agent framework」更有研究價值：

```text
Model choice
→ 開始用真正 A/B 測 ROI

Context compaction
→ 必須對 durable transcript 負責

Skills
→ 開始有 acquire / release lifecycle

Sandbox
→ durable binding 必須壓過 process cache

Agent result
→ live streaming object 與 durable artifact 分離
```

最值得直接帶進下一階段實驗的是：

1. **fixed strong model vs adaptive routing 的 actual USD A/B；**
2. **compaction 後 persist/reload correctness；**
3. **Skill load-only vs load/unload vs subagent isolation；**
4. **multi-worker sandbox/resource rebinding torture test。**

這四個方向共同支持一個更節制的 orchestration 原則：

> **先把單一 Agent 的 model routing、context lifecycle、tool/Skill lifecycle 與 runtime state authority 做對，再要求 multi-agent 證明它額外增加的 coordination complexity 確實換來可量化品質收益。**
