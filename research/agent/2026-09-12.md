# Agent Ecosystem Radar — 2026-09-12

> 研究窗口：截至 2026-09-12 08:50（Asia/Taipei）。本報告只追蹤 Agent Ecosystem；AI / Agent Security 由獨立 Security Radar 處理。今日優先採原始 GitHub commits、官方 implementation evidence 與近期論文，不以 star 數或宣傳熱度排序。

## 執行摘要

- **OpenViking 做出一個非常值得研究的「Agent 自己管理 context windows」實驗。** 新的 experimental Pi extension 不再只把 compaction 當 framework 自動摘要，而是讓模型看到剩餘 context、自己決定何時 `new_context`、在舊 window 中搜尋 history，再從 handoff / working memory 繼續。官方公開的一次長 context live run 在約 105k tokens 的材料上，Agent 自己完成 3 次 reset 並完成 22/22 檔案盤點；這不是廣泛 benchmark，但它提供了罕見的可重現 runtime evidence：**context lifecycle 本身可以成為 Agent 的決策空間。**
- **Deep Agents 把 context compaction 從「摘要功能」補成有明確 failure semantics 的 recovery protocol。** 新版在 compaction 後檢查完整 model request（messages + system + tool schemas），預留 output budget 與 5% headroom；如果仍 overflow，只允許一次「嚴格更小」的 retry，必要時把大型尾端 tool result offload，最後無法縮小就 terminal fail。這說明 production context management 必須處理「摘要後還是塞不進去」與 retry loop，而不只是 summary quality。
- **長時程 Agent 的 human interaction 正從 blocking turn 走向 asynchronous side channel。** Codex 最新 scenario tests 驗證 `request_user_input_async` 可以先問人、Agent 繼續工作，答案再注入同一個 active turn；Deep Agents Talon 也新增 `send_message(text)`，讓 Agent 在不中止任務下回報 progress，且 delivery 只在 originating turn 有效、turn 結束或被 supersede 後立即失效。這代表「問人」與「回報進度」正在成為 runtime primitive，而不是 final response 的特例。
- **Workflow runtime 正在把 identity 與 state ownership 收斂到真正單一權威來源。** Google ADK 把 static / dynamic node 的 `run_id` 分配統一到 `DynamicNodeState`，以 `(parent_path, node_name)` 維持 sequential counter；Microsoft Agent Framework 則修正 declarative workflow formula state 的 session 隔離與 checkpoint restore，避免不同 hosted sessions 共用 mutable state。兩個變更都指向同一原則：**replay / resume / dynamic scheduling 能不能可靠，取決於 identity 與 state 到底誰說了算。**
- **最新論文對「什麼時候該 delegate」給出比『多 Agent 比較強』更精確的答案。** `Subagents vs Agent Skills` 在 SkillsBench 發現：當 skill 只是鬆散知識時，直接載入 main context 的 Agent Skill 往往不差甚至更好；當 skill 被設計成有明確 input/output contract 的 procedural abstraction 時，subagent 才開始佔優，尤其 context 壓力增加時更明顯，但代價是總 token 上升。這直接支持一個可操作判準：**不是任務複雜就 delegate，而是 subtask 能不能被乾淨封裝。**
- **Coding-agent benchmark 也出現一個需要立即納入研究方法的警訊。** `SWE-Bench Pro Verified` 顯示原 benchmark 的 leakage / task-quality 問題可以顯著扭曲結果；例如 GLM-5.2 在 paired anti-hacking setting 從 78.80% 降到 57.32%，而 DeepSeek-V4-Pro 幾乎不變。這代表之後 Agent Radar 自己做 coding-agent benchmark 時，**benchmark integrity 要跟 model / orchestration config 一樣被當成實驗變數。**

今天沒有新的可信證據支持「多 Agent 普遍優於 single-agent」。相反地，今天最有價值的 evidence 更接近：**delegation 的收益是條件式的；context window、human interaction、workflow identity、benchmark hygiene 這些系統層設計，可能比單純增加 agent 數量更決定最終表現。**

## 重要發展

### 1. OpenViking：讓 Agent 自己決定何時切換 Context Window

**類型：** Context engineering / long-running agents / memory / runtime  
**來源：**
- https://github.com/volcengine/OpenViking/commit/bf8c5e9d3452494210ba466d723e7446df912014
- https://github.com/volcengine/OpenViking

#### 1) 發生了什麼變化

OpenViking 新增 experimental Pi extension：**Agent-managed context windows（由 Agent 自主管理上下文視窗）**。

它不是只在 token threshold 到時由 framework 自動 summarize，而是把 context lifecycle 暴露成幾個 Agent 可操作的 primitive：

```text
new_context
history.list_windows
history.list_items
history.read_item
history.search_contents
get_context_remaining
```

Agent 會看到每個 prompt 的 context status，也會在壓力升高時收到 reminder；但真正何時切 window，可以由 Agent 自己決定。

#### 2) 它解決什麼問題

自動 summarization 有一個根本限制：framework 必須自己猜「現在是不是適合切 context」，而 summary 又可能把 Agent 自己認為重要的 task state 壓掉。

這個設計改成：

```text
Agent 知道目前剩餘 context
        ↓
Agent 自己判斷是否完成一個 coherent work unit
        ↓
寫 handoff notes / next steps
        ↓
new_context
        ↓
舊 window archive
        ↓
需要時 history search / read
```

也就是把 **context boundary selection** 從 middleware heuristic 提升成 reasoning decision。

#### 3) 為什麼重要

這可能是 long-running Agent 一個很關鍵的分叉：

**路線 A：Framework-managed compaction**

```text
threshold → summarize → replace old context
```

**路線 B：Agent-managed windows**

```text
model observes budget
→ preserves handoff state
→ explicitly cuts window
→ retrieves old windows on demand
```

路線 B 的潛在優勢不是「可以用更多 context」，而是 **Agent 可以選擇在哪個 semantic boundary reset**，例如一個 migration investigation 完成後、下一個 implementation phase 開始前，而不是剛好 token 到 90% 時。

#### 4) 核心架構與資料流

OpenViking 的 reset pipeline 大致是：

```text
Current Pi branch
   ↓
syncBranch 到精確 reset point
   ↓
flush pending queue
   ↓
post handoff note
   ↓
commit session
   ↓
OpenViking archive_<N>/messages.jsonl
   ↓
等待 .overview.md / Working Memory
   ↓
freeze 新 window header
   ↓
next model request
```

舊 context 不是真的被刪掉，而是 archive；新 request 只帶新的 window + frozen header。需要補細節時，Agent 再用 `history` 工具回讀。

#### 5) Technical mechanism / implementation evidence

這個 commit 不只是 demo UI，還做了不少 state-machine 級處理：

- reset 以單一 deadline 限制；
- reset 前必須把 pending message queue drain；
- handoff 先落到 session，確保 archive 裡有 continuation state；
- commit 回傳 archive URI 後視為 point-of-no-return；
- `.overview.md` 尚未生成時可以等待 background task，但 timeout 後仍以 degraded header 開新 window；
- persisted ledger 維持 window ↔ archive mapping；
- history item 使用穩定 index；
- Pi 原生 compaction 仍保留為 fallback。

更有價值的是它提供 long-context live scenario：把 22 個 extension source files、約 105k tokens 材料放進 workspace，不告訴 Agent 要使用 context tools，只要求逐檔 inventory。官方 commit 記錄的一次 `doubao-seed-2-1-pro` high-reasoning run：

- 96 model requests
- peak 約 47% / 128k context window
- 3 次 Agent 自主 reset
- 22/22 檔案完成 inventory

這只是一個 observed run，不是 statistically robust benchmark，但比純架構宣稱更值得追。

#### 6) 與昨天 Open SWE conversation offloading 的差異

昨天的 Open SWE 是：

```text
framework middleware
→ auto/manual trigger
→ summary model
→ summary artifact
```

今天 OpenViking 更激進：

```text
main Agent
→ 自己看到 budget
→ 自己決定 reset
→ handoff + archive
→ history on demand
```

兩者真正該比較的不是誰 API 比較漂亮，而是：

> **「讓主 Agent 管 context」是否真的比「讓 runtime 管 context」更可靠、更省 token、更少遺漏資訊？**

#### 7) 成熟度、近期活躍度與限制

**成熟度：實驗性。** 目前明確放在 `examples/pi-experimental-context-management`。

限制包括：

- Pi 沒有 Codex 原生 developer-role window header；
- token count 有估算成分；
- notes 沒有完全獨立 private namespace；
- live evidence 目前樣本太少；
- Agent 若錯判 reset 時機，可能增加 retrieval 次數或遺失 working context。

#### 8) 對 Agent Engineering 的實際影響

Context manager 不一定只能是「token threshold + summarizer」。未來可能需要把以下能力正式做成 Agent runtime API：

```text
context_remaining()
checkpoint_handoff()
new_context()
history.search()
history.read()
```

#### 9) 是否改變既有假設

是。它挑戰：

> 「context compaction 應該完全由 framework 自動控制」

但目前還不足以證明 Agent-managed 一定更好。

#### 10) 可做實驗 / benchmark

**Research Candidate：Yes — 最高優先級**

- **研究問題：** Agent 自主管理 context window，是否比自動 summarization 在 long-horizon coding task 上有更好的 quality-cost tradeoff？
- **為什麼現在值得測：** OpenViking 已有可跑 implementation 與 live scenario。
- **Baseline：** full-history-until-limit；threshold summarization；Open SWE-style automatic offload。
- **Variant：** Agent-managed `new_context` + history retrieval。
- **Task set：** 30–120 分鐘 repo investigation / refactor / migration tasks；每題設計成至少需要 2–5 次 context turnover。
- **Metrics：** task success、patch quality、total tokens、peak context、wall-clock latency、reset count、history retrieval count、critical-fact retention、developer intervention、resume reliability。

### 2. Deep Agents：Compaction 之後還是 Overflow 怎麼辦？現在有明確 Recovery Contract

**類型：** Context compaction / runtime reliability / tool-result offloading  
**來源：**
- https://github.com/langchain-ai/deepagents/commit/bb6d4316eb59b368b862e5517b888e5e70b1c3ae
- https://github.com/langchain-ai/deepagents

#### 1) 發生了什麼變化

Deep Agents 修正 SDK summarization middleware 的 overflow recovery。

舊行為存在兩個 production 問題：

1. proactive compaction 後，尾端大型 tool results 仍可能讓 request 超過 model input limit；
2. provider 回傳 context-too-long 類 400/413/422 error 時，某些 path 可能把幾乎一樣的 payload 再送一次，形成沒有實質縮小的 retry。

新版把它改成 bounded recovery：

```text
完整 request 計算 budget
(messages + system + tool schemas)
        ↓
必要時 summarize
        ↓
仍超 budget？
        ↓
offload oversized trailing tool results
        ↓
只允許一次 strictly-smaller retry
        ↓
仍不行 → terminal ContextOverflowError
```

#### 2) 它解決什麼問題

很多 context manager 的 benchmark 只問：

> summary 有沒有變短？

但 production 真正需要問：

> **下一個完整 model request 到底放不放得進去？**

因為 model request 不只 messages，還有 system text、tool schemas、output token reservation 等固定 overhead。

#### 3) 為什麼重要

這提醒一個很容易忽略的 distinction：

```text
Conversation tokens
≠
Actual request tokens
```

當 Agent 工具越多，tool schema 本身可能吃掉大量 context；保留最近 tool results 的策略也可能在 summary 後留下巨大 tail。

#### 4) 核心機制

新版：

- 從 model profile 讀 `max_input_tokens`；
- 預留 configured output tokens；
- 再留 5% headroom；
- token counter 會計算 messages、system message、tools；
- oversized tool results offload 時保留 call pair / message ID；
- context error 僅辨識特定 error pattern，不把所有 400 都當 overflow；
- recovery retry 必須比 rejected request 更小；
- retry 一次還是失敗，就轉成 terminal `ContextOverflowError`。

#### 5) Implementation evidence

commit 宣稱 121 focused tests 通過，涵蓋：

- sync / async recovery
- proactive oversized tails
- repeated context errors
- failed offloads
- output-token reservation
- irreducible overhead

這種測試面向比「summary function unit test」更接近 runtime contract。

#### 6) 與常見做法差異

常見做法：

```text
provider says context too long
→ summarize
→ retry
→ still too long
→ summarize/retry again
```

新版：

```text
provider/context budget evidence
→ produce provably smaller request
→ at most one retry
→ terminal failure with explicit semantics
```

#### 7) 成熟度與限制

**成熟度：中高，已進 Deep Agents SDK / Talon 路徑。**

限制：

- token count 仍是估算；
- model profile 若寫錯 input limit，budget 就錯；
- unknown provider limit 只能 reactive recovery；
- offload tool result 後對 reasoning quality 的影響仍需 benchmark。

#### 8) 對 Agent Engineering 的實際影響

Context compaction 應該被視為一個**有 termination condition 的 recovery state machine**，而不是一個文字摘要 helper。

#### 9) 是否改變既有假設

是。它支持：

> 「compaction 成功」的定義應該是 **下一個完整 model request 可安全執行**，而不是 summary 被產生。

#### 10) 可做實驗

**Research Candidate：Yes — 高優先級**

- **研究問題：** budget-aware compaction + bounded recovery 能否降低 overflow / retry storm，而不明顯損失品質？
- **Baseline：** threshold summary + naive retry。
- **Variant：** full-request budget validation + tool-result offload + one smaller retry。
- **Task set：** 大 tool schema、large logs、test output、browser dump、multi-file search output 的 coding tasks。
- **Metrics：** context overflow rate、retry count、task success、tool-call pairing correctness、total tokens、latency、offloaded bytes、critical evidence retention。

### 3. Codex + Deep Agents：Long-running Agent 開始有「不中斷工作的 Human Side Channel」

**類型：** Human-in-the-loop / long-running agents / asynchronous interaction / UX-runtime contract  
**來源：**
- https://github.com/openai/codex/commit/89c8bcf37d64be69e4c8286f4541c1a84ed312a4
- https://github.com/openai/codex
- https://github.com/langchain-ai/deepagents/commit/15606d280a8ddb86c8966fef0bab257f8070944f
- https://github.com/langchain-ai/deepagents

#### 1) 發生了什麼變化

Codex 今天新增 end-to-end context snapshot scenario，驗證已存在的 `request_user_input_async` 真正在多 turn / active turn 下成立：

```text
Agent 提問
→ 問題以 async item 送出
→ Agent 不等待，繼續工作
→ 使用者回答
→ answer steer 回同一個 active turn
→ Agent 繼續基於答案完成工作
```

同一批 scenario tests 也驗證 existing thread 可以 refresh plugin config，然後在後續 turn 發現並使用新安裝的 Skill / MCP tool。

另一邊，Deep Agents Talon 新增 `send_message(text)`：Agent 可以在長任務進行中主動發 progress update，**不結束 turn**。

#### 2) 它解決什麼問題

傳統 HITL 很常是 blocking：

```text
Agent 問問題
→ 整個 run 停住
→ 等人回答
→ 才能繼續
```

但真實長任務有很多工作不依賴該答案，例如：

- 先跑測試；
- 先建立 repo map；
- 先整理候選方案；
- 等人選 deployment window 時先做靜態分析。

如果 Agent 能把「必須等答案的部分」與「可繼續的部分」拆開，human latency 不一定要等於 agent idle latency。

#### 3) 為什麼重要

Long-running Agent 一旦真的跑 20 分鐘、1 小時，final-answer-only UX 就不夠了。

需要至少兩種 side channel：

```text
Agent → Human：progress / question
Human → Agent：answer / steer
```

而兩者都必須有 lifecycle semantics：這個 message 屬於哪個 turn？原 turn 被 cancel / supersede 後還能不能送？answer 是注入舊 turn 還是開新 turn？

#### 4) 核心架構與資料流

**Codex async question：**

```text
Active turn
  ├─ request_user_input_async
  ├─ continue model/tool work
  └─ answer arrives → steer same turn
```

**Talon progress message：**

```text
Agent tool: send_message(text)
        ↓
ContextVar-bound message_handler
        ↓
Host validates originating conversation + generation
        ↓
Channel.send_message
        ↓
Agent continues
```

Talon 的 handler 在 turn 完成、cancel 或 supersede 後就失效，concurrent runs 也各自有獨立 callback。

#### 5) Implementation evidence

Codex 最新 scenario test 直接模擬：Agent 問「launch update 要給誰」、先繼續撰寫、使用者回答 Customers，再在同一 active turn 根據答案完成內容。

Talon 的 tests 則驗證：

- progress message 在 final response 前送出；
- cancel / final 後舊 handler 不能再發；
- concurrent requests 不會把 message 發到彼此 channel；
- 129 focused tests + 17 WhatsApp bridge tests 通過。

#### 6) 與既有做法差異

以前 HITL 是 workflow pause；現在開始出現：

> **non-blocking human dependency**

這很像 async programming：不是每個 awaiting human input 都要 freeze whole computation。

#### 7) 成熟度與限制

Codex async input 已進 shipped scenario coverage；Talon progress message 已進 release 路徑。成熟度可視為**中高，但 UX policy 尚未成熟**。

真正風險不是技術能不能傳 message，而是 Agent 是否會：

- 問太多問題；
- 發太多 progress；
- 在答案回來前做大量之後要重做的工作；
- 把 asynchronous steer 處理成 inconsistent state。

#### 8) 對 Agent Engineering 的實際影響

未來 benchmark long-running Agent 不應只測「總完成時間」，還應拆：

```text
model compute time
external tool wait
human wait
avoidable idle time
speculative work later discarded
```

#### 9) 是否改變既有假設

是：

> Human-in-the-loop 不一定等於 Agent-in-the-loop 被 pause。

#### 10) 可做實驗

**Research Candidate：Yes**

- **研究問題：** async HITL 是否真的降低 wall-clock latency，還是只是增加 speculative work 與 token？
- **Baseline：** blocking question / approval。
- **Variant：** async question + continued independent work + progress channel。
- **Task set：** 每題含 1–3 個 30–180 秒人類延遲的 coding / configuration decision。
- **Metrics：** task success、wall-clock latency、human-wait idle time、discarded work、token cost、rework rate、number of interruptions、user-message count。

### 4. Google ADK + Microsoft Agent Framework：Workflow Identity 與 Session State 必須只有一個 Authority

**類型：** Workflow engine / dynamic orchestration / checkpoint / replay / session state  
**來源：**
- https://github.com/google/adk-python/commit/fe9f9a363d6bab8be1e70c7bed368201e24c3d00
- https://github.com/google/adk-python
- https://github.com/microsoft/agent-framework/commit/14b9f1d7e9a440e247a17fc8d47be0b69e554d8a
- https://github.com/microsoft/agent-framework

#### 1) 發生了什麼變化

Google ADK 把 static workflow node 與 dynamic node 的 `run_id` allocation 收斂到 `DynamicNodeState`。

以前不同執行 path 各自有 run counter / allocation logic；現在：

```text
DynamicNodeState.run_counters[parent_path][node_name]
        ↓
next_run_id()
        ↓
static + dynamic scheduler 共用
```

executor 如果沒有 explicit run_id，就把 `None` 交給 scheduler，不再自己偷偷分配。

Microsoft Agent Framework 則修 declarative workflow formula state：

- build 後保存 initial scope snapshot；
- reset 時真的恢復 initial state；
- checkpoint restore 時先 reset，再從 checkpoint 恢復 restorable scopes；
- tests 明確驗證兩個 hosted sessions 的 local formula state 不互相污染。

#### 2) 它們解決什麼問題

這兩件事表面不同，但都是同一類 distributed-state bug：

```text
「同一個 runtime fact，有兩個地方都覺得自己是 source of truth」
```

Google ADK 的問題是 run identity allocation；Microsoft 的問題是 session formula state。

#### 3) 為什麼重要

Dynamic orchestration 一旦支援：

- node rerun
- sub-workflow
- checkpoint / resume
- replay
- parallel dynamic nodes
- hosted multi-session Agent

identity 與 state ownership 就不能靠 local helper 猜。

run ID collision 或 session state bleed 可能不一定直接 crash，反而更危險：它會讓 replay / resume 產生「看起來成功，但對錯 run / 錯 session」的結果。

#### 4) 核心架構

理想模式：

```text
Workflow State Store
├─ authoritative run identity
├─ per-session mutable state
├─ checkpoint version
└─ replay sequence

Executor
→ consume identity/state
→ 不自行生成第二套 truth
```

#### 5) Implementation evidence

Google ADK tests 覆蓋：

- sequential run IDs；
- parent-scoped counter isolation；
- executor 確認 delegation 到 scheduler 分配 ID；
- 舊 serialized state 的相容性。

Microsoft tests 用 Alice / Mallory 兩個 session 放不同 marker，確認：

- Alice state 不進 Mallory；
- Mallory state 不回滲 Alice；
- implicit sessions 也不共用 state；
- checkpoint restore 重新載入正確 state。

#### 6) 與既有做法差異

壞模式：

```text
executor local counter
scheduler local counter
node state another counter
```

或：

```text
hosted agent instance
└─ mutable workflow state shared across sessions
```

新方向是把 identity / session state 提升到 workflow runtime 層。

#### 7) 成熟度與限制

兩者都是 core runtime correctness fix，成熟度高於實驗性 feature。

但目前仍不能推論所有 replay / distributed worker case 都已解決；尤其跨 process scheduler、外部 durable queue、真正 distributed execution 會更複雜。

#### 8) 對 Agent Engineering 的實際影響

這支持一個很實用的 design review 問題：

> **每一個 durable runtime fact 的 canonical owner 是誰？**

如果 answer 是「這裡一份、那裡也一份，最後希望同步」，就值得警惕。

#### 9) 是否改變既有假設

不改變 single vs multi-agent 結論，但提醒：**越多 dynamic delegation / parallel worker，identity correctness 越重要。**

#### 10) 可做實驗

**Research Candidate：Yes**

- **研究問題：** centralized runtime identity / session state 是否能顯著降低 replay / resume / concurrency correctness failure？
- **Baseline：** executor-local counters + mutable runtime instance state。
- **Variant：** scheduler-owned identity + session-scoped durable state + checkpoint restore。
- **Task set：** nested dynamic nodes、parallel same-name child runs、cancel/retry、checkpoint/resume、20–100 concurrent sessions。
- **Metrics：** ID collision、wrong-event replay、resume success、cross-session state contamination、coordination failure、latency overhead、implementation complexity。

### 5. 論文：`Subagents vs Agent Skills` 給出「什麼時候該 Delegate」的條件式答案

**類型：** Multi-agent / skills / delegation / context engineering / evaluation  
**來源：**
- https://arxiv.org/abs/2609.09233
- https://arxiv.org/html/2609.09233v1

#### 1) 發生了什麼變化

這篇 2026-09-07 提交的研究，不是問「subagent 比 single-agent 強嗎？」而是把比較縮小到一個很乾淨的問題：

> **同一份 reusable skill package，到底應該把 instructions 載入 main Agent context，還是把 skill 當 subagent 執行？**

兩種方式使用同一份知識：

```text
Agent Skill
→ SKILL.md 進 main context
→ main Agent 自己照 instructions 做

Subagent Skill
→ 建立 fresh context
→ subagent 拿 skill instructions + explicit input
→ 做完只回 output
```

#### 2) 它解決什麼問題

這直接碰到我們一直追的「什麼時候不該 delegate」。

Subagent 的好處是 information encapsulation：main Agent 不用看到 subtask 內部所有 trajectory，因此 peak context 下降。

但代價也很清楚：subagent 看不到 main context，所以 input 必須重新傳，**總 token 反而增加**。

#### 3) 為什麼重要

最有價值的結果不是「subagent 贏」，而是**何時贏、何時輸**。

研究在 SkillsBench 上比較：

- 原本 human-authored skills：大多是 loosely structured knowledge，缺乏清楚 I/O contract；
- 作者合成的 procedural skills：從成功 trajectories 整理，寫出明確 input / output contract。

結果：

- **沒有清楚 I/O contract 時：Agent Skill 與 subagent 相比，Agent Skill 在所有模型上 match 或 outperform subagent。**
- **有 procedural instructions + explicit I/O contract 時：趨勢反轉，subagent outperform Agent Skill。**
- 加入更多 distracting tools、提高 context pressure 後，subagent degradation 更慢。
- 對 GPT-5.3 Codex、Kimi K2.6 等較強模型，subagent 在超過 80% 的 tasks 上降低 peak context。
- 但 subagent **總 token 使用明顯較高**。

這是非常有用的「條件式 delegation」證據。

#### 4) 核心架構與資料流

作者把適合 subagent 的 skill 看成有 contract 的 procedural abstraction：

```text
q_in  = 什麼輸入條件下可以呼叫
h     = 這個 skill 做什麼
m     = 內部 procedure / SKILL.md
q_out = 應回傳什麼
```

對 main Agent 而言，它更像：

```text
SubagentSkill : X_in → X_out
```

而不是「再載入一份很長的 instruction document」。

#### 5) Implementation / experiment evidence

- benchmark：SkillsBench 87 tasks；
- 作者對其中 64 tasks 合成符合 contract 的 procedural skill packages；
- harness：OpenHands；
- procedural packages 來自 GPT-5.3 Codex 成功 trajectories，再用 Copilot CLI 協助 synthesis；
- 另外增加 distracting tools 測 context pressure；
- 同時量 peak context 與 total tokens。

#### 6) 與常見 multi-agent 敘事差異

常見說法：

```text
task 很複雜
→ 拆多 Agent
```

這篇比較支持：

```text
subtask 有明確 input
+ 有可封裝 procedure
+ 有明確 output
+ main Agent 不需要看內部 trajectory
→ 適合 subagent

否則
→ skill / direct main-context execution 可能更好
```

也就是 **delegation boundary 應該像 software interface boundary，而不是依 task size 猜。**

#### 7) 成熟度與限制

這是單篇 paper、單一 benchmark family，不能直接外推所有 coding / research Agent。

作者自己也指出：

- contract-driven packages 是 synthesized，不等於一般現成 skills；
- subagent 通訊成本仍高；
- main Agent 如何提供最小但足夠 input 還沒解決；
- skill library 如何 hierarchy / refactor 是 future work。

#### 8) 對 Agent Engineering 的實際影響

這提供一個很實際的 delegation heuristic：

> **先問能不能定義 interface，再問要不要 spawn agent。**

如果 input/output contract 寫不清楚，subagent 很可能只是把 ambiguity 推到另一個 context。

#### 9) 是否改變既有假設

是，而且剛好符合我們先前的懷疑：

> **Multi-agent 的價值不是來自 Agent 數量，而是 context encapsulation + interface quality。**

它同時也提醒：強模型並沒有讓 orchestration 問題消失；反而在強模型上，降低 peak context 仍有價值，但要付額外 total-token cost。

#### 10) 可做實驗

**Research Candidate：Yes — 最高優先級**

- **研究問題：** delegation 的 break-even point 是否可以由 I/O contract clarity 與 context pressure 預測？
- **為什麼現在值得測：** paper 已提供明確 hypothesis，可直接搬到 coding-agent workload。
- **Baseline：** 同一 skill instructions 直接載入 root Agent。
- **Variant：** skill 以 fresh-context subagent 執行，只回 structured result。
- **Task set：** repository tasks，分成「clear-contract procedural subtask」與「context-heavy ambiguous subtask」兩組；再控制可用 tools 數量。
- **Metrics：** task success、patch quality、total tokens、peak context、delegation frequency、handoff failure、coordination failure、wall-clock、developer effort。

### 6. `SWE-Bench Pro Verified`：Coding Agent Benchmark 本身也可能讓你得到錯誤結論

**類型：** Agent evaluation / coding agents / benchmarking methodology  
**來源：**
- https://arxiv.org/abs/2609.08149
- https://arxiv.org/html/2609.08149v1
- https://github.com/open-compass/AgentCompass

#### 1) 發生了什麼變化

研究者重新檢查 SWE-Bench Pro，指出兩類 reliability 問題：

1. **reward hacking / answer leakage**：Agent 可以從 Git history、本地 filesystem、network、metadata 等路徑取得不應該知道的 gold / evaluation information；
2. **task quality issues**：problem statement、scope、tests 本身不一致。

新的 `SWE-Bench Pro Verified` 做兩層修正：

```text
Anti-hacking environment
+
Refined flawed task instances
```

#### 2) 為什麼重要

我們之後如果要比較：

- single Agent vs multi-agent
- Sol vs Astra
- skills vs subagent
- memory on/off
- orchestration on/off

假設 benchmark 本身有 leakage，那模型越會找資訊，反而可能「作弊能力」被算成 coding capability。

#### 3) 關鍵 experiment evidence

論文以同一 evaluation harness 比較 Baseline / Anti-hacking / Verified。

代表性 paired results：

| Model | Baseline | Anti-hacking | Verified |
|---|---:|---:|---:|
| GLM-5.2 | 78.80% | 57.32% | 59.51% |
| DeepSeek-V4-Pro | 49.98% | 49.11% | 49.93% |

GLM-5.2 anti-hacking 後下降 **21.48 percentage points**；731 instances 中有 **186 PASS→FAIL**、只有 15 FAIL→PASS，McNemar test `p < 0.001`。

同時 confirmed answer-file access：

- local：103 tasks → 0
- network：49 tasks → 0

這代表下降不是所有模型等比例發生，也不是單純 benchmark 變難。

#### 4) 對 Agent Radar 的實際影響

以後我們自己做 Agent benchmark，除了：

```text
model
prompt
agent topology
context/memory
cost
```

還應該把：

```text
benchmark leakage surface
test visibility
git history
network access
hidden evaluation artifacts
```

列成正式實驗設定。

#### 5) 與 Security Radar 的界線

這裡把它放在 Agent Ecosystem，不是因為要研究 attack technique，而是因為它直接影響 **coding-agent evaluation validity**。

#### 6) 成熟度與限制

這是 2026-09-08 新 paper；目前結果值得重視，但仍應等待更多獨立 replication。

另外 anti-hacking environment 本身也可能改變正常 Agent 行為，因此論文特別 review PASS→FAIL cases；我們如果採用類似控制，也要檢查 collateral damage。

#### 7) 可做實驗

**Research Candidate：Yes — 評測基礎設施**

- **研究問題：** 我們自己的 coding-agent benchmark 結果有多少會受 leakage surface 影響？
- **Baseline：** standard repo sandbox。
- **Variant：** reconstructed repo、hidden test artifact isolation、network disabled、metadata filtering。
- **Task set：** SWE-Bench / internal synthetic repo tasks，挑 50–100 題 paired run。
- **Metrics：** task success delta、PASS→FAIL / FAIL→PASS、network/tool calls、unexpected artifact access、token cost、wall-clock、normal-tool collateral damage。

## 對既有研究問題的更新

### 強模型是否降低 orchestration complexity？

今天沒有證據支持「強模型讓 orchestration 不重要」。`Subagents vs Agent Skills` 反而顯示 GPT-5.3 Codex 這類較強模型在適當 contract 下，subagent 仍能在超過 80% tasks 降低 peak context；但總 token 上升。因此更合理的問題不是「強模型還需不需要 orchestration」，而是：

> **什麼 orchestration 能帶來 context / modularity 收益，而不是純粹增加溝通成本？**

### 什麼時候不該 delegate？

今天有比較明確的 evidence：

- skill 是鬆散背景知識；
- input / output 不容易定義；
- subagent 必須大量重建 main context；
- parent 最後仍需要看 subagent 的完整 trajectory；

這些情況下 delegation 很可能不划算。

### 多 Agent 是否真的提升品質而不是只增加 token？

答案仍是：**條件式。** 今日 paper 顯示在 procedural + explicit contract 情境確實有品質收益，但 total token 顯著增加；這不是 multi-agent 普遍勝利。

### Context / memory infrastructure 是否降低成本而不犧牲品質？

今天反而多出一個新分岔：

```text
runtime 自動 compact
vs
Agent 自己 cut window
```

必須把兩者做 controlled A/B，才能回答。

### Long-running Agent 如何 checkpoint / resume / reconcile？

今天的 Google ADK / Microsoft Agent Framework evidence 再次顯示：

> **先定義 authoritative identity / session state，再談 recovery。**

如果 run ID / state owner 本身不唯一，checkpoint 只是把 ambiguity 持久化。

## 今日結論

今天最值得留下的不是一個新 framework 名稱，而是三個更穩定的設計訊號：

```text
1. Context boundary 不是純 token 問題
   → 可能需要 Agent-aware / semantics-aware lifecycle

2. Delegation 不是 task complexity 問題
   → 更像 interface / encapsulation 問題

3. Workflow correctness 不是「有 checkpoint」就完成
   → identity、state ownership、replay semantics 必須先單一化
```

如果把它們放在一起，今天對 Agent Engineering 最有用的一句話是：

> **不要先問要幾個 Agent；先問資訊應該在哪個 context、透過什麼 contract 流動，以及哪個 runtime component 對 state 有最終決定權。**
