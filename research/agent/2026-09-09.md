# Agent Ecosystem Radar — 2026-09-09

> 研究窗口：截至 2026-09-09（Asia/Taipei）上午。這份報告只追蹤 Agent Ecosystem；AI / Agent Security 另由 Security Radar 處理。今日優先採用近期 repository commit、release 與可驗證 implementation evidence，不以 star 數、媒體熱度或單純產品宣傳排序。

## 執行摘要

- **Codex 正把長時程 Agent 的「狀態」從 transcript 拆成正式的 durable runtime state。** 9/9 最新 commit 新增 transactional `thread attachments`：每個 thread 可持久掛載有型別、穩定 identity key、大小上限與 idempotent semantics 的資料，不再要求所有工作狀態都塞進 conversation。另一個同日修正則讓 thread startup / resume / rollback 的 RPC lifetime 持續到真正 delegated work 完成，顯示「request 已回應」與「Agent 工作已結束」必須分開建模。
- **Codex Memory V2 採用 dual-write + readiness gate，而不是直接切換。** V1 繼續供應 context，V2 在背景獨立 extraction / consolidation，只有當 summary 合法且 consolidated thread 數達門檻後才標記 `v2Ready`。這是一個值得借鑑的 memory migration pattern：先 shadow-build、量 readiness，再 cut over。
- **Deep Agents Code 開始明確處理「舊 thread 不一定應該 resume」以及「切 workspace 不一定需要重啟 server」。** 新增 `max_resume_age` / `resume_after`，避免 model 或 policy 已變更時載入過時 context；同時在 server 能安全承載目標 workspace 時直接重新 bind，刷新 MCP metadata、tools、hooks、settings，而不是一律 restart。兩者合起來代表 resume 正從 UI 功能變成 runtime compatibility decision。
- **OpenViking 與 `codebase-memory-mcp` 今天的變化都在處理 derived/background infrastructure 的可靠性。** OpenViking 把 cron state 改成 atomic replace，且保留 `LockAcquisitionError` 的 retry semantics；Codebase-Memory 則修正 nested `.gitignore` 不完整導致大量不該 index 的檔案被納入，以及 indexer 自己輸出的 artifact 反過來觸發無限 reindex。這些不是模型能力問題，而是 Agent context infrastructure 必須先做到的 distributed-systems / build-system correctness。

## 重要發展

### 1. OpenAI Codex：Thread state 從 transcript 擴張成 transactional durable attachments

**類型：** Agent runtime / long-running agents / state model / context engineering  
**來源：**
- https://github.com/openai/codex/commit/589874be811a4034026dbae27d328776c25bb73c
- https://github.com/openai/codex/commit/102e1763b90e70d79a0bba5d262cf71f904583c1
- https://github.com/openai/codex

#### 發生了什麼變化

9/9 最新的 Codex state-runtime commit 把既有 `ThreadArtifact` 正式改名為 `ThreadAttachment`，並新增：

- `StateRuntime::add_thread_attachment`
- `StateRuntime::remove_thread_attachment`

mutation 使用 SQLite transaction；同一個：

```text
thread_id + attachment_type + identity_key
```

重複新增時不會產生第二份資料，而是直接回傳既有 attachment，且不修改原 payload / creation time。

另外明確限制：

- 每個 thread 最多 100 個 attachments
- 單一 serialized payload 最多 64 KiB
- `attachment_type` / `identity_key` 各最多 256 bytes
- type / identity key 不可空白
- unknown thread 直接拒絕
- removal 成功後立即釋放容量

測試包含 concurrent additions，確認多個同時請求最後只建立一筆 record。

同日上午另一個 commit 修正 app-server thread RPC lifecycle：thread startup、running-thread resume、rollback 可能在 request handler 已返回後仍持續工作，現在會等待 delegated listener / startup 真正完成；connection 關閉時也會清掉仍在 serialization queue 的 request 與 pending rollback waiter。

#### 它解決什麼問題

長時程 Coding Agent 很容易把所有狀態都塞進：

```text
conversation transcript
AGENTS.md
system prompt
tool messages
```

這會把兩種不同的東西混在一起：

```text
Model Context
≠
Runtime / Workflow State
```

例如以下資訊未必應永久佔用模型 context：

- thread 綁定的 artifact reference
- 某個 external resource identity
- durable task / goal metadata
- tool-produced structured state
- resume 時需要恢復、但不必逐字塞進 prompt 的 metadata

`thread attachments` 提供一個 bounded、typed、durable、idempotent 的 side-state surface。

另一個 RPC fix 則補上生命週期問題：

```text
RPC handler finished
≠
Delegated work finished
```

如果 runtime 在 response queued 後就開始 drain connection / teardown，真正執行 resume 或 rollback 的 listener 可能還沒完成。

#### 為什麼重要

這兩個 commit 放在一起看，比單看某個 API 更有意義：Codex 正逐步建立一個比較像 workflow runtime 的狀態層，而不是「一個模型對話加一些 tools」。

核心分離變成：

```text
Conversation / Prompt Context
        │
        │ bounded projection
        ▼
Agent reasoning

Durable State Runtime
├─ thread metadata
├─ goals
├─ attachments
├─ queued submissions
└─ lifecycle / rollback state
```

這對 compaction、cold resume、multi-agent coordination 都很重要，因為 canonical state 不必跟著 prompt 一起被摘要。

#### 核心架構與資料流

Attachment path：

```text
Client / Runtime
    ↓
(type, identity_key, payload)
    ↓
validate bounds
    ↓
BEGIN IMMEDIATE
    ↓
thread exists?
    ↓
identity already exists?
    ├─ yes → return Existing
    └─ no  → enforce capacity → INSERT → Created
```

RPC lifetime path：

```text
request handler
    ↓
delegate to thread listener
    ↓
listener actually processes resume / rollback
    ↓
completion signal
    ↓
request/drain lifecycle can finish
```

#### Implementation evidence

Attachment commit 有 regression coverage 驗證：

- idempotency
- thread isolation
- capacity reuse
- invalid inputs
- unknown threads
- concurrent writes 只產生一筆 identity

RPC commit 有測試覆蓋：

- queued connection 關閉後被釋放
- rollback waiter 被 listener cleanup 釋放
- rollback 進行中 pipeline 一個 resume request，兩邊都能完成

這不是 conceptual RFC，而是 state runtime 與 app server 的實際執行語意。

#### 與既有方法的差異

簡單 Agent framework 常見：

```text
state = messages[] + maybe checkpoint blob
```

Codex 現在更接近：

```text
messages = reasoning/history surface
state DB = canonical runtime state
context = state 的有限投影
```

這和昨天看到 Multi-Agent V2 用 durable agent registry 產生 bounded `<subagents>` context 是同一條設計方向，但今天的新 evidence 擴張到一般 thread metadata，不只是 subagent roster。

#### 成熟度與已知限制

**成熟度：中高，屬核心 state runtime 的 active development。**

限制：

- attachment schema 目前仍是 client-defined `type + identity_key + JSON payload`，不是 domain-specific workflow schema
- 100 records / 64 KiB 是 bounded storage contract，不代表模型知道何時應讀哪些 attachment
- durable state 解決「保存」問題，不自動解決 context routing
- SQLite transaction 保證 local state mutation，不代表 external tool effects 有 exactly-once semantics

#### 對 Agent Engineering 的實際影響

自製 Agent Runtime 可以採用相同原則：

> **不要把所有 durable truth 寫進 prompt。**

比較合理的是：

```text
Canonical durable state
→ runtime query / routing
→ 只把當下需要的 projection 注入模型
```

#### 是否改變既有假設

是。它進一步削弱「長 Agent = 長對話」這個假設。

Long-running Agent 更接近：

```text
durable workflow state
+ bounded model context
+ resumable executor
```

而不是無限長 transcript。

#### 可做實驗

**Research Candidate：Yes — 高優先級**

- **研究問題：** typed durable thread state 是否能比 transcript-only state 降低 context 成本與 resume 錯誤？
- **為什麼現在值得測：** Codex 已出現可直接參考的 transactional implementation。
- **Baseline：** 所有 goal / artifact / ownership metadata 寫入 transcript 或 repository instruction。
- **Variant：** bounded durable attachment store，只注入 task-relevant projection。
- **Task set：** 20–50 turns 的 coding / migration 任務，含 compaction、restart、revert、5–20 個 artifacts / goals。
- **Metrics：** task success、lost-state rate、duplicate-state rate、context tokens、tool calls、resume latency、recovery success、developer effort。

### 2. OpenAI Codex：Memory V2 用 dual-write + readiness gate 做 shadow migration

**類型：** Agent memory / context engineering / migration / observability  
**來源：**
- https://github.com/openai/codex/commit/2cbbf0c9b542a36a1c3284b5e804917635b6f666
- https://github.com/openai/codex

#### 發生了什麼變化

Codex 新增：

```toml
[memories]
dual_write = true
```

預設關閉。啟用後 V1 與 V2 memory extraction / consolidation 會同時執行，但：

- 使用者目前選定的 memory version 照常供應 context
- 另一版本在獨立 store / directory 背景建立
- 不把既有 V1 notes 偷偷 import 進 V2

同時增加 experimental `memory/status`：

```text
v2ConsolidatedThreads
v2Ready
```

`v2Ready` 不是「V2 有檔案就算 ready」，而是同時要求：

1. 有合法的 V2 `memory_summary.md`
2. successful consolidation 的 distinct thread 數達 `minConsolidatedThreads`

預設 threshold 是 20，可設定 1–4096。

成功 consolidation 的最大 thread count 會跨 pruning 保留，但 `memory/reset` 會歸零；metrics 也開始加 `memory_version` tag。

#### 它解決什麼問題

Memory pipeline 升級最危險的做法是：

```text
今天 V1
明天 deploy V2
直接切流量
```

因為 memory 是長期累積系統，V2 剛啟用時通常沒有足夠 history，或 consolidation artifact 還沒準備好。

Dual-write 讓 migration 變成：

```text
V1 serves context
     │
     ├──────────────┐
     ▼              ▼
V1 extraction    V2 extraction
V1 consolidate   V2 consolidate
                    ↓
                readiness check
                    ↓
                 cutover decision
```

這本質上就是 database / ranking system 常見的 shadow migration pattern，被帶進 Agent Memory。

#### 為什麼重要

Memory benchmark 常只比較：

```text
V1 quality vs V2 quality
```

但 production 真正還有另一個問題：

> **怎麼從 V1 安全搬到 V2？**

新的 design 開始把 migration readiness 本身變成 runtime state，而不是人工猜「應該差不多可以切了」。

#### Implementation evidence

測試明確驗證：

- V1 / V2 dual-write output 相互獨立
- V1 現有 notes 不被匯入 V2
- consolidation job ownership 不正確時不增加 readiness progress
- 沒有合法 summary，即使 thread count 足夠仍 `v2Ready=false`
- configurable threshold
- source thread 被刪除後，成功 consolidation 的 progress 仍保留
- memory reset 後 readiness 歸零

#### 與既有方法差異

常見方案：

```text
feature flag → hard switch
```

這次比較像：

```text
shadow write
→ independent store
→ readiness signal
→ explicit cutover
```

但目前 readiness 還偏「資料是否準備好」，不是「V2 quality 是否真的比 V1 好」。

#### 成熟度與已知限制

**成熟度：中，`memory/status` 仍標 experimental。**

主要限制：

- `minConsolidatedThreads` 只是 coverage proxy，不是 quality metric
- valid summary 代表格式 / minimum semantics 合法，不代表 retrieval quality 好
- dual-write 一定增加 extraction / consolidation compute 成本
- 沒看到自動 quality comparison 或 automatic rollback

#### 對 Agent Engineering 的實際影響

很值得直接借鑑的是：

> **Memory 版本升級不應直接 cut over；先 shadow-build，再以 readiness + quality gate 決定。**

如果未來要測 OpenViking、自己的 memory layer、甚至不同 embedding / summarization pipeline，都可以用相同 migration harness。

#### 是否改變既有假設

它提醒我們：memory infrastructure 的成本不能只算 query token。

還必須算：

- background extraction cost
- consolidation cost
- migration overlap cost
- rollback / dual-run complexity

所以「memory 省 token」只有在 end-to-end cost + quality 都成立時才有意義。

#### 可做實驗

**Research Candidate：Yes — 高優先級**

- **研究問題：** dual-write + readiness gate 是否能降低 memory pipeline 升級 regression？
- **為什麼現在值得測：** Codex 已公開具體 shadow migration mechanism。
- **Baseline：** V1 → V2 hard cutover。
- **Variant A：** dual-write + coverage readiness。
- **Variant B：** dual-write + coverage + offline quality gate。
- **Task set：** 多 session coding / research histories，包含 20、50、100 個 threads。
- **Metrics：** downstream task quality、retrieval relevance、context tokens、memory generation cost、time-to-ready、cutover regression rate、rollback success、latency。

### 3. Deep Agents Code：Resume 開始有 compatibility policy，workspace switch 則避免不必要 restart

**類型：** Long-running agents / thread lifecycle / workspace orchestration  
**來源：**
- https://github.com/langchain-ai/deepagents/commit/318311f56c3d3b9c4af4ece22fcfc387eeece5cc
- https://github.com/langchain-ai/deepagents/commit/ca2d1ef7f270d0fa1040e5473f43e99937b5f03f
- https://github.com/langchain-ai/deepagents/commit/80898ade19fd42171d3222bfeaa7d945fe68fe85
- https://github.com/langchain-ai/deepagents

#### 發生了什麼變化

Deep Agents Code 新增兩種 thread resume cutoff：

```toml
[threads]
max_resume_age = "7d"
# 或
resume_after = "2026-09-01T00:00:00+00:00"
```

兩個都存在時採更嚴格 cutoff。

Policy 套用於：

- launch-time resume
- in-session resume
- thread selector
- cross-agent thread switch

如果 restriction 已啟用但 thread timestamp 缺失 / malformed，會 fail closed；managed config 值本身非法時也會停止 launch，不會默默退回較弱 policy。

同一天另一個 change 則讓 thread 切換到不同 workspace 時，不再一律換掉 server：

1. 先問現有 server 是否能 validate / bind 目標 workspace
2. compatible → 保留 server，切 workspace
3. refresh MCP metadata、tool inputs、hooks、settings、UI state
4. 如果本地 cwd switch 失敗，rollback client + workspace state
5. server 回報 conflict 或 process-wide sandbox → fallback restart

#### 它解決什麼問題

「可以 resume」不代表「應該 resume」。

舊 thread 可能帶著：

- 舊 model assumptions
- 舊 policy
- 舊 tools / MCP setup
- 舊 project configuration
- 舊 instruction context

所以 thread age / migration boundary 是 compatibility 問題，不只是 UI history。

另一邊，如果每次 resume 到另一個 directory 就 restart server，則會付出：

- server startup latency
- MCP reconnect
- tool catalog reload
- hooks / settings reload
- background runtime churn

因此合理 runtime 應該同時處理：

```text
該不該 resume？
以及
resume 後需要重啟多少東西？
```

#### 為什麼重要

這比單純「支援 persistent thread」再前進一步。

Long-running Agent 真正需要的是：

```text
Thread State
+ Compatibility Policy
+ Workspace Binding
+ Runtime Reuse Decision
+ Rollback
```

這非常接近 application server / VM scheduler 的 lifecycle 管理。

#### 核心架構與資料流

Resume admission：

```text
resume request
    ↓
resolve effective cutoff
    ↓
validate thread updated_at
    ↓
old / invalid?
    ├─ yes → block / new session
    └─ no  → continue resume
```

Workspace switch：

```text
resume target workspace
      ↓
existing server validates binding
      ├─ compatible → rebind + refresh runtime metadata
      ├─ conflict   → restart server
      └─ failure    → keep previous workspace
```

#### Implementation evidence

Resume cutoff implementation 會標出 policy source（managed config / `config.toml`），並在 cross-agent switching 也重新檢查，避免只在 startup 擋一次。

Workspace reuse implementation 有 explicit state snapshot / restore：如果 local cwd / metadata update 過程拋錯，會把 server workspace、MCP info、server cwd 與 process cwd 還原。

#### 與最接近方案的差異

簡單 thread persistence 通常只有：

```text
thread exists → resume
```

Deep Agents 現在變成：

```text
thread exists
→ thread 還相容嗎？
→ workspace 可被目前 host 承載嗎？
→ 能 reuse runtime 還是必須 restart？
```

這是更接近 production runtime 的狀態機。

#### 成熟度與近期活躍度

`deepagents-talon` 0.0.7 在 9/7 發布，release 已包含：

- persistent LangGraph checkpoints
- chat-scoped conversation history + optional hybrid search
- background / expendable subagents
- fork / fresh subagent modes
- per-task tool selection
- cron schedules
- active turn interruption

而 9/8 仍有大量 thread / workspace / history hardening commits，代表這一塊非常活躍，但 Talon 自己仍標示 experimental。

#### 已知限制

- age cutoff 是 heuristic；「7 天舊」不一定不相容，「1 小時前」也可能已跨 policy migration
- 更準確應該是 model / policy / toolset / workspace compatibility fingerprint
- server reuse 的收益需要實測，因為 refresh MCP / tools / hooks 本身仍有成本
- sandboxed session 仍需 restart，表示 runtime isolation boundary 會限制 reuse

#### 對 Agent Engineering 的實際影響

比「永遠 resume」更合理的 policy 可能是：

```text
resume allowed if:
  model compatibility ok
  policy generation compatible
  tool/runtime schema compatible
  workspace binding valid
```

age 只是 fallback proxy。

#### 是否改變既有假設

是。它直接提出：

> **Resume 本身應該是一個 admission decision，而不是永遠成功的 feature。**

而 runtime reuse 也不應是 binary 的「新 session = 新 process」。

#### 可做實驗

**Research Candidate：Yes**

- **研究問題：** version-aware resume admission + compatible server reuse 是否比「永遠 resume + 永遠 restart」更可靠且更快？
- **Baseline：** 任意舊 thread 可 resume；workspace switch 一律 restart。
- **Variant A：** age cutoff + runtime reuse。
- **Variant B：** policy/model/toolset fingerprint + runtime reuse。
- **Task set：** 50–100 個 coding threads，期間進行 model switch、AGENTS/policy 更新、MCP tool change、workspace switch。
- **Metrics：** stale-context failure、task success、resume latency、server restart count、MCP/tool reinitialization 次數、rollback success、operator intervention、developer effort。

### 4. OpenViking：Background Agent durability 開始處理 atomic persistence 與 typed retry semantics

**類型：** Agent scheduling / memory pipeline / reliability / recovery  
**來源：**
- https://github.com/volcengine/OpenViking/commit/d3bdd5494e679b5775f8ca9087ad6e2bb2af42f3
- https://github.com/volcengine/OpenViking/commit/5626633e560e2d224ff3e05fd99d19b8d5c2d870
- https://github.com/volcengine/OpenViking

#### 發生了什麼變化

OpenViking `vikingbot` 原本存 cron jobs 是直接：

```text
cron.json.write_text(...)
```

若 process 在 write 中途 crash，原檔可能被截斷。

現在改成：

```text
write temporary file
→ replace target atomically
→ cleanup temp
```

regression test 直接模擬只寫入前 10 bytes 後丟 `OSError`，確認舊 `cron.json` 仍完整可讀。

同一天 memory semantic processor 修正另一個 retry contract：`LockAcquisitionError` 不再被 generic exception handler 包成 `RuntimeError`，而是原樣往上拋。

原因是上層 `_handle_message` 會依 exact error type 決定：

```text
lock contention
→ requeue semantic message
→ 不算進 API circuit breaker
→ 不丟掉 message
```

如果 error type 被抹掉，上層會把可重試 contention 當成一般失敗。

#### 它解決什麼問題

Background Agent / scheduled Agent 的可靠性不只取決於 LLM。

兩個典型 failure：

1. **Persistence corruption**：排程更新到一半 crash，下一次啟動整個 store 壞掉。
2. **Retry semantics loss**：本來是 transient lock conflict，卻在 exception wrapping 後變成 generic failure，導致 message 被 drop 或錯誤觸發 circuit breaker。

#### 為什麼重要

當 Agent 進入：

- cron
- background jobs
- memory consolidation
- knowledge indexing
- asynchronous queue

runtime 必須開始區分：

```text
retryable
non-retryable
contention
external API failure
corrupted state
```

所有 exception 都包成 `RuntimeError` 會讓上層 orchestration 無法做正確 recovery。

#### 核心架構與資料流

Cron persistence：

```text
current durable store
       ↓
write unique temp
       ↓
write success?
   ├─ no  → old store untouched
   └─ yes → atomic replace
```

Memory retry：

```text
semantic write
   ↓
LockAcquisitionError
   ↓
preserve semantic type
   ↓
queue handler requeues
   ↓
retry later
```

#### Implementation evidence

Cron test 主動 monkeypatch `Path.write_text`，先寫 partial content 再失敗，驗證：

- original JSON 仍有效
- temporary file 被 cleanup

Memory test 則參數化：

- `LockAcquisitionError` → 仍是同 type
- `ValueError` → 包成 `RuntimeError` 且保留 cause

這是在鎖定 orchestration contract，不是只測 happy path。

#### 與既有方法差異

很多 Agent demo 的 scheduler state 仍只是：

```text
JSON file + overwrite
```

retry 也常是：

```python
except Exception:
    retry()
```

OpenViking 這些改動雖小，但方向更接近可靠 queue / workflow engine：storage commit 與 error taxonomy 都必須有明確 semantics。

#### 成熟度與已知限制

**成熟度：中，屬快速補強中的 runtime。**

限制：

- `Path.replace()` 提升 local file atomicity，不等於完整 WAL / fsync durability protocol
- cron store 還是單檔 JSON，不是 transactional scheduler DB
- typed lock retry 只處理目前這一種 semantic conflict；其他 transient failure 是否分類完整仍需研究

#### 對 Agent Engineering 的實際影響

如果要做自己的 long-running runner，至少應該把：

```text
scheduler state write
queue ack
checkpoint write
memory index update
```

都當成 crash-recovery contract，而不是一般檔案 I/O。

#### 可做實驗

**Research Candidate：Yes**

- **研究問題：** atomic persistence + typed retry 是否能顯著降低 background Agent crash / contention 下的 state loss？
- **Baseline：** direct overwrite + generic exception wrapping。
- **Variant：** atomic replace + explicit retryable error taxonomy。
- **Task set：** cron create/update/delete、memory semantic jobs；在 write、rename、lock acquisition、queue ack 等位置 fault injection。
- **Metrics：** corrupted store rate、lost jobs、duplicate jobs、message drop rate、retry latency、recovery success、API call amplification、operator intervention。

### 5. `codebase-memory-mcp`：Shared code context 要先保證「index 什麼」與「何時重建」是正確的

**類型：** Code intelligence / context infrastructure / indexing / worktree  
**來源：**
- https://github.com/DeusData/codebase-memory-mcp/commit/b5185d10c4122da345d969464d936fb26f591c72
- https://github.com/DeusData/codebase-memory-mcp/commit/6741c29fc24d72ad4642a78335d05e32963df06e
- https://github.com/DeusData/codebase-memory-mcp

#### 發生了什麼變化

今天有兩個新的 material fix。

**A. Nested `.gitignore` semantics 修正**

舊 discovery walker 只正確處理較淺的一層 nested `.gitignore`；如果更深目錄又有自己的 `.gitignore`，可能不會套用。

實際 issue 中，一個空的：

```text
storage/.gitignore
```

讓更深層：

```text
storage/dump/.gitignore
```

裡的 `*` 沒生效，結果數千個本來 Git 已 ignore 的 dump 被 discovery / index，最後甚至碰到 OOM killer。

新實作把從 repo root 到目前目錄的每一層 `.gitignore` 建成 root→leaf chain，採 Git precedence：

- deeper `.gitignore` 優先
- 同一檔案最後 matching rule 優先
- negation 可 re-include
- lookup cost O(depth)，不重掃整棵樹

**B. Watcher 排除 indexer 自己的 `.codebase-memory` artifact**

原本每次 index publish 後都會 export：

```text
.codebase-memory/graph.db.zst
artifact.json
```

watcher 的 Git dirty signature 又把這些自己產生的 output 算進 change，因此：

```text
index
→ export artifact
→ watcher sees dirty change
→ reindex
→ export artifact again
→ watcher sees new change
→ ...
```

issue 的實際觀察是 15 分鐘內 100+ 次 self-trigger，兩個 index workers 持續吃滿。

現在 Git status pathspec 明確排除 `.codebase-memory`，同時 regression test 驗證：

- 自己 export artifact 不觸發 reindex
- artifact 被 commit / 修改也不造成 loop
- 真實 source edit 仍正常觸發一次 reindex

#### 它解決什麼問題

昨天我們關注的是「共享 code graph 能不能降低 Agent 重複探索」。今天的新 evidence 提醒另一面：

> **Context infrastructure 本身如果 source selection 或 invalidation 錯了，Agent 會拿到錯資料、花掉大量 compute，甚至把機器 index 到 OOM。**

兩個核心問題：

```text
What belongs in the index?
When is the index stale?
```

這比 retrieval algorithm 更基礎。

#### 為什麼重要

對 multi-worktree / multi-agent coding workflow 特別重要：

- 不同 worktree 會有 derived artifacts
- monorepo 常有多層 `.gitignore`
- index daemon 長駐監控 source change
- 多個 Agent 可能共用同一份 graph

如果 invalidation loop 失控，shared context layer 反而成為全系統 bottleneck。

#### 核心架構與資料流

正確 source discovery：

```text
repo root .gitignore
      ↓
nested .gitignore
      ↓
deeper .gitignore
      ↓
Git-compatible precedence
      ↓
indexable source set
```

Watcher：

```text
source change
→ dirty signature
→ reindex
→ derived artifact export
       │
       └─ excluded from dirty signature
```

也就是 derived output 不能反饋成自己的 input trigger。

#### Implementation evidence

`.gitignore` fix 的 code comment 直接記錄實際 OOM scenario，並實作 `gitignore_link` chain。

watcher fix 有完整 linked worktree regression fixture，包含：

- 長 hyphen branch name（排除原先錯誤懷疑）
- untracked artifact
- committed artifact
- repeated polling
- real source edit

因此可確認 root cause 是 artifact self-trigger，而不是 branch naming。

#### 與既有方法差異

簡化的 indexer 很容易做：

```text
walk filesystem
ignore some extensions
watch git dirty
```

但真正與 Git / worktree 整合時，需要：

- Git-compatible ignore semantics
- generated-output exclusion
- stable dirty signature
- source vs derived artifact boundary

這些是 build system / incremental compiler 已經很熟悉的問題，Agent context system 不能重新踩一次。

#### 成熟度與已知限制

**成熟度：中高，專案近期 implementation churn 非常高。**

這次 fix 也反映大型 / monorepo / worktree 邊界仍在持續收斂，所以在把它當 production shared context plane 前，應先用自己的 repo topology 做 stress test。

#### 對 Agent Engineering 的實際影響

如果 Context Graph 要讓多個 Agent 共用，至少必須量：

```text
index correctness
incremental freshness
reindex amplification
resource usage
```

不能只量 QA accuracy / token saving。

#### 可做實驗

**Research Candidate：Yes — 延續昨天，但 benchmark scope 擴大**

- **研究問題：** code-context indexer 在 monorepo / nested ignore / worktree / derived artifact 情境下是否仍維持正確且穩定的 incremental indexing？
- **Baseline：** native Agent `rg/read`，無 persistent index。
- **Variant A：** Codebase-Memory persistent graph。
- **Variant B：** 其他 context graph（例如 Graphify）若支援同場景。
- **Task set：** 真實 monorepo + 人工建立 3–5 層 `.gitignore`、linked worktrees、committed/untracked graph artifacts、連續 source edits。
- **Metrics：** indexed-source precision/recall、stale graph rate、reindex count、CPU / RAM、index latency、context tokens、downstream QA quality、tool calls。

## 今日跨專案綜合觀察

今天沒有看到新的可信 evidence 能回答：

> 「多 Agent 一定比單 Agent品質更高嗎？」

也沒有新的 compute-matched benchmark 能證明：

> 「更強模型已經讓 orchestration 不再需要。」

反而今天最強的 implementation signal 全部集中在另一條線：

> **Agent 系統正在從『model + tools』演化成需要正式 state、migration、lifecycle、scheduler 與 incremental-computation semantics 的 runtime。**

可以把今天五個發現拼成：

```text
                     ┌──────────────────────┐
                     │  Durable Thread State │
                     │ goals / attachments  │
                     └──────────┬───────────┘
                                │ bounded projection
                                ▼
                         Agent Reasoning
                                │
                   ┌────────────┴────────────┐
                   ▼                         ▼
          Runtime Lifecycle           Context / Memory
       resume / rollback / drain      dual-write / index
                   │                         │
                   ▼                         ▼
          Scheduler / Background       Derived Infrastructure
         atomic state + retries       ignore / invalidation
```

這裡最值得吸收的不是任何單一 framework，而是五個 pattern：

1. **Durable truth 不要只放 transcript。**
2. **Migration 用 shadow/dual-write，不要 blind cutover。**
3. **Resume 是 compatibility admission，不只是 load history。**
4. **Background work 要有 atomic persistence + typed retry。**
5. **Derived context 要避免 self-trigger，並尊重 source-system semantics。**

這些 pattern 都不依賴特定模型，因此即使未來 model capability 再上升，仍然不會因「模型更聰明」而消失。

## Research Candidates

### Candidate A：Durable Thread State vs Transcript-Only State

- **研究問題：** 把 workflow metadata 拆出 transcript，是否降低 context cost 且提升 resume correctness？
- **為什麼現在值得測：** Codex 已有 transactional attachment implementation。
- **Baseline：** metadata 全寫 transcript / instruction files。
- **Variant：** durable keyed attachments + task-aware context projection。
- **Task set：** long coding / refactor threads，含 restart、compaction、revert、artifact handoff。
- **Metrics：** task quality、lost / duplicate state、context tokens、tool calls、recovery latency、reliability、developer effort。

### Candidate B：Memory Shadow Migration

- **研究問題：** dual-write + readiness 是否能降低 memory version cutover regression？
- **為什麼現在值得測：** Codex V2 已提供明確 dual-write / status contract。
- **Baseline：** hard cutover。
- **Variant：** dual-write + coverage gate；dual-write + quality gate。
- **Task set：** 20–100 thread 的 multi-session histories。
- **Metrics：** downstream quality、retrieval relevance、token use、memory compute cost、time-to-ready、cutover regression、rollback reliability。

### Candidate C：Resume Compatibility & Runtime Reuse

- **研究問題：** resume admission + compatible server reuse 是否能降低 stale context 與 startup churn？
- **為什麼現在值得測：** Deep Agents 同時落地 resume cutoff 與 workspace-server reuse。
- **Baseline：** always-resume + always-restart。
- **Variant：** age gate；model/policy/tool fingerprint gate + server reuse。
- **Task set：** cross-workspace coding sessions with policy/model/MCP changes。
- **Metrics：** task success、stale-context failures、resume latency、server restarts、tool reinitialization、rollback success、operator intervention。

### Candidate D：Background Agent Crash / Contention Recovery

- **研究問題：** atomic state write 與 typed retry error 是否實際改善 scheduler / memory worker recovery？
- **為什麼現在值得測：** OpenViking 出現可直接 fault-inject 的兩個 implementation case。
- **Baseline：** overwrite + generic exception。
- **Variant：** temp+replace + explicit retryable taxonomy。
- **Task set：** cron store + semantic memory queue，注入 partial write / crash / lock contention。
- **Metrics：** corrupted state、lost / duplicate jobs、retry latency、recovery rate、API amplification、operator effort。

### Candidate E：Persistent Code Context Incremental Correctness

- **研究問題：** shared code graph 在真實 monorepo / worktree 下會不會因 source selection / invalidation 錯誤抵消 token savings？
- **為什麼現在值得測：** Codebase-Memory 最新兩個真實 bug 分別造成 OOM 級 over-indexing 與 100+ 次 self-trigger reindex。
- **Baseline：** native `rg/read`。
- **Variant：** Codebase-Memory；可選 Graphify 作第二 variant。
- **Task set：** nested `.gitignore`、linked worktree、derived artifacts、連續 edits。
- **Metrics：** index precision/recall、reindex amplification、CPU/RAM、freshness latency、tokens、tool calls、downstream answer quality。
