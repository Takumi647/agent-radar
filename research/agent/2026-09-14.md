# Agent Ecosystem Radar — 2026-09-14

> 研究窗口：截至 2026-09-14 08:37（Asia/Taipei）。本報告只追蹤 Agent Ecosystem；AI / Agent Security 由獨立 Security Radar 處理。今日以原始 GitHub commits、官方產品 / engineering 公告與可驗證 implementation evidence 為主；不以 star 數、排行榜或單一 vendor 宣稱判斷價值。

## 執行摘要

- **OpenAI Codex 正把 Git worktree（Git 工作樹：同一 repository 的獨立 checkout）正式升格成 coding-agent runtime primitive。** 最新 Agents Overview 可以直接從專案預設分支建立 managed worktree，綁定一個新的空白 session，而且保留來源 checkout 的未提交修改、不主動 fetch、不打斷其他 running agents。建立失敗時還區分「可安全清掉的未認領 clean worktree」與「可能含狀態、必須保留給人處理的 checkout」。這比單純「開另一個 subagent」更接近真正的平行 software-engineering isolation。
- **Codex 的 observability（可觀測性）開始從 turn-level 改成 step-level provenance（步驟級來源歸因）。** 同一個 turn 內若模型、reasoning effort、tool router 或 review policy 發生變化，Responses metadata、MCP tool call、pre/post-tool hooks 現在會記錄「真正發出該 request / tool call 的 step 設定」，而不是 turn 開始時的舊設定。這是做 adaptive model routing、delegation ROI 與 tool-cost attribution 的必要基礎。
- **OpenViking 把 context retention 從「保留最近 N 則 message」推向「以完整 user turn + token budget 做切分」。** 新 `turn_budget` 模式預設最多保留最近 3 個 user turns、12,000-token budget，且至少保留最新 assistant/tool step；超大的最新 turn 可以把早期步驟 archive、保留 user question 與 tail。`pending_tokens` 也只計真正會離開 live window 的內容。這直接碰到 long-running Agent 最核心的 context / memory 邊界問題。
- **OpenViking 的 Skills lifecycle 正從 CLI 本地 clone / 打包轉成 server-side Git import / update。** server 可以解析 Git source、列出可安裝 Skills、選擇性安裝，並記錄 source metadata 供後續 `from_source` 更新。這代表 Skill 正逐步從「一包 prompt / script」變成有 provenance、版本來源、遠端更新生命週期的可管理資產。
- **Google ADK 的 workflow graph 開始從單純 adjacency（節點連線）走向 route-aware graph semantics（路由感知圖語義）。** 同一對節點現在可以有多條 edge，只要 routes 互斥；無條件 edge 或 route overlap 仍拒絕。這個小改動其實反映 orchestration DSL 需要把「拓撲」和「條件路由」一起當作 graph identity，而不是只用 `(from, to)` 判斷重複。
- **重要補漏：OpenAI 於 9/10 公開 Agents API public beta，正式把 Codex harness 變成託管 runtime 層。** 官方提供 durable session、context compaction、tool search、programmatic tool calling、subagent orchestration 與 hosted / BYO sandbox。這是近一週非常大的 Agent infrastructure 事件，先前 daily briefs 沒有獨立收錄，因此今天補進；但官方客戶案例的 4x latency、60% cost reduction 等數字仍屬 vendor-hosted testimonials，不能當成 multi-agent 或 managed harness 普遍優勢的獨立證據。

今日最強的共同訊號不是「更多 Agent framework」，而是 **Agent runtime 正逐步把 workspace isolation、step provenance、context-retention policy、Skill lifecycle 與 workflow routing 變成明確 contract**。這些 contract 比單純再加一層 planner / subagent 更值得先做 benchmark。

## 重要發展

### 1. OpenAI Codex：Managed Worktree 成為平行 Coding Agent 的一級 Session Primitive

**類型：** agent coding / software-engineering agents / parallel work / workspace isolation  
**來源：**
- https://github.com/openai/codex/commit/6f39a47bb3b04de4c804187bfbf55edc56939aab
- https://github.com/openai/codex

#### 1) 發生了什麼變化

Codex 的 Agents Overview 新增 `new_worktree` action。對支援 worktree 的本地 repository，使用者可以直接從 dashboard 建立：

```text
Project default branch
        ↓
Managed Git worktree
        ↓
Blank Codex session
        ↓
Bind session ↔ worktree
```

這個流程不是簡單執行 `git worktree add`：

- base 優先使用 cached remote `HEAD`；
- fallback 到 `main` / `master`；
- **不為了建 worktree 額外 fetch**；
- 保留目前所選 subdirectory；
- 不改動 source checkout 的 edits；
- 保留 selected approval reviewer；
- 建立後先開 blank session，不自動送 first turn；
- 建立期間會暫停衝突 action；
- reconnect 會清 pending creation state。

#### 2) 它解決什麼問題

多 Agent coding 最常見的一個隱性 coordination problem 不是模型怎麼溝通，而是：

> **兩個 Agent 是否正在碰同一份 mutable checkout？**

shared checkout 容易出現：

- 一個 Agent 的未提交修改干擾另一個 Agent；
- test / build artifact 相互污染；
- branch / index state 被其他 worker 改變；
- cherry-pick / merge attribution 困難；
- 任務失敗後不知道哪些檔案屬於哪個 worker。

Worktree 讓每個 coding session 有獨立 filesystem / Git index，但仍共享 object database，成本通常遠低於完整 clone。

#### 3) 為什麼重要

這改變了 multi-agent coding 的一個基本假設：

```text
Multi-Agent coordination
不只是
Prompt / message passing

還包含
Workspace topology + ownership
```

如果 workspace 本身沒有 isolation，任何「subagent 平行化提升速度」的 benchmark 都可能被 checkout conflict 污染。

#### 4) 核心架構與資料流

```text
Agents Overview
    ↓ new_worktree
Resolve project default branch locally
    ↓
WorktreeManager.create()
    ↓
PendingWorktree owns checkout
    ↓
Start blank session in checkout cwd
    ↓
Verify server really applied worktree cwd
    ↓
Bind thread ID to worktree
    ↓
Attach UI to new session
```

其中 `PendingWorktree` 的 ownership semantics 很值得注意：如果 worker 被取消、event 沒送達，而且 checkout 仍是 clean / unclaimed，drop path 會嘗試清理；但如果 session startup 已經進入不確定狀態，系統會保留 checkout path 並要求人工決定是否移除。

#### 5) Implementation evidence

commit regression coverage 包含：

- default branch selection；
- source checkout preservation；
- selected subdirectory；
- session ownership；
- approval settings；
- clean worktree cleanup；
- startup failure；
- reconnect pending state；
- busy-state rendering；
- unrelated non-UTF-8 Git refs。

這不是純 UI shortcut，而是完整 workspace/session lifecycle。

#### 6) 與既有方法差異

常見 coding-agent parallelism：

```text
Main checkout
├─ Agent A 修改
├─ Agent B 修改
└─ 靠 prompt 告訴彼此不要衝突
```

Codex 方向更像：

```text
Repository
├─ Worktree A ↔ Session A
├─ Worktree B ↔ Session B
└─ Integration / merge boundary
```

也就是把 coordination boundary 從語言層下沉到 Git / filesystem 層。

#### 7) 成熟度與限制

**成熟度：production-facing implementation。** 目前此 path 明確要求 local worktree support；remote workspace / environment 不走這條流程。

限制仍包括：

- worktree 可以隔離檔案，但不能自動解決 semantic merge conflict；
- dependency cache、database、外部 service 仍可能共享；
- base branch 不 fetch，可能以 stale cached default branch 開始；
- 多 worker 最後的 integration strategy 仍需設計。

#### 8) 對 Agent Engineering 的實際影響

對 multi-agent coding，應把以下變數納入 architecture：

```text
Delegation strategy
+
Workspace isolation strategy
+
Integration strategy
```

不能只 benchmark「有幾個 subagent」。

#### 9) 是否改變 single-agent vs multi-agent 假設

是。它說明 multi-agent 的 overhead 有一部分不是 token，而是 workspace orchestration。若單一強 Agent 可以在同一 checkout 完成工作，多 Agent 的 isolation / merge overhead 可能不值得；只有能真正平行、低耦合的 subtasks 才較有機會受益。

#### 10) 可做 experiment / replication / benchmark

**Research Candidate：Yes — P0**

- **研究問題：** per-agent worktree isolation 是否能提高 multi-agent coding 的 reliability，並抵銷額外 orchestration overhead？
- **為什麼現在值得測：** Codex 已提供 production implementation，可對照 shared checkout。
- **Baseline：** 2–4 agents 共用同一 checkout。
- **Variant A：** per-agent worktree + manual merge。
- **Variant B：** per-agent worktree + lead-agent integration。
- **Task set：** 可平行的多檔 feature、跨模組 bugfix、互相重疊的 refactor 三類。
- **Metrics：** task success、merge conflict rate、rework、wall-clock latency、model cost、token use、coordination failure、tool calls、developer effort。

### 2. OpenAI Codex：Observability 從 Turn-level 升級成 Step-level Execution Provenance

**類型：** observability / tracing / adaptive model routing / tool attribution  
**來源：**
- https://github.com/openai/codex/commit/16537b20a5ec0ea9aa079f4ad4b0e30e8a9efacf
- https://github.com/openai/codex

#### 1) 發生了什麼變化

Codex 修正一個很典型的 long-running turn attribution bug：

同一個 turn 中，model、reasoning effort、approval / review settings、tool router 可能在不同 step 改變；但先前部分 metadata 與 hooks 仍使用 turn 初始設定。

現在 Responses、MCP calls、extension tools、pre/post-tool hooks、permission hooks 都改成讀取 **captured StepContext / GuardianReviewContext**。

#### 2) 它解決什麼問題

假設一個 turn 是：

```text
Step 1: Sonnet / low effort
→ router 決定升級
Step 2: Sol / high effort
→ MCP call
Step 3: Astra / review
```

如果 telemetry 全部寫成「turn 起始 model = Sonnet」，後續就無法回答：

- 哪個 model 真正發了昂貴 tool call？
- 哪個 reasoning effort 導致結果？
- 某個 MCP call 的 tool inventory 當下是什麼？
- review / approval 到底採用哪個 policy？

#### 3) 為什麼重要

這對我們一直追的 **adaptive routing / delegation ROI** 特別關鍵。

沒有 step-level attribution，就算 final quality 變好，也無法精確計算：

```text
quality gain
÷
實際是哪個 model / step / tool 增加的 cost
```

也就無法判斷 router 是否真的有效。

#### 4) 核心架構

```text
Turn Context
    ↓
Step captures finalized settings
    ├─ model
    ├─ reasoning effort
    ├─ approval policy
    ├─ auto review flags
    └─ finalized tool router
          ↓
Responses / MCP / hooks / permissions
          ↓
step-correct metadata
```

Remote compaction 甚至另外 attach finalized tool inventory，避免 compaction 只看到過時的 tool set。

#### 5) Implementation evidence

測試覆蓋：

- turn 中 model 切換；
- reasoning effort 切換；
- MCP metadata；
- pre-tool hook model attribution；
- captured review flags；
- tool inventory 與 issuing request 一致。

#### 6) 與既有方法差異

舊 mental model：

```text
One turn = one execution configuration
```

新 mental model：

```text
One turn = sequence of execution steps
Each step can have its own effective model / policy / tool surface
```

這是更接近 workflow engine / distributed tracing 的設計。

#### 7) 成熟度與限制

**成熟度：production runtime instrumentation fix。**

限制：即使 metadata 正確，仍需統一 trace ID、delegation parent-child linkage、token / USD accounting 才能形成完整 end-to-end ROI。

#### 8) 對 Agent Engineering 的實際影響

任何 model router、escalation、multi-agent benchmark 若只記「session model」或「turn model」，都可能嚴重錯估成本與責任歸因。

#### 9) 是否改變既有假設

是。對強模型 / orchestration 的比較，應從 session-level comparison 走向 **step-level causal attribution**。

#### 10) 可做 benchmark

**Research Candidate：Yes — P0**

- **研究問題：** step-level provenance 是否會改變我們對 adaptive routing / escalation ROI 的結論？
- **Baseline：** session / turn-level model attribution。
- **Variant：** step-level actual issuer attribution。
- **Task set：** 固定 model、mid-turn escalation、tool-heavy routing、review escalation。
- **Metrics：** attribution error、model monetary cost、quality、tool calls by model、latency、routing decisions、developer effort。

### 3. OpenViking：Auto-commit Context Retention 從 Message Count 改成 Turn-aware Token Budget

**類型：** context engineering / memory / compaction / long-running agents  
**來源：**
- https://github.com/volcengine/OpenViking/commit/e757dd3749275718406c66fd87766c44556626e0
- https://github.com/volcengine/OpenViking

#### 1) 發生了什麼變化

OpenViking 的 OpenClaw integration 原本 auto-commit 後預設保留最近 10 則 messages。這種 count-based retention 可能剛好從一個 tool-rich user turn 中間切斷。

現在新增 opt-in：

```json
"commitRetentionMode": "turn_budget"
```

使用 server 的 turn-aware planner，預設：

- 最多最近 3 個 user turns；
- 12,000-token retention budget；
- 至少 final assistant/tool step；
- 最新 turn 過大時，保留 user question + recent tail，把較舊 step archive；
- mandatory tail 允許超過 nominal budget。

#### 2) 它解決什麼問題

Message 不是好的 semantic boundary。

一個 user turn 可能是：

```text
User request
→ tool call
→ tool result
→ tool call
→ tool result
→ assistant synthesis
```

如果只保留最後 N messages，可能留下結果卻丟掉原始問題，或留下 tool output 但丟掉產生它的 reasoning / request context。

#### 3) 為什麼重要

Context retention policy 其實同時決定：

- live working memory；
- archive / checkpoint 邊界；
- long-term memory extraction timing；
- 下一 turn 可以立即看到什麼；
- `pending_tokens` 何時觸發 commit。

因此「保留幾則 message」不是 UI 參數，而是 Agent runtime policy。

#### 4) 核心資料流

```text
Live session messages
      ↓
pending token threshold
      ↓
Turn-aware retention planner
      ├─ retained live tail
      └─ archived prefix → checkpoint / memory extraction
      ↓
next turn
```

`pending_tokens` 也調整成只計真正會離開 live window 的 message；user question 如果同時被 archive 與 live retention 參考，不重複計算。

#### 5) Implementation evidence

commit 新增 config schema、client API `retentionMode`、integration tests，並刻意保留：

- manual commit 全 archive；
- `/compact` 全 archive；
- legacy `message_count` 為預設，避免破壞既有行為。

#### 6) 與既有方法差異

```text
message_count
→ implementation boundary

turn_budget
→ semantic boundary + token constraint
```

它比單純 sliding window 更接近 Agent 真正的 interaction unit。

#### 7) 成熟度與限制

**成熟度：已實作、目前 opt-in。**

限制：固定「3 turns / 12k」未必適合所有模型與任務；tool-heavy turn 與 long-document turn 仍可能極不對稱。

#### 8) 對 Agent Engineering 的影響

Memory / context benchmark 不應只問「摘要得好不好」，也要問 **切在哪裡**。錯的 boundary 可能讓後續 summary / memory extractor 在資訊已經殘缺的情況下工作。

#### 9) 是否改變既有假設

是。Context window management 應從 message-list truncation 轉向 turn / event topology-aware retention。

#### 10) 可做 experiment

**Research Candidate：Yes — P0**

- **研究問題：** turn-aware retention 是否比 message-count retention 更能維持 quality，且不增加過多 token？
- **Baseline：** keep last 10 messages。
- **Variant A：** last N user turns。
- **Variant B：** turn-aware token budget。
- **Variant C：** importance-aware turn budget。
- **Task set：** coding tool loops、research browsing、long-document analysis、multi-agent handoff。
- **Metrics：** task success、critical-context retention、recovery after compaction、token use、compaction frequency、latency、memory recall quality。

### 4. OpenViking：Skill 安裝 / 更新改成 Server-side Git Lifecycle

**類型：** skills / tool lifecycle / agent capability management / context infrastructure  
**來源：**
- https://github.com/volcengine/OpenViking/commit/fafccb1c2bb3439632b9526f6a3e687c0058089b
- https://github.com/volcengine/OpenViking

#### 1) 發生了什麼變化

OpenViking 將 Git Skill 的解析與匯入責任從 CLI 本地端搬到 server。

以前 CLI 會自己：

- parse Git URL；
- clone；
- 找 Skill；
- 建 temporary directory；
- 打包 / upload；
- 建立 source record。

現在 client 可以直接把 `data`（Git URL / source）交給 server，並提供：

- `skills`：選擇特定 Skills；
- `list_only`：只列 source 內有哪些 Skills；
- `target_uri`；
- `source_metadata`。

更新時，如果既有 Skill 的 source type 是 `git`，可以直接：

```text
PUT /api/v1/skills/<name>
{ "from_source": true }
```

讓 server 依記錄來源更新。

#### 2) 它解決什麼問題

Local CLI clone 的問題是 capability lifecycle 分散在每台 client：

- 不同 client 的 Git / network 環境不同；
- source metadata 容易不一致；
- server 無法成為 Skills 的 canonical lifecycle owner；
- web / remote client 不容易共用相同行為。

#### 3) 為什麼重要

這代表 Skill 正從「prompt 旁邊的一個資料夾」走向：

```text
Source
→ Discovery
→ Selection
→ Import
→ Processing
→ Installed Skill
→ Source-aware Update
```

也就是具有 lifecycle 的 Agent capability asset。

#### 4) 核心架構

```text
CLI / Client
    ↓ Git source + selectors
Skill Server
    ├─ discover
    ├─ list
    ├─ import
    ├─ source metadata
    └─ update from source
        ↓
Viking Skill namespace
```

#### 5) Implementation evidence

commit 大幅移除 CLI-side `GitSource`、`PreparedSource`、TempDir clone 與 target resolution；選擇 / listing / Git update 改由 server API 負責。

這是責任邊界改變，不只是多一個 URL input。

#### 6) 與既有方法差異

```text
舊：client materializes capability → server receives bundle
新：server owns source-to-capability lifecycle
```

#### 7) 成熟度與限制

**成熟度：已進主線。**

目前最值得後續追的是版本 pinning、更新策略、source revision identity、rollback 與多租戶 capability registry；安全風險由 Security Radar 另外追蹤，本篇只看 lifecycle architecture。

#### 8) 對 Agent Engineering 的影響

Skills 如果真的要成為跨 Agent / 跨 workspace 的 reusable capability，最終很可能需要和 package manager 類似的：

- source identity；
- version / revision；
- update semantics；
- install scope；
- dependency / compatibility metadata。

#### 9) 是否改變既有假設

是。Skills 不應只被當成 context file；它們正在變成可部署、可更新的 runtime capability。

#### 10) 可做 benchmark

**Research Candidate：Yes — P1**

- **研究問題：** centralized Skill lifecycle 是否能降低多 workspace / 多 Agent 的維運成本與版本漂移？
- **Baseline：** 每個 client local clone + install。
- **Variant：** server-side source registry + update-from-source。
- **Task set：** 10 / 50 / 100 workspaces 共用 5–20 Skills，模擬更新與 rollback。
- **Metrics：** version drift、install/update latency、failure rate、developer effort、reproducibility、token / context impact。

### 5. Google ADK：Workflow Graph 的 Edge Identity 變成 Route-aware

**類型：** orchestration / workflow engine / graph semantics  
**來源：**
- https://github.com/google/adk-python/commit/460715b6c62c8e9ab00931c502381ee0364e39b6
- https://github.com/google/adk-python

#### 1) 發生了什麼變化

Google ADK 過去把 `(from_node, to_node)` 相同的 edge 一律視為 duplicate。

現在若同一對節點有多條 routed edges，只要 route sets **互斥（disjoint）** 就允許，例如：

```text
A --route=approved--> B
A --route=rejected--> B
```

以下仍視為衝突：

- 任一 edge 無條件（`None`）；
- route 相同；
- route list 有 overlap。

#### 2) 它解決什麼問題

在 conditional workflow 中，edge identity 不只由 endpoints 決定，還包括 activation condition。

如果 validator 只看 `(A, B)`，會把合法的不同 routing case 當成重複 graph topology。

#### 3) 為什麼重要

這是 workflow engine 從「靜態 DAG」往「typed / conditional transition system」成熟的一個訊號。

Agent orchestration 真正需要驗證的是：

```text
(source, target, route-domain)
```

而不只是 source / target。

#### 4) 核心機制

validator 將每個 route 正規化成 set：

```text
None → {None}
"a" → {"a"}
["a", "b"] → {"a", "b"}
```

同一 `(from, to)`：

- 有 `None` → reject；
- route intersection 非空 → reject；
- route sets disjoint → accept 並 union。

#### 5) Implementation evidence

新增 tests 覆蓋單 route、多 route list、overlap、unconditional 與 disjoint cases。

#### 6) 與既有方法差異

舊 validator 把 edge 當 pair；新版把 edge 視為帶 activation domain 的 transition。

#### 7) 成熟度與限制

**成熟度：workflow graph validation refactor。**

目前 route equality 仍是明確 value set，還不是任意 predicate 的可判定 overlap；若未來 route 支援複雜 expression，static validation 會更難。

#### 8) 對 Agent Engineering 的影響

當 multi-agent workflow 使用 conditional handoff / retry / approval / fallback 時，graph tooling 需要能理解 routing semantics，否則 visualization、validation、replay 都可能與真正 runtime 不一致。

#### 9) 是否改變既有假設

小幅改變：workflow topology 不應只看「有哪些 Agent / node」，而應包含「在什麼條件下 transition」。

#### 10) 可做 experiment

**Research Candidate：Yes — P1**

- **研究問題：** static route validation 能否在複雜 Agent workflow 中提前抓到 unreachable / overlapping / ambiguous transitions？
- **Baseline：** endpoint-only graph validation。
- **Variant：** route-domain-aware validation。
- **Task set：** approval、retry、multi-agent handoff、fallback workflow。
- **Metrics：** configuration bugs caught、false reject、runtime routing failure、debugging effort、developer effort。

### 6. 重要補漏：OpenAI Agents API 把 Codex Harness 正式平台化

**類型：** Agent runtime / managed harness / long-running agents / multi-agent / tool use  
**官方來源：**
- https://openai.com/index/introducing-the-agents-api/

**日期：** 2026-09-10  
**狀態：** public beta

#### 1) 發生了什麼變化

OpenAI 將 Codex 背後的 agent harness 作為 **Agents API** 對開發者提供託管 runtime。

API 層負責：

- agent loop；
- session persistence / long-running execution；
- automatic context compaction；
- tool search；
- programmatic tool calling；
- MCP / custom functions / built-in tools；
- subagent orchestration；
- hosted sandbox 或自帶 sandbox / partner sandbox。

開發者仍控制 model、instructions、tools、knowledge、environment 與 business workflow。

#### 2) 它解決什麼問題

過去 Agent application 往往自己維護：

```text
LLM call loop
+ tool dispatch
+ context truncation / compaction
+ retries / recovery
+ session persistence
+ subagent spawning
+ sandbox lifecycle
```

Agents API 的定位是把這些抽成 platform layer。

#### 3) 為什麼重要

這代表 **harness engineering 本身開始商品化 / 平台化**。

如果 managed harness 能跟著 model 一起優化，應用團隊可能不再需要自己維護大量 orchestration glue code。

但這同時提出一個很重要的研究問題：

> 強 model + vendor-optimized managed harness，是否真的能降低 custom orchestration complexity，而不犧牲可觀測性、可控性與成本？

這正好對應我們 Radar 的核心問題。

#### 4) 核心架構

```text
Developer application
        ↓
Agents API
        ├─ Codex harness
        ├─ context management
        ├─ tool selection / calling
        ├─ subagent orchestration
        └─ durable session
        ↓
Environment
   ├─ OpenAI hosted sandbox
   ├─ own infrastructure
   └─ sandbox partner
```

OpenAI 特別把 **harness 與 execution environment 分開**：runtime coordination 可以託管，但 code/files 的工作環境仍可選擇不同 provider / VPC。

#### 5) Implementation / evidence

官方目前公開的功能包括：

- session approaching context limit 時自動 compaction；
- tool search 按需載入 tool definitions；
- programmatic tool calling 可平行 / chain / filter results；
- subagent 各自擁有獨立 context，由 main agent aggregate；
- `multi_agent.max_concurrent_subagents` 可限制平行數量。

官方頁面也列出客戶 testimonials，例如 4x latency reduction、60% cost per case reduction、86% failed responses reduction。**這些是 vendor-hosted customer claims，不是公開、compute-matched、可獨立重現 benchmark，因此本 Radar 不把它們當成一般性證明。**

#### 6) 與既有方法差異

```text
Self-managed framework
→ team owns harness + infra + upgrades

Agents API
→ OpenAI owns harness
→ developer chooses capabilities + environment
```

它更像 managed application runtime，而不是只多一套 Agent SDK。

#### 7) 成熟度與限制

**成熟度：public beta。**

未知 / 待驗證：

- harness version pinning 與升級行為；
- compaction policy 可控程度；
- subagent topology / delegation policy 的細粒度；
- tracing / replay / deterministic evaluation；
- vendor managed runtime 相對 self-hosted 的真實成本；
- lock-in 與 portability。

#### 8) 對 Agent Engineering 的實際影響

如果 managed harness 能提供夠好的 default，未來 architecture 的重心可能從：

```text
How do I build an Agent loop?
```

轉成：

```text
What capabilities / context / authority / workflow should I give the Agent?
```

#### 9) 是否改變 single-agent vs multi-agent 假設

目前**不能**。官方有 subagent success testimonials，但沒有公開證據證明 multi-agent 普遍勝過 single-agent。

更合理的假設是：managed runtime 降低「實作 multi-agent 的工程成本」，但是否降低 model monetary cost 或提高 task quality，仍需 task-specific benchmark。

#### 10) 可做 experiment

**Research Candidate：Yes — P0**

- **研究問題：** Managed Codex harness 是否能在 quality 不下降前提下降低 custom orchestration 的成本 / latency / developer effort？
- **Baseline A：** 單一強 Agent + 自建簡單 tool loop。
- **Baseline B：** 現有自建 Fable / Opus / Sonnet / Codex orchestration。
- **Variant：** Agents API single-agent；Agents API multi-agent。
- **Task set：** repo bugfix、code review、research synthesis、tool-heavy operational analysis。
- **Metrics：** task success、model monetary cost、token use、wall-clock latency、tool calls、delegation frequency、coordination failure、reliability、developer effort、recovery success。

## 與核心研究問題的關係

### 強模型是否降低 orchestration complexity？

今天最直接的新 evidence 不是模型 benchmark，而是 **Agents API 將 harness 平台化**。它可能降低 application team 自己維護 orchestration 的工程複雜度；但這和「模型本身讓 orchestration 不再需要」是兩件事。需要 Managed Harness vs Custom Orchestration benchmark 才能回答。

### 什麼時候不該 delegate？

Codex worktree implementation 讓 multi-agent 的 hidden cost 更具體：每多一個真正平行 coding worker，除了 tokens，還會有 checkout lifecycle、integration、merge、environment duplication。若 subtask 沒有清楚可平行的 workspace boundary，就更不應因為「任務看起來複雜」而 fan-out。

### 多 Agent 是否真的帶來品質提升而不是只增加 token？

**今天仍沒有新的獨立、compute-matched evidence 可以證明 multi-agent 普遍勝過 single-agent。** Agents API 頁面雖有 4x latency improvement testimonial，但屬客戶宣稱，且沒有公開 task set / baseline / token / model / orchestration details。本 Radar 不把它升級成一般結論。

### Context / Memory 是否真的降低成本且不犧牲品質？

OpenViking 的 `turn_budget` 提供很好的可重現 A/B：message-count vs semantic-turn retention。這比再比較不同 summary prompt 更接近 root cause。

### Long-running Agent 如何 checkpoint / resume / reconcile？

今日新增的是 checkpoint **邊界選擇**：OpenViking 開始明確區分 retained live turns 與 archived prefix，並讓 `pending_tokens` 和實際 archive boundary 一致。這與前幾天的 resume ownership / durable state 研究可直接串成完整 lifecycle。

### Runtime authority 與 agent intelligence 如何分離？

今日 Agent track 沒有新的重大 authorization evidence，因此不重複 Security Radar；但 Codex worktree/session binding 與 Agents API 的 harness/environment separation 都顯示：runtime resource ownership 正越來越由系統 contract 決定，而非只靠模型自行協調。

## 今日結論

2026-09-14 最值得記錄的不是某個新 Agent demo，而是五個越來越具體的 runtime contract：

```text
1. Coding workspace
   → per-session / per-agent worktree ownership

2. Execution provenance
   → metadata 必須屬於真正 issuing step

3. Context retention
   → semantic turn boundary + token budget

4. Capability lifecycle
   → Skills 有 source / discovery / install / update lifecycle

5. Workflow topology
   → edge identity 包含 route domain
```

再加上 Agents API 把 Codex harness 變成 managed platform，可以看到 Agent 生態正在從「誰的 planner prompt 比較漂亮」快速轉向 **誰能提供清楚、可測、可恢復、可觀測的 runtime semantics**。

對接下來實驗優先級，我會先做：

```text
P0-1  Managed Harness vs Custom Orchestration
P0-2  Per-Agent Worktree vs Shared Checkout
P0-3  Turn-aware vs Message-count Context Retention
P0-4  Step-level Model / Tool Cost Attribution
```

這四條剛好可以直接回答目前最重要的兩個問題：

> **更強的 harness / runtime 能不能在品質不降的情況下，減少我們自己堆 orchestration 的必要性？**

以及：

> **當真的要 delegate 時，workspace、context 與成本 attribution 要怎麼設計，才不會讓 multi-agent 的額外複雜度掩蓋真正收益？**
