# Agent Ecosystem Radar — 2026-09-08

> 研究窗口：截至 2026-09-08（Asia/Taipei）上午。這份報告只追蹤 Agent Ecosystem；AI / Agent Security 另由 Security Radar 處理。今天優先看近期 repository commit 與可驗證 implementation evidence，不以 star 數或宣傳熱度排序。

## 執行摘要

- **Agent runtime 的難題正從「會不會 call tool」轉向「能不能正確恢復」。** `openai/openai-agents-python` 昨日修正一個重要的 session resume 邊界：如果 Agent 已經產生並接受 terminal output、guardrail 與 terminal hook 也已完成，但最後的 Session 持久化失敗，就不應直接 resume，否則可能重跑 model call 與具 side effect 的 lifecycle。SDK 現在用 `_terminal_unrecoverable` 標記這個 crash window，採 fail-closed。
- **Multi-agent 的狀態不能只等同「目前載入記憶體的 child threads」。** `openai/codex` Multi-Agent V2 修正 cold resume + compaction 後 subagent roster 遺失問題：改從已註冊的 direct children 建 roster，即使 child thread 尚未重新載入也保留；同時設 8 agents / 1,024 bytes 的 context budget。這是一個很具體的「durable world state vs prompt context」分離案例。
- **OpenViking 正把 memory extraction 從純 JSON 改成受限 Python DSL，並用同一層 operation model 收斂兩種輸出。** 更值得注意的是同一個 PR 暴露一個 end-to-end memory recall regression：SDK 介面變更導致 peer memory 沒有真正注入，agent iteration 約從 1.3 升到約 4，內部準確率從約 83% 掉到約 76%。這說明 memory 系統不能只測「資料寫進去了沒有」，必須測 retrieval → injection → answer 的整條鏈。
- **`codebase-memory-mcp` 把 Codex 的詳細全域 guidance 從 `AGENTS.md` 移到按需 Skill，只留下 activation pointer。** 這是很乾淨的 progressive disclosure（漸進式揭露）pattern：常駐 context 只告訴 agent「何時啟用能力」，真正工具使用說明在 skill 被需要時才載入。同一天它也修正 parallel extraction 下 complexity pass 會受 worker 排程順序影響的非決定性問題，代表 shared context graph 若要成為多 Agent 共用基礎，結果 reproducibility 不能被忽略。

## 重要發展

### 1. OpenAI Agents SDK：對「已完成輸出但尚未持久化」的 resume 採 fail-closed

**類型：** Agent runtime / long-running agents / checkpoint & recovery  
**來源：**
- https://github.com/openai/openai-agents-python/commit/e51633133e671e82df221e1f1713f7cb1cef9711
- https://github.com/openai/openai-agents-python

#### 發生了什麼變化

`openai/openai-agents-python` 在 2026-09-07 合入 `fix(sessions): reject resuming a run whose accepted terminal output was not persisted (#4698)`。

新的 `RunState` 增加 `_terminal_unrecoverable`：

1. final output 已產生；
2. output guardrails 已通過；
3. terminal hooks 已執行；
4. 但 Session append / persistence 還沒完整成功；

在這個區間，state 被標記為不可安全 resume。只有 terminal turn 成功持久化後才清除 marker。

resume 時，SDK 會在任何 Session、sandbox、model、tool、guardrail 或 hook 工作之前先檢查 marker；若命中就直接拒絕 resume。

#### 它解決什麼問題

這是一個典型的 **lost-ack / crash-window** 問題。

假設 Agent 的 terminal path 包含：

```text
Model decides action
→ approved tool executes
→ tool side effect succeeds
→ terminal output accepted
→ terminal hook succeeds
→ Session persistence fails
```

如果 runtime 看到「Session 裡沒有 final turn」就直接 resume，可能再次呼叫模型、再次跑 hook，甚至再次觸發有 side effect 的 operation。

換句話說，**「持久化紀錄不存在」不代表「真實世界的 action 沒發生」。**

#### 為什麼重要

Long-running Agent 一旦開始接支付、GitHub write、部署、Email、資料庫 mutation、工單等工具，resume correctness 就不只是 UX 問題，而是 execution semantics。

這個 commit 的重要訊號是：Agent runtime 開始需要像 workflow engine / distributed system 一樣，明確處理：

- durable checkpoint
- side-effect ownership
- lost acknowledgement
- replay safety
- terminal state recoverability

而不是只有「把 conversation JSON 存起來」。

#### 核心架構與資料流

```text
final output accepted
      ↓
guardrails complete
      ↓
terminal hooks complete
      ↓
_terminal_unrecoverable = true
      ↓
Session append / maintenance
      ├─ success → marker=false → resumable/durable
      └─ failure → marker=true  → reject resume
```

marker 也會進入 RunState schema（1.17+），因此 live state 與 JSON round-trip 都保留這個 recovery boundary。

#### Implementation evidence

commit 中的 regression tests 不只測一般 exception，還特別測：

- streaming / non-streaming
- live / serialized RunState round trip
- persistence 在 append 前失敗
- append 已發生、但 caller 收到 failure 的 lost-ack 情境
- 一個需要 approval、具有 side effect 的 `charge` tool，驗證後續 resume 不會重播 effect

這比單純「catch exception」更接近真實 workflow failure model。

#### 與最接近方案的差異

簡單 Agent runtime 常見做法：

```text
checkpoint missing
→ reload previous state
→ replay last turn
```

這個方案則承認某些 state 是：

```text
not durable enough to continue
AND
not safe enough to replay
```

因此選擇 fail-closed，要求新 run 或由上層 reconciliation 決策。

#### 成熟度與已知限制

**成熟度：高，屬 SDK 核心 session correctness 修正。**

但 `_terminal_unrecoverable` 本身不是完整 exactly-once protocol。它避免某一類 unsafe replay，卻沒有自動解決：

- 外部 tool 本身的 idempotency
- 已成功寫入外部系統、但 tool response 遺失
- cross-service transaction
- operator 如何安全 reconcile 不可 resume 的 run

因此更精確的說法是：**它建立了一個明確的「不可自動重播區間」，不是保證 exactly-once。**

#### 對 Agent Engineering 的實際影響

對任何自製 Agent Workflow，checkpoint 設計至少要區分：

```text
safe-to-retry
safe-to-resume
needs-reconciliation
terminal-and-durable
```

而不能只有 `pending / completed / failed`。

#### 是否改變既有假設

是。它直接否定一個常見假設：

> 「Agent crash 後從最後一個 checkpoint 繼續就好。」

真正需要的是 **checkpoint + effect semantics + persistence boundary**。

#### 可做實驗

**Research Candidate：Yes — 高優先級**

- **研究問題：** 哪種 recovery protocol 能在 Agent 執行具 side-effect tool 時兼顧可恢復性與不重複執行？
- **Baseline：** conversation/checkpoint 缺什麼就 replay 什麼。
- **Variant A：** terminal-unrecoverable fail-closed marker。
- **Variant B：** marker + tool idempotency key + reconciliation state。
- **Task set：** GitHub comment/label、建立 issue、模擬付款、DB write、artifact upload；在 model/tool/hook/session append 的不同邊界注入 crash。
- **Metrics：** duplicate side effects、task success、successful recovery rate、operator intervention、recovery latency、額外 state complexity、tool calls。

### 2. OpenAI Codex Multi-Agent V2：cold resume 後保留未載入的 direct children

**類型：** Multi-agent / context engineering / checkpoint & recovery  
**來源：**
- https://github.com/openai/codex/commit/d665e3bbc81b013baa73d067507169c20395b988
- https://github.com/openai/codex

#### 發生了什麼變化

Codex 在 2026-09-07 修正 Multi-Agent V2 的 environment context：先前 root thread 經過 cold resume 與 compaction 後，subagent roster 只會看到已重新載入的 child threads，沒有載入的 direct children 會消失。

新版本改成從 runtime 已註冊的 live/direct child metadata 建 roster，而不是只從已開啟 thread 列表取得。

同時新增 context budget：

- 最多 8 個 subagents
- 最多 1,024 bytes roster
- loaded children 優先
- group 內維持穩定排序
- 只列 direct children，不把 grandchildren 混進 root roster

#### 它解決什麼問題

Multi-agent 系統至少有兩種狀態：

```text
Durable Agent Topology
≠
Currently Loaded Agent Threads
```

如果 runtime 把「目前載入的 object」誤當「實際存在的 agent tree」，cold resume、compaction、lazy loading 都會讓 root agent 對團隊狀態產生錯誤認知。

可能造成：

- 重複 spawn 已存在角色
- 無法 follow-up 某個尚未 loaded 的 worker
- 誤判 task coverage
- coordination state 在 compaction 後退化

#### 為什麼重要

這個變更不是證明 multi-agent 比 single-agent 更強；它揭露的是另一件事：

> 一旦採 multi-agent，**coordination state 本身就是 durable state**，不能只藏在 transcript 或 process memory。

這與 long-running runtime 的設計直接相關。

#### 核心架構與資料流

```text
Persistent / registered agent metadata
        ↓
find direct children of parent path
        ↓
separate loaded vs unloaded
        ↓
loaded first + stable ordering
        ↓
context budget (8 agents / 1024 bytes)
        ↓
render <subagents> world-state context
```

這是一個「完整 runtime state → bounded model context」的典型 context routing pattern。

#### Implementation evidence

integration test 明確覆蓋：

- cold root resume
- compaction 後重新組 context
- 一個 child 已載入、另一個 alphabetically earlier sibling 尚未載入
- roster 仍同時包含兩者
- loaded child 優先
- grandchild 不出現在 root direct-child roster

#### 與既有方法差異

舊模式比較接近：

```text
open threads → render roster
```

新模式：

```text
agent registry / topology = truth
open threads = runtime locality / priority signal
```

這個 separation 很重要：**runtime truth 不應由 context cache 的載入狀態決定。**

#### 成熟度與已知限制

**成熟度：中高；屬 Codex Multi-Agent V2 的實際 runtime 修正。**

限制也很明確：8 agents / 1,024 bytes 是 bounded context heuristic，當 direct children 很多時一定會截斷，因此 roster 仍不是完整 control-plane API；它只是給模型的一個精簡 world-state view。

#### 對 Agent Engineering 的實際影響

如果未來有 lead agent + 多個 worker：

- Agent tree / ownership / task assignment 應存在 durable control state
- prompt 裡只注入「模型此刻需要知道的 bounded projection」
- loaded/unloaded 可以影響排序，但不能影響「Agent 是否存在」的 truth

#### 是否改變 single-agent vs multi-agent 假設

它**沒有提供 multi-agent quality uplift 的新證據**。反而提醒我們：delegation 會引入額外 coordination state、resume semantics 與 context budget 問題。

因此今天的 evidence 更支持：

> multi-agent 必須在「品質或並行效益」能補償這些 coordination complexity 時才值得使用。

#### 可做實驗

**Research Candidate：Yes**

- **研究問題：** bounded subagent roster 在 long-running / compacted multi-agent workload 中，多少資訊才足以維持 coordination quality？
- **Baseline：** 只列 loaded children。
- **Variant A：** durable direct-child roster，固定 8 agents / 1 KB。
- **Variant B：** task-aware routing，只注入與目前 goal 相關 workers。
- **Task set：** 4、8、16、32 worker 的 repo research / code migration / test fan-out，期間主動 unload、compact、restart。
- **Metrics：** duplicate delegation、missed follow-up、coordination failures、task success、context tokens、latency、delegation count、recovery success。

### 3. OpenViking：Memory extraction 預設改為 Restricted Python DSL；同時暴露 retrieval regression 對 Agent 品質的直接影響

**類型：** Memory systems / context engineering / evaluation  
**來源：**
- https://github.com/volcengine/OpenViking/commit/a843ab6bf220b2b3bc82321576d623d1c55c6598
- https://github.com/volcengine/OpenViking

#### 發生了什麼變化

OpenViking 在 2026-09-07 將長期記憶 extraction 的預設輸出格式從 JSON 改為 **restricted Python DSL（受限 Python 領域語言）**。

不是直接 `exec` 任意 Python，而是：

```text
LLM output
→ restricted Python AST parser/compiler
→ ResolvedOperations
→ shared schema rules / repair path
→ memory write
```

JSON 與 Python 兩個 protocol 透過 `ExtractionOutputProtocol` abstraction 共用後處理。

同一個 PR 還新增 `memory_organization` A/B benchmark，並修正多個 extraction / retrieval 的 end-to-end 問題。

#### 它解決什麼問題

長期記憶 extraction 不只是把自然語言轉成一個 JSON object；它常需要表達：

- create/update/delete
- 多種 custom memory types
- event resolution
- patch repair
- canonical merge
- 多筆 fact preservation

用 DSL 可以讓模型表達 operation intent，而 storage 層仍收到統一的 typed operations。

#### 技術機制與 implementation evidence

值得注意的設計：

- Python protocol 只允許受控 AST surface
- 兩種 protocol 最後都 compile 成相同 `ResolvedOperations`
- 非合法 identifier 的 custom memory type / field 透過 alias mapping 處理
- alias collision 直接 fail loudly，而不是默默覆蓋
- syntax error 會回報 offending line，repair instruction 也依 active protocol 產生
- expression size 有 pre-allocation guard，避免小 input 產生巨大 string

這顯示它不是單純「LLM 比較喜歡輸出 Python」，而是把 memory operation language 當成一個正式 interface。

#### 更重要的 regression evidence：Memory 有沒有真的被 Agent 用到

這個 PR 也修了一個 SDK API drift：`context_type` / `filter` 搬進 `FindOptions` 後，VikingBot 的 peer recall 仍用舊呼叫方式，導致每輪 memory recall exception，最後其實沒有 memory 被注入。

commit 記錄的內部觀察是：

- iteration 約從 1.3 增至約 3.9–4
- accuracy 約從 83% 掉到 72–77% / 約 76%
- 修正後 smoke test 可 recall 13 memories，iteration 回到 1，答案正確

這些數字是 **repository commit 中的 internal observation，不是獨立 standardized benchmark**，但它很有研究價值：Agent memory 的價值應該由 downstream behavior 驗證，不是只看 retrieval endpoint 回 200。

#### 與既有方法差異

常見 memory pipeline：

```text
LLM → JSON → validate → DB
```

OpenViking 現在變成：

```text
LLM → JSON or restricted DSL
          ↓
   protocol compiler
          ↓
 canonical operation model
          ↓
      memory store
```

這讓「模型輸出語言」與「storage semantics」解耦。

#### 成熟度與已知限制

**成熟度：快速演進中。** Repo 活躍度很高，但同一個大型 PR 也連續修補 protocol repair、SDK compatibility、alias collision、expression inflation 等問題，顯示新 DSL 還在明顯收斂期。

而 Python DSL 是否真的比 JSON 在不同模型上更準、更省 token、更容易 repair，目前不能從 commit 本身直接下結論；它值得 A/B，而不是直接視為通用最佳實踐。

#### 對 Agent Engineering 的實際影響

兩個值得吸收的 pattern：

1. **Memory write 先 compile 成 canonical operation model，再落 storage。**
2. **Memory evaluation 必須從 extraction/retrieval 一路量到最終 agent task outcome。**

只測 memory precision@k 不夠，還要看它是否真的減少 agent iteration / tool calls 並提升 task quality。

#### 是否改變既有假設

是，尤其針對「加 memory 就能省 context / 提升品質」這個假設。

今天的 regression 顯示：memory layer 只要 interface integration 斷一小段，Agent 可能不 crash，卻會默默改走更多 manual search，造成 cost / iteration / quality 同時惡化。

#### 可做實驗

**Research Candidate：Yes — 高優先級**

- **研究問題 A：** restricted Python DSL 是否比 JSON extraction 更穩定？
- **Baseline：** JSON protocol。
- **Variant：** restricted Python DSL。
- **Task set：** LoCoMo 類長期對話 memory、custom schemas、event correction、merge/update/delete 混合案例。
- **Metrics：** valid extraction rate、repair rounds、fact preservation、token cost、latency、memory write accuracy。

另外做 downstream A/B：

- **Baseline：** 無 persistent memory / memory recall 失效。
- **Variant：** 正常 memory retrieval + injection。
- **Metrics：** answer accuracy、agent iterations、tool calls、retrieval latency、tokens、failure detectability。

### 4. codebase-memory-mcp：從全域詳細 guidance 改成 activation pointer + Skill progressive disclosure

**類型：** Context engineering / coding agents / code intelligence  
**來源：**
- https://github.com/DeusData/codebase-memory-mcp/commit/c43ea2ac9d7f3ce7c246789bc0f9f81bc1f78c85
- https://github.com/DeusData/codebase-memory-mcp/commit/29dbf0bfa1500a3947c141edb79dbfefa285bb76
- https://github.com/DeusData/codebase-memory-mcp

#### 發生了什麼變化

`codebase-memory-mcp` 對 Codex integration 做了一個很值得注意的 context change：以前會在全域 `$CODEX_HOME/AGENTS.md` 放入完整的 code graph 工具說明與「應優先用 graph tools」等 guidance；現在只保留一個很小的 managed activation pointer：

```text
For structural codebase exploration, use the installed `codebase-memory` skill.
```

所有詳細行為改放在 `codebase-memory` Skill 中，只有需要 structural exploration 時才載入。

install / upgrade / uninstall lifecycle 也有測試，會保留 user 自己的 `AGENTS.md` bytes，只替換/移除 managed block。

#### 它解決什麼問題

這正是 context engineering 常見的「always-on guidance inflation」：

每裝一個 MCP / tool / skill，都往 global prompt 放一大段使用說明，最後每個 turn 都付出 token，模型也永遠看到一堆當下不相關的 instructions。

新的方式是：

```text
Always-on context
→ 只保留 capability activation cue

Need detected
→ load Skill
→ detailed tool semantics
```

這是 progressive disclosure，而不是單純 prompt 瘦身。

#### 為什麼重要

Agent tool ecosystem 越大，真正的 bottleneck 很可能不是「少一個 tool」，而是：

- 何時知道有這個 capability
- 何時載入說明
- 載入多少
- 何時不要讓它干擾模型

這個 commit 給了一個很簡單、可測的 interface pattern：**pointer 常駐，manual/skill 按需。**

#### Implementation evidence

commit 中新增完整 lifecycle smoke tests，驗證：

- fresh install 建立 exact pointer
- skill / MCP / subagents / hooks 仍存在
- legacy managed block upgrade 只換 managed bytes
- reinstall 不重複插入 pointer
- uninstall 只移除 managed pointer，保留 user guidance

這比只改 README 更可信，因為 integration lifecycle 有被實際測試。

#### 同日另一個重要修正：context graph 必須 deterministic

`29dbf0b` 修正 complexity pass 在 parallel extraction 下會因 worker ID / scheduling order 不同，讓 recursive flag 在相同輸入上出現不同結果。

根因是 temporary node ID 來自 shared counter，ID order 實際上反映 worker scheduling，而 DFS cycle detection 又會受 traversal entry order 影響。

修正後改用 content-derived canonical order：

- qualified name
- file path
- start line

並對 seed / callee traversal 做 deterministic sorting。

這對 Agent Context 很關鍵：**derived knowledge graph 如果同一 commit 每次 index 出不同語意結果，就不適合作為多 Agent 共用 context plane。**

#### 與既有方法差異

Always-on：

```text
Global prompt = 所有 capability 的完整說明
```

Progressive disclosure：

```text
Global prompt = capability pointer
Skill = detailed operating knowledge
MCP = actual tool surface
```

同時，graph 生成從「parallel worker output order 可影響語意」改成「input-derived canonical order」。

#### 成熟度與已知限制

**成熟度：中高、非常活躍。**

但 activation pointer 是否真的提升 coding-agent quality / token efficiency，目前 commit 沒有提供正式 A/B benchmark；也可能在某些模型上因 pointer 太弱而降低 tool adoption。

另外 deterministic complexity 修正只代表已知 non-determinism 被處理，不代表整個 graph pipeline 已經完全 deterministic。

#### 對 Agent Engineering 的實際影響

這裡有兩個可直接移植的原則：

> **Context：always-on 放「何時啟用」，按需內容放「怎麼做」。**

> **Derived context：同一 source revision 應盡量產生 deterministic artifact。**

#### 是否改變既有假設

它支持一個值得測的假設：

> Agent 不一定需要「一開始知道所有工具細節」；可能只需要足夠的 activation cue，再透過 skill progressive disclosure 取細節。

這與大量 MCP tools 全塞入 context 的做法相反。

#### 可做實驗

**Research Candidate：Yes**

- **研究問題：** activation pointer + on-demand Skill 能否在不降低 tool adoption / task quality 的前提下降低常駐 context？
- **Baseline：** global `AGENTS.md` 放完整 graph-tool guidance。
- **Variant：** 一行 activation pointer + Skill on demand。
- **Task set：** code architecture QA、impact analysis、bug localization、small code change；其中一半需要 graph、一半不需要。
- **Metrics：** task success、graph tool adoption rate、input tokens、skill-load frequency、wall-clock latency、tool calls、錯誤使用 grep/graph 的比例。

另做 reproducibility test：同一 repo / commit 在 1、2、4、8 workers 重複 index，hash semantic graph outputs，量 non-deterministic property rate。

## 今日 Agent Ecosystem 綜合判斷

今天沒有新的 primary evidence 能證明「多 Agent 一定比單 Agent 品質高」。相反，今天幾個最有價值的變更都集中在**Agent infrastructure 的隱性成本**：

```text
Single / Multi-Agent Intelligence
            ↓
    Runtime Durability
            ↓
 Durable Coordination State
            ↓
   Bounded Context Projection
            ↓
 Progressive Capability Loading
            ↓
 Deterministic Shared Context
            ↓
 End-to-end Memory Evaluation
```

我認為今天最重要的 architecture signal 是：

### 1. Conversation state 不等於 workflow state

Agents SDK 的 terminal crash window 與 Codex 的 unloaded child roster 都在說同一件事：真正要恢復的是 execution / topology state，不只是 messages。

### 2. Runtime Truth 不應直接等於 Prompt Content

Codex 保存完整 direct-child topology，再只投影 bounded roster 給模型；這比把 control state 全塞進 context 更合理。

### 3. Context 應該 progressive disclosure

`codebase-memory-mcp` 的 activation pointer 是很小但很值得研究的 pattern。工具越多，context routing 的重要性會大於「把所有 tool manual 都寫進 system prompt」。

### 4. Memory / Knowledge layer 要用 Agent outcome 驗收

OpenViking 的 recall regression 很直接：memory integration 壞掉時系統可能仍能回答，但 iteration 變多、品質下降。這種 silent degradation 只有 end-to-end eval 看得出來。

## Research Candidates

### Candidate A — Crash-window / Resume Semantics Benchmark

- **問題：** Agent 在外部 side effect 與 state persistence 之間 crash 時，哪種 recovery strategy 最可靠？
- **Baseline：** checkpoint replay。
- **Variants：** fail-closed marker；marker + idempotency key + reconciliation。
- **Task set：** GitHub mutation、DB write、模擬 payment、artifact upload。
- **Metrics：** duplicate effects、task success、recovery rate、latency、operator intervention、implementation complexity。

### Candidate B — Multi-Agent Durable World-State Projection

- **問題：** 多 Agent topology 應如何持久化，模型每 turn 又該看到多少 roster？
- **Baseline：** loaded threads only。
- **Variants：** bounded durable roster；goal-aware roster routing。
- **Task set：** 4–32 workers，搭配 compaction / cold restart / lazy load。
- **Metrics：** coordination failure、duplicate delegation、missed worker reuse、context tokens、quality、recovery time。

### Candidate C — Global Guidance vs Activation Pointer + Skill

- **問題：** progressive disclosure 是否真的降低 context cost 而不犧牲 capability adoption？
- **Baseline：**完整 always-on tool guidance。
- **Variant：** activation pointer + on-demand Skill。
- **Task set：** 混合需要/不需要 code graph 的 coding tasks。
- **Metrics：** task success、input tokens、tool adoption、skill loads、latency、tool calls。

### Candidate D — Memory Protocol + Downstream Outcome A/B

- **問題：** JSON vs restricted DSL 哪個 extraction protocol 更可靠？memory recall 是否實際降低 agent search/reasoning 成本？
- **Baseline：** JSON extraction；無/失效 memory recall。
- **Variants：** restricted Python DSL；正常 persistent-memory injection。
- **Task set：** LoCoMo 類 long-term memory + custom memory schema cases。
- **Metrics：** extraction validity、repair rounds、fact preservation、answer accuracy、iterations、tokens、latency、tool calls。
