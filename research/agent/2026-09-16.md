# Agent Ecosystem Radar — 2026-09-16

> 研究窗口：截至 2026-09-16 08:33（Asia/Taipei）。本報告只追蹤 Agent Ecosystem；Security 題材不拿來補篇幅。今日優先檢查 9/15 上午之後至 9/16 早上的原始 GitHub commits，確認是否出現真正改變 Agent runtime、long-running execution、context/tool routing、automation side effects、memory integration 與 streaming semantics 的 material changes。

## 執行摘要

- **Codex 的 managed daemon recovery 開始從「記住哪些 thread 要重開」進化成「記住中斷中的 turn 本身」。** 最新 recovery snapshot 不只保存 thread ID，還會保存仍在執行、未取消 turn 的 `turn_id`、output schema、service tier 與 cyber access program，且與 candidate set 一起 atomic write。這代表 long-running Agent 的 recovery unit 正從 conversation/session 往 execution attempt 移動。
- **Open SWE 把 workspace 正式做成 Agent runtime routing boundary。** Workspace 現在由 PostgreSQL 持久化，擁有 repositories、Slack channels、team settings 與 MCP connections；inbound work 依 thread → tag → repository → channel → user default → default workspace 的 precedence 路由。更重要的是，既有 thread 會 pin 住原本 workspace，不會因 repository 後來搬家就中途換掉 settings / MCP connections。
- **Open SWE 也補出一個非常接近分散式系統 exactly-once 問題的 Agent automation pattern。** 對外送 Slack notification 不再只有「有紀錄 / 沒紀錄」，而是 `absent → pending → posted → delivered`；如果 post 已嘗試但 store write 失敗，系統寧可停住也不重送，因為結果未知時重試可能造成 duplicate side effect。這對任何能發信、發訊息、下單、寫 ticket 的 long-running Agent 都比單純 retry policy 更重要。
- **OpenViking 做了一次非常大的跨 harness memory-plugin 收斂。** Claude Code、Codex、OpenCode、Pi、Cursor、TRAE、ZCode 等整合原本各自有 config precedence、capture filter、peer identity、HTTP headers、vendored runtime、release/version gate 的漂移；現在大量邏輯往單一 shared declaration / shared runtime 收斂，並讓不同 distribution mode 在 pack time 或 committed-copy 階段自動產生所需內容。這不是新 retrieval algorithm，而是回答「同一個 memory capability 如何跨不同 coding-agent harness 保持語意一致」。
- **Google ADK 再次證明 tool streaming 的 correctness 不能靠 arrival order 或『看起來一樣』。** `StreamingResponseAggregator` 會在 progressive streaming 下重複或遺失 function calls；修正後優先用 model-provided function-call ID dedupe，沒有可靠 ID 才退回 `(tool name, canonicalized args)` signature。昨天 Microsoft Agent Framework 才修 interleaved parallel arguments；今天 Google 又修 duplicate/drop，兩者共同指向：**tool-call identity 必須是一級 runtime primitive。**
- **Deep Agents 把 interrupt recovery 的兩次 checkpoint mutation 合併成單一 state update。** 以前 reconstructed partial assistant message 與 interruption notice / context-token count 分兩次 `aupdate_state` 寫入，遠端 recovery 多一次 round trip，也存在第一筆成功、第二筆失敗後留下 incomplete checkpoint 的窗口；現在同一個 delta 原子化送出。這是很小的 patch，但對 crash consistency 很有研究價值。

今天沒有新的可信、compute-matched evidence 能證明「多 Agent 普遍優於單一強模型」，也沒有證據顯示強模型已經讓 orchestration complexity 可以普遍移除。相反地，今天的 implementation evidence 更強烈地指向：**當 Agent 變成長時程、可恢復、可跨 channel / workspace / tool runtime 執行的 software actor 後，真正的複雜度集中在 execution identity、routing stability、side-effect delivery、state atomicity 與 cross-harness semantic consistency。**

## 重要發展

## 1. Codex：Recovery Snapshot 開始保存「中斷中的 Turn」，而不只 Thread ID

**類型：** long-running agents / checkpoint-recovery / managed daemon / runtime state  
**來源：**
- https://github.com/openai/codex/commit/4d2807023aae3ee317d39a9868fb187618699df2
- https://github.com/openai/codex

### 1) 發生了什麼變化

Codex 的 managed daemon 原本在 restart / shutdown recovery 時，主要保存哪些 persisted threads 應該在 daemon 起來後 cold-resume。

最新 commit 把 recovery snapshot 擴充成：

```text
RecoverySnapshot
├─ loaded thread IDs
└─ interrupted turns
   └─ thread_id →
      ├─ turn_id
      ├─ output_schema
      ├─ service_tier
      └─ cyber_access_program
```

只有「regular、尚未取消、且 input 已經記錄」的 active turn 會進 interruption metadata；completed / canceled / compaction 等路徑都有 regression coverage。

此外，interruption metadata 沒有另開 sidecar file，而是編碼回原本 candidate array 的同一份 atomic file，讓舊版 server 還能把它當 candidate set best-effort 讀取。

### 2) 它解決什麼問題

只知道：

```text
thread X 之前是 loaded
```

不足以恢復：

```text
thread X 當時正在執行哪一個 turn？
這個 turn 有什麼 output contract？
當時用哪種 service tier？
它是否帶 turn-specific execution policy？
```

如果這些資訊只存在 process memory，daemon crash / restart 後即使 thread 能重新載入，也無法重建「中斷點上的 execution intent」。

### 3) 為什麼重要

這讓 recovery granularity 從：

```text
conversation/session recovery
```

往：

```text
execution-attempt recovery
```

移動。

對 long-running Agent 很關鍵，因為一個 thread 可能存活數天，但其中每個 turn 的：

- output schema；
- model/service routing；
- execution policy；
- automation vs user-trigger provenance；

都可能不同。

如果 recovery 只恢復 thread，而沒有恢復 interrupted turn contract，就可能「看起來有續跑」，實際上語意已經變了。

### 4) 核心架構與資料流

新路徑大致是：

```text
Active thread
   ↓
input 已 durable
   ↓
turn 正在執行
   ↓
shutdown requested
   ↓
admitted operations drain
   ↓
collect persisted threads
+ collect eligible interrupted turn options
   ↓
RecoverySnapshot
   ↓
atomic write
   ↓
managed daemon restart
   ↓
cold resume + interrupted-turn-aware recovery
```

另一個細節是 snapshot collection 與 thread listener attachment 被移出主要 event-loop dependency，避免 forced shutdown 因 snapshot lock / listener attach 卡死。

### 5) 技術機制與 implementation evidence

原始 commit 顯示：

- 新增 `RecoverySnapshot` / `InterruptedTurn` typed structure；
- `write_atomically()` 仍是持久化 primitive；
- interruption metadata 放入同一 candidate array；
- snapshot eligibility 會先確保 thread 可 persist；
- 測試涵蓋 running、completed、canceled、compacting turns；
- 測試 managed shutdown 中仍有 admitted resume 的狀況；
- 測試 blocked rollout writer / child listener attachment 下 forced shutdown responsiveness；
- 保留 legacy candidate-array compatibility。

這比只在 changelog 寫「improved recovery」有更具體的 implementation evidence。

### 6) 與舊版本 / 其他方案的差異

舊模型：

```text
thread 是 recovery unit
```

新模型：

```text
thread 是 durable container
turn 是可中斷、可恢復 execution attempt
```

這與傳統 workflow engine 比較接近：workflow instance 與 activity / task attempt 是不同層級。

### 7) 成熟度、近期活躍度與限制

**成熟度：高活躍 production runtime implementation。**

限制：

- 目前保存的 turn-specific options 仍是有限 subset；
- recovery 是否應 replay、resume、重新 issue model request，還需要更完整 semantics；
- external side effects 若已部分完成，光恢復 turn metadata 仍不能保證 exactly-once；
- tool calls 的 in-flight state 與 external transaction state 仍可能需要更細粒度 checkpoint。

### 8) 對 Agent Engineering 的實際影響

設計 long-running Agent 時，不應只問：

```text
「session 有沒有 checkpoint？」
```

而要問：

```text
checkpoint 的 recovery unit 到底是：
- thread？
- turn？
- tool call？
- external action？
```

層級不同，能承諾的 recovery correctness 完全不同。

### 9) 是否改變 single-agent vs multi-agent / runtime 既有假設

它不直接證明 single/multi-agent 誰比較好，但會讓 multi-agent overhead 更可量化。

每增加一個 delegated worker，如果 worker 也有自己的 turn、output contract 與 restart semantics，就增加另一組 recovery state。

因此「delegate 是否值得」應把 **recovery-state surface area** 算入 orchestration complexity，而不只算 tokens。

### 10) 可做的 experiment / replication / benchmark

**Research Candidate：Yes — P0**

建立 **Execution-Granularity Recovery Benchmark**。

- **研究問題：** 只存 thread checkpoint vs 保存 turn contract vs 保存 tool-call state，哪個層級能在 crash 後兼顧 correctness 與成本？
- **為什麼現在值得測：** Codex 已有具體 implementation，可設計對照。
- **Baseline A：** thread-only resume。
- **Variant B：** thread + interrupted-turn metadata。
- **Variant C：** thread + turn + tool-call / side-effect journal。
- **Task set：** 長程 coding、structured-output、background automation、human interrupt、model/service-tier change。
- **Metrics：** task success、recovery success rate、duplicate tool/action rate、lost-progress rate、retry count、recovery latency、model monetary cost、operator intervention。

### 11) 是否值得列為 Research Candidate

**是，P0。** 它直接回答 long-running Agent 的 checkpoint / resume / reconcile 核心問題。

## 2. Open SWE：Workspace 從 UI 設定升級成 Runtime Routing Boundary

**類型：** coding agents / workspace routing / MCP / context routing / multi-tenant runtime  
**來源：**
- https://github.com/langchain-ai/open-swe/commit/9d5f2a9c2e133993a7657c23daf4da8d1ee5e9ee
- https://github.com/langchain-ai/open-swe

### 1) 發生了什麼變化

Open SWE 把原本的 `environments` 概念重構成真正的 `workspaces`，並把 workspace record 搬進 PostgreSQL。

Workspace 現在會擁有：

- repositories（單一 ownership）；
- Slack channels；
- workspace/team settings；
- MCP connections；
- sandbox setup / snapshot config；
- inbound work routing identity。

Routing resolver 的 precedence 是：

```text
thread
→ tag
→ repository
→ channel
→ user default
→ global default
```

Dashboard、Slack、GitHub、Linear、schedule 等入口建立 thread / run 時都會 stamp workspace。

### 2) 它解決什麼問題

若同一套 coding-agent 平台服務多個 team / repo / Slack channel，只靠 thread-local config 或「每次收到事件再重新推算 workspace」會產生 drift。

原始 commit 已捕捉到一個真實 failure：

- GitHub PR thread 原本屬於 workspace A；
- repository 後來搬到 workspace B；
- 舊邏輯每次 comment 都重新 resolve repo owner；
- 於是同一個既有 conversation 會中途改用 B 的 settings / MCP connections。

修正後：**已存在 thread 的 saved workspace 優先。**

### 3) 為什麼重要

這是一個很典型但容易被低估的 Agent runtime 問題：

> **Context routing 必須在什麼時間點被 bind？**

如果 runtime context（tools、MCP、repo、sandbox image、prompt、team settings）可以在 conversation 中途因外部 mapping 改變而無聲切換，Agent 的行為就不再可重現。

因此 workspace 不只是 UI folder，而是類似：

```text
execution namespace
+
context/tool routing boundary
+
configuration authority
```

### 4) 核心架構與資料流

```text
Inbound event
(GitHub / Slack / Linear / schedule / dashboard)
        ↓
Routing Resolver
        ↓
thread/tag/repo/channel/user/default precedence
        ↓
Workspace ID
        ↓
Thread + Run metadata stamp
        ↓
Workspace-scoped:
  ├─ MCP connections
  ├─ team settings
  ├─ model gateway setting
  ├─ sandbox configuration
  └─ repository/channel ownership
```

對既有 thread：

```text
saved workspace
> re-resolve current repository ownership
```

### 5) 技術機制與 implementation evidence

commit 包含：

- PostgreSQL migrations；
- LangGraph Store → PostgreSQL one-time import；
- workspace ownership tables；
- inbound routing resolver；
- thread/run stamping；
- workspace-aware team settings / MCP connection lookup；
- repository moved between workspaces 的 regression fix；
- migration skipped / stranded records 的 fail-closed 行為。

特別值得注意的是 import failure：如果有舊 workspace record 無法讀取或 ownership 衝突，startup 不會把 migration 誤標 complete；相關 repo 會被記成 stranded，GitHub delivery 回 `503` 讓來源重試，而不是 `200` 後默默路由到 default workspace。

### 6) 與舊版本 / 最接近方案的差異

弱 routing：

```text
每次 event
→ 看 repo / channel
→ 算目前該去哪
```

穩定 routing：

```text
conversation creation
→ bind workspace
→ conversation lifetime 內保持 stable
```

除非明確執行 migration / handoff，否則 runtime context 不應因 control-plane mapping 變更而偷偷漂移。

### 7) 成熟度、近期活躍度與限制

**成熟度：高活躍、正在大規模 refactor 的 production-oriented coding agent。**

限制：

- 這次仍保留部分舊 `environment` metadata key 作 compatibility window；
- routing precedence 變複雜後，debugging / observability 必須能解釋「為何被路由到這個 workspace」；
- repository single ownership 很清楚，但跨 workspace collaboration / shared repo 的 semantics 仍需額外設計；
- thread pinning 與 workspace policy 更新之間，需要定義哪些 settings 是 snapshot、哪些是 live lookup。

### 8) 對 Agent Engineering 的實際影響

對企業型 Agent / SaaS 特別重要：

- `workspace_id` 應該成為第一級 execution identity；
- tool / MCP / memory / prompt routing 應以 workspace scope 查詢；
- existing session 不應因 tenant/resource mapping 改動就無聲換 context；
- migration failure 應 fail closed / retryable，而不是 fallback default。

### 9) 是否改變 single-agent vs multi-agent / context routing 假設

這次更支持一個觀點：

> 很多「multi-agent context isolation」其實先需要正確的 **workspace / execution namespace isolation**，不一定需要多 Agent。

如果一個 single strong agent 已能在穩定 workspace 內完成任務，增加 subagents 並不能解決 routing correctness；反而每個 worker 還要繼承或重新 resolve workspace。

### 10) 可做的 experiment / replication / benchmark

**Research Candidate：Yes — P0**

建立 **Pinned Workspace vs Live Re-resolution Benchmark**。

- **研究問題：** 長時程 coding thread 遇到 repo ownership、MCP config、team settings 更新時，哪些 config 應 pin、哪些應 live-refresh？
- **Baseline：** 每個 event 重新 resolve workspace / tools。
- **Variant A：** thread creation 時全量 snapshot。
- **Variant B：** pin workspace identity + live-read versioned policy/settings。
- **Task set：** repo transfer、MCP connection change、model gateway change、sandbox image refresh、Slack → dashboard continuation。
- **Metrics：** task success、context drift incidents、wrong-tool/MCP selection、reproducibility、operator effort、resume reliability、configuration propagation latency。

### 11) 是否值得列為 Research Candidate

**是，P0。** 它非常適合研究 context routing 與 runtime authority，而不是只研究 prompt routing。

## 3. Open SWE：Agent Automation 的 External Side Effect 開始採「Outcome Unknown」State Machine

**類型：** background agents / agent scheduling / side-effect delivery / reliability  
**來源：**
- https://github.com/langchain-ai/open-swe/commit/3229b6e7863415401a0e01e08ecc05a139799ccd

### 1) 發生了什麼變化

Open SWE 的 scheduled automation 可以完成工作後通知 Slack channel。

舊邏輯的核心問題是：

```text
Slack post 成功
↓
但把 success 寫回 store 失敗
↓
下一次 retry 看到沒有 delivered record
↓
再 post 一次
↓
duplicate message
```

新的 state model 區分：

```text
absent
  = 尚未嘗試，可以 post

pending
  = 已保留 reservation / post outcome 可能未知

posted
  = channel message_ts 已確認，可繼續 reply/finalize

delivered
  = notification lifecycle 完成
```

如果 record 存在但沒有 `message_ts`，runtime 會明確回報「previous outcome unknown」，**不再次 post**。

### 2) 它解決什麼問題

這其實不是 Slack-specific bug，而是 long-running Agent 做 external side effect 時的經典 distributed systems 問題：

> 呼叫外部系統成功了，但本地 durable state 沒成功寫下來，retry 到底該不該重做？

對 message 還只是 duplicate；如果是：

- 發 email；
- 建 issue；
- 建 PR；
- 下單；
- 支付；
- 寫 CRM；
- deploy；

duplicate side effect 可能非常昂貴。

### 3) 為什麼重要

Agent framework 很常把 retry 視為：

```text
exception → retry
```

但 external side effect 必須區分：

```text
known failed
known succeeded
unknown outcome
```

**unknown outcome 不是 failure。**

把它當 failure retry，就是重複副作用的來源。

### 4) 核心架構與資料流

```text
absent
  ↓ reserve durable record
pending
  ↓ attempt external post
  ├─ known fail → release reservation → retryable
  └─ success → get message_ts
              ↓ persist immediately
            posted
              ↓ optional thread reply
              ↓ finalize
          delivered
```

關鍵點：如果 external success 後 `posted` state persist 失敗，系統不會 delete reservation，也不允許下一輪重新 post。

### 5) 技術機制與 implementation evidence

commit 中新增：

- typed `AutomationNotification`；
- `pending / posted / delivered` lifecycle；
- `message_ts` 成為 external outcome evidence；
- successful top-level post 後立即 persist `message_ts`；
- unknown state 不允許 repost；
- finalization write failure 不觸發 duplicate thread reply；
- regression tests 模擬 store failure。

另外長內容會拆成 top-level summary + thread full content，這部分是 UX；真正值得研究的是 durable side-effect state machine。

### 6) 與舊版本 / 常見 Agent retry 差異

常見：

```text
try action
except:
  retry
```

更正確：

```text
prepare
→ durable intent
→ side effect
→ durable external receipt / id
→ finalize
```

這已經接近 saga / outbox / idempotency-key 類分散式系統設計。

### 7) 成熟度、近期活躍度與限制

**成熟度：production implementation pattern。**

限制：

- Slack message API 本身不是 transactional；
- pending + unknown 狀態需要 operator / reconciliation job 處理，否則可能永久卡住；
- 如果外部 API 支援 idempotency key，應優先利用，而不是只靠 fail-stop；
- cross-region / multiple workers 仍需 durable compare-and-set 或唯一鍵確保 reservation race 不重複。

### 8) 對 Agent Engineering 的實際影響

任何可 autonomous act 的 Agent 都應為 tool/action 定義 side-effect class：

```text
read-only
idempotent write
non-idempotent write with idempotency key
non-idempotent write without reliable dedupe
```

不同 class 的 retry policy 不應相同。

### 9) 是否改變 single-agent vs multi-agent 假設

這個問題與模型數量無關，但 multi-agent 會放大它：多 worker 可能同時認為自己要完成同一個副作用。

因此 delegation/fan-out 在 write-heavy task 上應額外評估：

- action ownership；
- dedupe key；
- commit coordinator；
- duplicate side-effect rate。

### 10) 可做的 experiment / replication / benchmark

**Research Candidate：Yes — P0**

建立 **Agent Side-Effect Delivery Semantics Benchmark**。

- **研究問題：** retry-heavy background Agent 如何在 crash / timeout / store failure 下避免 duplicate external actions？
- **為什麼現在值得測：** coding / workflow agents 已大量支援 background automation。
- **Baseline：** exception-based retry。
- **Variant A：** reservation + pending/posted/delivered state。
- **Variant B：** external idempotency key + local journal。
- **Variant C：** transactional outbox / reconciliation worker。
- **Task set：** synthetic Slack/email/issue/create-PR/deploy APIs，注入 timeout-before-response、success-then-store-failure、worker crash、duplicate delivery。
- **Metrics：** duplicate side effects、lost side effects、time-to-reconcile、operator intervention、retry count、latency、implementation complexity、task success。

### 11) 是否值得列為 Research Candidate

**是，P0。** 這是 long-running / scheduled agents 真正走向 production 時必測的 runtime correctness。

## 4. OpenViking：把多個 Coding-Agent Harness 的 Memory Plugin 從「多份相似實作」收斂成 Shared Runtime

**類型：** memory systems / coding-agent integrations / skills/plugins / context routing / agent-native developer tooling  
**來源：**
- https://github.com/volcengine/OpenViking/commit/aa3ee2f4315f9d27c2a86672908882b6dcd70228
- https://github.com/volcengine/OpenViking

### 1) 發生了什麼變化

OpenViking 合入一個非常大的 plugin refactor，核心目標可以濃縮成：

> 同一套 memory capability 不應因為跑在 Claude Code、Codex、OpenCode、Pi、Cursor、TRAE、ZCode 等不同 harness，就出現不同 config、identity、capture、HTTP、release semantics。

此次 refactor 處理的漂移包含：

- Codex outage 時 captured turns 被直接丟掉，offline queue 實際上沒接上；
- Codex 的 bypass patterns 設定存在但沒有真正被 hooks 使用；
- Pi 的 legacy peer memory 變得不可讀；
- 不同 harness 有不同 bypass matcher；
- plugin version 沒 bump，導致 shared code 已更新但 marketplace 使用者拿不到；
- vendored file list 靠人工維護，可能少檔或多檔；
- Cursor / TRAE capture 沒走共同 filter；
- config precedence / credential / peer resolution 在不同 harness 不一致；
- HTTP headers、identity headers、actor peer headers 在不同 integration 上不同；
- 多份 session / recall / URI guard / doctor / config loader 持續 drift。

### 2) 它解決什麼問題

很多 Agent memory / context layer 在論文或 demo 裡只考慮：

```text
Agent ↔ Memory API
```

但真正落地到多個 coding harness 後，會變成：

```text
Claude Code hooks
Codex hooks
OpenCode plugin
Pi extension
Cursor hooks
TRAE hooks
ZCode hooks
...
```

每個 host 的 lifecycle、config、package delivery、hook event 都不同。

如果每個 integration 各自「薄薄複製一份」，半年後 memory semantics 已經不是同一套系統。

### 3) 為什麼重要

這是 **Agent capability portability** 很現實的一面。

真正可重用的 Skill / Memory / MCP integration 應該追求：

```text
host-specific adapter 薄
shared semantic core 厚
```

而不是：

```text
每個 host 都有一份 80% 相同、20% 偷偷不同的實作
```

否則使用者會得到「同樣設定，在 Codex 有效、Cursor 無效；同樣 memory，在 Pi recall scope 不同」這類極難 debug 的行為差異。

### 4) 核心架構與資料流

這次收斂後比較接近：

```text
Host adapter
(事件名稱 / payload shape / response envelope)
        ↓
Shared configuration schema
        ↓
Shared credential / peer resolution
        ↓
Shared capture / recall / bypass logic
        ↓
Shared HTTP / header builder
        ↓
OpenViking server
```

Packaging 則依 delivery mode 分流：

```text
Git-path installed plugin
→ generated shared copies committed / CI regenerated

npm / tar package
→ shared copies generated at pack time
```

### 5) 技術機制與 implementation evidence

這個 commit 有大量實際 drift case，而不是純架構清理：

- Codex `catchUpTurns` outage 會 drop turns；
- Pi legacy peer 沒傳進 shared recall builder；
- Cursor / TRAE 把低價值 / bypass 內容送進 extractor；
- plugin manifests 與實際 shared changes 沒同步 bump；
- config key aliases / precedence 不一致；
- credentials 在某些 harness 竟讀另一個 harness 的 `ov.conf` section；
- HTTP header builder 多份實作造成 credential / identity headers 差異；
- generated vendored copies 有缺檔與不必要檔案；
- release triggers 因只 watch plugin directory 而漏掉 shared-library changes。

最後新增的 tests / CI 會從 import closure、manifest pair、config layer order、wire headers、proxy contract 等面向檢查一致性。

### 6) 與舊版本 / 最接近方案差異

舊：

```text
Shared library
+ N 個 integration copies
+ N 個 config loaders
+ N 個 HTTP clients
+ N 個 release rules
```

新方向：

```text
Shared semantic runtime
+ generated projections
+ host adapter
+ delivery-mode-specific packaging
```

這和 compiler / codegen 思路相似：不要求所有 host API 相同，但要求共同 semantics 從一個 source of truth 投影出去。

### 7) 成熟度、近期活躍度與限制

**成熟度：快速演進中的 real-world integration stack。**

限制：

- commit 非常大，表示 migration / regression surface 也大；
- host lifecycle 本來就不同，不可能完全 zero adapter；
- generated copy + package-time generation 的 release pipeline 本身增加 build complexity；
- 目前一致性主要靠 tests / CI，仍需跨 harness end-to-end behavioral parity benchmark。

### 8) 對 Agent Engineering 的實際影響

如果我們設計通用 Agent Skill / Memory / Observability plugin，應該把 portability 拆成：

1. **Semantic core**：真正能力邏輯；
2. **Host lifecycle adapter**：不同 Agent harness 的 hook/event mapping；
3. **Config projection**：同一 canonical config 映射到不同 host；
4. **Delivery contract**：git path / npm / marketplace / bundled copy；
5. **Parity tests**：相同行為是否跨 host 一致。

### 9) 是否改變 single-agent vs multi-agent / tooling 假設

它不直接回答 multi-agent 效益，但提醒我們：

> tooling / memory capability 的成本不能只算 runtime token；**integration drift / maintenance cost 也是 developer effort。**

如果多 Agent 架構要求每種 worker harness 都維護自己的 memory/tool adapter，orchestration ROI 可能被 integration tax 吃掉。

### 10) 可做的 experiment / replication / benchmark

**Research Candidate：Yes — P1**

建立 **Cross-Harness Capability Parity Benchmark**。

- **研究問題：** 同一 memory / skill capability 接到不同 coding-agent harness，行為是否一致？
- **Baseline：** 各 harness 獨立 integration。
- **Variant：** shared semantic core + generated/projection adapters。
- **Task set：** capture、recall、bypass、offline queue、peer switch、config precedence、credential reload、plugin upgrade。
- **Metrics：** behavioral divergence count、lost turns、recall parity、configuration mismatch、integration LOC、regression rate、developer effort、release lead time。

### 11) 是否值得列為 Research Candidate

**是，P1。** 這更像 Agent platform engineering / capability portability，而不是模型研究，但實際價值很高。

## 5. Google ADK：Streaming Function Call 必須有穩定 Identity 與 Dedupe Contract

**類型：** tool use / streaming / function calling / runtime correctness  
**來源：**
- https://github.com/google/adk-python/commit/3cf4ce2b8d6d1523903e32f772f9112e09ac0c74
- https://github.com/google/adk-python/issues/6566

### 1) 發生了什麼變化

Google ADK 修正 `StreamingResponseAggregator` 在 progressive streaming 模式下 function calls 被 drop / duplicate 的問題。

新的 close path 會 deduplicate function calls：

1. 如果 model 提供可靠 ID，而且不是 ADK 自己補的 client-generated ID，使用 ID 去重；
2. 若沒有可靠 model ID，退回 `(function name, canonicalized args JSON)` signature 去重。

### 2) 它解決什麼問題

Streaming 模型輸出不是一次拿到完整：

```text
response A
response B
response C
final aggregate
```

function-call part 可能在 progressive chunk 與 final aggregate 重複出現；若 aggregator 沒有 identity semantics，就可能：

- 同一 tool call 執行兩次；
- final history 出現 duplicate call；
- 某些 call 在 flush/merge 過程被掉掉。

### 3) 為什麼重要

昨天 Microsoft Agent Framework 才修：parallel tool-call arg deltas 交錯時不能靠「最後一個 call」merge，必須用 `call_id`。

今天 Google 又修 duplicate/drop。

兩個獨立 framework 同期遇到同類問題，已足以形成一個更一般的 runtime conclusion：

> **tool call 必須是有 stable identity 的 event stream entity，而不是 assistant message 裡的一小段 JSON。**

### 4) 核心架構與資料流

```text
Streaming chunks
   ↓
function-call parts
   ↓
identity resolution
  ├─ model call ID
  └─ fallback semantic signature
   ↓
ordered aggregation
   ↓
deduplicated final response/history
```

### 5) 技術機制與 implementation evidence

commit 新增 `_deduplicate_function_calls()` 並加入：

- repeated model-provided ID；
- no-ID calls；
-不同 name/args calls；
- progressive SSE close behavior；

等 regression tests。

### 6) 與舊版本 / 常見方案差異

弱模型：

```text
position / arrival order = identity
```

較正確：

```text
call_id = identity
stream chunk = mutation/event of that identity
```

fallback signature 只能是相容性手段，因為兩次合法、參數完全相同的 tool call 仍可能是不同 logical action。

### 7) 成熟度、近期活躍度與限制

**成熟度：active framework bug fix。**

限制：

- 沒有 model-provided stable ID 時，用 name+args dedupe 可能把兩次真正相同但獨立的 calls 誤認成 duplicate；
- provider 對 function-call ID 的穩定性不同；
- resume / retry 後 ID 是否延續，還需更完整 contract。

### 8) 對 Agent Engineering 的實際影響

Tool runtime 應該顯式保存：

```text
logical_call_id
provider_call_id
attempt_id
stream_sequence
execution_status
result_id
```

而不是只有 `tool_name + args + result`。

### 9) 是否改變 single-agent vs multi-agent 假設

Parallel tool use 與 multi-agent 都會增加 concurrent event streams，因此 identity correctness 是 prerequisite。

如果基礎 streaming merge 還會 duplicate/drop，拿它去比較 fan-out throughput 沒有意義。

### 10) 可做的 experiment / replication / benchmark

**Research Candidate：Yes — P1**

建立 **Tool-Call Stream Identity Torture Test**。

- **研究問題：** 各 Agent framework 在 fragmented / duplicated / reordered / resumed tool streams 下能否保持 exactly-once logical call history？
- **Baseline：** arrival-order merge。
- **Variant：** stable logical call ID + per-attempt sequence。
- **Task set：** single call、parallel calls、identical args repeated calls、duplicate chunks、reordered chunks、reconnect/resume。
- **Metrics：** duplicate execution、lost calls、wrong-args merge、history correctness、tool success、recovery rate。

### 11) 是否值得列為 Research Candidate

**是，P1。** 尤其適合與昨日 Microsoft fix 合併成 cross-framework regression suite。

## 6. Deep Agents：Interrupt Recovery 從「兩次 State Write」收斂成一個 Atomic Delta

**類型：** coding agents / interrupt / checkpoint / state consistency  
**來源：**
- https://github.com/langchain-ai/deepagents/commit/2ab439449f0040fdf0f89f30fbf852313c24a5a6

### 1) 發生了什麼變化

當使用者 interrupt 一個進行中的 turn 時，Deep Agents Code 會：

- 重建已經串流出的 partial assistant response；
- 加一則 interruption notice；
- 保存最新 nonzero context-token count，供 resume 使用。

以前它分兩次 `aupdate_state`：

```text
write #1: reconstructed assistant message
write #2: interruption notice + context tokens
```

現在合併成一次 state update。

### 2) 它解決什麼問題

兩次 durable mutation 之間存在 crash window：

```text
#1 成功
#2 失敗
```

checkpoint 就只剩半套 recovery state。

遠端 backend 還多一次 round trip。

### 3) 為什麼重要

這個 patch 很小，但原則很大：

> **同一個 logical recovery transition，應盡量對 durable state 做一次 atomic mutation。**

Agent runtime 很容易因為 Python code 看起來「先 append A，再 append B」就做兩次 store writes；但 crash/retry 之後，兩步之間其實是 observable state。

### 4) 核心架構與資料流

舊：

```text
interrupt
→ reconstruct partial response
→ checkpoint write A
→ add interruption notice / token state
→ checkpoint write B
```

新：

```text
interrupt
→ build one ordered state delta
→ atomic state update
```

`messages` 使用 LangGraph `add_messages` reducer 維持同一 delta 內順序，`_context_tokens` 則是 last-value private channel。

### 5) 技術機制與 implementation evidence

commit 明確指出：

- local / remote `aupdate_state` 都套相同 channel updates；
- 沒有 code 依賴兩次 write 中間的 checkpoint；
- 其餘 interrupt semantics、remote cancellation ordering、hooks、tracing 行為保持不變。

### 6) 與舊版本差異

這不是新 feature，而是把 recovery transition 從「程序上的兩步」重新定義成「storage 上的一步」。

### 7) 成熟度、限制

**成熟度：production correctness patch。**

限制：一次 state write 只保證 framework store 的 atomicity；若同一 transition 還包含外部 tool side effect，仍需更大的 transaction/reconciliation boundary。

### 8) 對 Agent Engineering 的實際影響

應該建立一條設計檢查：

> 每個 checkpoint / recovery transition 是否有 multi-write partial-commit window？

尤其是：

- human interrupt；
- model switch；
- context compaction；
- subagent handoff；
- tool completion；
- external action finalization。

### 9) 是否改變 orchestration 假設

它再次提醒：subagent / parallelism 越多，durable state transition 越多；coordination cost 不只是 token，也包含 state mutation / recovery complexity。

### 10) 可做 experiment

這項不單獨列新 P0，而併入 **Execution-Granularity Recovery Benchmark**：加入 crash injection between writes，量 incomplete checkpoint rate。

### 11) Research Candidate

**Yes — 合併至 Candidate A。**

# 今日對既有研究問題的更新

## 強模型是否降低 orchestration complexity？

**今日沒有新的可信 evidence 可以下結論。**

今天的 commits 反而指出，即使 model 更強，以下 complexity 仍在 runtime 層存在：

- active-turn recovery；
- workspace / context routing；
- external side-effect dedupe；
- tool-call streaming identity；
- cross-harness integration parity。

這些不是換更強模型就自然消失的問題。

## 什麼時候不該 delegate？

今天新增一個工程上的判斷維度：

> 如果 delegated work 會增加另一組 workspace binding、recovery state、tool-call stream、external side-effect ownership，但 subtask 本身沒有明確獨立 contract，那 delegation 的 runtime tax 可能高於收益。

所以除了前幾天整理出的 I/O contract / context-pressure 條件，現在還應加入：

```text
Recovery surface
+ Side-effect ownership
+ Workspace/context inheritance
+ Stream identity complexity
```

## 多 Agent 是否真的提升品質，而不是只增加 token？

**今天仍沒有新的 compute-matched benchmark 證明普遍提升。**

更值得先做的是把 runtime correctness 固定住，否則 multi-agent 比 single-agent 多出的 failure 可能只是：

- worker resume state 不完整；
- workspace context 漂移；
- duplicate external action；
- streaming tool call 重複；
- capability integration 在不同 harness semantics 不一致。

## Context / Memory Infrastructure 是否真的降低成本而不降品質？

今日沒有新的 quality-cost benchmark，但 OpenViking 提供另一個重要維度：**integration semantic consistency**。

Memory 系統即使 retrieval quality 很高，如果不同 coding harness 會：

- 漏 capture；
- bypass 設定失效；
- peer identity 不一致；
- plugin 根本沒被新版本 delivery；

實際產品品質仍會崩掉。

所以 memory benchmark 應增加 operational parity / lost-turn / configuration-drift 指標。

## Long-running Agent 如何 checkpoint / resume / reconcile？

今天是非常明確的進展：

```text
thread checkpoint
↓
active turn metadata
↓
atomic recovery transition
↓
external side-effect journal
```

這四層應分開研究，不要再用單一「支持 resume」布林值描述 framework。

## Runtime authority 與 Agent intelligence 如何分離？

今日 Open SWE workspace routing 與 side-effect state machine 都指向同一原則：

```text
Model 決定 intent / content
Runtime 決定：
- workspace / tools 從哪裡來
- 哪個 execution state 是 canonical
- action 是否已執行
- 是否允許 retry
- 如何恢復
```

這些都應是 deterministic runtime responsibility，而不是讓模型從 transcript 猜。

# 今日結論

今天最重要的 Agent 生態訊號不是新 planner，也不是新的「多 Agent demo」，而是 **Agent runtime 正在補傳統 distributed systems / workflow systems 早就必須處理的 correctness contract**：

```text
Stable execution identity
      ↓
Stable workspace/context binding
      ↓
Atomic durable state transition
      ↓
Idempotent / reconcilable external side effects
      ↓
Stable tool-call identity across streaming
      ↓
Cross-harness capability parity
```

這讓我們對 Agent Architecture 的研究優先級更清楚：

1. **P0：Execution-Granularity Recovery & Atomic Transition**
2. **P0：Stable Workspace Binding vs Live Re-resolution**
3. **P0：External Side-Effect Delivery Semantics**
4. **P1：Cross-Harness Capability Parity**
5. **P1：Tool-Call Stream Identity Torture Test**

如果這些底層 contract 沒固定，就算多 Agent 在 benchmark 上平均分數更高，也很難確定 production failure 是模型、orchestration、transport、state store 還是 side-effect retry 造成。

因此今天的研究結論仍然偏向：**品質優先下，先把 runtime 的可恢復性、可歸因性與 side-effect correctness 建成可測的基準，再決定在哪些 task boundary 引入 delegation / fan-out。**
