# Agent Ecosystem Radar — 2026-09-18

> 研究窗口：截至 2026-09-18 上午（Asia/Taipei）。本報告只追蹤 Agent Ecosystem，不以 Security 題材補篇幅。今日優先檢查 9/17 上午之後的原始 GitHub commits、官方 implementation evidence、近期論文與可形成可重現實驗的架構變化。

## 執行摘要

- **Codex 把「thread 設定」與「正在執行的 turn 執行環境」正式拆開。** 使用者在某個 turn 執行途中切換 environment（執行環境）時，新設定只保存給下一個 turn；目前 turn 的 tools、MCP workspace roots 與 capability roots 仍綁定啟動時的 `TurnEnvironmentSnapshot`。這代表 long-running Agent 的一個核心 contract 正逐漸清楚：**可變的 session/thread configuration 不應熱切換正在執行中的 authority / workspace。**
- **PydanticAI 發現 durable execution（可持久恢復執行）裡，toolset lifecycle 必須跟 execution engine 的 process model 對齊。** `DynamicToolset` 過去在每個 durable unit 都重新 resolve / enter，MCP session 與 tool cache 因此反覆重建；現在 DBOS / Prefect 這類 durable unit 與 workflow 同 process 的引擎，可以一個 run resolve 一次並復用，而 Temporal 因 activity 可能跑在不同 worker，仍需 per-activity 重建。這不是 API 小優化，而是「runtime topology 決定 tool lifecycle semantics」的具體證據。
- **Microsoft Agent Framework 對 MCP session 做出另一個相反但同樣合理的 scope 選擇：provider-backed authentication 下改成每次 invocation 建立獨立 MCP session。** 原因是動態 `httpClientProvider` 身分沒有進 session cache key；若仍共用 cache，session identity 與實際 caller identity 可能不一致。代價是每次呼叫增加 setup、也不保留 server-side session continuity。這形成很好的研究題目：**MCP session 到底應該 per-run、per-invocation、per-user 還是 shared？答案取決於 cache identity、statefulness 與 engine topology。**
- **Deep Agents Talon 把「transcript 裡有什麼」和「什麼值得進 semantic memory（語意記憶）」拆開。** 新版只把真實 user messages 與「確實成功送達使用者」的 final replies 做向量索引；tool output、subagent results、intermediate replies、suppressed/failed deliveries 不再污染 semantic search，但仍保留在 archive 供 keyword search。另一個配套 commit 讓向量 dedup（去重）跨 message revision 與 restart 持久化。這是一個很強的訊號：**memory quality 不只取決於 retrieval algorithm，也取決於 ingestion eligibility 與 provenance。**
- **Google ADK 今天提供了罕見的「同一類能力、三種 orchestration topology」官方實作樣本。** 同一個 Antigravity coding harness 可以被放成 `LlmAgent → single_turn coding sub-agent`、`Antigravity root → ADK sub-agent as tool`，或明確 `Workflow planner → builder`。官方只做 end-to-end smoke test，沒有宣稱哪個較好；但這正好讓「何時不該 delegate」變成可控實驗，而不是抽象討論。
- **Agent 評測正在從 token / success proxy 往真實交付流程補資料。** Open SWE 新增「run start → PR creation」平均 wall-clock；Codex 開始記錄每個 turn 起始時實際 active plugin inventory。前者把 delivery latency 納入 coding-agent outcome，後者讓 tool/plugin exposure 能與 task result、cost、latency 做歸因。
- **新論文 `M-SQE` 把 Skill routing 從 relevance-only 拉向 post-retrieval quality estimation。** 作者報告在三種 retriever 上平均 task success 至少提升 3.5 個百分點，低資源語言改善更大；但目前應視為 author-reported evidence，尚未看到可獨立重現的公開 code / benchmark package。它真正值得保留的研究問題是：**Agent 找到「相關 Skill」不代表找到「可執行、可用的 Skill」。**

今天仍沒有新的可信、compute-matched 證據能支持「multi-agent 普遍優於 single strong agent」。相反，今天所有重要變化幾乎都指向同一件事：**先把 lifecycle scope 對齊。** Turn 的 environment scope、toolset 的 run scope、MCP session 的 invocation scope、memory 的 delivery/provenance scope如果不清楚，再多 orchestration 只會放大 coordination failure。

## 1. OpenAI Codex：Environment Selection 改成「下一個 Turn 才生效」

**類型：** Agent runtime / long-running agent / workspace / MCP / execution authority  
**來源：**
- https://github.com/openai/codex/commit/c775dd3c332de1b69b25a4580f6c5bc44b94e284
- https://github.com/openai/codex

### 1) 發生了什麼變化

Codex 修正 environment selection（執行環境選擇）的生命週期。

以前 thread 設定改變時，environment selection 可能直接影響正在執行中的 turn；這會造成一個危險的 runtime ambiguity：同一個 turn 前半段在 workspace A / capability roots A，後半段卻被重新導向 workspace B / roots B。

現在設計改成：

```text
Running Turn
  └─ Active Environment Snapshot A
       ├─ cwd
       ├─ workspace roots
       ├─ MCP roots
       └─ capability configuration

User / host updates thread environments
  ↓
Saved Future Selection B
  ↓
不改 Running Turn
  ↓
Next Turn starts
  ↓
activate B
```

另外，若 manual compaction（手動上下文壓縮）要採用新的 saved environment，runtime 會先停止目前 task，再進入新的 execution context，而不是在同一個 active task 中途換 authority。

### 2) 它解決什麼問題

它解的是 **mutable thread configuration 與 active execution state 混在一起** 的問題。

Long-running Agent 常同時存在：

- 使用者可以修改的 thread settings；
- 遠端 environment 還在 background setup；
- MCP runtime / workspace roots 已經被某個 turn 使用；
- subagent / child session 可能從 parent 繼承環境；
- tool call 正在執行。

如果設定變更立即 hot-swap，Agent 的同一個 logical turn 就可能沒有穩定 execution contract。

### 3) 為什麼重要

這會直接影響：

- tool path / cwd correctness；
- MCP tool 能看到哪個 workspace；
- remote environment 初始化完成後應套到哪個 turn；
- child agent resume 時該繼承哪一份 parent settings；
- checkpoint / replay 是否能重建同一個 execution environment。

因此一個很重要的 runtime principle 是：

> **Thread settings 是未來意圖；Turn snapshot 才是目前執行事實。**

### 4) 核心架構與資料流

```text
Thread SessionConfiguration
        │
        │ future settings
        ▼
prepare new work
        │
        ▼
activate_turn_environments()
        │
        ▼
TurnEnvironmentSnapshot
        │
        ├─ tool execution
        ├─ MCP workspace roots
        ├─ cwd
        └─ capability roots

Mid-turn config update
        └──> SessionConfiguration for future turn only
```

### 5) 技術機制與 implementation evidence

原始 commit 明確新增 / 修改：

- future selections 與 active environment 分離；
- `environment_selections()` 回報 configured-for-future 的 selection；
- `activate_turn_environments()` 只在沒有另一個 task 正在執行時採用新 selection；
- `ThreadEnvironments::snapshot()` 先捕捉當下 selected list，再等待 setup，避免等待期間被新的 selection 偷換；
- workspace roots 從 snapshot 取得；
- remote environment callback 可以分別完成 active / future selection 的 setup；
- regression test 驗證 running task 保持原 working directory / workspace roots，而下一個 task 才採新設定。

這是很強的 implementation evidence，不只是文件語意。

### 6) 與舊版本 / 最接近方案差異

舊思路比較像：

```text
Thread config changes
→ shared environment state changes
→ active runtime 也跟著看到
```

新版則更接近 database MVCC / deployment snapshot：

```text
Thread config = future desired state
Turn snapshot = immutable-ish execution view
```

### 7) 成熟度、近期活躍度與已知限制

**成熟度：高活躍、直接進 production runtime 的 correctness fix。**

已知限制 / 待驗證點：

- snapshot 不代表所有外部 service 狀態真的 immutable；
- turn 跨 crash/recovery 時是否能完整重建同一份 environment snapshot，仍需要 end-to-end torture test；
- multi-agent parent/child 在環境更新同時發生 reload / resume 時，仍是高風險交錯路徑。

### 8) 對 Agent Engineering 的實際影響

如果系統允許使用者在 Agent 執行中調整：

- repository；
- sandbox；
- toolset；
- workspace；
- credentials / environment；
- model routing profile；

應該先問「這是立即生效，還是 next-turn 生效？」而不是直接 mutate shared state。

### 9) 是否改變既有假設

它強化一個假設：**runtime authority 與 agent intelligence 必須分離，且 authority 應綁在 execution unit。**

模型可以在 turn 中 reasoning 很久，但它看到與能操作的 environment 不應因 UI / control-plane setting 更新而突然漂移。

### 10) 可做的 experiment / replication / benchmark

**Research Candidate：Yes — P0**

**Turn-Bound Environment Snapshot Benchmark**

- **研究問題：** mid-turn configuration change 採 live mutation 或 next-turn snapshot，哪種在 long-running / multi-worker / MCP workload 下較可靠？
- **為什麼現在值得測：** Codex 已提供具體 production implementation 與 regression semantics。
- **Baseline：** shared mutable environment state，設定立即生效。
- **Variant：** turn-bound snapshot + future desired state。
- **Task set：** 長時間 coding task、remote environment delayed setup、repo/workspace switch、MCP root switch、manual compaction、parent/subagent reload。
- **Metrics：** task success、wrong-workspace/tool-root incident count、retry/recovery、wall-clock latency、coordination failure、reliability、developer effort。

### 11) 是否值得列為 Research Candidate

**是，P0。**

## 2. PydanticAI：Durable Toolset 從 Per-Unit 重建改成可 Per-Run 復用

**類型：** durable execution / MCP / tool lifecycle / workflow engine / checkpoint-recovery  
**來源：**
- https://github.com/pydantic/pydantic-ai/commit/58988b4799e98a87e63c2e9c139059a356caea5c
- https://github.com/pydantic/pydantic-ai

### 1) 發生了什麼變化

PydanticAI 的 `DynamicToolset`（動態工具集合）在 durable execution 中，過去每個 durable unit 都會獨立 resolve / enter 一次。

這代表一次 Agent run 可能是：

```text
get_tools step
→ resolve toolset
→ connect MCP
→ teardown

validate_args step
→ resolve toolset
→ connect MCP
→ teardown

tool call step
→ resolve toolset
→ connect MCP
→ teardown
```

現在對支援同-process durable units 的引擎，若 factory 使用 `per_run_step=False`：

```text
Durable Run
→ resolve DynamicToolset once
→ first durable unit lazily enter/connect
→ later units reuse same entered toolset
→ run end closes it
```

### 2) 它解決什麼問題

它解決：

- MCP repeated `initialize` round-trips；
- tool discovery cache 每個 step 都被丟掉；
- toolset 自己的 caching 與 non-durable run 行為不一致；
- 反覆 connect / teardown 增加 latency 與 race surface。

### 3) 為什麼重要

這個 commit 最重要的不是效能，而是它明確說明：

> **Tool lifecycle 不能只由 Agent framework API 決定，也受到 durable execution engine 的 process topology 限制。**

DBOS / Prefect 的 durable unit 可以跟 workflow container 在同一 process，因此能持有 live toolset object。

Temporal activity 可能在另一個 worker process 執行，所以 run context 裡的 live object 無法跨 process 傳過去；因此仍必須 activity-local resolve。

### 4) 核心架構與資料流

DBOS / Prefect 類：

```text
Durable Run Container
  │
  ├─ resolve DynamicToolset once
  │
  ├─ durable step A ─┐
  ├─ durable step B ─┼─ reuse same RunResolvedToolset
  └─ durable step C ─┘
           │
           └─ MCP session/cache survives within run
```

Temporal 類：

```text
Workflow process
   │
   ├─ Activity A -> Worker X -> resolve toolset
   └─ Activity B -> Worker Y -> resolve toolset again
```

### 5) 技術機制與 implementation evidence

Commit 新增 `RunResolvedToolset`，由 run context 保存 per-run resolved toolset。

重要細節：

- toolset factory 在 durable container code 執行；
- 建立 toolset 不等於 network connect；`MCPToolset` 要到 `enter` 才開連線；
- connect 仍發生在 durable step/task 裡，因此 connection failure 可以由 engine retry；
- entered toolset 維持到 run 結束，讓 `cache_tools` 等內部 cache 有效；
- Temporal 明確不保證 `per_run_step=False`，因為 activity 可能在另一 process。

### 6) 與舊版本 / 最接近方案差異

舊版偏向最安全的 durable isolation：每 unit 自給自足。

新版是：

- **能安全共享 live runtime object 的 engine → per-run reuse；**
- **不能共享的 distributed engine → per-unit resolve。**

不是「統一最佳 scope」，而是 topology-aware scope。

### 7) 成熟度、近期活躍度與已知限制

**成熟度：高活躍，且文件同步更新 DBOS / Prefect / Temporal 行為。**

限制：

- factory 現在在 container code 執行，必須 deterministic；
- factory 內若偷偷做 I/O，replay 時可能重做且不受 durable checkpoint 保護；
- per-run live session 會增加長時間 connection 的 lifetime，需要另外觀察 stale connection / server restart 行為。

### 8) 對 Agent Engineering 的實際影響

「一個 Agent run 應不應該只建立一次 MCP session？」不能脫離 execution engine 回答。

設計 tool runtime 時至少要標明：

- toolset resolution scope；
- connection scope；
- cache scope；
- retry unit；
- process boundary；
- replay semantics。

### 9) 是否改變既有假設

它削弱「framework 可以抽象掉 workflow engine 差異」這個假設。

對 Agent durable runtime 而言，**process locality 是 observable semantics**：它會直接改變 tool caching、MCP session continuity、latency 與 recovery 行為。

### 10) 可做的 experiment / replication / benchmark

**Research Candidate：Yes — P0**

**Durable Toolset Scope Benchmark**

- **研究問題：** per-unit resolve 與 per-run resolve 對 quality / latency / reliability 的實際影響多大？不同 durable engine 能否給出相同行為？
- **為什麼現在值得測：** PydanticAI 已同時提供 DBOS / Prefect / Temporal 的不同 lifecycle implementation。
- **Baseline：** every durable unit resolve + enter + teardown。
- **Variant A：** per-run resolve、first-use enter、run-end teardown。
- **Variant B：** distributed activity-local resolve（Temporal-style）。
- **Task set：** 多次 `tools/list`、反覆 MCP tool calls、args validation、approval/resume、worker restart、MCP server restart。
- **Metrics：** task success、wall-clock latency、tool calls、MCP initialize/connect count、retry/recovery、reliability、developer effort、model cost（若 tool discovery 影響 context/token）。

### 11) 是否值得列為 Research Candidate

**是，P0。**

## 3. Microsoft Agent Framework：Provider-backed MCP Session 改成 Per-Invocation

**類型：** MCP / tool runtime / session lifecycle / concurrency / identity scope  
**來源：**
- https://github.com/microsoft/agent-framework/commit/0275ebfd026e3549b9377788aedb58f424997fb2
- https://github.com/microsoft/agent-framework

### 1) 發生了什麼變化

Agent Framework 對自訂 `httpClientProvider` 的 MCP client 做 breaking change：

- 沒有 provider 時：仍依 server URL、label、connection、headers hash cache MCP session；
- 有 provider 時：每個 tool invocation 都建立、使用、dispose 自己的 MCP session，連 `tools/list` 也一樣。

### 2) 它解決什麼問題

`httpClientProvider` 可以依每次 invocation 動態回傳不同 authentication / identity，但這個 identity 沒有被完整編進既有 MCP session cache key。

如果繼續 cache：

```text
Invocation A identity
→ create cached MCP session

Invocation B different identity
→ accidentally reuse A's session
```

因此 framework 選擇最保守、語意最清楚的作法：provider-backed session 不共享。

### 3) 為什麼重要

這件事跟上一節 PydanticAI 剛好形成很有價值的對照：

- PydanticAI：為了避免重複初始化，在可行時拉長 session/toolset lifetime；
- Agent Framework：當 cache identity 無法正確表示 caller identity 時，反而縮短 session lifetime 到 invocation。

兩者都對，因為 scope 的依據不同。

### 4) 核心架構與資料流

Provider-backed：

```text
Tool Invocation
→ httpClientProvider(server)
→ new MCP transport/session
→ invoke / tools-list
→ dispose session + transport
```

Default cached path：

```text
(server URL, label, connection, headers hash)
→ cached ClientConnection
→ reuse across calls
```

### 5) 技術機制與 implementation evidence

Commit 新增：

- active provider invocation accounting；
- invocation-local `ClientConnection`；
- shutdown 等待 active provider invocations drain；
- active invocation 內 reentrant dispose 直接拒絕；
- session / transport cleanup failure 不覆蓋原本 invocation result / error；
- 文件直接警告 per-call session 增加 setup，且不保留 server-side session state；
- 若應用需要 continuity，應自己提供明確 scoped authentication/session lifetime 的 handler。

### 6) 與舊版本 / 最接近方案差異

舊版隱含假設：

```text
server cache key ≈ caller/session identity
```

新版承認在 provider-backed auth 下這不成立，因此改成：

```text
unknown/dynamic auth identity
→ no cross-invocation session reuse
```

### 7) 成熟度、近期活躍度與已知限制

**成熟度：正式 breaking runtime behavior，.NET / Python 都補 lifecycle coverage。**

限制：

- latency 與 connect overhead 增加；
- stateful MCP server 的 session continuity 會消失；
- 若每個 invocation 實際上身份相同，這個方案較保守，可能浪費可安全復用的 session。

### 8) 對 Agent Engineering 的實際影響

MCP client pool / cache 應把「session identity」當成一級設計，而不是只 cache by URL。

可能的 scope 包含：

```text
shared server session
per tenant
per user
per agent run
per invocation
```

選錯 scope 會在 correctness、state continuity、setup overhead 間付代價。

### 9) 是否改變既有假設

它顯示「MCP server 是一個 stateless tool endpoint」不是安全的通用假設。很多實作有 session state、auth context、初始化成本，因此 session lifecycle 本身就是 Agent runtime architecture。

### 10) 可做的 experiment / replication / benchmark

**Research Candidate：Yes — P0**

**MCP Session Scope Granularity Benchmark**

- **研究問題：** shared / per-run / per-user / per-invocation MCP session，在不同 statefulness / auth 模式下的最佳 trade-off 是什麼？
- **為什麼現在值得測：** PydanticAI 與 Agent Framework 同一天出現相反方向但互補的 production fixes。
- **Baseline：** URL-based shared cached session。
- **Variant A：** per-run session。
- **Variant B：** per-user / identity-aware cache key。
- **Variant C：** per-invocation session。
- **Task set：** stateless tools、stateful MCP server、dynamic auth provider、concurrent invocations、cancel/shutdown、server restart。
- **Metrics：** task success、wall-clock latency、connect/initialize count、tool calls、retry/recovery、session-state correctness、reliability、developer effort。

### 11) 是否值得列為 Research Candidate

**是，P0。**

## 4. Deep Agents Talon：只有「使用者真的看到的對話」進 Semantic Memory

**類型：** memory system / context engineering / provenance / retrieval / long-running agent  
**來源：**
- https://github.com/langchain-ai/deepagents/commit/f6850e9d25854b5679010c08f02adae99e6b8a2c
- https://github.com/langchain-ai/deepagents/commit/b3d4967bdcda5b42e976b3e97c357deea82d63ac
- https://github.com/langchain-ai/deepagents

### 1) 發生了什麼變化

Talon persistent conversation history 過去比較接近「checkpoint 裡出現的 message 都可能進向量索引」。

新版增加來源標記與 eligibility：

**可以進 semantic vector index：**
- 真實 user message；
- 確實成功 delivery 的 final assistant reply。

**不進 semantic vector index：**
- tool output；
- subagent result；
- synthetic input；
- intermediate reply；
- suppressed reply；
- delivery failed 的 reply。

這些內容仍保留在 archive，因此 keyword / lexical search 仍可查到，但不再跟 user-visible memory 混成同一個 semantic retrieval surface。

另一個配套 commit 讓相同內容的 vector dedup 跨 message revision 與 restart 持久化，只有 archive write 真正被 acknowledge 後，checkpoint 才能被視為已處理。

### 2) 它解決什麼問題

如果把整個 Agent trajectory 都向量化：

- tool output 會大量稀釋真正 conversation facts；
- subagent scratch result 可能與 final decision 重複；
- intermediate answer 後來被修正，但舊版本仍可被檢索；
- reply 根本沒送到使用者，未來 Agent 卻以為那是 shared conversational history；
- repeated checkpoint / edited message 會反覆 embedding 相同 chunk。

### 3) 為什麼重要

這把 memory 問題從「怎麼 retrieve」往前推了一層：

> **先決定什麼有資格成為 memory，再談如何檢索。**

對 long-running Agent，ingestion policy 可能比 vector DB / embedding model 更重要。

### 4) 核心架構與資料流

```text
Raw Agent Trajectory / Checkpoint
        ↓
Source tagging
  ├─ user
  ├─ delivered
  ├─ internal
  ├─ subagent
  └─ synthetic
        ↓
Archive Store  ← 保留完整文字
        ↓
Semantic eligibility filter
  ├─ user        → vector index
  ├─ delivered   → vector index
  └─ others      → 不做 semantic vector
        ↓
Persistent content dedup
        ↓
Hybrid retrieval
```

Final reply 不是模型生成完就算 `delivered`，而是 host/channel 確認成功送出後才 promotion。

### 5) 技術機制與 implementation evidence

`f6850e9`：

- `talon_history_source` 標記 message provenance；
- delivery callback 成功後呼叫 `record_delivered_reply()`；
- semantic search 在 vector hit 後再做 eligibility 過濾；
- existing vectors without trusted provenance 用 bounded background batches 清除；
- 295 focused tests passed；live PostgreSQL / MongoDB 未在該驗證環境執行。

`b3d4967`：

- `checkpoint_acknowledged` / `acknowledge_checkpoint` 把 archive persistence 與 checkpoint storage 分開確認；
- 相同 session+content 的 vector content identity 可跨 revision/restart 復用；
- failed archive write 後不會錯誤跳過 message；
- 222 tests passed，同樣未跑 live PostgreSQL / MongoDB。

### 6) 與舊版本 / 最接近方案差異

舊版：

```text
conversation log ≈ semantic memory corpus
```

新版：

```text
conversation archive ≠ semantic memory corpus
```

archive 是完整 forensic / lexical history；semantic memory 是經過 eligibility / provenance 過濾的子集合。

### 7) 成熟度、近期活躍度與已知限制

**成熟度：高度活躍、有大量 focused tests，但部分 external backend 未在 commit 驗證環境跑 live integration。**

限制：

- 只 index visible conversation 可能丟掉「其實對未來很有用」的 tool-derived fact；
- 因此最佳設計未必是永遠排除 internal data，而可能需要不同 memory namespace / tier；
- lexical archive 全留會有自己的儲存與 retrieval noise trade-off。

### 8) 對 Agent Engineering 的實際影響

Memory pipeline 應至少區分：

```text
raw trajectory
user-visible conversation
verified facts
procedural memory
tool artifacts
subagent scratch state
```

不要全部丟進同一個 vector namespace。

### 9) 是否改變既有假設

它削弱「更多記憶一定比較好」這個假設。

對 Agent memory，**precision of what gets remembered** 可能比 total recall 更重要；尤其 multi-agent 系統內部 traffic 很大時，全部 index 會直接把 coordination noise 永久化。

### 10) 可做的 experiment / replication / benchmark

**Research Candidate：Yes — P0**

**Memory Surface & Durable Dedup Benchmark**

- **研究問題：** semantic memory 只收 user-visible / delivered content，是否能在不降低 task success 的情況下提高 retrieval precision、降低 embedding / context cost？
- **為什麼現在值得測：** Talon 已有可操作的 provenance / delivery-aware implementation。
- **Baseline：** transcript-all semantic indexing。
- **Variant A：** user + delivered final replies only。
- **Variant B：** A + persistent revision/restart dedup。
- **Variant C：** multi-tier memory，把 tool/subagent facts 放獨立 namespace。
- **Task set：** 長對話、tool-heavy Agent、subagent delegation、message edit、failed delivery、restart/recovery。
- **Metrics：** quality / task success、retrieval precision/recall、token use、embedding count/cost、context compaction frequency、wall-clock latency、restart reliability。

### 11) 是否值得列為 Research Candidate

**是，P0。**

## 5. Google ADK + Antigravity：同一類 Coding Capability 出現三種 Orchestration Topology

**類型：** multi-agent / delegation / planner-executor / coding agent / workflow  
**來源：**
- https://github.com/google/adk-python/commit/c803f88b54bd7918ff8ff60eca351ae850fbd0d4
- https://github.com/google/adk-python/commit/79ac8cfcac0e81df3c3758d615dd21cdf10f7d9b
- https://github.com/google/adk-python/commit/5dbe1b907a98253ba0725110fb8864a04316640c
- https://github.com/google/adk-python

### 1) 發生了什麼變化

Google ADK 同時新增三個 Antigravity integration samples，剛好把同一類 capability 放進三種架構。

#### A. `LlmAgent` root → `AntigravityAgent` single-turn sub-agent

```text
User
 ↓
Coordinator LlmAgent
 ├─ general question → 自己回答
 └─ coding/file work → code_writer as inline tool
                         ↓
                    Antigravity harness
```

Parent 不把 session history 傳給 coding child；它必須組出 self-contained request。每個 delegated call 是獨立 conversation。

#### B. `AntigravityAgent` root → ADK `LlmAgent` child as client-side tool

```text
User
 ↓
Antigravity root + workspace/file tools
 ↓ when needed
ADK child tool
 ↓
child own Runner/session
 ↓
final text back to root
```

Child 執行在獨立 Runner / session，只回 final text。

#### C. Explicit `Workflow`: planner → builder

```text
START
 ↓
LlmAgent planner
 ↓ concrete build spec
Antigravity builder
 ↓
workspace files
```

這不是 `sub_agents`；資料流由 workflow edge 明確傳遞。

### 2) 它解決什麼問題

這些 sample 不是修 bug，而是在回答 integration boundary：

- heterogeneous harness 怎麼包成 Agent / tool / workflow node；
- 哪一層持有 workspace authority；
- parent 是否需要 child history；
- delegation request 是否應 self-contained；
- planner/executor 是由 model 自己決定，還是 workflow graph 固定。

### 3) 為什麼重要

我們一直在問「什麼時候不該 delegate」。這三個 sample 很難得，因為它們提供相近 capability 下的具體 architecture choices，可以直接做 controlled comparison。

官方目前只證明「三種都能 end-to-end 跑通」，**沒有證明 subagent 比 workflow 好，也沒有證明 planner-executor 比單 Agent 好。**

### 4) 核心架構與資料流

三種 topology 的根本差異：

| Topology | 誰決定 delegation | Child context | 資料交換 | Authority |
|---|---|---|---|---|
| Coordinator → coding sub-agent | root model | independent | self-contained request / final text | coding child 持 workspace tools |
| Coding root → reasoning child | root coding model | independent Runner/session | tool request / final text | root 持 workspace tools |
| Planner → builder workflow | workflow graph 固定 | node-local | planner output → builder input | builder 持 workspace tools |

### 5) 技術機制與 implementation evidence

官方 commits 各自附 end-to-end Gemini 測試說明：

- coordinator 可以直接回答 general question，也能把 coding request 組成 self-contained task 給 `code_writer`；
- Antigravity root 能 call bridged ADK child，再用自己的 file tools 寫入 workspace；
- Workflow 能把 planner 產生的 build spec 傳到 builder，實際建立檔案。

而且 sample 清楚暴露了一個重要 interface contract：**sub-agent description 本身就是 parent model 的 routing signal。**

### 6) 與最接近方案 / 舊版本差異

常見討論會把「multi-agent」當單一類別。

這三個 sample 顯示至少要區分：

- model-decided tool-like delegation；
- inverse specialist consultation；
- deterministic workflow decomposition。

它們的 context flow、coordination overhead 與 failure mode 完全不同。

### 7) 成熟度、近期活躍度與已知限制

**成熟度：官方 sample / integration evidence，不是 benchmark evidence。**

限制：

- sample 任務很小；
- smoke test 不能說明 production reliability；
- 沒有 quality / cost / token / latency 對照；
- 沒有 single-agent equivalent baseline。

### 8) 對 Agent Engineering 的實際影響

「開 subagent」之前可以先問：

1. 這個 handoff 能否形成 self-contained input contract？
2. 子任務是否需要 parent history？
3. authority 是否真的應該搬到 child？
4. decomposition 是 deterministic 的，還是需要 model 動態決定？

如果 decomposition 是固定的，Workflow 可能比 model-decided delegation 更簡單。

### 9) 是否改變既有假設

它支持一個更細緻的假設：

> **Multi-agent 的價值不應由「Agent 數量」衡量，而應由 boundary 是否對應清楚的 I/O contract、authority 與 context isolation 衡量。**

### 10) 可做的 experiment / replication / benchmark

**Research Candidate：Yes — P0**

**Same Capability, Three Orchestration Topologies**

- **研究問題：** 同一 coding capability 在 single agent、tool-like subagent、inverse specialist、fixed planner→builder workflow 下，哪種最接近 quality-cost Pareto frontier？
- **為什麼現在值得測：** ADK 已提供三種官方可跑 topology，可大幅降低實驗工程成本。
- **Baseline：** 單一 coding Agent，自己 planning + execution。
- **Variant A：** coordinator → single-turn coding subagent。
- **Variant B：** coding root → reasoning/specialist child。
- **Variant C：** explicit planner → builder Workflow。
- **Task set：** small file edit、multi-file feature、repo exploration、ambiguous requirement、well-specified procedural task、需要跨 turn 修改的 task。
- **Metrics：** quality / task success、actual model cost、token use、wall-clock latency、tool calls、delegation frequency、coordination failure、retry/recovery、developer effort。

### 11) 是否值得列為 Research Candidate

**是，P0。這是今天最直接回答 single-agent vs multi-agent 的實驗候選。**

## 6. M-SQE：Skill Retrieval 之後還要判斷「這個 Skill 是否真的可用」

**類型：** Agent Skills / tool routing / multilingual agent / retrieval / evaluation  
**來源：**
- https://arxiv.org/abs/2609.18445

論文：`M-SQE: Multilingual Skill Quality Estimation for Enhancing Language Equality in Agentic Skill Use`

### 1) 發生了什麼變化

這篇 2026-09-16 提交的新論文提出 M-SQE（Multilingual Skill Quality Estimation，多語 Skill 品質估計）。

它放在 retrieval 後面，不只問「Skill 與 query 是否相關」，還分成：

- **Theory view：** Skill 本身內在品質；
- **Action view：** 放到目前 task 裡是否真的有可執行效用；
- 再用 domain-conditioned score 合成排序。

### 2) 它解決什麼問題

Skill library 增長後，retriever 找到的 top-k 可能：

- 語意相關，但 procedure 不完整；
- 語言不匹配；
- 是合成 Skill，但品質不穩；
- 對該 domain 的 action constraints 不夠。

所以「相關」不等於「可執行」。

### 3) 為什麼重要

這與一般 RAG 很不一樣：document retrieval 找到不完美 passage，model 還可能自行整合；Skill 則通常是直接介入 Agent 行為流程，因此低品質 Skill 可能比沒有 Skill 更糟。

### 4) 核心架構與資料流

```text
Task query
  ↓
Retriever top-k Skills
  ↓
M-SQE post-retrieval scoring
  ├─ Theory quality
  ├─ Action/task utility
  └─ domain-conditioned fusion
  ↓
Selected Skill
  ↓
Agent execution
```

### 5) 技術機制與 implementation evidence

論文作者在 general、tool-use、cultural 三類 domain 與三種 retriever 上做實驗，報告：

- 相較 baseline，平均 task success 至少 +3.5 percentage points；
- Hindi +12.9pp；
- Swahili +5.6pp。

這些數字目前應標記為 **author-reported**；本輪研究未找到足以獨立重跑完整結果的官方 code / benchmark artifact。

### 6) 與最接近方案差異

傳統：

```text
query ↔ Skill embedding relevance
→ top-k
```

M-SQE：

```text
relevance retrieval
→ quality / action utility reranking
→ execution
```

### 7) 成熟度、近期活躍度與已知限制

**成熟度：新論文 evidence，尚不足以視為 production-proven pattern。**

限制：

- 增加 evaluator / reranker 成本與 latency；
- 品質 estimator 本身可能有 domain bias；
- 尚需測試強模型是否本來就能忽略低品質 Skill；
- 缺乏目前可直接驗證的公開實作證據。

### 8) 對 Agent Engineering 的實際影響

Skill registry 若只支援 embedding similarity，未來可能不夠。

更完整的 Skill router 可能需要：

```text
relevance
+ quality
+ language fit
+ domain fit
+ execution contract fit
+ historical success
```

### 9) 是否改變既有假設

它挑戰「progressive disclosure 只要少載幾個相關 Skill 就好」的假設。

真正重要的是：**少而對，而且能完成 task。**

### 10) 可做的 experiment / replication / benchmark

**Research Candidate：Yes — P1**

**Skill Relevance vs Skill Utility Benchmark**

- **研究問題：** relevance-only routing、quality reranking、execution-grounded reranking，哪個在強模型上仍有穩定收益？
- **為什麼現在值得測：** Skill ecosystem 已快速增長，而 M-SQE 提供了新的 post-retrieval hypothesis。
- **Baseline：** embedding relevance top-1 / top-k。
- **Variant A：** relevance + static quality score。
- **Variant B：** relevance + task-grounded action utility。
- **Task set：** coding Skill、CLI/tool-use Skill、中文/英文/低資源語言 task、quality-controlled good/bad Skill pairs。
- **Metrics：** quality / task success、token use、model cost、wall-clock latency、tool calls、wrong-skill selection rate、reliability。

### 11) 是否值得列為 Research Candidate

**是，P1；先重現，再決定是否升 P0。**

## 7. Observability：從「用了多少」走向「多久交付、當時到底有哪些 Tools / Plugins」

**類型：** agent evaluation / observability / coding-agent analytics  
**來源：**
- https://github.com/langchain-ai/open-swe/commit/cf7430d7ffdcc7c36d7cdf9b4490b3ada7c471ca
- https://github.com/openai/codex/commit/a1efb59c4a1721c42b9a974baf23b375c068e61c

### 1) 發生了什麼變化

Open SWE 新增 `Avg time to PR`：從 opening run start 到 PR creation 的平均 wall-clock，而不是只看 merge rate 或 merge 之後多久合併。

Codex 則在 turn analytics 新增 `active_plugin_ids_at_turn_start`：保存 turn 開始時實際 active host plugins + selected plugin packages；`null` 代表 unknown、`[]` 代表確定沒有 plugin，而且保留 first received inventory，不被後來的 config refresh 改寫。

### 2) 它解決什麼問題

Agent evaluation 常只留下：

- task pass/fail；
- token；
- cost；
- final model。

但這不足以回答：

- 哪種 model / effort 真的更快產出 PR？
- 某次成功是否因為多了一個 plugin / Skill？
- tool/plugin inventory 變動是否造成 latency 或 quality 變化？

### 3) 為什麼重要

如果要研究 orchestration ROI，**沒有 treatment attribution 就沒有可信結論。**

模型、Skill、plugin、tool exposure、routing、delegation 都必須能連回同一次 run/turn 的 outcome。

### 4) 核心架構與資料流

```text
RUN_STARTED
   ↓ timestamp/model/effort
TURN_STARTED
   ↓ active plugin inventory
Agent execution
   ↓
PR_OPENED
   ↓ delivery latency
PR outcome
   ↓ merge/close/open
```

### 5) 技術機制與 implementation evidence

Open SWE：

- 以 `PR_OPENED.opening_run_id` 對 `RUN_STARTED`；
- 排除缺 start time 或時間反序的 invalid pair；
- model-level 聚合 `avg_delivery_seconds`。

Codex：

- plugin IDs sort / dedupe；
- invalid / >512 inventory 轉 unknown；
- remote plugin ID 優先；
- 測試 plugin reconciliation 後 analytics inventory 是否與實際 active set 一致。

### 6) 與舊版本差異

舊版 analytics 較像 resource accounting；新版逐漸能重建 **execution configuration → trajectory → delivery outcome**。

### 7) 成熟度、近期活躍度與已知限制

**成熟度：production observability plumbing。**

限制：

- correlation 不等於 causal attribution；
- `Avg time to PR` 仍受 task complexity 影響；
- plugin inventory 只說「可用」，不代表真的被 call。

### 8) 對 Agent Engineering 的實際影響

未來任何 Agent A/B benchmark 最好至少保存：

- actual model / effort；
- active tools / Skills / plugins；
- actual tool calls；
- delegation events；
- retries/fallbacks；
- delivery milestone timestamps；
- final outcome。

### 9) 是否改變既有假設

它讓「平均 token 少 20%」這類單一效率指標更不夠用。真正有價值的是 end-to-end delivery efficiency。

### 10) 可做的 experiment / replication / benchmark

**Research Candidate：Yes — P1**

**Outcome-Attributed Agent Telemetry Schema**

- **研究問題：** 補齊 model/tool/plugin/delegation exposure 後，能否更準確解釋 quality-cost-latency 差異？
- **為什麼現在值得測：** Codex / Open SWE 已分別補上 configuration inventory 與 delivery milestone。
- **Baseline：** aggregate tokens + final success。
- **Variant：** turn/run-level configuration + trajectory + delivery milestone attribution。
- **Task set：** coding PR workload，包含不同 models、skills、plugins、delegation policies。
- **Metrics：** task success、actual model cost、wall-clock latency、time-to-PR、tool calls、delegation frequency、retry/recovery、coordination failure、attribution completeness。

## 今日綜合結論

今天最值得保留的不是某個新的 Agent framework，而是一個越來越一致的系統設計方向：

```text
Lifecycle Scope Must Match State / Authority Scope
```

具體來看：

```text
Thread configuration
≠ Active turn environment snapshot

Durable workflow run
≠ Durable unit / activity process

MCP server URL
≠ Session identity

Full trajectory archive
≠ Semantic memory corpus

Sub-agent
≠ Workflow node
≠ Tool-like specialist
```

這對「強模型是否降低 orchestration complexity」也有直接意義。

如果單一強 Agent 的 turn environment、tool lifecycle、MCP session、memory ingestion 都還沒做到 scope-correct，那加更多 Agent 很可能只會讓 lifecycle 數量增加，而不是讓能力增加。

目前最合理的研究順序仍是：

```text
1. Single strong-agent correctness baseline
2. Context / memory / tool lifecycle correctness
3. Adaptive model routing
4. 明確 I/O contract 的 selective delegation
5. Fixed workflow decomposition（若 task 結構可預先知道）
6. 最後才是 open-ended fan-out / multi-agent orchestration
```

Google ADK 今天的三種 Antigravity topology 正好提供一個可以真的去測第 4、5 步的實驗平台，而不是再用抽象的「multi-agent vs single-agent」平均分數做結論。
