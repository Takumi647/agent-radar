# Agent Ecosystem Radar — 2026-09-15

> 研究窗口：截至 2026-09-15 08:33（Asia/Taipei）。本報告只追蹤 Agent Ecosystem；Security 題材不拿來補篇幅。今日以 9/14 晚間至 9/15 上午的原始 GitHub commits 為主，並補入一篇近期、與我們既有 memory 研究高度相關且具有成本/品質實驗數據的論文。

## 執行摘要

- **Agent memory 的研究焦點開始從「怎麼存」轉向「寫入 memory 前，是否能回頭向環境驗證」。** `Grounding Agent Memory: Environment-Probing Curation for Enterprise Agents` 提出 post-task curator 在任務結束後，使用最小權限、read-only world tools 驗證候選 memory，再寫入持久層。CLBench 上 pass rate 從 39% 升到 73%，task-agent cost 從 3.38 美元降到 1.68 美元；這是目前非常直接地回答「memory 是否能在不犧牲 correctness 下同時降低成本」的證據。
- **Google ADK 把 agent handoff（代理交接）正式收進 `DynamicNodeScheduler` 的 replay / resume / interrupt state machine。** 這次 refactor 修掉一個實質 bug：向上 transfer 到另一個 parent context 後，如果目標 agent 被 human input interrupt，caller 之前可能被錯記成 `COMPLETED`，而且沒有 checkpoint。這說明 multi-agent handoff 的難點不是「能不能 transfer」，而是 transfer 之後誰擁有 run state、interrupt 與 checkpoint authority。
- **Microsoft Agent Framework 修正 AG-UI resume 的 transcript duplication。** 當 client 在 resume 時重送自己已有的完整 transcript，runtime 不能再把 server snapshot 盲目 prepend；新邏輯改成 overlap reconstruction。反過來，只有 interrupt response / checkpoint ID 的空 resume 仍必須 seed server history。這是很典型的 distributed state reconciliation：`resume` 不是單純 reload，而是要判斷 client/server 各自持有哪一段 canonical history。
- **同一 framework 也修掉 parallel tool-call streaming 的 merge bug。** 兩個 tool call 的 argument deltas 可以交錯抵達；舊邏輯只把新 chunk merge 到最後一個 function call，會把兩個 call 的 JSON 參數混在一起。現在優先依 `call_id` 找真正的 in-flight call。這說明 tool parallelism 的 correctness 需要 event identity，不是只靠 arrival order。
- **Deep Agents 0.1.69 把 nested-agent monetary cost attribution 再修正一層。** nested response 沒帶 model name 時，先前可能錯用 parent model 的價格；streaming provisional usage 也無法被 completion 的 authoritative total 正確修正。現在優先用 request-level model metadata、completion 可以替換 chunk-built provisional record，且 provisional cost 以 request 為 bucket，避免一個 request 的 correction 扣到另一個 request。對「實際 model monetary cost」作為 Agent efficiency 主指標非常關鍵。
- **Codex 開始把 attachment / multimodal artifact 從 inline payload 變成可替換 storage contract，而且 delegated sessions 會繼承 store。** 新 `AttachmentStore` 拆成 `upload` / `resolve`，可返回 inline bytes 或 durable `file_id`；resolution 支援 metadata 與有最小 TTL 的 fresh download URL。這讓長時程 / 多 Agent session 能用穩定 reference 傳遞 image/file artifact，而不是把所有 bytes 一直塞在 context 或 transport。
- **OpenViking 的 QueueFS 再往真正 background runtime 靠攏。** queue backend 現在區分 `pending` / `processing`，completion status 由 backend snapshot 擁有；後續 refactor 又把 success / failed / requeued / cancelled 收斂成 typed `ProcessResult`，並把 task cancellation、ack rollback、active-task registration 放進 middleware。這比各 consumer 自己 `report_success()` / `report_error()` 更接近一致的 queue execution contract。

今天最重要的共同訊號是：**Agent engineering 的核心逐漸從「prompt / planner / subagent 數量」轉到 state reconciliation、handoff authority、concurrency identity、cost attribution、memory write quality 與 durable artifact/queue contracts。** 在這些 runtime contract 還不穩定前，直接比較 single-agent vs multi-agent 很容易量到 framework bug，而不是 architecture 本身。

## 重要發展

### 1. Agent Memory：Environment-Probing Curation 把「反思」變成「可驗證的記憶寫入」

**類型：** memory systems / long-running agents / continual learning / cost-quality evaluation  
**來源：**
- https://arxiv.org/abs/2609.11060

論文：`Grounding Agent Memory: Environment-Probing Curation for Enterprise Agents`

#### 1) 發生了什麼變化

常見 persistent-memory pipeline 是：

```text
Task Agent
→ 完成 trajectory
→ Curator / Reflection Agent
→ 從 trajectory 摘要 lesson
→ 寫入 memory
```

這篇工作的核心修改很小，但很關鍵：**curator 不再只能看 trajectory，而能在 task 結束後，用 read-only world tools 主動查環境，驗證候選 memory。**

其架構是：

```text
Task Agent
  ├─ environment tools
  └─ read-only memory
        ↓
完成 task + grade
        ↓
Distiller（不寫 memory）
        ↓
Curator Agent
  ├─ memory CRUD（唯一可寫 memory 的角色）
  └─ read-only environment tools
        ↓
propose → probe → commit
```

Task Agent 本身不獲得更多能力；變的是 **memory write-time evidence quality**。

#### 2) 它解決什麼問題

單一 trajectory 很容易產生錯的 generalization：

- 成功答案只是偶然，不代表 procedure 可重用；
- 某個 join / file path / tool convention 只在當下成立；
- agent 只看過環境的一小部分；
- environment drift 後，舊 memory 仍被保留；
- trajectory 內的錯誤中間推理可能被當成 lesson。

單純讓 curator「更會反思」仍無法知道 trajectory 沒看過的 state。

#### 3) 為什麼重要

它直接回應我們一直追的問題：

> **context / memory infrastructure 是否真的能降低成本，而且不犧牲 correctness？**

論文報告在 CLBench：

- pass rate：`39% → 73%`
- pass-discounted reward：`8.60 → 22.60`
- task-agent queries：`8.8 → 4.7`
- task-agent cost：`$3.38 → $1.68`

APEX 的六個 document worlds 上，memory 相對 baseline 的 18 組 mean reward comparison 全部為正；task-agent tool calls 降低 16–75%，environment probing 在五個 world 得到最佳 reward-per-dollar。

這些數字是論文作者實驗結果，仍需 replication；但至少比「memory 讓 agent 看起來更聰明」這種定性宣稱強很多。

#### 4) 核心架構與資料流

重要的 authority separation 是：

```text
Task Agent
  memory: READ
  environment: task-required access

Curator Agent
  memory: READ / CREATE / UPDATE / DELETE
  environment: READ-ONLY probe
```

也就是 **執行任務的人不能直接永久改 memory；能永久寫 memory 的 curator 又只拿到 read-only world tools。**

這是一個很乾淨的 continual-learning boundary。

#### 5) 技術機制與 implementation evidence

作者使用 production-like GitHub Copilot SDK harness：每個 task 都是 fresh agent session，但外部 memory index 跨 session 持久化。

環境 probing 會：

- 驗證 schema / join key / encoding；
- 檢查程序必要前提；
- 重新查 environment drift；
- 在不同 slice 重驗 relation；
- 發現 trajectory 沒走過的 relevant state；
- 必要時 narrow / delete / skip memory，而不是只 append。

#### 6) 與既有 memory 方案的差異

Trajectory-only：

```text
過去做過什麼
→ 反思
→ 寫 lesson
```

Environment-probing：

```text
過去做過什麼
→ 提出候選 lesson
→ 回環境驗證 / 找反例 / 確認 scope
→ 再寫 memory
```

它沒有改 retrieval algorithm，也沒有要求 weight update；改的是 **memory creation epistemology：記憶不只從行為紀錄來，而要允許外部驗證。**

#### 7) 成熟度、限制

**成熟度：研究系統，但 evaluation 與 production harness 接近。**

限制：

- probing cost 被移到非 critical path，但不是免費；
- 需要存在安全、低副作用的 read-only environment surface；
- benchmark 仍只有有限 world / task distribution；
- memory write quality 的長期漂移需要更長 sequence 才能驗證。

#### 8) 對 Agent Engineering 的實際影響

如果我們未來做 Agent memory，不應只比較：

```text
vector store A vs B
summary prompt A vs B
```

而應加入一個維度：

```text
Memory write authority
+
Memory evidence boundary
+
是否允許 post-task verification
```

#### 9) 是否改變 single-agent vs multi-agent 假設

它其實提供一種「有理由增加第二個 Agent」的範例。

Curator 的存在不是因為「多 Agent 看起來比較強」，而是因為它有**不同權限、不同時間點、不同 objective**：

- Task Agent optimize current task；
- Curator optimize future task memory quality。

這比角色扮演式 multi-agent 更容易 justify。

#### 10) Experiment / replication

**Research Candidate：Yes — P0**

- **研究問題：** memory curator 多一個 read-only environment-probing loop，是否能在相同 task model 下提高 future-task quality 並降低 task-time model/tool cost？
- **為什麼現在值得測：** 有清楚 baseline、production-like harness 與公開數據可重現。
- **Baseline A：** stateless。
- **Baseline B：** trajectory-only curator memory。
- **Variant：** propose–probe–commit curator。
- **Task set：** codebase conventions、資料庫 schema drift、企業文件 workflow、API/tool usage conventions。
- **Metrics：** future task success、task-agent model monetary cost、tool calls、curator cost、memory precision、stale-memory rate、memory deletions/updates、wall-clock critical-path latency。

### 2. Google ADK：Agent Transfer 正式進入 Scheduler 的 Replay / Interrupt / Checkpoint State Machine

**類型：** multi-agent / delegation / workflow engine / checkpoint-recovery  
**來源：**
- https://github.com/google/adk-python/commit/198139ef31f8c51b723b58a7a74d8eb2eb15dc31
- https://github.com/google/adk-python

#### 1) 發生了什麼變化

ADK 把原本 `_dynamic_node_executor.py` 裡的 sequential agent transfer loop 移進 `DynamicNodeScheduler.__call__`。

現在 scheduler 統一負責：

1. fresh execution；
2. replay / dedupe；
3. interrupt resumption；
4. sequential agent handoff。

同時移除另一份 `Context._child_run_counters` mirror，`DynamicNodeState.run_counters` 成為唯一 sequential run-id allocator。

#### 2) 它解決什麼問題

舊結構把：

```text
workflow scheduling
與
agent transfer loop
```

拆在不同 execution layer。

這導致一個實際 bug：如果 Agent A transfer 到不同 parent context 下的 Agent B，而 B 之後需要 human input、進入 interrupt，interrupt ID 可能被記到 B 的 parent context；真正等待它的 caller NodeRunner 看不到，因此 caller 被錯標為 `COMPLETED`，而且 checkpoint 不會產生。

#### 3) 為什麼重要

這是 multi-agent framework 很容易忽略的核心問題：

> handoff 完成後，**誰擁有 execution state？**

handoff 不只是「下一個 agent 名字」。它還包含：

- run ID authority；
- checkpoint authority；
- replay event ownership；
- interrupt ownership；
- output delegation；
- resume input routing。

任何一個錯，long-running workflow 都可能在 crash / human approval 後無法正確恢復。

#### 4) 核心架構

新路徑比較像：

```text
ctx.run_node()
      ↓
DynamicNodeScheduler
      ├─ execute step
      ├─ replay prior result
      ├─ resume interrupt
      └─ inspect transfer_to_agent
               ↓
      resolve target + parent context
               ↓
      target parent 的 owning scheduler
               ↓
      next hop
```

每個 hop 使用真正擁有該 parent context 的 scheduler，所以 run counters 與 replay state 不再由外層 executor 猜。

#### 5) Implementation evidence

commit 加入：

- transfer loop execution tests；
- interrupt halting；
- target validation；
- parent-context scheduler handover；
- replay opt-out；
- transfer 後 interrupt ID propagation。

#### 6) 與舊版本差異

舊版：executor 自己維護 transfer pointer，scheduler 只處理 workflow node。

新版：**scheduler 是 dynamic execution 的 single runtime driver**，handoff 只是其中一種 state transition。

#### 7) 成熟度與限制

**成熟度：production framework refactor + bug fix。**

它解決 sequential handoff 的 state ownership，但還不能代表 concurrent fan-out / join 的 merge semantics 已完整；那是另一個問題。

#### 8) 對 Agent Engineering 的影響

多 Agent runtime 應該把 handoff 當成 state-machine transition，而不是 prompt-level event：

```text
TRANSFER
→ RUNNING(target)
→ WAITING / COMPLETED / FAILED
→ CHECKPOINT
→ RESUME
```

#### 9) 是否改變 delegation 假設

是。每多一個 handoff，就多一組 state ownership / recovery complexity。因此「delegate 就能隔離 context」不是免費收益；必須把 recovery surface 算進 orchestration cost。

#### 10) Experiment / replication

**Research Candidate：Yes — P0**

- **研究問題：** multi-agent handoff 在 interrupt / crash / resume 下是否保持 exactly-once execution 與正確 caller state？
- **Baseline：** simple direct handoff without centralized scheduler authority。
- **Variant：** scheduler-owned handoff/replay/checkpoint。
- **Task set：** sibling transfer、upward transfer、A→B→C chain、human approval at each hop、crash before/after checkpoint。
- **Metrics：** task success、duplicate execution、lost interrupt、wrong terminal state、resume success、replay count、coordination failure、developer effort。

### 3. Microsoft Agent Framework：Resume 不再盲目 Prepend Server History，而改做 Transcript Reconciliation

**類型：** long-running agents / resume / AG-UI / distributed state reconciliation  
**來源：**
- https://github.com/microsoft/agent-framework/commit/61d6c2c23db5d435eaa8c70fa8e5d8770b70720d
- https://github.com/microsoft/agent-framework

#### 1) 發生了什麼變化

AG-UI client 在 reconnect / resume 時，有些 client 會把自己目前整段 transcript 再傳一次。

舊版 runtime 一律：

```text
stored server history
+
incoming messages
```

造成 replayed transcript 被 double-persisted。

新邏輯區分兩種 resume shape：

```text
A. incoming messages 非空
   → overlap reconstruct / reconcile

B. incoming messages 為空
   → prepend stored history
```

而 approval/checkpoint resume 還有更細的 special case：若 retained approval result 已能完全處理 request，就直接 re-emit result，不應因 reconstructed raw messages 非空而再跑一次 agent。

#### 2) 它解決什麼問題

Distributed Agent UI 其實有兩份 state：

```text
Server Thread Snapshot
Client Transcript
```

Resume 時不能假設其中一邊一定是 delta，也不能假設 client 沒有 replay history。

盲目 concat 會造成：

- duplicated messages；
- context window 膨脹；
- checkpoint 持久層重複；
- approval tool result 被再次處理；
- 不必要的新 model invocation。

#### 3) 為什麼重要

很多「Agent resume」只測 server restart 後 thread 能不能開，但真正 production client 還包含：

- browser reconnect；
- mobile ↔ desktop switch；
- UI local transcript cache；
- approval / interrupt response；
- dropped streaming event。

因此 resume protocol 必須定義 reconciliation semantics，而不是只有 `thread_id`。

#### 4) 核心架構

```text
Stored snapshot S
Incoming transcript C
        ↓
Detect resume shape
        ↓
if C has transcript:
    overlap-merge(S, C)
else:
    seed S
        ↓
append interrupt / approval resume events
        ↓
persist one reconciled history
```

#### 5) Implementation evidence

commit 有 regression test 明確驗證：

```text
stored:   u1, a1
incoming: u1, a1, u2
result:   u1, a1, u2
```

而不是 `u1, a1, u1, a1, u2`。

同時涵蓋 empty resume、workflow resume、checkpoint、approval retry。

#### 6) 與舊版本差異

舊 mental model：

```text
Resume payload = only new data
```

新 mental model：

```text
Resume payload = 可能是 delta，也可能是 replayed view
```

所以 runtime 必須 reconcile。

#### 7) 成熟度與限制

**成熟度：production interoperability fix。**

目前仍高度依賴 message identity / overlap heuristics；如果 client/server 都能改寫 message content 或缺穩定 ID，reconciliation 仍可能變複雜。

#### 8) Agent Engineering 影響

應把 resume benchmark 從：

```text
Can reopen thread?
```

提升成：

```text
Can reconcile divergent client/server views without duplicate execution?
```

#### 9) single vs multi-agent 關聯

即使只有 single agent，這種 state sync 也存在；multi-agent 只會把 state copies 增加更多。因此先把 single-thread resume protocol 做正確，比先加更多 subagents 更基礎。

#### 10) Experiment / replication

**Research Candidate：Yes — P0**

- **研究問題：** 在 dropped events / reconnect / replayed transcript / approval resume 下，Agent session 是否具備 idempotent resume？
- **Baseline：** blind prepend / append。
- **Variant：** overlap reconstruction + stable message IDs + retained-result replay。
- **Task set：** 20–100-turn session、tool approval、client reconnect、server restart、client full replay、partial replay。
- **Metrics：** duplicate messages、duplicate model/tool calls、context token inflation、resume success、final task correctness、recovery latency。

### 4. Microsoft Agent Framework：Parallel Tool Streaming 必須用 Call Identity Merge，不能相信 Arrival Order

**類型：** tool use / parallel execution / streaming / runtime correctness  
**來源：**
- https://github.com/microsoft/agent-framework/commit/0ff9e40cd41d5aae9514b76c20f86614a739a9e7

#### 1) 發生了什麼變化

當模型平行發出兩個 tool call 時，stream 可能長這樣：

```text
call_1 start
call_2 start
call_1 args delta
call_2 args delta
call_1 args delta
call_2 args delta
```

舊 `_process_update` 只嘗試把 function-call chunk merge 到 `message.contents[-1]`。

結果是 call_1 後續 delta 到達時，最後一個 content 其實可能是 call_2，造成 argument JSON 被拆碎、重複或混在錯的 call。

新 `_merge_function_call_content`：

1. chunk 有 `call_id` → 從所有 in-progress calls 找 matching ID；
2. 有 ID 但找不到 matching call → 視為新 call；
3. chunk 沒 `call_id` → 才允許 fallback 到 trailing function call。

#### 2) 它解決什麼問題

這是典型 concurrency identity 問題：

```text
Sequential assumption:
next chunk belongs to latest call

Parallel reality:
next chunk belongs to call_id X
```

#### 3) 為什麼重要

我們在 benchmark parallel tool use 時，如果 runtime merge 本身會錯，最後看到的：

- tool failure；
- JSON parse failure；
- retry；
- higher latency；
- lower task success；

很可能不是模型不會 parallelize，而是 client runtime 把 stream 合錯。

#### 4) 技術機制

新的 correctness anchor 是：

```text
arrival order
≠
logical ownership

call_id
=
logical ownership
```

而且 commit 特別處理 provider 差異：有些 provider 不會在每個 continuation chunk 重複 `call_id`，所以仍需保留「無 ID chunk → trailing call」的兼容 fallback。

#### 5) Implementation evidence

新增測試涵蓋：

- interleaved parallel streaming；
- no-call-id continuation；
- reused call_id；
- tagged new call 不可被 untagged trailing call 吸收。

#### 6) 與舊方法差異

這跟 distributed logs / network stream 一樣：一旦有 concurrency，就不能把 sequence position 當 entity identity。

#### 7) 成熟度與限制

**成熟度：core runtime bug fix。**

限制在於不同 providers 對 `call_id`、occurrence `id` 的語義仍不完全一致，需要 compatibility matrix。

#### 8) Agent Engineering 影響

任何 parallel-tool benchmark 應記錄至少：

- logical call ID；
- stream occurrence ID；
- merge errors；
- incomplete JSON arguments；
- provider-specific chunk semantics。

#### 9) single vs multi-agent 關聯

這說明「平行化帶來更低 latency」之前，必須先付 correctness complexity。單一強 Agent 同樣可能平行 call tools，所以這不是 multi-agent 專屬問題，而是 concurrency overhead。

#### 10) Experiment / replication

**Research Candidate：Yes — P1**

- **研究問題：** 不同 provider / SDK 在 2、4、8 路 parallel tool streaming 下是否保持 call reconstruction correctness？
- **Baseline：** arrival-order merge。
- **Variant：** ID-based merge + provider compatibility fallback。
- **Task set：** interleaved synthetic streams + real parallel API calls。
- **Metrics：** reconstructed-call accuracy、invalid JSON rate、retry count、tool success、latency、token waste。

### 5. Deep Agents 0.1.69：Nested-Agent Cost Attribution 修正，終於更接近「實際 Model Monetary Cost」

**類型：** observability / cost accounting / subagents / evaluation  
**來源：**
- https://github.com/langchain-ai/deepagents/commit/f413a40f7e74ada749b18491aa276ee1224c7368
- https://github.com/langchain-ai/deepagents/commit/1d3232c0852c47af09119edea10eeec887e4f0da

#### 1) 發生了什麼變化

Deep Agents 先前已有 thread lifetime cost tracking，但 nested usage 還有兩個 attribution bug：

1. nested response 沒有 model name 時，可能 fallback 到 **parent model** 的價格；
2. streaming chunks 先建立 provisional usage 後，final completion 的 authoritative total 無法正確替換它。

新版本改成：

- 優先讀該 request 的 configured model/provider metadata；
- completed message 可以 replace partial chunk-built request record；
- correction 保留 request identity；
- provisional USD 以 request 為獨立 bucket；
- late correction 不可扣掉其他 concurrent request 的 provisional cost。

#### 2) 它解決什麼問題

假設：

```text
Main Agent = expensive model
Subagent   = cheaper model
```

subagent streaming event 若沒回 model name，卻用 main model pricing，會讓 multi-agent cost 被系統性高估。

反過來，如果 final usage 對 chunks 有 downward correction，而 runtime 不允許 replace，又會把 provisional overcount 留在 dashboard。

#### 3) 為什麼重要

我們已經把 Agent efficiency 主指標定義成 **實際 model monetary cost**，不是 output token。

因此 cost accounting 需要至少知道：

```text
每個 request
├─ model
├─ provider
├─ input/output/cache tokens
├─ request attempt
├─ parent / nested origin
└─ final authoritative usage
```

否則「multi-agent 貴 30%」可能只是 attribution bug。

#### 4) 核心架構

```text
stream chunks
    ↓ provisional request bucket
request-level model metadata
    ↓
provisional cost
    ↓
completion arrives
    ↓
replace partial request record
    ↓
request-scoped correction
    ↓
thread durable total
```

#### 5) Implementation evidence

commit 明確處理：

- request metadata model precedence；
- chunk → completion replacement；
- retry-attempt scoping；
- per-request provisional balances；
- server total 已吸收 request 後，late correction 不可再次 inflate / retract。

#### 6) 與舊方法差異

舊：session / parent model 是 fallback truth。

新：**request 是 cost attribution 的最小單位。**

這與昨天 Codex 把 observability 推到 step-level provenance 的方向一致，但這次更直接落到 USD accounting。

#### 7) 成熟度與限制

**成熟度：production-facing cost fix。**

仍然有 provider 不回足夠 token bucket、unknown model pricing、subscription-style access 無法映射 per-token USD 等不可估情況；這些情況應標為 missing cost，而不是硬猜。

#### 8) Agent Engineering 影響

之後 orchestration benchmark 最低限度應輸出：

```text
quality
actual model USD
latency
tool calls
subagent calls
missing-cost percentage
```

而不是只看 total tokens。

#### 9) 是否改變 strong-model vs orchestration 假設

它不證明 multi-agent 更便宜或更貴；它做的是讓這個問題**終於比較能被正確量測**。

#### 10) Experiment / replication

**Research Candidate：Yes — P0**

- **研究問題：** fixed strong model、cheap-router→strong model、main→cheap subagent、main→strong subagent 的實際 USD / quality frontier 如何？
- **Baseline：** single strong model。
- **Variants：** adaptive routing、single-level delegation、2–4-way fan-out。
- **Task set：** coding、research、tool-heavy、多檔案分析。
- **Metrics：** task success、actual model monetary cost、missing-cost %、latency、tool calls、delegation frequency、coordination failure、retry count。

### 6. Codex：AttachmentStore 從「把 bytes 塞進 context」走向 Durable Artifact Contract

**類型：** runtime / multimodal agents / artifact persistence / delegation  
**來源：**
- https://github.com/openai/codex/commit/446b771049d41617c66d7475d292b010e9165c71

#### 1) 發生了什麼變化

Codex 將 `AttachmentStore::persist` 重構成：

- `upload(request)`
- `resolve(request)`

upload 可以返回：

```text
Inline { bytes }
或
File { file_id }
```

resolve 則可依 `file_id` 返回：

- filename；
- digest；
- size；
- MIME type；
- image width/height；
- optional fresh file URL。

而 URL 只有 caller 明確要求 `download_url_ttl` 時才產生，且 store 必須保證至少剩餘指定 lifetime。

Thread manager 會把 configured image/attachment store 傳進 session，**delegated sessions 也會繼承同一 store。**

#### 2) 它解決什麼問題

Long-running / multi-agent runtime 很難一直傳：

```text
base64 image
large binary payload
signed URL with short expiry
```

真正需要的是穩定 identity：

```text
artifact bytes
→ durable file_id
→ metadata
→ on-demand fresh URL
```

#### 3) 為什麼重要

這讓 artifact lifecycle 與 context lifecycle 解耦。

context 可以 compact / resume / delegate，但 image/file 不需要跟著被重新 inline；subagent 只要繼承 store，就能透過 reference 取得同一 artifact。

#### 4) 核心架構

```text
Session A
  ↓ upload
AttachmentStore
  ↓ durable file_id
Thread / checkpoint state
  ↓ delegate
Session B inherits same store
  ↓ resolve(file_id, TTL)
fresh metadata / URL
```

#### 5) Implementation evidence

API 還特別：

- redacts inline bytes in debug；
- redacts signed file URL；
- typed errors：`NotFound / InvalidAttachment / Backend`；
- inline store 保留原 PNG/JPEG bytes；
- inline implementation 不假裝能 resolve nonexistent file IDs。

#### 6) 與舊方法差異

舊：attachment reference 比較像 persistence helper。

新：attachment store 是明確可替換的 runtime capability，有 upload/resolve contract、metadata 與 expiry semantics。

#### 7) 成熟度與限制

**成熟度：active runtime refactor。**

目前 format-specific metadata 主要看到 image；對大型 generic files、artifact versioning、跨 session garbage collection 的完整 policy 還要再觀察。

#### 8) Agent Engineering 影響

Agent state 建議拆成：

```text
Language Context
Durable Structured State
Artifact References
```

而不是全部都塞 transcript。

#### 9) single vs multi-agent 關聯

multi-agent 特別需要 shared artifact identity，否則每次 delegation 都複製 payload，增加 token / transport / storage cost。

#### 10) Experiment / replication

**Research Candidate：Yes — P1**

- **研究問題：** durable attachment reference 是否能降低 multimodal long-session context / transfer cost，又保持 resume/delegation correctness？
- **Baseline：** inline data / repeated upload。
- **Variant：** durable `file_id` + on-demand resolve。
- **Task set：** 多圖片 code/debug、PDF/image inspection、多 subagent 共用 artifact。
- **Metrics：** task success、context tokens、transport bytes、upload duplication、resume success、delegation latency、artifact-not-found / expiry failures。

### 7. OpenViking QueueFS：Background Work 從 Consumer 自報狀態，轉成 Backend-owned Lifecycle

**類型：** background agents / queue runtime / retry-recovery / observability  
**來源：**
- https://github.com/volcengine/OpenViking/commit/7df74141c01a19de1df6bfdfdcbf7494feb74916
- https://github.com/volcengine/OpenViking/commit/192b813e7e3106680a5534e2d4c9bcf6d2390abd

#### 1) 發生了什麼變化

QueueFS 先把 queue state 明確拆成：

```text
pending
processing
```

`dequeue` 後 message 不再只是從 pending 消失，而是進 processing，直到 `ack` 才真正移除。

後續 refactor 又把 consumer 各自呼叫：

```text
report_success()
report_error()
report_requeue()
```

改成回傳統一的 typed `ProcessResult`：

```text
success
failed
requeued
cancelled
```

task cancellation、active-task tracking、ack prepare/rollback 也放進 Queue middleware，而不是散落在 embedding / deletion 等 handler。

#### 2) 它解決什麼問題

Background worker 最怕 ambiguity：

- message 已 dequeue，但 handler crash，算 completed 嗎？
- requeue 前 crash，誰恢復？
- cancellation 發生在 handler unwind 中，應 ack 還是重新投遞？
- queue 顯示 size=0，但其實有 20 個 in-flight messages，算 idle 嗎？

Backend-owned pending/processing state 才能回答這些問題。

#### 3) 為什麼重要

Long-running Agent 的 memory ingestion、embedding、artifact processing、background summarization 都可能跑在 queue 上。

若 queue completion 是 consumer-local boolean，Agent dashboard 很容易把「in-flight」誤認為「done」。

#### 4) 核心架構

```text
Queue backend = durable truth
      ↓ dequeue
pending → processing
      ↓ middleware
handler
      ↓ ProcessResult
success / failed / requeued / cancelled
      ↓
ack / rollback / recover
```

#### 5) Implementation evidence

- memory / SQLite / cache backends 都有 `status()`；
- `list_unacked` 同時涵蓋 pending + processing；
- ack 只從 processing 移除；
- task middleware 在 ack 未 commit 時 rollback index；
- handler cancellation 先 unwind，再決定 delivery settlement。

#### 6) 與舊方法差異

舊：handler 擁有「我覺得這次成功/失敗」的 side-effect reporting。

新：handler 回傳結果；**queue runtime 擁有 lifecycle transition。**

#### 7) 成熟度與限制

**成熟度：快速演進中的 production runtime。**

仍要觀察 crash recovery 的 exactly-once / at-least-once contract、visibility timeout、poison message policy。

#### 8) Agent Engineering 影響

Background Agent 不該把 queue 當簡單 FIFO；應定義完整 delivery state machine。

#### 9) single vs multi-agent 關聯

background orchestration 的可靠性往往比「多一個 reasoning agent」更先成為 bottleneck。只要有 async memory / embedding / review worker，這個問題就存在。

#### 10) Experiment / replication

**Research Candidate：Yes — P1**

- **研究問題：** backend-owned delivery state 是否降低 crash/requeue/cancel 時的 lost-work 與 duplicate-work？
- **Baseline：** dequeue + consumer-local success/error reporting。
- **Variant：** pending/processing + typed outcome + ack middleware。
- **Task set：** embedding、memory curation、background review、artifact processing。
- **Metrics：** lost jobs、duplicate jobs、recovery latency、queue state accuracy、retry count、task success、operator effort。

## 對既有研究問題的更新

### 強模型是否降低 orchestration complexity？

**今天仍沒有新證據可以直接回答「是」。**

但 Deep Agents 的 cost attribution fix 告訴我們：在回答之前，先確保 nested model 的 USD 沒被算成 parent model。否則 cost-match / compute-match 結論會直接錯。

### 什麼時候不該 delegate？

今天新增一個很實用的判斷：

如果 delegate 只是因為「想分工」，但沒有不同的：

- authority；
- lifecycle；
- context boundary；
- validation role；

那未必值得。

相反地，memory curator 是合理的 second agent，因為它有獨立 objective（提高 future memory quality）、不同時序（post-task）、不同 authority（唯一 memory writer + read-only world probe）。

### 多 Agent 是否真的提升品質，而不是只增加 token？

今天沒有新的 universal multi-agent benchmark 支持普遍提升。

反而又看到三個 overhead source：

- handoff checkpoint / interrupt ownership；
- nested cost attribution；
- shared artifact state。

因此 multi-agent benchmark 必須把這些 orchestration/runtime overhead 算進去。

### Context / Memory infrastructure 是否真的能降低成本且不犧牲品質？

**今天有很強的正向 evidence。**

Environment-probing memory 在 CLBench 同時提高 pass rate、降低 query 次數與 task-agent USD cost，是目前 Radar 裡非常值得 replicate 的結果之一。

### Long-running Agent 如何 checkpoint / resume / reconcile？

今天答案更清楚：

```text
Durable state
+
Stable logical identities
+
Canonical ownership
+
Client/server reconciliation
+
Idempotent replay
```

只存 transcript 不夠；只存 checkpoint 也不夠。

### Runtime authority 與 Agent intelligence 應如何分離？

今日兩個案例都支持：

- Google ADK：scheduler 擁有 replay / handoff / run-state authority；
- Memory paper：curator 擁有 memory write authority，task agent 不直接寫。

也就是 intelligence 可以提出下一步，但 durable state transition 最好由明確 runtime owner 執行。

### Codex `tool_event_type`：開始區分 model tool call 與 inner tool call

來源：

這是昨天 step-level provenance 的延伸，值得持續追蹤，因為要做真正的 orchestration ROI，最終需要能回答：**哪些 tool 是模型直接叫的、哪些是 code-mode / agent runtime 內部再 dispatch 的 child call。**

### Deep Agents：Preserved Thinking 與 Client-side Compaction 的相容性

來源：
- https://github.com/langchain-ai/deepagents/commit/fe01fac1fa3c4d30d9379a9e5f4273a622710049

Deep Agents 發現 memory injection / client-side compaction 改變 prompt prefix 後，Anthropic preserved-thinking block 可能因 prefix mismatch 讓下一 turn 直接失敗。新版本對新 Claude models 預設 `prefix_mismatch_behavior="drop_block"`。

這是一個值得後續獨立研究的 interoperability signal：**context compaction 不只影響文字 history，也可能讓 provider-specific hidden/preserved reasoning state 失效。**

## 今日結論

今天的資料進一步支持一個很強的 Agent runtime 方向：

```text
Agent Intelligence
    ↓ proposes

Runtime State Machine
    ├─ owns handoff / checkpoint / resume
    ├─ reconciles client/server history
    ├─ tracks logical tool-call identity
    ├─ attributes model/tool monetary cost
    ├─ manages artifact references
    └─ owns background queue transitions

Memory Curator
    ↓ verifies
Durable Memory
```

如果要決定下一階段實驗優先級，我會把順序排成：

1. **Environment-Probing Memory Curation** — 因為已有非常明確 quality + cost evidence；
2. **Idempotent Resume / Handoff Recovery Suite** — 因為 production Agent 一定會碰到；
3. **True Monetary Cost Attribution Benchmark** — 這是所有 single vs multi-agent 決策的量測基礎；
4. **Parallel Tool Streaming Correctness**；
5. **Durable Artifact / Background Queue Semantics**。

今天仍不應得到「multi-agent 普遍優於 single-agent」這種結論。相反地，最新實作一直在提醒：**在 delegate 之前，要先確認多出來的 Agent 有清楚的 contract / authority / independent objective，並把 handoff、recovery、artifact、concurrency、cost attribution 的代價全部算進去。**
