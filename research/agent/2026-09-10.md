# Agent Ecosystem Radar — 2026-09-10

> 研究窗口：截至 2026-09-10 08:47（Asia/Taipei）。本報告只追蹤 Agent Ecosystem；AI / Agent Security 由另一條 Security Radar 處理。今日優先採近期 repository commits、release 與 implementation evidence，不以 star 數或單純產品宣傳排序。

## 執行摘要

- **OpenAI Codex 正把「背景 Agent」做成真正可恢復、可自動續跑、也會自行停止空轉的 runtime。** 最新 commit 讓 managed daemon 重啟後，不必等 client reconnect，就會從 recovery snapshot 背景 cold-resume 已保存 thread，active goal 可繼續執行；同時新增 liveness breaker，automatic goal continuation 若連續三回合只有空 final answer、沒有 tool / commentary /有效文字等活動，就把 goal 標成 `blocked`。這兩個改動一起看，比單純「支援 resume」更接近 supervisor / workflow engine semantics。
- **Open SWE 把 adaptive model routing 變成 runtime 的一等能力。** 它新增 `fast / balanced / performance` 三層 model profile，由一個輕量 classifier 根據當前 task 選擇整個 turn 使用哪一層，並把 routing decision 放進 Agent state。預設 mapping 是 GLM-5.3 Flash、GPT-5.6 Sol、GPT-6 Astra，但功能目前仍預設關閉、由 profile opt-in。這是目前非常適合實測「便宜 router + 強模型 escalation 是否能同時保品質與降成本」的開源案例。
- **Open SWE 同一天把 provider-specific tools 從 hardcoded integration 重構成 workspace-scoped MCP。** MCP runtime 被拆成 shared runtime 與 workspace scope，支援 OAuth client credentials，並移除部分內建 Datadog / LangSmith / Currents integration。方向很清楚：tool surface 越來越像可配置、可發現、workspace-scoped 的能力層，而不是每多一個 SaaS 就往 Agent code 裡再寫一套 connector。
- **Google ADK 正補 A2A 與中斷 tool-call 的 distributed-runtime semantics。** Remote A2A stream 若乾淨結束，但最後 task state 還是 `submitted / working / unknown`，現在會明確報錯，不再把「transport stream 結束」誤認成「remote task 完成」；同時 session history 在 turn 被 cancel / restart / follow-up 打斷後，會清掉沒有對應 response 的 orphaned function calls，但保留真正 long-running / auth / confirmation pending calls。這是多 Agent / long-running tool system 很實際的 recovery correctness。
- **Microsoft Agent Framework 一次新增 Redis、Qdrant、PostgreSQL pgvector、Azure AI Search 四組 vector store connector。** 這顯示 memory / knowledge backend 正被抽象成可替換 storage layer；但目前 evidence 主要是 CRUD、filter、vector/hybrid search 與 lifecycle correctness，還沒有證明「換成這些 backend 就能提升 Agent 最終品質」。下一步應測 backend semantics 對 retrieval consistency、cost、latency 與 Agent outcome 的影響，而不是只測 vector DB 本身 QPS。

## 重要發展

### 1. OpenAI Codex：Managed daemon restart 後自動恢復 thread，並為 automatic goals 增加空轉 breaker

**類型：** Agent runtime / long-running agents / checkpoint-recovery / scheduling  
**來源：**
- https://github.com/openai/codex/commit/e1b23086acbf905592036c587cb37a12d68c441e
- https://github.com/openai/codex/commit/0735c519789d300097554425cc3d7cf3f2d718a1
- https://github.com/openai/codex

#### 發生了什麼變化

Codex 在 9/10 台北時間清晨補了兩個彼此高度相關的 runtime 行為。

第一個是 daemon recovery：graceful managed-daemon shutdown 之前保存的 root thread recovery candidates，現在新 daemon 啟動時會先 consume snapshot，再用既有 cold-resume path 在背景 restore thread。重要細節包括：

- 不需要 client 先 reconnect 才啟動恢復；
- 已 loaded 的 thread 不被重複接管；
- individual thread 恢復失敗不會中止其他 thread；
- shutdown 時會 abort background recovery；
- recovery snapshot 在本 generation consume 後移除，避免把舊 generation state 傳給下一次 daemon；
- idle lifecycle work 也能在沒有 client subscription 時被重新啟動。

第二個是 goal liveness breaker：若 Agent 的 automatic goal continuation 連續三回合都只產生空的 `final_answer`，且沒有 commentary、reasoning summary、tool activity、file change、subagent activity、web search、context compaction 等有效活動，就把 goal 標成 `blocked`。一旦出現有效活動，streak 會重置。

#### 它解決什麼問題

長時程 Agent 若只做到「thread 可以存檔」，仍然缺兩塊 production semantics：

```text
1. Process restart 之後，誰主動把工作撿起來？
2. 撿起來之後，如果 Agent 沒進展，誰讓它停？
```

舊式 resume 通常是：

```text
process crash
→ 等人重新打開 UI / client
→ resume thread
```

現在 Codex 更接近：

```text
managed daemon restart
→ consume recovery snapshot
→ background cold-resume
→ goal continues
→ runtime observes progress
→ no-progress threshold → blocked
```

#### 為什麼重要

這是從「聊天 session 恢復」往「Agent supervisor」移動。

一個可長時間工作的 Agent runtime，至少需要：

- durable identity
- checkpoint / recovery candidates
- background resume
- liveness / progress signal
- stuck detection
- explicit blocked / paused / completed states

否則 restart 只是把 transcript 打開，不等於工作流真的恢復。

#### 核心架構與資料流

```text
Graceful shutdown
      ↓
loaded persistent root thread IDs
      ↓
atomic recovery snapshot
      ↓
new daemon startup
      ↓
consume + delete snapshot
      ↓
background shared cold-resume
      ↓
restore history / tools / goal runtime
      ↓
automatic goal continuation
      ↓
progress accounting
      ├─ activity → reset empty streak
      └─ 3 empty turns → blocked
```

#### Implementation evidence

Daemon recovery integration test 覆蓋：

- client 尚未 reconnect 前 goal 已能繼續；
- conversation history / tools 恢復；
- idle thread restoration；
- malformed snapshot / invalid thread ID 不拖垮整批 recovery。

Empty-response breaker 則有 public API regression test，明確測：

- 三次空 continuation 後 blocked；
- final answer text / commentary / tool activity 會重置 streak；
- normal turn completion 與 streamed deltas 不因 breaker 被破壞。

#### 與既有方法的差異

很多 Agent framework 的 checkpoint 是：

```text
save state → client later calls resume()
```

Codex 現在開始加入：

```text
save recovery intent
+ daemon-managed restoration
+ runtime liveness accounting
```

這比較像 workflow engine / actor supervisor，而不是純 session persistence。

#### 成熟度、近期活躍度與已知限制

**成熟度：中高，屬核心 app-server / daemon runtime 的 active development。**

限制：

- recovery snapshot 仍是 local daemon generation 的 handoff，不等於跨 host distributed recovery；
- active external tool side effects 是否 exactly-once 仍不是這套 snapshot 能保證；
- 「三個空回合」是 heuristic threshold，不代表已經是最佳 stuck detector；
- 目前 liveness 更像 activity detection，還不是 semantic progress evaluation。

#### 對 Agent Engineering 的實際影響

如果要做 background / long-running coding agent，值得把 runtime state 至少分成：

```text
Persistence
→ thread / task 能否存活

Recovery ownership
→ restart 後誰負責撿起

Liveness
→ 怎麼判斷仍有進展

Termination policy
→ blocked / paused / failed / completed 何時觸發
```

不能只用「有 checkpoint」代表可恢復。

#### 是否改變既有假設

是。它再次強化一個方向：

> **Long-running Agent 的核心問題已經從 prompt chaining 移到 runtime semantics。**

#### 可做實驗

**Research Candidate：Yes — 最高優先級**

- **研究問題：** daemon-managed auto-recovery + liveness breaker 是否能比 client-triggered resume 降低 lost work 與 infinite-loop cost？
- **為什麼現在值得測：** Codex 已有可直接參考的 open-source implementation。
- **Baseline：** checkpoint 存檔，但只有 client reconnect 才 resume；沒有 no-progress breaker。
- **Variant：** daemon startup auto-resume + progress accounting + blocked threshold。
- **Task set：** 20–50 個 30–120 分鐘 coding tasks，隨機注入 process restart、network interruption、empty-model response、tool transient failure。
- **Metrics：** recovery success、time-to-resume、lost-work rate、duplicate tool effects、stuck duration、wasted tokens、task success、operator intervention。

### 2. Open SWE：Adaptive Model Routing 成為 per-thread runtime capability

**類型：** Agent orchestration / model routing / cost-quality trade-off / escalation  
**來源：**
- https://github.com/langchain-ai/open-swe/commit/201d41deb62b9687b2f86d339ca35cb2832d6738
- https://github.com/langchain-ai/open-swe

#### 發生了什麼變化

Open SWE 新增 `ModelSelectionMiddleware`，把 model routing 從人工固定設定提升為 Agent runtime 的一層 middleware。

目前定義三個 routing tier：

```text
fast
balanced
performance
```

預設 model / effort mapping 是：

```text
fast        → Fireworks GLM-5.3 Flash / high
balanced    → OpenAI GPT-5.6 Sol / medium
performance → OpenAI GPT-6 Astra / low
```

這些 mapping 可由 team admin 改寫。

Routing classifier 不是看 prompt 長度，而是根據 task characteristics 判斷：

- direct lookup / mechanical operation / explicit target → `fast`
- ordinary bugfix / bounded investigation / multi-file implementation → `balanced`
- architecture / ambiguous requirements / novel root cause / cross-component judgment → `performance`

若一開始就在 plan mode，直接走 `performance`；否則 classifier 對最近 human task 做 structured-output classification。Classifier 失敗時 fallback `balanced`。

Routing decision 存進 Agent state，實際 model call 由 middleware 依 `model_route` override model。

值得注意的是：雖然 commit title 寫「roll out adaptive model routing to all threads」，code 中 profile flag **預設仍為 `False`**，因此比較精確的描述是：routing machinery 已成為所有 thread 可用的一等能力，但目前仍 opt-in。

#### 它解決什麼問題

典型 Agent deployment 很容易陷入兩個極端：

```text
A. 全部用最強模型
→ 品質高，但 cost / latency 高

B. 固定便宜模型
→ 成本低，但複雜任務 failure / retry 增加
```

Adaptive routing 嘗試把 model selection 本身變成 orchestration decision：

```text
Task
 ↓
cheap routing decision
 ↓
fast / balanced / performance
 ↓
selected executor model
```

#### 為什麼重要

這直接碰到我們一直追的問題：

> **強模型應該永遠當 default executor，還是只在需要時 escalation？**

很多 multi-agent / router paper 都會宣稱省成本，但 Open SWE 提供了一個 production-style implementation，可以真的量：

- classifier 自己的成本；
- route mistake 導致的 retries；
- performance tier 的 marginal quality gain；
- task phase 是否應改變 routing；
- routing 是否比「固定 Sol / 固定 Astra」更划算。

#### 核心架構與資料流

```text
Current human task
      ↓
Routing classifier
      ↓ structured RouteDecision
fast / balanced / performance
      ↓
persist model_route in Agent state
      ↓
ModelSelectionMiddleware
      ↓
actual executor model + effort
```

#### Implementation evidence

commit 不是只有設定 UI；它新增：

- team-level three-tier model / reasoning effort settings；
- profile-level enable/disable；
- `ModelSelectionState`；
- structured-output classifier；
- fallback route；
- middleware model override；
- route state persistence；
- plan mode special handling。

這已足以建立可重現的 routing benchmark。

#### 與既有方法的差異

常見簡化 router：

```text
prompt length / keyword / token count
→ model A or B
```

Open SWE 的 classifier prompt 明確說 prompt length 與 eventual runtime **不是 difficulty signal**，而是根據：

- acceptance criteria 清晰度
- reversibility
- test strength
- ambiguity
- architecture breadth
- consequence / stakes

做 task-level routing。

另一方面，它目前是一 turn 一 route，而不是每個 phase / tool step 重新切 model，所以 coordination complexity 比 fine-grained router 小。

#### 成熟度、近期活躍度與已知限制

**成熟度：中；implementation 已進 main，但預設關閉。**

主要限制：

- 沒看到公開 compute-matched benchmark 證明這三層配置優於 fixed model；
- classifier 本身仍是 LLM，會產生 routing error；
- classifier prompt 最多取最近 task 的 8,000 字元，可能忽略更早需求；
- one-route-per-turn 可能對長 turn 的 phase transition 不夠細；
- `performance = Astra low` 不一定普遍勝過 `balanced = Sol medium`，必須依 task set 實測。

#### 對 Agent Engineering 的實際影響

如果實驗成立，這比「所有事情先 delegate 給 subagent」更值得優先做：

```text
先決定這個 task 到底需不需要更強 executor
再決定要不要 fan-out / delegate
```

也就是 model routing 可以成為 delegation 之前更便宜的一層 decision。

#### 是否改變既有假設

目前**還不能說已證明**「便宜 router + 強模型 escalation」一定比較好；但這是一個非常適合驗證該假設的真實開源 implementation。

#### 可做實驗

**Research Candidate：Yes — 最高優先級**

- **研究問題：** adaptive routing 是否能在維持 fixed-frontier-model 品質下顯著降低 model cost？
- **為什麼現在值得測：** 已有 production-style route state + model override implementation。
- **Baseline A：** 全程 GPT-5.6 Sol medium。
- **Baseline B：** 全程 GPT-6 Astra low / medium。
- **Variant：** classifier → fast / balanced / performance。
- **Task set：** mechanical fixes、bounded bugs、multi-file implementation、architecture change、ambiguous product task，各 20–30 題。
- **Metrics：** task success / quality、model cost、routing accuracy、retry count、wall-clock latency、tool calls、wrong-escalation rate、under-routing failure rate。

### 3. Open SWE：Provider-specific tools 重構成 Workspace MCP

**類型：** MCP / tool architecture / workspace capability / integration runtime  
**來源：**
- https://github.com/langchain-ai/open-swe/commit/5999851098e26f2923c9bd4dd9d0278c4ab2f7e2
- https://github.com/langchain-ai/open-swe/commit/1c24c8f184b0f02e5d14bf51daaf0351fd0a2adb
- https://github.com/langchain-ai/open-swe

#### 發生了什麼變化

Open SWE 把一批原本 hardcoded 的 provider tool integration 重構到 **workspace MCP**。

這次變更包含：

- MCP runtime 分成 shared runtime 與 workspace scope；
- workspace MCP 支援 OAuth client credentials；
- OAuth identity 變更時要求重新提供 secrets；
- workspace MCP tools 可提供給所有 coding-agent users；
- provider agent tools 改走 workspace MCP；
- 移除 dedicated Currents integration；
- 移除部分 Datadog / LangSmith credential-specific integration surface；
- UI 從「每個 provider 一套 integration 設定」往一般化 workspace MCP 設定收斂。

#### 它解決什麼問題

每新增一個 SaaS 就在 Agent runtime 裡直接寫：

```text
DatadogTools
LinearTools
CurrentsTools
VendorXTools
```

會帶來：

- codebase integration explosion
- credentials lifecycle 重複
- tool schema / refresh 行為不一致
- 每個 workspace 的工具集合難以隔離
- provider 變動就要改 Agent 本身

Workspace MCP 把它改成：

```text
Workspace configuration
      ↓
MCP server + auth identity
      ↓
discover tools
      ↓
workspace-scoped tool surface
      ↓
Agent
```

#### 為什麼重要

MCP 的價值不只「統一 tool calling protocol」。真正進 production 後，更重要的是 capability lifecycle：

- 哪個 workspace 有哪些 MCP；
- credential 屬於誰；
- identity 改變時舊 connection / secret 是否能繼續用；
- shared runtime 能不能與 workspace-specific capability 分離；
- Agent thread switch 時如何 refresh tool surface。

Open SWE 這次變更開始把這些問題往 runtime 層收斂。

#### 核心架構與資料流

```text
Shared Agent Runtime
      │
      ├─ common MCP lifecycle
      │
Workspace Scope
      ├─ MCP config
      ├─ OAuth client identity
      ├─ secrets
      └─ discovered tools
             ↓
       Agent tool surface
```

#### Implementation evidence

這不是只改 docs；commit 同時修改：

- workspace MCP APIs；
- auth / secrets handling；
- runtime scope；
- agent tool wiring；
- provider-specific credential APIs；
- dashboard integration UI；
- documentation。

因此可以視為 architecture refactor，而不是單一 connector feature。

#### 與既有方法的差異

舊模式：

```text
Agent Runtime
├─ built-in provider A integration
├─ built-in provider B integration
└─ built-in provider C integration
```

新模式：

```text
Agent Runtime
└─ generic workspace MCP capability layer
      ├─ provider A MCP
      ├─ provider B MCP
      └─ provider C MCP
```

這會把 integration complexity 從 application code 移向 protocol + configuration + lifecycle management。

#### 成熟度、近期活躍度與已知限制

**成熟度：中，剛完成大範圍 refactor。**

限制：

- MCP server 品質與 tool schema consistency 仍由各 provider 決定；
- generic protocol 不會自動消除 provider-specific auth semantics；
- tool discovery 增加後，模型 tool-selection overhead 可能上升；
- workspace tool surface 若太大，仍需 tool routing / progressive disclosure；
- 尚未看到 refactor 前後的 task success / latency / developer effort benchmark。

#### 對 Agent Engineering 的實際影響

這一方向很適合自製 enterprise Agent：

> **Agent core 不應知道每一家 SaaS 的細節；Agent core 應知道如何載入、隔離、刷新與使用 capability。**

#### 是否改變既有假設

是。Tool integration 越來越不像「一堆 Python functions」，而像：

```text
capability registry
+ identity
+ lifecycle
+ scope
+ dynamic discovery
```

#### 可做實驗

**Research Candidate：Yes**

- **研究問題：** generic workspace MCP 是否能降低 integration maintenance cost，而不增加模型 tool-choice cost？
- **Baseline：** 3–5 個 hardcoded provider toolsets。
- **Variant：** 相同 provider 改為 workspace MCP discovery。
- **Task set：** GitHub / observability / issue tracker / browser verification 的跨工具 workflows。
- **Metrics：** task success、tool-selection errors、initial context tokens、tool schema tokens、connection/setup latency、integration LOC、provider upgrade effort、operator configuration effort。

### 4. Google ADK：A2A stream completion 與 remote task completion 正式分開；Interrupted tool calls 也開始做 history repair

**類型：** Multi-agent / A2A / long-running tools / recovery / context correctness  
**來源：**
- https://github.com/google/adk-python/commit/e29ee231e02ec9e82dc91ee008c8a2798d021f3d
- https://github.com/google/adk-python/commit/54274cdeba42a46e4346f48589c84fe2ebcc0da2
- https://github.com/google/adk-python/commit/6de43b05a07f8ca89909664b3a21049646d7336c
- https://github.com/google/adk-python

#### 發生了什麼變化

Google ADK 今天值得放在一起看的，是兩個 recovery semantics 修正。

第一個是 A2A remote agent：以前 remote response stream 如果「正常結束」，caller 可能把它當成 remote task 已完成。但其實最後 task 仍可能是：

```text
unknown
submitted
working
```

新版會記住 `last_task`；如果 stream 結束時 task 還在上述 unfinished state，明確產生 error event：stream ended before task reached a terminal state。

但 `input_required` / auth waiting 這類 deliberate pause 不被當成 truncation，因為 remote agent 本來就可能故意停止 streaming 等外部輸入。

第二個是 interrupted tool-call history repair：turn 被 user cancel、process restart 或新的 follow-up 打斷時，history 可能留下：

```text
function_call(id=X)
但沒有
function_response(id=X)
```

OpenAI / Anthropic 等 provider 可能直接拒絕這種不閉合 history，回 HTTP 400。

ADK 現在會清掉沒有 matching response 的 orphaned function call；但如果 call ID 被標在 `long_running_tool_ids`，包括真正 long-running tool、auth request、confirmation request，就保留，因為它們合法地仍在等待 resume。

另外，前一個同窗口 commit 也修正 resume without `new_message` 時仍要套用 `state_delta`，進一步補齊 resume path。

#### 它解決什麼問題

分散式 Agent / tool runtime 常犯一個基本錯誤：

```text
Transport lifecycle
≠
Task lifecycle
≠
Tool lifecycle
```

例如：

- SSE / A2A stream 關閉，不代表工作完成；
- thread turn 結束，不代表 long-running tool 已完成；
- process restart 後，history 中的 function call 不一定還應該 replay；
- pending auth / confirmation 不能被當 orphan 清掉。

#### 為什麼重要

Multi-agent protocol 真正困難的不是「Agent A 可以 call Agent B」，而是：

> **Agent A 如何知道 Agent B 的工作到底完成、暫停、失聯，還是仍在等待外部事件？**

這些狀態如果混在 transport stream 裡，遇到 reconnect / partial failure 就會誤判。

#### 核心架構與資料流

A2A path：

```text
A2A stream items
      ↓
track last remote Task state
      ↓
stream closes
      ↓
terminal / deliberate-pause ?
      ├─ yes → normal end
      └─ no  → explicit truncation error
```

Tool-history repair：

```text
session events
      ↓
collect function_response IDs
collect long_running_tool_ids
      ↓
function_call ID
      ├─ response exists → keep
      ├─ long-running pending → keep
      └─ neither → prune as orphan
```

#### Implementation evidence

A2A tests 明確覆蓋：

- `working` stream end → error；
- `unknown` stream end → error；
- `completed` → normal；
- `input_required` → normal deliberate pause；
- task mode 下 truncation 會 release task control。

Tool repair tests 覆蓋：

- orphan call 被移除；
- call 後又有 follow-up user turn 仍正確修復；
- surrounding text 保留；
- marked long-running call 保留；
- sliding-window / token-threshold compaction interaction。

#### 與既有方法的差異

天真的 implementation：

```text
async iterator ended
→ done
```

比較健全的 implementation：

```text
transport ended
→ inspect durable/protocol task state
→ decide completed / paused / failed / truncated
```

Tool history 也從「照 transcript 重播」轉向「依 runtime semantics 修復後再投影給模型」。

#### 成熟度、近期活躍度與已知限制

**成熟度：中高，屬 ADK core flow / RemoteA2aAgent 的 correctness fix。**

限制：

- 偵測 truncation 不代表自動恢復 remote task；
- cross-agent exactly-once execution 仍未被解決；
- orphan pruning 依 function IDs 與 `long_running_tool_ids` metadata 正確性；
- remote peer 若錯誤回報 terminal state，caller 仍可能誤判。

#### 對 Agent Engineering 的實際影響

A2A / multi-agent runtime 的 state machine 至少應明確分：

```text
transport state
remote task state
local invocation state
pending human/auth state
long-running tool state
```

不要只靠「stream 有沒有關」推理一切。

#### 是否改變既有假設

它削弱「只要有 A2A protocol 就解決 multi-agent orchestration」這個假設。Protocol message shape 只是第一步；recovery / task ownership / terminal semantics 才是 production correctness。

#### 可做實驗

**Research Candidate：Yes — 高優先級**

- **研究問題：** explicit task-state semantics 能否降低 multi-agent partial-failure 誤判與 replay errors？
- **為什麼現在值得測：** ADK 已提供真實 failure cases 與修補 implementation。
- **Baseline：** stream-close = done；history 原樣 replay。
- **Variant：** terminal-state validation + orphan repair + long-running pending preservation。
- **Task set：** A2A remote tasks，隨機注入 stream cut、client cancel、process restart、auth wait、human confirmation、late tool response。
- **Metrics：** false-completion rate、resume success、duplicate execution、HTTP history rejection、task success、recovery latency、operator intervention。

### 5. Microsoft Agent Framework：Memory / Knowledge backend 開始形成可替換 Vector Store Layer

**類型：** Agent memory / knowledge systems / vector stores / storage abstraction  
**來源：**
- https://github.com/microsoft/agent-framework/commit/16b330516a9120c445fd1149fe6305ebfbb45838
- https://github.com/microsoft/agent-framework/commit/aa3c8bec4d63df2510ed5d6c3caa1e8759dabd08
- https://github.com/microsoft/agent-framework/commit/9ad620067862f042131024394686c62961b8352c
- https://github.com/microsoft/agent-framework/commit/df1e50c306b62d74db74a2b003e6f7b018324480
- https://github.com/microsoft/agent-framework

#### 發生了什麼變化

在今天研究窗口內，Microsoft Agent Framework 的 Python side 一次新增四組 vector store connector：

- Redis HASH / JSON
- Qdrant
- PostgreSQL + pgvector
- Azure AI Search

它們不是只有「丟 embedding 進去」的 sample，而是逐步對齊共同的 Agent Framework storage abstraction，包含不同程度的：

- async collection / store APIs
- batch CRUD
- native filtering
- dense vector search
- hybrid search（Azure AI Search）
- connection / lifecycle ownership
- schema / vector precision validation
- request preflight / pagination correctness
- transactional batch behavior（PostgreSQL）

#### 它解決什麼問題

Agent Memory / Knowledge 系統常被某一個 vector DB 綁死：

```text
retrieval logic
+ schema
+ filter syntax
+ connection lifecycle
+ vector backend semantics
```

全部揉成一套。

共同 storage abstraction 的理想目標是：

```text
Agent memory / retrieval policy
          ↓
portable vector-store interface
          ↓
Redis / Qdrant / pgvector / Azure Search
```

讓 memory policy 與 storage product 分開。

#### 為什麼重要

企業 Agent 實際部署時，vector backend 往往不是 purely technical choice：

- 公司已有 PostgreSQL / Redis；
- cloud governance 要求 Azure managed service；
- 特定 workload 需要 hybrid search；
- latency / cost / consistency / operational burden 不同。

如果 Agent framework 本身能維持近似的 retrieval semantics，就能減少 backend lock-in。

#### 核心架構與資料流

```text
Agent / Memory component
        ↓
AF collection / vector-store API
        ↓
query + filters + vectors
        ↓
Backend adapter
        ├─ Redis
        ├─ Qdrant
        ├─ pgvector
        └─ Azure AI Search
        ↓
retrieved records
        ↓
Agent context
```

#### Implementation evidence

幾個 commit 特別值得注意的是它們在補「語意一致性」而不只是 happy path：

- Qdrant：拒絕可能在分頁下漏資料 / 重複資料的 ordered retrieval；
- Redis：重新驗證 index / schema、限制 supported client settings；
- PostgreSQL：transactional batch CRUD、filter compiler、vector precision validation；
- Azure Search：write 前先做 native action / serialized request limit preflight，並處理 collection/client lifecycle。

這表示 framework 已經遇到「同一抽象在不同 backend 上不一定有相同 semantics」的實作問題。

#### 與既有方法的差異

簡單 abstraction 常只定義：

```text
upsert()
search()
```

但 production portability 真正困難的是：

- ordering
- paging
- filters
- vector numeric representation
- transaction semantics
- schema validation
- lifecycle / ownership

Microsoft 這一輪 commit 已開始處理這些差異。

#### 成熟度、近期活躍度與已知限制

**成熟度：早中期；多個 connector 明確仍是 alpha / preview。**

最重要的限制是：

> **Storage correctness ≠ Agent memory quality。**

目前 evidence 能說「adapter 比較完整」，不能說「Agent 使用這個 memory backend 後回答更準」。

另外不同 backend 的 hybrid search、filter、ordering、precision semantics 仍不完全等價。

#### 對 Agent Engineering 的實際影響

Memory stack 可以更清楚拆成：

```text
What to store
How to consolidate
When to retrieve
How to rank
How much context to inject
----------------------------
Where to persist/search
```

Vector DB 應該位於最後一層，而不是反過來決定整套 memory architecture。

#### 是否改變既有假設

它支持「memory infra 應 backend-portable」這個方向，但尚未證明 backend abstraction 對最終 Agent quality 無損。

#### 可做實驗

**Research Candidate：Yes**

- **研究問題：** 同一 memory / retrieval policy 換不同 vector backend 時，Agent outcome 是否保持一致？
- **為什麼現在值得測：** AF 已有四組近似 interface 的 implementation。
- **Baseline：** PostgreSQL pgvector。
- **Variants：** Redis、Qdrant、Azure AI Search。
- **Task set：** LongMemEval / repository knowledge QA / multi-turn support-agent memory，可混合 metadata filter 與 semantic search。
- **Metrics：** answer quality、retrieval recall@k、ranking stability、p95 latency、storage cost、index/update latency、filter parity、failure recovery、developer effort。

## 今日綜合判斷

今天幾個看似分散的 commit，其實高度收斂到同一件事：

> **Agent 系統正在從「模型 + tools」轉成「runtime-managed state machine」。**

可以看到五個 runtime concern 同時變得一等重要：

```text
1. Recovery ownership
   Codex daemon restart 後誰自動撿起工作

2. Liveness
   Agent 有沒有真的進展，什麼時候該 blocked

3. Model routing
   哪個 task 值得更強模型

4. Capability routing
   哪個 workspace 應該載入哪些 MCP tools

5. Distributed task semantics
   remote stream / tool call / task state 如何在 partial failure 下保持一致
```

這對「強模型是否降低 orchestration complexity」的答案也越來越細：

- 強模型可能減少 prompt decomposition / hand-written planner；
- 但 **recovery、liveness、state、capability lifecycle、task terminal semantics** 並不會因模型變強而消失；
- 甚至模型越能長時間自主工作，這些 runtime concerns 越重要。

而對「什麼時候不該 delegate」今天仍沒有新的 compute-matched evidence 足以下普遍結論。Open SWE 的 model routing 反而提供一個更便宜的替代假設值得先測：

> 在 fan-out / multi-agent 之前，先判斷是不是只需要換一個更合適的 executor model。

這可能比預設 multi-agent 更值得優先 benchmark。
