# AI / Agent Security Radar — 2026-09-08

> 研究窗口：截至 2026-09-08（Asia/Taipei）上午。今日只追蹤 AI / Agent Security，不以一般 Agent 生態新聞補量；優先採官方 security advisory、原始 commit / issue、論文與可重現 implementation evidence。

## 執行摘要

- **Agent 的 context compaction（上下文壓縮）本身已經變成安全邊界。** `Tencent/AI-Infra-Guard` 今天修正 `mcp-scan`：長對話被壓縮時，已確認或疑似的 security findings 可能被摘要掉，導致掃描器「早先找到了漏洞，最後交付卻忘了」。修正後把 `<security_findings>` 提升為不可丟棄的一級 state，並加入 regression test。這顯示對長時程安全 Agent 而言，**memory / compaction fidelity 不只是品質問題，也是安全完整性問題**。
- **`github/gh-aw` 修正一個很重要的網路隔離假設：host loopback publication 不等於 container-to-container 不可達。** 在 bridge mode 下，共用網路的容器仍可能直接打到 `mcpg` container 的 control listener；真正被依賴的安全控制其實是 256-bit capability authentication，而不是 Docker port publication topology。這是一個典型的「不要把網路拓撲誤當 authorization」案例。
- **最新 prompt injection 研究開始把 attacker compute（攻擊者測試時計算量）當成安全評測變數。** `Rethinking Indirect Prompt Injection as a Test-Time Search Problem` 把 indirect prompt injection 重構成 test-time search：攻擊者先偵察環境、管理策略、根據 victim feedback 調整。核心結論不是一個固定 ASR，而是：**給攻擊者更多 search budget，會找到更多可利用路徑，因此 benchmark 必須報告 attack procedure + compute budget。**
- **安全掃描器自己的「可視範圍」也可能成為 supply-chain 繞過面。** `AI-Infra-Guard` 的 `skill-scan` 先前主動忽略 `__pycache__` 與 `.pyc/.pyo/.pyd`，使可在 runtime 執行的 compiled bytecode 被從 Agent audit surface 隱藏；官方 issue 已關閉並有 patch，GitHub Advisory Database 於 9/2 收錄為 `CVE-2026-84809`。這件事非常值得當成「LLM security scanner 不應只評模型推理，還必須評 scanner tool visibility」的 benchmark case。

## 重要發展

### 1. `Tencent/AI-Infra-Guard`：Context compaction 可能遺失 Security Findings，今天已修正

**類型：** Agent Security / MCP Scan / context integrity / observability  
**來源：**
- https://github.com/Tencent/AI-Infra-Guard/commit/dd6bd54655c9ff5fb7351f4299b56916f09ec6da
- https://github.com/Tencent/AI-Infra-Guard/pull/628
- https://github.com/Tencent/AI-Infra-Guard

#### 發生了什麼變化

2026-09-08，`Tencent/AI-Infra-Guard` 合入 `fix(mcp-scan): preserve security findings in context compaction prompt`。

原本 `mcp-scan` 的 compact prompt 會優先保留 current task、errors、final code、system context、design decisions 等資訊，但沒有把「已找到的 security findings」視為不可丟失 state。

新的模板把 security findings 提升到最高優先級，要求逐條保留：

- confirmed / suspected 狀態
- `file:line`
- `risk_type`
- evidence 摘要
- confidence

並新增 `<security_findings>` 區塊與 regression test，明確禁止在壓縮時合併或刪除 security finding 條目。

#### 威脅模型與攻擊前提

這不是傳統 adversary 直接輸入一段 prompt 就能利用的漏洞，而是 **long-running security agent 的 state-loss failure**：

1. Agent 已在早期 tool calls 找到重要漏洞。
2. 對話太長，runtime 觸發 context compaction。
3. 摘要器把 security finding 視為「過往細節」壓掉。
4. 後續 Agent 不再知道該 finding，最終 report 漏報。

若攻擊者可以刻意製造大量低價值 context，理論上可能放大這類風險；但目前 commit 本身沒有證明存在可利用的 adversarial context-flooding attack，因此這一點只應視為合理推論。

#### 可能造成的影響

- 已發現漏洞在 final report 消失
- finding 與 evidence 脫鉤
- confidence / file location 遺失，造成不可重現
- Agent restart / compaction 後錯誤判斷「尚未發現問題」
- 安全稽核的 audit completeness 降低

#### 攻擊鏈位於哪一層

```text
Tool / Scanner Findings
        ↓
Agent Working Context
        ↓
Context Compaction   ← failure point
        ↓
Future Reasoning
        ↓
Final Security Report
```

主要屬於 **context / memory / observability integrity**，不是 input classifier 問題。

#### 現有防禦怎麼做

這次實作採用的是明確 state schema：

```text
security findings
→ 專屬結構區塊
→ 最高保留優先級
→ 不得合併 / 刪除
→ regression test 鎖定模板契約
```

這比單純在 prompt 裡寫「請記得重要資訊」更好，因為它至少把 security state 變成有格式、可測試的 contract。

#### 為什麼仍可能失效

目前 enforcement 仍主要靠 compaction prompt；test 只確認模板中存在對應標記與文字，**沒有證明模型在長 context、極端 token 壓力或 adversarial noise 下真的 100% 保留 finding**。

更強的架構應考慮：

- security finding 外置成 structured durable state
- compaction 只引用 finding IDs
- final report 從 durable finding store 重新 materialize
- finding lifecycle 有 dedupe / status / evidence hash

也就是：**不要讓安全發現的 canonical state 只存在於自然語言 context。**

#### 可安全重現的實驗

**Research Candidate：Yes — 高優先級**

建立 Security-State Compaction Fidelity Benchmark。

- **研究問題：** 長時程 security agent 經多次 compaction 後，finding 是否完整保留？
- **Baseline defense：** 一般自然語言摘要
- **Variant A：** 現在的 `<security_findings>` priority prompt
- **Variant B：** structured external finding store + context reference
- **Task set：** 受控 code/MCP scan，預埋 5–20 個可驗證 finding，中間加入大量 benign noise 與長 tool traces
- **Metrics：** finding recall、evidence retention、false merge、final-report completeness、token cost、latency、recovery after restart

### 2. `github/gh-aw`：修正「host loopback = container isolation」的錯誤安全假設

**類型：** Agent runtime / capability security / container networking / authorization  
**來源：**
- https://github.com/github/gh-aw/commit/e42a43e9cf3c993e0ccfe717034d5ce8e1076a38
- https://github.com/github/gh-aw/issues/59268
- https://github.com/github/gh-aw

#### 發生了什麼變化

2026-09-08 台北時間早上，`github/gh-aw` 修正文檔與 code comments：先前文字宣稱 delegation control port 只 publish 到 host `127.0.0.1`，因此 primary agent network、enclave executor network 與 sandbox guest「無法 route 到 control listener」。

這個說法不成立。

在 Docker bridge mode 中，`mcpg` container 內部 listener 需要 bind `0.0.0.0`；如果其他 container 與 `mcpg` co-attached 到同一個 network，它們可能直接透過 container IP 存取 listener，而不經過 host 的 `127.0.0.1` publication。

因此現在明確寫成：

> host-side loopback publication 只限制「外部如何進 host」，**不能作為 container-to-container authorization boundary**。

#### 威脅模型與攻擊前提

攻擊前提是某個 untrusted / compromised container 與 `mcpg` 共用可互通 network，且能定位並連到 delegation control listener。

這不代表它就能執行控制操作，因為真正的控制面還有 capability authentication。

#### 可能造成的影響

如果系統錯把 network topology 當成唯一安全邊界，可能導致：

- control API 被同網段 workload 掃描或連線
- 未預期 container-to-container reachability
- executor data-plane credential 被錯誤認為等價於 control-plane authority

但在目前 `gh-aw` 設計中，commit 明確指出 control plane 還有獨立 authentication，因此這次是**安全模型文件修正，不是已知 control-plane bypass**。

#### 技術機制與真正防禦

真正被依賴的 enforcement 是：

- AWF 生成 256-bit capability secret
- capability 不放進 primary agent、enclave executor 或 model sidecar 的 environment / mount
- `mcpg` 在 routing 前以 SHA-256 digest 做 constant-time verification
- control handler 與 executor-facing data plane 分離

核心 security principle：

```text
Network Reachability ≠ Authorization
```

即使 endpoint 可被碰到，也必須有獨立 capability 才能操作。

#### 與既有方法差異

很多 Agent sandbox 設計會用：

```text
localhost bind
private Docker network
container namespace
```

然後把「看起來隔離」當成 authority control。

`gh-aw` 這次修正反而提醒：network topology 應該被視為 defense-in-depth，而不是最終授權根據。更可靠的 boundary 應該是：

```text
Reachable endpoint
→ explicit authentication
→ scoped capability
→ separate control handler
→ policy enforcement
```

#### 可安全重現的實驗

**Research Candidate：Yes**

建立 Agent Container Boundary Matrix：

- **研究問題：** 不同 Docker/network 組態下，哪些 endpoint 實際可達？可達是否等於可操作？
- **Baseline defense：** 只靠 host loopback / Docker topology
- **Variant defense：** topology + independent capability authentication
- **Task set：** 多 container、bridge / host / isolated network 組態，測 data plane / control plane reachability 與授權
- **Metrics：** unintended reachability、unauthorized control success、false deny、latency overhead、operator complexity

### 3. 新論文：Indirect Prompt Injection 應該被視為 Test-Time Search，而不是固定 ASR

**類型：** Prompt Injection / adaptive red teaming / evaluation methodology  
**來源：**
- https://arxiv.org/abs/2609.04495

論文：`Rethinking Indirect Prompt Injection as a Test-Time Search Problem`

#### 發生了什麼變化

這篇 2026-09-03 提交、目前進入本週研究雷達的論文，將 **indirect prompt injection（間接提示注入）** 重構成一個 task-dependent test-time search problem。

作者設計一個 agentic attacker，包含：

- environment reconnaissance
- structured attack-strategy management
- 根據 victim-agent feedback 的 adaptive evaluation
- 可增加的 test-time compute budget

論文觀察到：增加 attacker test-time compute，會提升 vulnerability discovery 與 exploitation；而 strategy management 能減少重複探索，使較大 budget 仍持續有效。

#### 為什麼重要

很多 Prompt Injection benchmark 會報：

```text
Defense A ASR = 5%
Defense B ASR = 12%
```

但如果 attack set 是固定的，這些數字可能只代表「對這批靜態 injection 有效」。

新的問題應該是：

> 當攻擊者可以根據你的防禦反覆搜尋、改策略、投入更多 compute 時，ASR 曲線怎麼變？

所以安全評測不應只有單一 ASR，而應報告：

```text
ASR = f(attacker search algorithm, feedback access, compute budget)
```

#### 威脅模型

攻擊者能控制 agent 會讀取的外部內容，並能在受控測試環境中根據 victim 行為反覆優化 injection。

這和「一次性塞一句固定 malicious prompt」不同，更接近真正 adversarial adaptation。

#### 攻擊鏈位於哪一層

```text
Environment / Untrusted Content
        ↓
Adaptive Attacker Search
        ↓
Indirect Prompt Injection
        ↓
Victim Agent Reasoning
        ↓
Tool / Action Attempts
```

主要涵蓋 **input / context / tool-use trajectory**。

#### 現有防禦為什麼可能失效

靜態 classifier、keyword filter、固定 guard prompt 可能對 benchmark distribution 過度適配；adaptive attacker 可以尋找：

- 更像正常資料而不像 instruction 的表達
- 任務本身存在的 ambiguity
- defense decision boundary 附近案例
- 不同 tool trajectory 下的新 attack surface

這與 `AutoDojo` 等 adaptive IPI 研究方向一致：**防禦不能只對固定攻擊集合報漂亮數字。**

#### 已知限制

目前從 abstract 可確認的是 search formulation 與 compute-scaling 結論；在沒有完整重跑作者實驗前，不應自行宣稱某個具體 defense 已被擊破到特定比例。

#### 可安全重現的實驗

**Research Candidate：Yes — 高優先級**

建立 Adaptive IPI Compute Curve Benchmark。

- **研究問題：** 同一 defense 的安全性會如何隨 attacker compute 增長而退化？
- **攻擊模型：** 受控 benchmark 中的 indirect injection，自動搜尋策略，不接觸真實第三方系統
- **Baseline defense：** system prompt / static injection filter
- **Variant defense：** action-commit policy、capability boundary、provenance-aware filtering
- **Task set：** AgentDojo 類型 tool-use 任務 + MCP / browser / email synthetic environments
- **Metrics：** ASR vs compute curve、benign task success、unsafe-action recall、false intervention、attacker tokens、victim tokens、latency

### 4. `CVE-2026-84809`：AI Security Scanner 的 Tool Visibility 本身可被 Supply Chain 繞過

**類型：** Skill supply-chain / scanner blind spot / executable artifact coverage  
**來源：**
- https://github.com/advisories/GHSA-7vc4-66f2-3f5f
- https://github.com/Tencent/AI-Infra-Guard/issues/531
- https://github.com/Tencent/AI-Infra-Guard/commit/7e0f749e3c023e5c6ab7b32fe97b3f6f2e8aeb04

#### 發生了什麼變化

GitHub Advisory Database 在 2026-09-02 收錄 `CVE-2026-84809`，指向 `Tencent/AI-Infra-Guard` 的 `skill-scan`。

根因非常值得研究：不是 LLM 沒看懂惡意程式，而是 scanner tools 根本**不讓 LLM 看見某類 runtime-reachable executable artifact**。

舊版會在多個 scanning surface 中忽略：

- `__pycache__`
- `.pyc`
- `.pyo`
- `.pyd`

因此 skill package 可以存在乾淨 source 與另外的 compiled artifact，而 scanner 的 directory tree / pre-scan 會把 compiled artifact 從 audit surface 排除。

官方 issue #531 已關閉，patch `7e0f749` 改成：

- 不再忽略 compiled bytecode
- 在 tree 中標記 `[compiled-bytecode]`
- pre-scan 遇到 compiled artifact 時主動產生 warning
- 加入專門 regression tests

#### 威脅模型與攻擊前提

攻擊者提供一個第三方 Skill / Plugin package，package 內包含 scanner 未納入分析範圍、但 runtime 可能執行的 artifact。

重要的是：這是 **scanner architecture blind spot**，不是 prompt injection。

#### 為什麼重要

這直接說明一個 AI Security Scanner 的評測錯誤：

> 「模型看到了什麼之後能不能判斷」只是一半問題；另一半是「scanner pipeline 到底有沒有把所有 executable / influential artifacts 暴露給模型」。

因此 Agent security scanner 的 threat model 必須包含：

```text
Package
 ↓
Discovery / file enumeration
 ↓
Decoder / parser
 ↓
Pre-scan filters
 ↓
LLM-visible audit surface
 ↓
LLM reasoning
```

任何一層漏掉內容，後面模型再強都沒用。

#### 與一般 SAST / malware scanning 的差異

LLM Agent scanner 常強調「能理解語意、推理多步攻擊」。但 traditional scanner 的基本 coverage discipline 仍然不能少：

- executable artifact enumeration
- archive / generated file handling
- symlink / hidden path coverage
- decoder failures
- binary / bytecode / native extension policy

AI reasoning 不能取代 audit-surface completeness。

#### 可安全重現的實驗

**Research Candidate：Yes**

建立 Skill / MCP Scanner Audit-Surface Completeness Suite。

- **研究問題：** scanner 是否能發現所有 runtime-reachable、policy-relevant artifacts？
- **攻擊模型：** 只使用 benign marker payload，不執行破壞行為
- **Baseline defense：** 現有 scanner default filters
- **Variant defense：** full artifact enumeration + explicit unsupported-artifact warning
- **Task set：** source、bytecode、archive、hidden file、symlink、generated config、native extension 等 packaging variants
- **Metrics：** artifact discovery recall、false SAFE rate、unsupported-artifact visibility、scan latency、false positive、LLM token cost

### `CVE-2026-86237` / `openagents-org/openagents` SSRF 爭議

2026-09-07 GitHub Advisory Database 收錄一則 **unreviewed** advisory，聲稱 `OpenAgents` 的 `test_default_model` endpoint 接受使用者提供的 `base_url`，可能造成 SSRF。

來源：
- https://github.com/advisories/GHSA-969x-2pm2-x3hx
- https://github.com/openagents-org/openagents/issues/566
- https://github.com/openagents-org/openagents/blob/develop/sdk/src/openagents/sdk/transports/http.py

這一項目前**不升為 confirmed finding**，原因是證據存在衝突：

- advisory / 原始 issue 主張 endpoint 未做 authorization 且 `base_url` 可流入 HTTP client；
- maintainer 於 8/31 關閉 issue，表示 HTTP transport 已變更、報告不再適用；
- 但截至今天檢視 `develop` 的 `test_default_model` function，仍可看到 `base_url` 被讀入並交給 provider creation，function 本體沒有明顯 `_require_admin()` 呼叫。

目前尚未完整驗證 route registration / upstream middleware 是否已在別處加上 authorization，因此最正確的狀態是：**值得重現驗證，但不能只因 NVD / GitHub unreviewed advisory 就宣稱當前版本確定可利用。**

下一步若要升級成 Research Candidate，應在本地 isolated environment 做 route-level auth tracing 與 network egress mock，不碰真實 metadata / internal services。

## 今日安全架構綜合觀察

今天四個主題表面上完全不同：context compaction、Docker networking、prompt injection benchmark、Skill scanner bytecode coverage；但其實都指向同一個核心問題：

> **Agent Security 最危險的錯誤，常發生在模型推理「之外」的系統層。**

可以整理成四種 non-model failure：

```text
1. State loss
   security finding 在 compaction 後消失

2. Authority misconception
   把 network topology 誤認成 authorization

3. Evaluation under-modeling
   只測固定 injection，不讓 attacker adaptive search

4. Observation blind spot
   scanner tool 沒把 runtime artifact 暴露給 LLM
```

因此值得持續採用這個設計原則：

```text
Untrusted Input / Artifact
        ↓
Complete + Provenance-aware Observation
        ↓
LLM Reasoning
        ↓
Durable Security State
        ↓
Typed Proposed Action
        ↓
External Policy / Capability Check
        ↓
Sandboxed Execution
        ↓
Auditable Outcome
```

這比單純追求「更會拒絕 prompt injection 的模型」更接近 production-grade Agent Security。
