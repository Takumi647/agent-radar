# Agent Radar — 2026-09-06

> 研究範圍：截至 2026-09-06（Asia/Taipei）可取得的公開資訊。本日為第一份報告，因此刻意優先採用第一手來源與具體實作變更，而不是追求廣泛但低訊號的生態盤點。

## 每日摘要

- **GitHub 正在把 Agent 委派（delegation）明確做成 control plane 問題。** `github/gh-aw-mcpg` 今天合入新的 `github-repository-delegation-v1`，包含持久化 delegation state、capability-gated 控制操作、私有 control channel、generation 追蹤與經過遮蔽的 audit events。這比「又多一個 orchestration framework」更值得注意，因為它直接處理被委派 Agent 到底如何取得權限、如何被限制與撤銷。
- **Skills over MCP 正從概念走向可實作的 wire contract。** MCP Working Group 在 9 月 4 日加入 SEP-2640 的 stable-format 規格文件。真正重要的不只是「Skill 存在」，而是 Skill 可能成為可由遠端發現與配送的結構化 context，並且帶有 host-side loading 與 security rules。目前 Working Group 仍明確標示為 experimental，因此不能描述成已正式完成標準化。
- **GPT-6 Astra 提高了 computer-use 與 long-horizon agent 的能力基準。** OpenAI 公布的數據顯示，相較 GPT-5.6 Sol，Astra 在 computer-use 任務有明顯提升，也更強調 intent adherence。值得研究的問題不再只是「模型更聰明」，而是：更強模型是否能減少 delegation、retry、context reset 與其他 harness complexity？
- **GitHub Agentic Workflows 值得當成 Agent infrastructure 追蹤，而不只是 Copilot 功能。** 它把 Markdown Agent 定義編譯成 GitHub Actions，支援多種 engine，預設讓 Agent job 處於 sandboxed / read-only 狀態，再把實際 write 隔離到受控的 `safe-outputs` job。近期 commit 持續處理 MCP routing、模型相容性、execution budget 與 safe-output 行為。

## 重要進展

### 1. GitHub MCP Gateway 加入 repository delegation control plane

**類型：** 開源 Repository / Runtime Infrastructure  
**來源：**
- https://github.com/github/gh-aw-mcpg/commit/0ba9575ba3bd0844cdd8b0e99b3acd4a87702332
- https://github.com/github/gh-aw-mcpg
- https://github.com/github/gh-aw-firewall/commit/2822f043d8fb6c1e70e15c23ef14ad99e1c77100

#### 發生了什麼

以 Asia/Taipei 時間計算，`github/gh-aw-mcpg` 在 2026-09-06 合入 `github-repository-delegation-v1` 的核心實作。這次變更新增 delegation state store，以及一條獨立 control path，用來建立／確認、撤銷、過期與 reconciliation 被委派的 repository identity。

實作也加入明確的 delegation envelope、policy generation、state path、control listener address 與 control capability key。Delegation mode 也被刻意與既有 enclave proxy mode 分開。

#### 為什麼重要

很多 multi-agent 範例把 delegation 當成純邏輯 orchestration：Lead Agent 把任務交給 Subagent。但 production system 還要回答更難的問題：**Subagent 到底拿到什麼權限？可以存取哪個 repository？能用多久？依哪個 policy generation？權限如何撤銷？操作如何 audit？**

GitHub 的做法是把這些問題視為 control-plane primitive，而不是只靠 prompt convention。這對 long-running coding agent、ephemeral subagent、cross-repository automation，以及所有希望做到 least privilege delegation 的 runtime 都很重要。

#### 技術機制

已合入程式碼可看到幾個重要機制：

- controller-only capability value：`MCP_GATEWAY_DELEGATION_CONTROL_KEY`
- 與 executor-facing proxy 分離的 private delegation control listener
- 持久化 delegation state，加上 policy `generation`
- delegation envelope 使用 strict JSON 驗證
- lifecycle operation 有明確 outcome，例如 admitted、confirmed、denied、revoked、mismatch、expired
- audit event 保留結構化 correlation ID，但 repository selector、run ID、handle 在寫 log 前會先 hash
- 明確禁止 delegation mode 與 enclave proxy mode 在同一 process path 混用

另一個相關 firewall change 定義了 dynamic repository enclave contract，表示 repository-scoped isolation 與 dynamic delegation 很可能被設計成互補的兩層，而不是只依賴單一 global sandbox boundary。

#### 與既有方法的差異

一般 Agent framework 多半在 application layer 實作 delegation：建立 child agent、傳入 task、限制部分 tools，然後相信 framework 能守住邊界。

GitHub 的方向更接近 capability-based infrastructure。Delegation state 位於 model conversation 之外，由 gateway / control plane 執行。這讓 authorization state 可以被獨立檢視、撤銷、持久化與 audit，而不依賴模型「以為自己能做什麼」。

#### 證據與信心

**信心：實作事實為高；較廣泛的架構推論為中。**

Control-plane code 已直接出現在 merged commit。尚未確定的是 GitHub 最終會把這個 delegation model 暴露到什麼程度、scale 下的行為，以及它是否會成為 Agentic Workflows 之外可重用的通用 pattern。

#### 可做的實驗

建立一個最小 delegation benchmark：一個 Lead Coding Agent 搭配多個 ephemeral worker，比較：

1. prompt-only / tool-whitelist delegation
2. 每個 worker 使用 sandbox + static credentials
3. capability-gated gateway delegation，具 explicit create/revoke lifecycle

注入 stale worker、嘗試存取第二個 repository、重複 delegation request、已撤銷 credential 等失敗情境。衡量 policy violation、recovery behavior、operational complexity 與 auditability。

**研究候選：是**

### 2. MCP Skills Extension 加入 SEP-2640 stable-format 規格文件

**類型：** Protocol Proposal / Open-source Specification  
**來源：**
- https://github.com/modelcontextprotocol/ext-skills/commit/f1f8605b72274e8ab667b72194103fe8096e9552
- https://github.com/modelcontextprotocol/ext-skills
- https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2640

#### 發生了什麼

9 月 4 日，Skills Over MCP Working Group 新增 `specification/stable/skills.mdx`，把 SEP-2640 Skills Extension（`io.modelcontextprotocol/skills`）整理成正式 spec format。

Working Group repository 明確標示目前仍是 **experimental**，而 SEP-2640 PR 才是 source of truth。因此這次真正的變化是 specification maturity 與 implementation clarity 提升，而不是「已成為正式 MCP 標準」。

#### 為什麼重要

MCP 原本主要解決的是「Agent 可以碰哪些 tool / data？」。Skill 解決的是另一層問題：**Agent 應該如何正確組合與使用這些 capability 才能完成工作？**

如果 Skill discovery / distribution 能互通，MCP server 就可能同時配送 tool 與使用這些 tool 的 structured know-how。這會支援 dynamic update、remote skill distribution、progressive disclosure、multi-server composition，以及企業環境的 skill policy，而不必要求每個 client 手動安裝相同 instruction bundle。

#### 技術機制

Working Group 目前把 Skill 視為可透過 MCP 傳遞的 structured context。v1 工作方向聚焦在明確的 skill discovery / retrieval 與 resource manifest，而不是把全部 instruction 一次灌入 initial context。

近期 repository 裡的 implementation findings 也揭露幾個實務限制：

- Skill 可能需要 on-demand file retrieval，而不是 eager loading
- Host 需要同時考慮 server identity + skill URI，不能假設 skill name 全球唯一
- digest 與 resource manifest 對 integrity 與 approval binding 很重要
- discovery 如果反覆重新計算，可能意外形成 denial-of-service 風險
- client 端的實作面比單純 MCP resource reader 更廣，會碰到多個 host surface

因此這個方向不是把 Skill 當靜態 prompt file，而是把 **progressive disclosure** 與 provenance / integrity 一起處理。

#### 與既有方法的差異

目前 Agent Skill 多半是 local file 或 application-specific bundle。Tool definition 說明「可以做什麼」，而 orchestration knowledge 則散落在 system prompt、repository file、plugin 或人工安裝的 skill 中。

Skills over MCP 嘗試讓 remote MCP server 的 Skill discovery / distribution 具互通性。Local Skill 優化的是簡單 packaging；MCP-distributed Skill 則更偏向 dynamic discovery、remote update、multi-server environment 與 policy-controlled enterprise distribution。

#### 證據與信心

**信心：Working Group 的方向為高；最終標準形狀為中。**

Repository、SEP、implementation findings 與新的 spec-format 文件都是第一手來源。但 repository 本身明確警告這仍是 exploratory work，不能當成最終官方 recommendation。

#### 可做的實驗

把同一個非簡單 multi-tool workflow 做成兩種版本：

1. 本機安裝的 `SKILL.md`
2. 透過 MCP discovery / retrieval 的 Skill

測量 initial context token、discovery latency、cache behavior、update propagation、server 變更 Skill 後的 failure handling，以及不同 Agent Host 對同一 remote Skill 的 interoperability。

**研究候選：是**

### 3. GPT-6 Astra 提高 computer-use 與 long-horizon agent 的能力基準

**類型：** Model Release  
**來源：**
- https://openai.com/index/gpt-6-astra/
- https://openai.com/zh-Hant/products/release-notes/

#### 發生了什麼

OpenAI 在 9 月 3 日發布 GPT-6 Astra，先提供給部分組織，之後預計逐步擴大。OpenAI 將 Astra 定位為 software engineering、browsing、computer use、research 與 complex multi-step work 的重大進展。

對 Agent Engineering 而言，最值得注意的公開比較之一是 OSWorld 2.0 latency simulation：OpenAI 報告 Astra 約 **72.6%，每個 task 約 40 分鐘**；GPT-5.6 Sol 約 **65.7%，每個 task 約 75 分鐘**。OpenAI 也公布新的 intent-boundary evaluation：在未額外加 guard 的情況下，Astra 超出授權目標的比例為 0%，GPT-5.6 Sol 則為 48%。

#### 為什麼重要

Agent architecture 有一部分其實是在補 model weakness。Harness 之所以塞入 retry、decomposition、context reset、verification loop、permission gate 與 delegation rule，是因為模型本身無法可靠完成整段長任務。

當 model capability 大幅提升，部分舊假設可能失效。真正值得問的不是「Astra 比較聰明嗎？」，而是：**哪些 agent scaffolding 可以因此移除？哪些仍然必須保留，因為它們是在 enforce system boundary，而不是補模型能力？**

#### 技術機制

OpenAI 尚未公開足以把這些提升歸因到特定 agent-runtime mechanism 的完整 training / runtime 細節。目前公開證據主要是 capability / safety evaluation 與產品行為。

因此在 Agent Radar 裡，Astra 應被視為新的 **model substrate**，而不是新的 open agent framework。

#### 與既有方法的差異

最有意思的比較不是 Astra 對另一個模型，而是「更強的單 Agent」對「在較弱模型外再疊更多 orchestration」。如果更強單模型能以更少 recovery 完成更長任務，那 delegation / fan-out 可能應該從 default strategy 退回 conditional optimization：只有在 parallelism、specialization、isolation 或 context separation 有可測量收益時才使用。

#### 證據與信心

**信心：模型發布與官方 benchmark 數字為高；架構推論為中。**

Benchmark 目前主要是 vendor-reported。仍需要 independent agent-runtime comparison、cost-normalized evaluation 與 harness-matched experiment。

#### 可做的實驗

未來 API 可取得時，用相同 tool、sandbox、context policy 與 task set，對 GPT-6 Astra、GPT-5.6 Sol 與另一個 frontier coding model 做 harness-matched evaluation。比較：

- task success / product-quality score
- model cost
- wall-clock latency
- tool call 次數
- retry / recovery 次數
- context compaction 次數
- delegation frequency 與 marginal benefit
- boundary violation 或 unnecessary action

**研究候選：是**

### GitHub Agentic Workflows (`github/gh-aw`)

**來源：**
- https://github.com/github/gh-aw
- https://github.com/github/gh-aw/commit/34f1e023839fd606efeee668633db3f1a8eb5aaf
- https://github.com/github/gh-aw/commit/b3d0bd9e9981ea46c1f104e8477254d953a841fb
- https://github.com/github/gh-aw/commit/988d3d9a82f36555d39062ce169b228b2b36571c

`gh-aw` 越來越值得當成 repository-native Agent 的 reference architecture。它用 Markdown + YAML frontmatter 定義 agentic workflow，編譯成一般 GitHub Actions workflow，支援多種 engine（包含 Copilot、Claude Code、Codex、Gemini、Pi），並預設讓 Agent job 使用 sandboxed / read-only access，再把 write 交給 scope 明確的 `safe-outputs` job。

今天的 commit 包含：把某個 workflow 的 GitHub operation 改經 MCP proxy、引導 Codex workflow 使用相容的 Copilot model、提高 code-scanning fixer 的 execution budget，以及替 safe outputs 加入 deterministic footer template。

單看每一筆都不算大改，但放在一起看，會很清楚暴露 Agent 長期跑在 CI 之後必須處理的 production problem：provider / model compatibility、tool egress mediation、deterministic post-processing、execution budget 與 write isolation。

**判斷：持續追蹤。** 即使最後不直接採用 GitHub Actions 這套實作，它仍非常適合當 production-pattern 來源。

## Research Candidates

### Candidate：Capability-based Repository Delegation

- **問題：** Gateway-level 的顯式 delegation，是否真的比 tool whitelist 或 per-agent static credential 更安全、更容易操作？
- **為什麼現在值得測：** GitHub 已經合入實際 open-source implementation，而不只是架構描述。
- **建議實驗：** 用三種 authorization architecture 跑同一套 multi-agent coding workflow，並注入 stale、revoked、cross-repository access attempt。
- **Baseline：** Prompt / tool whitelist；sandbox + static token；capability-gated delegation control plane。
- **衡量指標：** policy violation、revocation 成功率、recovery time、audit completeness、implementation complexity、latency overhead。

### Candidate：Skills over MCP vs Local Skills

- **問題：** Remote Skill discovery / distribution 在什麼條件下能優於 local skill packaging，而且不會帶來不可接受的 latency、trust 或 consistency cost？
- **為什麼現在值得測：** SEP-2640 已經成熟到可以做 realistic prototype comparison，但 Working Group 仍在積極調整設計。
- **建議實驗：** 在至少兩種 Agent Host 上，把同一個 non-trivial multi-tool workflow 分別做成 local 與 MCP-distributed 版本。
- **Baseline：** Local `SKILL.md` / plugin bundle。
- **衡量指標：** initial context tokens、discovery latency、skill-loading tokens、cache hit、update propagation、integrity failure、cross-host compatibility。

### Candidate：Strong Model vs Orchestration Complexity

- **問題：** Frontier model 越來越強之後，delegation 要在什麼情況下才能提升足夠品質，值得支付額外 cost 與 coordination complexity？
- **為什麼現在值得測：** Astra 公布的 computer-use 提升提供了一個新的 model substrate，值得重新檢驗舊 harness assumption。
- **建議實驗：** 相同 task、tool、sandbox，比較 single-agent 與 delegated variant，分別跑 compute/cost-matched 與 unconstrained setting。
- **Baseline：** GPT-5.6 Sol 或其他成熟 frontier-model harness。
- **衡量指標：** task quality、model cost、latency、context use、delegation count、retry count、coordination failure。

| Repository | 在 Agent Stack 裡的角色 | 判斷 |
|---|---|---|
| `chuspeeism/dashi-taskboard` | Task ownership / Human control surface | 借 claim / optimistic concurrency pattern，不當第二個 truth DB |
| `DeusData/codebase-memory-mcp` | Persistent code intelligence | **立即 benchmark** |
| `github/gh-aw` | Agent execution + safe write boundary | **最高優先級研究** |

| `volcengine/OpenViking` | Long-term context / memory / skills | V2 導入，永遠只做 advisory context |

## 核心 synthesis

這九個 repo 並不是要選一個當「終極 Agent Framework」。它們真正有價值的是分別解決 Agent Stack 的不同責任：

```text
Human / Product Authority
        ↓
GitHub Issue + Git Tree
        ↓
Deterministic workflow-driver
        ↓
Fable / Codex / Opus
        ↓
Structured Agent Output
        ↓
Validated Runner Write Boundary
        ↓
Git / Issue / PR / Actions
        ↓
Acceptance
        ↓
Derived Knowledge / Memory
```

建議維持四個邊界：

> **GitHub 保存 Truth；Runner 保存 Authority；Agent 提供 Intelligence；Graph / Wiki / Memory 提供 Context。**

### 最值得直接吸收的 patterns

**Symphony：**不要複製它整個 workflow semantics，而是吸收 polling、bounded concurrency、per-issue workspace、retry queue、exponential backoff、reconciliation 與 restart recovery。

**gh-aw：**把 Agent reasoning 與 GitHub write authority 切開。Agent 不持 broad write credential，只產生 structured proposed mutation；Runner 驗證 schema、path、state transition、HEAD / frozen SHA 與 allowed mutation 後才寫 GitHub。

**Dashi：**借 task claim / ownership / optimistic concurrency，不要再建立一份與 GitHub Issue 平行的 canonical task database。

**Codebase-Memory / Graphify：**應做 A/B/C benchmark，而不是兩套都裝。比較 `native rg + read`、Codebase-Memory、Graphify 的 correctness、grounding、tokens、tool calls、wall time、index latency 與 stale-result rate。

**OpenWiki：**適合放在 accepted change 之後，維護 source-grounded derived knowledge；不能取代 OpenSpec 或 Git tree 的 authority。

**OpenViking：**progressive context loading 很值得研究，但 memory 必須保持 advisory。即使 OpenViking 完全不可用，fresh agent 仍必須能只靠 GitHub durable artifacts 恢復工作。

**Archify：**很適合在 Spec Freeze 與 PR Acceptance 產生 Before / Delta / After architecture artifact，用 deterministic validation 輔助 reviewer 看真正的架構變化。

## 五個下一步 Research Candidates

1. **Workflow-driver vs Symphony failure recovery**：agent crash、stale HEAD、auth blocked、issue state change、machine restart。
2. **gh-aw-style safe write boundary**：Agent 直接持 credential vs structured mutation → Runner validation → scoped write。
3. **Code Context A/B/C**：native search vs Codebase-Memory vs Graphify。
4. **OpenWiki stale-claim experiment**：刻意改 code 讓 wiki 失效，測 stale claim precision / recall。
5. **Archify spec → implementation delta**：比較 reviewer 只看 diff/spec 與額外看 Before/Delta/After 的 review quality。
