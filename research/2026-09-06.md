# Agent Radar — 2026-09-06

> Research window: public information reviewed through 2026-09-06 (Asia/Taipei). This first brief intentionally favors primary sources and concrete implementation changes over broad ecosystem coverage.

## Executive summary

- **GitHub is turning agent delegation into an explicit control-plane problem.** A new `github-repository-delegation-v1` implementation landed in `github/gh-aw-mcpg` today, with durable delegation state, capability-gated control operations, a private control channel, generation tracking, and redacted audit events. This is a stronger architectural signal than another orchestration framework release because it addresses how delegated agents are actually authorized and contained.
- **Skills-over-MCP is moving from concept toward an implementable wire contract.** The MCP working-group repository added a stable-format specification document for SEP-2640 on September 4. The important direction is not merely "skills exist": skills become remotely discoverable/distributable context with explicit host-side loading and security rules. The working group still labels the project experimental, so this should not be described as a finalized MCP standard.
- **GPT-6 Astra materially raises the capability ceiling for computer-use and long-horizon agents.** OpenAI reports large gains over GPT-5.6 Sol on computer-use tasks and emphasizes better intent adherence. The interesting research question is now whether stronger models reduce the amount of harness complexity, delegation, retry logic, and context-management scaffolding needed for real agent workloads.
- **GitHub Agentic Workflows is worth tracking as infrastructure, not just as a Copilot feature.** Its design compiles Markdown agent definitions into GitHub Actions, supports multiple engines, defaults agent execution to sandboxed/read-only behavior, and separates model reasoning from validated write operations. Recent commits continue tightening MCP routing, model compatibility, execution budgets, and safe-output behavior.

## Notable developments

### 1. GitHub MCP Gateway adds repository-delegation control plane

**Type:** Open-source repository / Runtime infrastructure  
**Sources:**
- https://github.com/github/gh-aw-mcpg/commit/0ba9575ba3bd0844cdd8b0e99b3acd4a87702332
- https://github.com/github/gh-aw-mcpg
- https://github.com/github/gh-aw-firewall/commit/2822f043d8fb6c1e70e15c23ef14ad99e1c77100

#### What changed

On 2026-09-06 Asia/Taipei time, `github/gh-aw-mcpg` merged the core of `github-repository-delegation-v1`. The change adds a delegation state store and a separate control path for creating/confirming, revoking, expiring, and reconciling delegated repository identities.

The implementation also introduces explicit configuration for a delegation envelope, policy generation, state path, control-listener address, and a control capability key. Delegation mode is deliberately kept separate from the existing enclave proxy mode.

#### Why it matters

Most multi-agent examples model delegation as a logical orchestration decision: a lead agent asks a subagent to do work. Production systems additionally need to answer a harder question: **what authority does the delegated worker receive, for which repository, for how long, under what policy generation, and how is that authority revoked or audited?**

GitHub's implementation treats those questions as control-plane primitives rather than prompt conventions. That makes it relevant to long-running coding agents, ephemeral subagents, cross-repository automation, and any runtime that wants least-privilege delegation.

#### Technical mechanism

The merged code shows several notable mechanisms:

- a controller-only capability value (`MCP_GATEWAY_DELEGATION_CONTROL_KEY`)
- a private delegation control listener separate from the executor-facing proxy
- persisted delegation state plus a policy `generation`
- delegation envelopes validated as strict JSON
- lifecycle operations with explicit outcomes such as admitted, confirmed, denied, revoked, mismatch, and expired
- audit events that keep structural correlation IDs but hash repository selectors, run IDs, and handles before logging
- an explicit prohibition on combining delegation and enclave proxy modes in the same process path

A related firewall change defines a dynamic repository-enclave contract, suggesting that repository-scoped isolation and dynamic delegation are being designed as cooperating layers rather than relying on one global sandbox boundary.

#### Difference from existing approaches

Typical agent frameworks implement delegation at the application layer: create a child agent, pass a task, optionally give it a tool subset, then trust the framework to enforce the boundary.

The GitHub direction is closer to capability-based infrastructure. Delegation is represented outside the model conversation and enforced by a gateway/control plane. That makes authorization state inspectable, revocable, persistent, and auditable independently of what the model believes it can do.

#### Evidence and confidence

**Confidence: High for the implementation facts; Medium for broader architectural conclusions.**

The control-plane code is directly visible in the merged commit. What is not yet established is how broadly GitHub will expose this delegation model, how it performs at scale, or whether it becomes a reusable pattern outside Agentic Workflows.

#### Possible experiment

Build a minimal delegation benchmark with one lead coding agent and multiple ephemeral workers. Compare:

1. prompt-only/tool-whitelist delegation
2. per-worker sandbox + static credentials
3. capability-gated gateway delegation with explicit create/revoke lifecycle

Inject failures such as stale workers, attempted access to a second repository, duplicated delegation requests, and revoked credentials. Measure policy violations, recovery behavior, operational complexity, and auditability.

**Research Candidate:** Yes

### 2. MCP Skills extension gets a stable-format SEP-2640 specification document

**Type:** Protocol proposal / Open-source specification  
**Sources:**
- https://github.com/modelcontextprotocol/ext-skills/commit/f1f8605b72274e8ab667b72194103fe8096e9552
- https://github.com/modelcontextprotocol/ext-skills
- https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2640

#### What changed

On September 4, the Skills Over MCP Working Group added `specification/stable/skills.mdx`, a spec-format rendering of the SEP-2640 Skills Extension (`io.modelcontextprotocol/skills`).

The working-group repository explicitly says it is still **experimental** and that SEP-2640's pull request is the source of truth. Therefore, the important change is increased specification maturity and implementation clarity, not final standardization.

#### Why it matters

MCP originally solved the "what tools/data can this agent reach?" problem. Skills address a different layer: **how should the agent correctly use and orchestrate those capabilities to accomplish a task?**

If skill discovery/distribution becomes interoperable, a server could ship tools and the structured know-how for using them together. That enables dynamic updates, remote skill distribution, progressive disclosure, multi-server composition, and enterprise policy around skills without requiring every client to manually install matching instruction bundles.

#### Technical mechanism

The working-group material describes skills as structured context delivered through MCP. Current v1 work centers on explicit skill discovery/retrieval and resource manifests rather than dumping all instructions into the initial context.

Recent implementation findings in the repository also surface practical constraints:

- skills may need on-demand file retrieval rather than eager loading
- hosts need to reconcile server identity + skill URI, not assume a globally unique skill name
- digests and resource manifests matter for integrity and approval binding
- discovery can accidentally become a denial-of-service vector if recomputed excessively
- client implementations touch more host surfaces than a simple MCP resource reader might suggest

The direction therefore combines **progressive disclosure** with provenance/integrity concerns rather than treating a skill as a static prompt file.

#### Difference from existing approaches

Today, Agent Skills are often local files or application-specific bundles. Tool definitions describe operations, while orchestration knowledge lives separately in system prompts, repository files, plugins, or manually installed skills.

Skills-over-MCP attempts to make distribution and discovery interoperable across remote MCP servers. The distinction is significant: local skills optimize for simple packaging; MCP-distributed skills optimize for dynamic discovery, remote updates, multi-server environments, and policy-controlled enterprise distribution.

#### Evidence and confidence

**Confidence: High on working-group direction; Medium on eventual standard shape.**

The repository, SEP, implementation findings, and new spec-format document are primary sources. However, the repository explicitly warns that the work is exploratory and does not yet represent official MCP recommendations.

#### Possible experiment

Implement the same multi-tool workflow in two forms:

1. a locally installed `SKILL.md`
2. a skill discovered and retrieved over MCP

Measure initial context cost, discovery latency, cache behavior, update propagation, failure handling when the server changes skill contents, and how well multiple agent hosts interoperate with the same remote skill.

**Research Candidate:** Yes

### 3. GPT-6 Astra raises the baseline for computer-use and long-horizon agent capability

**Type:** Model release  
**Sources:**
- https://openai.com/index/gpt-6-astra/
- https://openai.com/zh-Hant/products/release-notes/

#### What changed

OpenAI released GPT-6 Astra on September 3, initially to a limited set of organizations with broader rollout planned. OpenAI positions Astra as a major step in software engineering, browsing, computer use, research, and complex multi-step work.

For agent engineering, one of the most relevant published comparisons is OSWorld 2.0 latency simulation: OpenAI reports Astra at **72.6% in roughly 40 minutes per task**, compared with GPT-5.6 Sol at **65.7% in roughly 75 minutes**. OpenAI also reports a new intent-boundary evaluation where an unguarded Astra went beyond the authorized target in 0% of tested cases versus 48% for GPT-5.6 Sol.

#### Why it matters

Agent architecture is partly a response to model weaknesses. Harnesses accumulate retries, decomposition logic, context resets, verification loops, permission gates, and delegation rules because the underlying model cannot reliably carry the whole task.

A substantial model capability jump can invalidate some of those assumptions. The important question is not simply "is Astra smarter?" but **which pieces of agent scaffolding become unnecessary, and which remain essential because they enforce system boundaries rather than compensate for model weakness?**

#### Technical mechanism

OpenAI has not published the full training or agent-runtime mechanism needed to attribute the gains to a specific architectural feature. The public evidence is primarily capability and safety evaluation data plus product behavior.

For this radar, Astra should therefore be treated as a changed **model substrate** rather than a new open agent framework.

#### Difference from existing approaches

The notable comparison is against building more orchestration around weaker models. If a stronger single model can perform longer end-to-end work with fewer recoveries, then delegation/fan-out may move from a default strategy toward a conditional optimization used only when parallelism, specialization, isolation, or context separation has measurable benefit.

#### Evidence and confidence

**Confidence: High that the model release and reported benchmark results are real; Medium on architecture implications.**

The benchmark numbers are vendor-reported. Independent agent-runtime comparisons, cost-normalized evaluations, and harness-matched experiments are still needed.

#### Possible experiment

When API access is available, run a harness-matched evaluation across GPT-6 Astra, GPT-5.6 Sol, and another frontier coding model using the same tools, sandbox, context policy, and task set. Compare:

- task success / product-quality score
- model cost
- wall-clock latency
- number of tool calls
- retries / recoveries
- context compactions
- delegation frequency and marginal benefit
- boundary violations or unnecessary actions

**Research Candidate:** Yes

## Existing projects with meaningful updates

### GitHub Agentic Workflows (`github/gh-aw`)

**Sources:**
- https://github.com/github/gh-aw
- https://github.com/github/gh-aw/commit/34f1e023839fd606efeee668633db3f1a8eb5aaf
- https://github.com/github/gh-aw/commit/b3d0bd9e9981ea46c1f104e8477254d953a841fb
- https://github.com/github/gh-aw/commit/988d3d9a82f36555d39062ce169b228b2b36571c

`gh-aw` is increasingly interesting as a reference architecture for repository-native agents. It defines agentic workflows in Markdown + YAML frontmatter, compiles them into ordinary GitHub Actions workflows, supports multiple engines (including Copilot, Claude Code, Codex, Gemini, and Pi), and defaults agent jobs to sandboxed/read-only access with writes passed through scoped `safe-outputs` jobs.

Today's commits include routing GitHub operations for one workflow through the MCP proxy, guiding Codex workflows toward compatible Copilot models, increasing an execution budget for a code-scanning fixer, and adding deterministic footer templates to safe outputs.

Individually these are small changes. Together they expose the operational problems that become important once agents run continuously inside CI: provider/model compatibility, tool egress mediation, deterministic post-processing, execution budgets, and write isolation.

**Assessment:** keep tracking. The project is useful as a production-pattern source even if the exact GitHub Actions implementation is not adopted elsewhere.

## Research Candidates

### Candidate: Capability-based repository delegation

- **Question:** Does explicit gateway-level delegation materially improve safety and operability over tool whitelists or per-agent static credentials?
- **Why now:** GitHub has landed a concrete open-source implementation rather than only describing the pattern.
- **Proposed experiment:** Run the same multi-agent coding workflow under three authorization architectures and inject stale/revoked/cross-repository access attempts.
- **Comparison / baseline:** Prompt/tool whitelist; sandbox + static token; capability-gated delegation control plane.
- **Useful measurements:** policy violations, successful revocation, recovery time, audit completeness, implementation complexity, latency overhead.

### Candidate: Skills over MCP vs local skills

- **Question:** When does remote skill discovery/distribution outperform local skill packaging without creating unacceptable latency, trust, or consistency costs?
- **Why now:** SEP-2640 has moved far enough to support realistic prototype comparisons, while the working group is still actively shaping the design.
- **Proposed experiment:** Implement one non-trivial multi-tool workflow in both local and MCP-distributed forms across at least two agent hosts.
- **Comparison / baseline:** Local `SKILL.md` / plugin bundle.
- **Useful measurements:** initial context tokens, discovery latency, skill-loading tokens, cache hits, update propagation, integrity failures, cross-host compatibility.

### Candidate: Strong-model vs orchestration complexity

- **Question:** As frontier models improve, when does delegation still increase quality enough to justify extra cost and coordination complexity?
- **Why now:** Astra's reported computer-use jump provides a new model substrate against which old harness assumptions should be re-tested.
- **Proposed experiment:** Same tasks, same tools, same sandbox; compare single-agent and delegated variants under compute/cost-matched and unconstrained settings.
- **Comparison / baseline:** GPT-5.6 Sol or another established frontier-model harness.
- **Useful measurements:** task quality, model cost, latency, context use, delegation count, retry count, coordination failures.

這次額外深入研究了以下九個與目前 AI Workflow / Agent Runtime 設計高度相關的開源專案：

| Repository | 在 Agent Stack 裡的角色 | 判斷 |
|---|---|---|
| `chuspeeism/dashi-taskboard` | Task ownership / Human control surface | 借 claim / optimistic concurrency pattern，不當第二個 truth DB |
| `DeusData/codebase-memory-mcp` | Persistent code intelligence | **立即 benchmark** |
| `github/gh-aw` | Agent execution + safe write boundary | **最高優先級研究** |
| `Graphify-Labs/graphify` | Code + docs knowledge graph | 與 Codebase-Memory / native search 對打 |
| `langchain-ai/openwiki` | Source-grounded durable repo knowledge | Workflow 穩定後導入 |
| `nashsu/llm_wiki` | Personal research / Knowledge OS | 適合個人研究，不進核心 control plane |
| `openai/symphony` | Scheduler / workspace / retry / reconciliation | **最高優先級研究** |
| `tt-a1i/archify` | Architecture verification artifact | 低耦合、適合快速 PoC |
| `volcengine/OpenViking` | Long-term context / memory / skills | V2 導入，永遠只做 advisory context |

## 核心 synthesis

這九個 repo 並不是要選一個當「終極 Agent Framework」。它們真正有價值的是分別解決 Agent Stack 的不同責任：

```text
Human / Product Authority
        ↓
GitHub Issue + Git Tree
        ↓
Deterministic workflow-driver
        ↓
Fable / Codex / Opus
        ↓
Structured Agent Output
        ↓
Validated Runner Write Boundary
        ↓
Git / Issue / PR / Actions
        ↓
Acceptance
        ↓
Derived Knowledge / Memory
```

建議維持四個邊界：

> **GitHub 保存 Truth；Runner 保存 Authority；Agent 提供 Intelligence；Graph / Wiki / Memory 提供 Context。**

### 最值得直接吸收的 patterns

**Symphony：**不要複製它整個 workflow semantics，而是吸收 polling、bounded concurrency、per-issue workspace、retry queue、exponential backoff、reconciliation 與 restart recovery。

**gh-aw：**把 Agent reasoning 與 GitHub write authority 切開。Agent 不持 broad write credential，只產生 structured proposed mutation；Runner 驗證 schema、path、state transition、HEAD / frozen SHA 與 allowed mutation 後才寫 GitHub。

**Dashi：**借 task claim / ownership / optimistic concurrency，不要再建立一份與 GitHub Issue 平行的 canonical task database。

**Codebase-Memory / Graphify：**應做 A/B/C benchmark，而不是兩套都裝。比較 `native rg + read`、Codebase-Memory、Graphify 的 correctness、grounding、tokens、tool calls、wall time、index latency 與 stale-result rate。

**OpenWiki：**適合放在 accepted change 之後，維護 source-grounded derived knowledge；不能取代 OpenSpec 或 Git tree 的 authority。

**OpenViking：**progressive context loading 很值得研究，但 memory 必須保持 advisory。即使 OpenViking 完全不可用，fresh agent 仍必須能只靠 GitHub durable artifacts 恢復工作。

**Archify：**很適合在 Spec Freeze 與 PR Acceptance 產生 Before / Delta / After architecture artifact，用 deterministic validation 輔助 reviewer 看真正的架構變化。

## 五個下一步 Research Candidates

1. **Workflow-driver vs Symphony failure recovery**：agent crash、stale HEAD、auth blocked、issue state change、machine restart。
2. **gh-aw-style safe write boundary**：Agent 直接持 credential vs structured mutation → Runner validation → scoped write。
3. **Code Context A/B/C**：native search vs Codebase-Memory vs Graphify。
4. **OpenWiki stale-claim experiment**：刻意改 code 讓 wiki 失效，測 stale claim precision / recall。
5. **Archify spec → implementation delta**：比較 reviewer 只看 diff/spec 與額外看 Before/Delta/After 的 review quality。
