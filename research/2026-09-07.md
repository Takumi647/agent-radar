# Agent Radar — 2026-09-07

> 研究窗口：截至 2026-09-07（Asia/Taipei）上午。今日優先追蹤「真正影響 Agent 權限邊界、安全控制面與 context infrastructure」的變更，不以 star 數或宣傳熱度排序。

## 執行摘要

- **GitHub Agentic Workflows 把動態跨 repository 存取正式收進 compiler policy。** `github/gh-aw` 在台北時間今天早上合入 dynamic repository enclave policy：主 Agent 可以在執行時選擇允許範圍內的一個 repository，但不是把 GitHub token 或 repository list 直接交給模型，而是由 compiler 產生 policy envelope，再交給 `gh-aw-mcpg` 的 delegation control plane 執行。這是「Agent delegation 應該由控制面授權，而不是 prompt 約定」的具體落地。
- **`codebase-memory-mcp` 修到一個非常值得研究的 Windows security boundary 問題。** 原先為了解決 path separator 不一致而做的 normalization，會讓 sensitive-root containment 在 Windows 上失效，使 `$HOME` 可能被誤判為可 index / watch。修正方式不是「全域 normalize path」，而是只在需要比較 job identity 的私有副本做 separator folding，保留 policy root 的 canonical native spelling。這是一個典型的 security canonicalization lesson。
- **OpenAgentFlow 值得納入 AI Security 主線研究。** 它把 GUI、API、tool 與 LLM-generated actions 正規化成共同 `AgentEvent`，並在真正執行前放一個共享 Policy Enforcement Point。v2（9/2）報告在 1,220-case AgentDojo-Traj split 上達到 96.59% unsafe-action recall、1.96% safe false-intervention rate。它與 `gh-aw safe outputs`、delegation control plane 的共同方向很明確：**security boundary 應該位於 action commit layer，而不是只靠 model prompt。**
- **Tencent `AI-Infra-Guard` 適合作為新的 Security Research Candidate。** 它已把 Agent Scan、Skill Scan、MCP Scan、AI infra CVE、jailbreak evaluation 整在同一套 red-teaming 平台，近期版本還加入 Skill instruction hijacking、memory poisoning、tool hijacking、MCP command injection、credential exfiltration 與 LLM API poisoning 等檢測。值得拿來當我們 Security Radar 的現成 baseline，而不是直接相信其 benchmark 宣稱。

## 重要發展

### 1. GitHub `gh-aw`：Dynamic Repository Enclave Policy

**類型：** Agent runtime / authorization / sandbox / delegation  
**來源：**
- https://github.com/github/gh-aw/commit/f345d0949131b2918fe23f27985c64219bdeeb37
- https://github.com/github/gh-aw
- https://github.com/github/gh-aw-mcpg

#### 發生了什麼變化

`github/gh-aw` 在 2026-09-06 14:00 UTC（台北時間 9/6 晚間）合入 compiler 對 **dynamic repository enclave policy** 的支援；而與此配套的 threat-spec / safe-output 相關更新持續到台北時間 9/7 早上。

新的 `dynamic:` agent enclave 允許 primary agent 在執行時選擇一個「事先被 policy 允許的 repository」，而不需要把所有 repo 都靜態列在 frontmatter。

可限制的欄位包含：

- `allowed-owners` / `allowed-repositories`
- 固定 `sensitivity`
- 封閉的 `github-policy`（目前只允許 `github-repository-read-v1`）
- `max-repositories`
- invocation / output bytes / execution seconds quotas
- audit labels
- 絕對到期時間 `expires-at`
- CPU / memory / PID / tmpfs / timeout 上限

compiler 會產生 dynamic policy envelope，並由 `gh-aw-mcpg` 啟動 `github-repository-delegation-v1` controller。最重要的是：**delegation-control capability 不會放進 primary agent 或 enclave agent 的 environment。**

#### 為什麼重要

這直接回答了 multi-agent 系統一個核心問題：

> Lead Agent 想臨時派 worker 去讀另一個 repository 時，到底要不要直接給它跨 repo token？

GitHub 的答案正在變得明確：**不要。**

模型可以提出「我要讀哪一個 repo」，但真正的授權是由外部 policy + control plane 決定，而且具有 owner/repo allowlist、quota、expiry 與 audit。

這比「在 prompt 裡告訴 subagent 只能看 repo A」強很多，因為模型即使被 prompt injection 或 tool output 誘導，也沒有能力自行擴張權限。

#### 技術機制

架構大致是：

```text
Primary Agent
    │
    │ request repository access
    ▼
Compiler-generated Dynamic Policy Envelope
    ▼
Delegation Control Plane (gh-aw-mcpg)
    │
    ├─ owner/repo admission
    ├─ sensitivity policy
    ├─ expiry
    ├─ quota
    └─ audit
    ▼
Repository-scoped Enclave Agent
```

它把 **intent（模型想做什麼）** 與 **authority（系統允許做什麼）** 分開。

#### 安全影響 / 攻擊面

正向效果：

- 降低 confused deputy（代理人被利用去做越權操作）
- 降低 prompt injection 後的 privilege escalation
- delegation 可 revoke / expire / audit
- 不把 controller capability 洩漏給 Agent
- 限制動態 repo 選擇範圍與 execution budget

仍要注意：

- policy selector canonicalization 本身可能成為繞過面
- 被允許的 repo 內容仍可能含 indirect prompt injection
- read-only 不等於沒有 data exfiltration 風險
- audit 完整不代表 policy 一定正確

#### 與既有方法差異

常見 framework：

```text
Lead Agent
→ spawn subagent
→ pass tools / token
→ 靠 application logic 約束
```

GitHub 的方向更像：

```text
Agent 提出需求
→ policy controller 核准 capability
→ runtime enforcement
→ expiration / revocation / audit
```

這更接近 OS / cloud IAM 的 capability-based security，而不是 prompt engineering。

#### 已知限制

目前這是 GitHub Agentic Workflows 特定 execution model，且 dynamic policy 仍有非常封閉的 GitHub read policy；不能直接推論它已解決一般 MCP 或跨 SaaS delegation 問題。

#### 可做實驗

**Research Candidate：Yes — 高優先級**

比較三種 delegation：

1. Agent 直接拿跨 repo credential
2. 靜態 per-agent repo token / tool whitelist
3. dynamic capability-based repository delegation

注入：

- malicious issue text 要求讀第二個 repo
- stale worker 在 revoke 後繼續存取
- repo selector 大小寫 / encoding / path 變體
- 超出 quota 的連續 tool call

Metrics：

- unauthorized access success rate
- revocation success rate
- audit completeness
- benign task success
- latency overhead
- operator complexity

### 2. `codebase-memory-mcp`：Path normalization 幾乎破壞 sensitive-root containment

**類型：** MCP / code intelligence / filesystem security  
**來源：**
- https://github.com/DeusData/codebase-memory-mcp/commit/9846c3f1711d557c78426913efaff340e37feb4e
- https://github.com/DeusData/codebase-memory-mcp

#### 發生了什麼變化

`codebase-memory-mcp` 在台北時間今天早上合入 Windows path handling 修正。

原始問題是同一個 repository root 在不同 code path 中有兩種表示：

```text
C:\Users\...
C:/Users/...
```

為了解決 job registry 比較失敗，前一版修正把 session root / allowed root 統一改成 forward slash。

結果 CI 發現這會破壞 **sensitive-root containment**：policy 檢查以 byte-exact prefix 去比對 `$HOME` 與 allowed root，當 policy root 被改寫成 `C:/Users/...`，但 `$HOME` 還是 native `C:\Users\...` 時，兩者不再匹配，原本應該禁止的 `$HOME` 可能被允許 auto-index / watch。

最後修法是：

- policy root 保持 OS canonical native spelling
- **只在 job identity equality 的 private copy 裡 fold separator**
- 不改動真正存放在 policy 中的 path representation

#### 為什麼重要

這不是只有 Windows 相容性 bug。

它是非常典型的安全工程問題：

> **Canonicalization 應該發生在哪一層？**

如果 authorization policy、filesystem identity 與 application comparison 各自使用不同 normalization contract，很容易出現「看起來同一條路徑，但 security check 認為不是」的 boundary bypass。

對 Agent / MCP 特別危險，因為這些系統常把 filesystem access、workspace root、allowed directory、worktree path 當作重要 security boundary。

#### 技術機制

錯誤方向：

```text
Canonical Path
→ 全域改寫 separator
→ 存進 policy
→ security containment byte-compare 失去一致性
```

修正方向：

```text
Canonical Path
→ policy 保留原生表示

只有比較 job identity 時：
copy(path A) + copy(path B)
→ separator fold
→ compare
```

這個原則可以抽象成：

> **不要為了讓「業務 equality」方便，而修改「security authority identity」。**

#### 安全影響 / 攻擊面

這次 CI 捕捉到的是 `$HOME` sensitive root admission regression。若類似問題存在於其他 path policy，理論上可能影響：

- workspace escape
- sensitive directory index
- secret/config ingestion
- unintended file watch
- cross-worktree contamination

目前沒有證據顯示已被實際利用，因此應視為 **security-relevant implementation defect**，不是已知 exploit。

#### 可做實驗

**Research Candidate：Yes**

建立 Agent filesystem boundary regression suite：

- Windows separator variants
- case variants
- symlink / junction
- `..` segments
- UNC path
- worktree roots
- HOME / SSH / credential directories

Baseline：單純 string prefix / normalize-all 方案。  
Variant：canonical identity + boundary-specific comparison。

Metrics：policy bypass count、false deny、cross-platform consistency。

### 3. OpenAgentFlow：把 Agent Security 放到 Action Commit Boundary

**類型：** 論文 / Agent Security Architecture  
**來源：**
- https://arxiv.org/abs/2609.00015

#### 發生了什麼變化

`OpenAgentFlow: Enabling System-Wide Safety Boundaries for Heterogeneous AI Agent Fleets` 在 2026-09-02 更新 v2。

論文的核心不是再做一個 prompt-injection classifier，而是把所有即將執行的 Agent 動作抽象成共同 `AgentEvent`：

- GUI actions
- API actions
- tool actions
- LLM-generated actions

然後在真正 commit 前統一經過 **Policy Enforcement Point（政策執行點）**。

provenance、session state、audit evidence 與 policy 都放在 Agent 外部。

#### 為什麼重要

Prompt injection 的難題之一是：模型同時看到「使用者意圖」與「不可信外部內容」，很難只靠 prompt 永遠分清楚。

OpenAgentFlow 走的是另一條路：

> 即使模型被說服了，真正執行 action 前仍需通過外部 policy。

這與今天 `gh-aw` 的 dynamic enclave，以及昨天研究過的 safe-output pattern，其實是同一個 architectural convergence：

```text
LLM Reasoning != Execution Authority
```

#### 技術機制

```text
GUI / API / Tool / LLM Action
        ↓
Normalized AgentEvent
        ↓
Shared Pre-execution Policy Enforcement Point
        ↓
ALLOW / BLOCK / policy handling
        ↓
Actual Executor
```

論文 v2 報告：

- controlled 300-case suite：94.00% accuracy、95.35% attack-block rate
- AgentDojo-Traj 1,220 cases：97.62% accuracy
- unsafe-action recall：96.59%
- safe false-intervention：1.96%

#### 安全影響 / 攻擊面

優勢：

- policy 不依賴單一 model / prompt / agent harness
- heterogeneous executors 共用 security boundary
- policy 可更新，不用重新修改 protected agent
- audit / provenance 外置

風險：

- Policy Enforcement Point 變成高價值集中元件
- event normalization 如果漏掉語意，可能造成 policy gap
- policy 本身可能有 false positive / false negative
- action-level policy 無法解決所有 information disclosure；「讀了什麼」本身也可能是風險

#### 已知限制

這仍是研究系統；paper benchmark 與真實企業 agent fleet 的 tool diversity、state complexity、policy authoring effort 有差距。

#### 可做實驗

**Research Candidate：Yes — 高優先級**

用我們自己的 coding-agent workflow 建一個縮小版 PEP：

```text
Agent proposed GitHub / shell action
→ normalize event
→ deterministic policy
→ execute
```

比較：

A. system prompt guardrail  
B. tool wrapper with ad-hoc checks  
C. shared action-commit PEP

Metrics：attack success rate、benign task success、false intervention、policy maintenance effort、latency。

### 4. Tencent `AI-Infra-Guard`：可以拿來當 Agent / MCP / Skill Security baseline

**類型：** Open-source AI red-teaming / scanner  
**來源：**
- https://github.com/Tencent/AI-Infra-Guard
- https://github.com/Tencent/AI-Infra-Guard/releases/tag/v4.6.0

#### 發生了什麼變化

這不是 9/7 單日新 release，但因為今天開始正式建立 AI Security 研究主線，它值得被納入 baseline。

`AI-Infra-Guard` 目前整合：

- Agent Scan
- Agent Skill Scan
- MCP Scan
- AI infrastructure CVE scan
- LLM jailbreak evaluation
- LLM API poisoning / model substitution audit

近期版本 v4.6.0（8/26）增加 LLM API poisoning detection，並持續擴充 MCP / Skill scan；v4.5.2（8/17）加入 `.pyc` bypass、charset smuggling、MCP dynamic-mode tool whitelist 等。

其 SkillTrustBench taxonomy 已涵蓋：

- Skill Instruction Hijacking
- Memory Poisoning
- Remote Payload Download & Execution
- Embedded Malicious Code
- Privilege Escalation
- System Persistence
- Tool Hijacking & Spoofing
- Insecure Dependencies
- Insecure Coding Practices

README 報告不同模型在 SkillTrustBench 上 F1 約 0.974–0.985；這些數字應視為專案自行公布的 benchmark，需要獨立重跑。

#### 為什麼重要

我們如果要研究 AI Security，不應該一開始就自己發明全部 scanner / benchmark。

更好的方式是：

> 用現有 security tool 當 baseline，找它抓不到什麼、誤報什麼，再決定研究缺口。

它也能讓 Agent Radar 的 security track 從「讀 paper」走向可執行 CI / red-team 實驗。

#### 安全影響 / 攻擊面

值得肯定：涵蓋 Agent、MCP、Skill、Jailbreak、infra 多層。

但自身也有重要 operational warning：README 明確表示目前服務 **沒有 authentication，不應部署到 public network**。也就是 security tool 本身仍需要被放在可信網段 / CI isolation 中。

#### 可做實驗

**Research Candidate：Yes**

建立一個小型 Security Corpus：

- benign skills
- prompt-injection skills
- memory-poisoning samples
- tool-description poisoning
- dependency risk
- credential exfiltration patterns

比較：

- AI-Infra-Guard
- static rules
- LLM-as-judge security reviewer
- hybrid static + model scanner

Metrics：precision、recall、F1、false positive、scan latency、token cost、可解釋性。

## Research Candidates

### Candidate A：Action-Commit Security Boundary

- **問題：** Prompt guardrail、tool wrapper、集中式 Policy Enforcement Point，哪一種最能阻止 indirect prompt injection 後的危險 action？
- **Baseline：** system prompt + model refusal。
- **Variants：** ad-hoc tool check、`gh-aw` safe-output style、OpenAgentFlow-style shared PEP。
- **攻擊測試：** malicious issue / webpage / tool output 誘導跨 repo 存取、寫檔、外傳資料。
- **Metrics：** attack success rate、unsafe-action recall、false intervention、benign success、latency、policy authoring effort。

### Candidate B：Capability-based Delegation

- **問題：** Delegation control plane 是否真的比 static token / tool whitelist 更安全且可維運？
- **Baseline：** per-agent static credentials。
- **Variant：** dynamic enclave + expire / quota / audit / revocation。
- **Metrics：** unauthorized access、revocation effectiveness、audit completeness、coordination latency、operator effort。

### Candidate C：Agent Filesystem Canonicalization Security Suite

- **問題：** coding agent / MCP server 在 Windows、symlink、worktree 情境下有哪些 path identity bypass？
- **Baseline：** string prefix + global normalization。
- **Variant：** canonical authority identity + boundary-specific comparison。
- **Metrics：** bypass rate、false deny、cross-platform consistency。

### Candidate D：AI Security Scanner Benchmark

- **問題：** AI-Infra-Guard 對 Skill / MCP / Agent threat 的偵測品質是否能獨立重現？
- **Baseline：** static security rules。
- **Variants：** AI-Infra-Guard、LLM reviewer、hybrid scanner。
- **Metrics：** precision、recall、F1、FPR、latency、token cost、explanation quality。

## Watchlist

### UI-TARS MCP unauthenticated exposure（CVE-2026-81735）

8/27 公開的 `CVE-2026-81735` 很值得納入 MCP Security threat model：`mcp-http-server` 預設 listen address 曾綁到所有 interfaces，authentication middleware 又不是 mandatory，導致 command / filesystem MCP surface 可能在網路上無認證暴露。

這不是今天新披露，因此不列為今日主題，但它是一個非常好的 architecture lesson：

> **Local MCP server 必須預設 loopback-only + authentication-by-default；高權限 tool 不應依賴呼叫端「記得傳 middleware」。**

參考：
- https://nvd.nist.gov/vuln/detail/CVE-2026-81735
- https://github.com/bytedance/UI-TARS-desktop/commit/c2ad42e3eb9b27830db41a3e6f51ca7179d9b168

### Prompt Injection 防禦：不要只做 injection detector

OpenAI 對 agent prompt injection 的公開安全設計持續強調：prompt injection 更接近 social engineering，單純「辨認惡意文字」不足以保證安全；需要限制 agent access、對 consequential action 做 confirmation、監控可疑 injection，以及限制資料外傳路徑。

這與今天觀察到的 `gh-aw` / OpenAgentFlow 結論一致：**把 deterministic control 放在 action 與 authority layer，才是比較可持續的方向。**

參考：
- https://openai.com/index/designing-agents-to-resist-prompt-injection/
- https://openai.com/safety/prompt-injections/

## 今日最值得帶回 AI Workflow 的設計原則

今天四個主題其實收斂到同一個架構：

```text
Untrusted Context
(issue / web / RAG / MCP / skill / repo)
        ↓
LLM Reasoning
        │
        │ 只有 intent，沒有完整 authority
        ▼
Proposed Action / Delegation Request
        ↓
Canonicalization + Provenance
        ↓
Policy Enforcement / Safe Output / Capability Controller
        ↓
Scoped Credential / Sandbox / Expiry / Quota
        ↓
Real Action
        ↓
Audit
```

最值得記住的是三句：

1. **不要把 Agent 的判斷當成授權。**
2. **不要為了方便 equality 比較而改寫 security authority identity。**
3. **Prompt injection 防禦的核心不是讓模型永遠不被騙，而是讓「被騙的模型」也無法直接越權。**
